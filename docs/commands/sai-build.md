# `/sai-build`

## Command function

Runs a change's build in one invocation. It chains [`/sai-3-implement`](sai-3-implement.md), then one pass of [`/sai-4-review`](sai-4-review.md), assesses the review findings itself, runs `/sai-3-implement` again for the findings it selects, and closes with the lists of fixed, excluded, and left-open findings.

## Flags and behavior modifiers

- The change name, or nothing when the project has one active change with a `tasks.md`.
- `--publish yes|no`: answers the publication question below in advance. Any other value ends the run before anything is written.

## In detail

The command runs the implementation segment, the review segment, and the fix segment in the same session, with no approval between segments. The behavior, preconditions, checks, and stops of each segment are the ones described in [`/sai-3-implement`](sai-3-implement.md) and [`/sai-4-review`](sai-4-review.md).

The change the implementation segment resolves (the name you gave, or the only active change with a `tasks.md`) is the one the review and fix segments use; they never resolve a change again. Like any `/sai-3-implement` run, the implementation segment also applies the open findings of the audit reports already in the change directory, while the fix segment applies only the findings of the `review.md` this run produced.

Each segment starts only when the previous one completes, including an implementation segment that found no new work. When the implementation segment or the fix segment is blocked, stopped, or fails its preconditions, the command prints that report, ends without the closing line, and starts no later segment.

The command runs exactly one review pass per run. Right after it, the command assesses each fixable finding of `review.md` itself and decides whether to fix it. It has no fixed rule, threshold, or severity cutoff: impact, the cost of the correction, and the risk of the correction are things it may weigh. It appends ` (EXCLUDED: <reason>)` to the heading of each finding it will not fix, never to a Question, and commits `review.md` alone when the project does not ignore it. The fix segment then applies the remaining findings and marks each one ` (FIXED)`. When it fixes at least one, it also stores the inherent-risk ratings block in `review.md` and commits it in its own local commit, as described in [`/sai-3-implement`](sai-3-implement.md). A build whose fix segment does not start leaves `review.md` without a ratings block, and [`/to-pr`](to-pr.md) computes the ratings. When every segment completed, the command creates the ADR/DDR records of the design's decisions at its own close, from the final code and the deviations of both implement segments, in one local commit; the segments create none, and a later run does not repeat a record that already cites the change (see [`/sai-3-implement`](sai-3-implement.md)). No review runs after the fixes. With no fixable finding, or when every fixable finding is excluded, the fix segment does not run.

The command then prints the finding counts by category (Critical, High, Medium, Low, Questions) and the recommended audits, and runs no audit. It lists the fixed findings, the excluded findings with their reasons, and the findings the fix segment left open with their reasons. To apply an excluded finding, remove its ` (EXCLUDED: …)` mark from `review.md` and run `/sai-3-implement {change}`. Questions stay open until you answer them, because the fix segment applies only fixable findings. Rerunning `/sai-build` reviews again and judges every finding from scratch. With zero findings, the command reports the zero counts and prints no list. When the diff has no changes against the parent branch, it says that no review ran.

The command asks one question at its start: whether to publish a **PR/MR that is ready for review** of the build on GitHub, GitLab or Azure DevOps when the run ends, through [`/to-pr`](to-pr.md). It asks once the implementation segment has accepted the change and before any worker starts, and it names the current branch and its remote. A new request is created ready for review, and an open request of the branch is updated; when it is a draft, it is marked ready for review. The answer comes from, in this order, the `--publish yes|no` argument, the answer a resumed run already recorded in its run state (whatever segment it resumes in), the [`pr.publishAfterRun`](../project-settings.md#plan-publication-answer) setting when it reads `yes` or `no`, and then the question; the first value found wins and nothing later is asked. A direct [`/sai-3-implement`](sai-3-implement.md) run and [`/sai-deep-review`](sai-deep-review.md) ask nothing and publish nothing.

With `no`, nothing is published, an existing request stays untouched (a draft included), and nothing is asked again. With `yes`, the answer is the authorization for exactly two operations on the current branch, and nothing asks you again: a push without force, and the creation or update of the request. The run publishes once, after its last segment and its telemetry commit and before the closing line, never between segments, and prints the verified request URL with its ready or draft state, or the reason nothing was published. A run that fails, stops, or ends blocked publishes nothing, whatever the answer. The recorded answer lives in the run state of the implementation segment, which stays open across the three segments of a `/sai-build` run and is closed at its end, so a run interrupted in any segment reuses it. On the default branch or a detached HEAD, with no provider or remote, a failed authentication, a rejected push (never retried with force), or a branch whose request was merged or closed (never reopened), publication is skipped with its reason and the run still counts as completed. When marking a draft request ready fails, or its read-back does not show it ready, the closing report says that the request stays a draft and why; the push and the content update stand. All committed branch changes enter the request. An unattended run publishes without a final look at the request text; you accept that when you answer `yes`.

With `experimental.changeTelemetry` on, the command records the run's cost in `telemetry.md` in the change folder at its close, and invoking it pre-authorizes one more local commit for that file; see [change telemetry](../project-settings.md#change-telemetry).

The command ends with `Build done.` at the end of the whole run, after the fix segment when one runs, when the review segment ended normally and no segment was blocked or stopped. When the review segment fails, is stopped, or cannot start, the command prints both reports and ends without the closing line.
