# `/sai-2-design`

## Command function

Turns an approved proposal into an actionable technical design and into the test oracle of the change: a short `design.md`, a `tasks.md` of ordered steps, and, in code, the interface stubs and the failing tests (the plan tests) that [`/sai-3-implement`](sai-3-implement.md) and [`/sai-build`](sai-build.md) later turn green step by step.

## Flags and behavior modifiers

The command takes the change name and optional feedback; it has no other option. Passing `--overview-lang` ends the run with an unknown-option error before anything is written (the change overview retired, because the draft pull request is the review surface).

Supply the change name first. Text after the name is feedback: on a change that already has `design.md`, `/sai-2-design my-change <feedback>` runs the same cycle again and updates the plan tests, the stubs, `design.md`, and `tasks.md` in place, in new commits.

## In detail

The command always runs unattended and runs two phases in one run. Invoking it approves the reviewed specs and records that approval; a change with `skip_specs: true` has no specs to approve, so no approval is recorded and the design works from the statements of `proposal.md`.

1. **Design.** `sai-2-design-worker` researches the proposal, specs, and any existing design, resolves blocking questions, and writes the reduced `design.md` and `tasks.md`, which record only what the code of the plan tests does not express. `design.md` holds the public signatures as `path :: signature` entries (no function bodies) with the file manifest, the decisions with their record family, and the risks. A step of `tasks.md` that has tests carries its title, its routing line, and the spec scenarios it covers; a step without tests (documentation, prompts, configuration) carries its title, routing line, files, what changes, and a closure criterion. The File Manifest lists only the files of the steps without tests, because the plan's pull request shows the tests and the stubs of the rest.
2. **Plan tests.** `sai-2-red-worker`, the plan RED, a worker with its own model, writes the stubs at the signature paths and one failing test per scenario, named with the scenario's literal title; it may modify an existing test only when that test uses a symbol whose signature the design changes or removes, or asserts a scenario the specs modify or remove, and it reports each such test with its reason. The command runs the tests and accepts one only when it is red by assertion (a failure on the behavior under test, not a compile or import error); a test that already passes is accepted only as a regression guard. It then runs the scenario coverage check and returns a missing or ambiguous scenario to the RED. A deterministic write-back puts each step's tests, its test command, and the regression-guard marks into `tasks.md` from the RED's report, so no model copies them by hand. A test that cannot be written as a meaningful assertion turns its step into a step without tests, recorded as an assumption. A change whose steps all carry closure criteria produces no plan tests and creates no plan RED.

The command answers a worker question itself when the artifacts or the repository settle it, records the answer as an assumption with its source, and escalates to you only what nothing settles. It runs the mechanical checks, reviews the artifacts and the plan tests in up to three incremental rounds, and commits the segment's own paths locally in two commits: the plan documents, then the plan code. The plan tests are committed failing, never skipped, so the continuous integration of a draft pull request of the branch stays red until the build runs. The assumptions and any findings still open after the third round are listed once in the closing report and are not written to the repository.

The design reads `SAI_LEARNINGS.md` when it exists. It writes no ADR or DDR: it marks each qualifying decision with its record family, and the implementing command creates the record at its close. A change planned with an earlier format (it has `interfaces.md` and no plan tests, or its `tasks.md` still has `**What Will Be Done**`, `## Required Documentation`, `**Existing Tests Broken**`, or `**Files Affected**` on a step with tests) does not enter the build: run `/sai-2-design` again on it, which rewrites both artifacts in the current format.

The command requires `proposal.md` and either a spec file or `.openspec.yaml` with `skip_specs: true`; otherwise it stops before any dispatch. It ends when the design is complete and does not implement the solution or execute tasks from the plan. In normal use, it stops so the user can review the design before running [`/sai-3-implement`](sai-3-implement.md) or [`/sai-build`](sai-build.md). [`/sai-plan`](sai-plan.md) runs this command after `/sai-1-spec` in one invocation.
