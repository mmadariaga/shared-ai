## Requirements
### Requirement: tasks-implementation-context-section

`tasks.md` SHALL contain a `## Implementation Context` section generated by `/sai-2-design` immediately after `## Required Documentation`.

The section SHALL contain exactly four fields:

    **Stack**: <primary language/framework + key versions relevant to this change>

    **Conventions**: <2–5 project-specific, non-obvious bullets derived from codebase research>

    **Avoid**: <anti-patterns the implementation agent might default to, given the declared stack>

    **Test Command**: <the exact command that runs this project's test suite>

Each field SHALL be derived from codebase research performed during design, not copied from generic content or inferred from the change description alone.

**Test Command** SHALL be directly executable from the project root by a subagent that has read neither `implementation.md` nor `design.md`. Where the project's runner supports scoping a run to a subset of tests, the field SHALL also carry that project's scoping idiom in parameterised form — the concrete flag and the concrete test-project or path argument, with a substitutable placeholder for the test identifier (for example `dotnet test tests/<Project> --filter FullyQualifiedName~<TestName>`). The scoping idiom is mandated for the same reason the base command is: the flag spelling is derivable from **Stack**, but the test-project path and the project's chosen filter expression are not, and they live in `implementation.md`, which the consumer may not read.

**Test Command** SHALL NOT pin a specific Step's filter value. Fully-resolved, step-scoped verification commands remain in `implementation.md`, where they already work; the field carries the reusable form, not one Step's instance of it.

When the project has no test runner at all — a documentation, prompt, or configuration repository with no executable test surface — **Test Command** SHALL carry the explicit sentinel `None — no test runner in this project`. That sentinel is a researched finding, not placeholder text, and SHALL NOT be treated as a violation of the no-placeholder rule below.

**Test Command** SHALL be a field of its own, sibling to **Stack**, **Conventions**, and **Avoid**. It SHALL NOT be written as a **Conventions** bullet and SHALL NOT consume any part of the 2–5 bullet quota, because a run command is an infrastructure fact rather than a project-specific convention.

`/sai-2-design` SHALL produce **Test Command** for every change, including changes whose Steps will all route to a single dispatch and where nothing will read it.

The section SHALL NOT be omitted or left with placeholder text.

#### Scenario: sai-2-design derives context from codebase research

- **WHEN** `/sai-2-design` generates `tasks.md`
- **THEN** `## Implementation Context` contains Stack with concrete versions, Conventions with 2–5 bullets that reflect patterns observed in the actual codebase (not generic best-practices), Avoid with anti-patterns specific to this stack that a model might default to, and Test Command with the exact command observed in the project's own test tooling

#### Scenario: Test Command carries the project's scoping idiom

- **WHEN** `/sai-2-design` writes **Test Command** for a project whose runner supports filtering a run to a subset of tests
- **THEN** the field shows the concrete test-project path and the concrete filter flag with a substitutable placeholder for the test identifier, rather than a bare whole-suite invocation

#### Scenario: Project has no test runner

- **WHEN** `/sai-2-design` researches the test command for a repository that has no executable test surface
- **THEN** it writes the sentinel `None — no test runner in this project` in **Test Command**, and this does not violate the no-placeholder rule

#### Scenario: sai-3-implement uses context as authoritative contract

- **WHEN** `/sai-3-implement` reads `tasks.md` to produce `implementation.md`
- **THEN** it adopts **Stack**, **Conventions**, **Avoid**, and **Test Command** as a non-negotiable implementation contract and does not perform codebase exploration to recover stack, convention, or test-command information

#### Scenario: conventions are project-specific, not generic

- **WHEN** `/sai-2-design` writes the Conventions field
- **THEN** each bullet describes a pattern specific to this project (e.g., a naming convention, file organization rule, or error-handling idiom observed in the codebase), not a universal best-practice such as "write readable code" or "follow SOLID principles"

#### Scenario: Test Command is not written as a Conventions bullet

- **WHEN** `/sai-2-design` records how this project's tests are run
- **THEN** it writes the command in the **Test Command** field and does not spend a **Conventions** bullet on it

#### Scenario: Test Command is produced even when no dispatch will read it

- **WHEN** `/sai-2-design` generates `tasks.md` for a change whose Steps contain no RED block, so no blind test-writer will ever be dispatched
- **THEN** `## Implementation Context` still contains a populated **Test Command** field rather than omitting it or writing a placeholder

### Requirement: tasks-implementation-context-replaces-expertise-profile

`## Implementation Context` SHALL replace the verbose Expertise Profile template (Primary Role, Technologies, Standards, Output Quality Bar subsections) that `/sai-3-implement` previously expected from the loaded `plan.md`.

`/sai-3-implement` SHALL read **Stack**, **Conventions**, **Avoid**, and **Test Command** from `tasks.md` as the equivalent of the Expertise Profile. It SHALL NOT require the user to supply a separate Expertise Profile, and SHALL NOT STOP when the Expertise Profile subsections are absent from other artifacts.

`sai/instructions/implement.md` SHALL NOT describe `## Implementation Context` as a three-field contract anywhere it enumerates or characterizes the section, so that the fourth field is not excluded by the instruction text that governs how the section is read.

Generic "Output Quality Bar" and universal standards SHALL remain in `plan.md` as hard rules and SHALL NOT be duplicated into `tasks.md`.

#### Scenario: sai-3-implement proceeds without separate Expertise Profile

- **WHEN** `/sai-3-implement` reads a `tasks.md` containing `## Implementation Context` with Stack, Conventions, Avoid, and Test Command
- **THEN** it treats those four fields as the complete Expertise Profile contract and does not STOP to request additional profile information

#### Scenario: sai-3-implement stops when implementation context is missing

- **WHEN** `/sai-3-implement` reads a `tasks.md` that lacks `## Implementation Context` entirely
- **THEN** it STOPs and asks the user to run `/sai-2-design` again or supply the missing context manually

#### Scenario: implement.md enumerates four fields

- **WHEN** `sai/instructions/implement.md` names the fields of `## Implementation Context` or characterizes it as the complete Expertise Profile contract
- **THEN** the enumeration includes **Test Command** and no passage describes the section as containing three fields

### Requirement: tasks-implementation-context-schema

The `tasks` artifact instruction in `openspec/schemas/sai-workflow/schema.yaml` SHALL include a directive requiring `/sai-2-design` to populate `## Implementation Context` from codebase research, with explicit guidance that generic content is not acceptable. The directive SHALL cover **Stack**, **Conventions**, **Avoid**, and **Test Command**.

The template at `openspec/schemas/sai-workflow/templates/tasks.md` SHALL show **Test Command** in its `## Implementation Context` scaffold as a field sibling to **Stack**, **Conventions**, and **Avoid**.

#### Scenario: schema instruction prohibits generic implementation context

- **WHEN** `openspec instructions tasks --change <name>` is run
- **THEN** the returned `instruction` field states that Stack, Conventions, Avoid, and Test Command MUST be derived from the actual codebase and that generic or placeholder content is not acceptable

#### Scenario: template scaffolds the Test Command field

- **WHEN** `openspec/schemas/sai-workflow/templates/tasks.md` is read
- **THEN** its `## Implementation Context` section shows a `**Test Command**:` placeholder alongside `**Stack**`, `**Conventions**`, and `**Avoid**`
