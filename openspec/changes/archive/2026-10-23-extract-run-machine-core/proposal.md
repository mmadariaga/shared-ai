## Why

`sai-state/machines/implement-run.js` mixed the generic run core (the attempt budget per obstacle, escalation, answers, path records, close, and the identifiers-only state) with implement-only vocabulary (the current step, the committed steps, and the implement reference kinds). A second run machine could not attach to that core by extension; it would have to copy the attempt-budget logic. This is an enabling refactor, not user-facing value: it opens the seam a later run machine builds on.

## What Changes

- New module `sai-state/machines/run-core.js` exports `createRunMachine({ machineId, hint, refs, extraState, handleEvent, onClose })`. It owns the attempt budget of 3 per obstacle, the stages `idle`, `running`, `escalated`, `completed`, and `stopped`, the identifiers-only state, and the events `start`, `attempt`, `escalate`, `answer`, `record`, `close`, and `status`. It returns `{ machineId, ATTEMPT_BUDGET, initialState, transition, project }`.
- A machine built on the core supplies only its own vocabulary: the reference kinds `record` appends to, its extra string or string-list state fields, a handler for the events the core does not own, and a hook run at close.
- `sai-state/machines/implement-run.js` becomes a thin machine over the core: it keeps the id `implement-run@1`, the reference kinds `deviation`, `override`, `report`, `finding`, and `baseline`, adds the `step` and `committed` state fields, handles `step-start` and `step-done` itself, and clears the current step at close. Its events, rejections, and emit responses are unchanged.

## Capabilities

### New Capabilities

- None

### Modified Capabilities

- `implement-new-resilience`: the `implement-run@1` run state machine keeps its behavior and is now built on a shared run core that later run machines reuse.

## Impact

- New: `sai-state/machines/run-core.js`
- Modified: `sai-state/machines/implement-run.js`
- No change to the `implement-run@1` registration, session key, events, or responses.
