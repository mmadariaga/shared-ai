**Complexity**: medium (4 files, 2 new capabilities + 1 retired + 1 modified, no breaking change)

## Why

Both fetch skills teach a Glob-based existence probe before Read (`skills/opencode/fetch/SKILL.md`, `skills/claude/fetch/SKILL.md`), and agents generalize that probe from the project branch to the user-global branch. A glob named at the user-global root sits outside every allow-glob of the shipped opencode `external_directory` allowlist, so it stalls the run on a permission prompt — an interruption that carries no safety value, because every path a fetch directive can name is already permitted (once the allowlist covers the fetch namespace). Separately, the shipped template grants only `~/.config/opencode/sai/**`, so a clean install still prompts on the first `@commands/...` fetch.

## What Changes

- Both fetch skills (opencode and Claude Code) replace the Glob-then-Read existence probe with a Read-then-Read fallback: read the project-local exact path first; on failure, read the user-global exact path; on double failure, stop and report. No directory-based probe remains in either branch.
- Both skills encode the resolution scope as a positive invariant: every resolved path begins with `sai/`, `commands/`, or `skills/` under the project or user-global root, and the root itself is never named — enforced by a stop-before-read guard: a directive whose resolved path would land outside the three prefixes is rejected before any filesystem access, so no permission prompt can be triggered by directive content.
- The shipped `configs/opencode.jsonc` template's `external_directory` allowlist gains the two missing fetch-namespace entries — `~/.config/opencode/commands/**` and `~/.config/opencode/skills/**` — alongside the existing `~/.config/opencode/sai/**`, all with forward-slash separators.
- The `fetch-existence-check-before-read` capability is retired: both its requirements are removed. The probe requirement's removal re-activates `claude-fetch-resolution` — which already normatively mandates Read-project-then-Read-global, no broad glob/grep search, and the Claude skill-tool mapping — as the sole Claude authority; the new capability does not restate Claude mechanics. `fetch-resolution-path-scoping` owns the opencode rule (previously governed by no spec), the opencode skill-tool mapping, and the shared path-scope invariant; `opencode-worker-system-prompt` remains consistent with both. `coordinator-instruction-loading` is amended in place (see Impact): its "Routed non-skill resolution is satisfiable through Glob and Read" requirement is retired-and-replaced by "Routed non-skill resolution is satisfiable through Read", so the routed resolver contract names Read-then-Read instead of Glob candidate selection and remains consistent with both capabilities.
- `test/install-opencode.test.js` gains additive allowlist assertions — the three fetch-namespace entries and the absence of backslash separators — executed by the implementation phase of this change, so the `opencode-permission-template` guard is enforced at merge, not deferred.

## Capabilities

### New Capabilities
- `fetch-resolution-path-scoping`: Defines the opencode fetch skill's Read-then-Read exact-path resolution — which no spec previously owned — and the positive path-scope invariant (`sai/`, `commands/`, `skills/`; the root is never named) encoded in both harness skill variants and enforced by a stop-before-read guard for out-of-namespace directives. The Claude Code resolution mechanics are not restated here: `claude-fetch-resolution` remains their sole normative owner.
- `opencode-permission-template`: The shipped `configs/opencode.jsonc` `external_directory` allowlist covers the full fetch namespace — `sai/**`, `commands/**`, `skills/**` — using forward-slash separators, and ships no platform-specific path.

### Modified Capabilities

## Additional Notes

- **"Backslash separators" premise not supported by current sources.** The request hypothesized that the shipped template's separators do not match on Windows; `configs/opencode.jsonc`, the installer pattern constant, and `INSTALL.opencode.md` all use forward slashes today, and `implementation-harness-bindings` ("Equivalent SAI path spellings are canonicalized") already treats backslash spellings as normalized equivalents. The forward-slash requirement in `opencode-permission-template` is therefore written as a durable regression guard, not a correction of a current violation.
- **Existing-config merge path is out of scope — recorded as a normative known limitation.** `bin/install-flow.js` appends only `~/.config/opencode/sai/**` to pre-existing configs, so the prompt-free property delivered by this change applies to fresh installs (template copy) and not to existing-config merges; every existing user keeps their narrower allowlist until the dependent follow-up lands. This divergence and its stated ordering are now recorded as a requirement under `opencode-permission-template` (not just prose), so the fresh-install template and the merge path cannot drift silently.
- **Open decision, tracked separately (L1): Windows-only temp-path entry.** The authoring machine's installed config carries `~/AppData/Local/Temp/opencode/*` (Windows-only) in addition to the three namespace entries. The `opencode-permission-template` requirement forbids the entry in the shipped template **unconditionally**; the separate question of whether a platform-specific temp-path entry belongs in a cross-platform template is recorded here as an open decision for `/sai-2-design` — it carries no normative force inside the requirement.
- **`INSTALL.opencode.md` drifts — and so does the installer's printed fallback guidance.** Its five narrow-template blocks (lines ~90-118 and ~179-207) show only the `sai/**` rule; the docs remain accurate for the merge path but understate the fresh-install template. Separately, `bin/install-flow.js`'s `printOpencodeConfigMessage` (verified hardcoded, not template-derived) prints a `sai/**`-only block when a config cannot be safely merged — understating the new three-entry allowlist for exactly the users who must configure by hand. Aligning both printed-guidance surfaces with the shipped template is one follow-up slice, per the request's sizing assumption.
- **Allowlist assertions are in scope (M6), not a follow-up slice.** `test/install-opencode.test.js` currently asserts `sai/**` membership only; the three-entry allowlist and backslash-absence assertions are pulled INTO this change — additive, breaking nothing — executed by the implementation phase per the `opencode-permission-template` test-ownership record. The guard is therefore enforced at merge, not inert until a follow-up lands.
- **`@skills/` fetches never resolve through the filesystem today.** Every `@skills/` directive in the repo ends in `/SKILL.md` and maps to the skill tool; the `skills/**` allow entry covers the general `@<subpath>` rule's namespace (any non-SKILL.md `@skills/...` fallback read), not the skill-tool mapping, which needs no permission entry.
- **Invariant enforcement (M3).** The path-scope invariant is enforced, not descriptive: a directive whose resolved path lands outside `sai/`, `commands/`, or `skills/` — or names a root directory — stops and reports before any read. The guard is keyed on the **resolved** path, not the directive's literal token, so the opencode wrappers' absolute first line `Fetch @~/.config/opencode/skills/fetch/SKILL.md before you continue.` (pinned by `thin-wrappers`) resolves under `skills/` and stays in namespace. Guard + template allowlist together make prompt-free operation a structural property: directive content can never reach the filesystem outside the three permitted subtrees.
- **Claude Code ownership is single and explicit.** `claude-fetch-resolution` already mandates Read-then-Read, "MUST NOT search the project filesystem broadly (glob/grep)", and the Claude skill-tool mapping for Claude Code; removing the later `fetch-existence-check-before-read` override re-activates it as the sole authority for Claude resolution mechanics. `fetch-resolution-path-scoping` does not restate the Claude rule — it owns the opencode rule (which no spec previously owned), the opencode skill-tool mapping, and the shared path-scope invariant. `fetch-existence-check-before-read` is fully retired (both requirements removed; the capability archives at sync), so at archive no Claude Code behavior has two normative owners and no requirement references the removed probe behavior.
