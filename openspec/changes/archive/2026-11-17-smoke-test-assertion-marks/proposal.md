## Why

In projects with slow test suites nothing tells the critical tests apart from the rest, so no quick check of the essential behavior is possible without running everything. Tagging the smoke tests at the source, from the plan's test assertions, lets execution be narrowed later.

## What Changes

- `sai/policies/step-contract-format.md` defines `**Test assertions**` in `interfaces.md` as a Markdown list with one assertion per item. An item may start with the `[smoke-test]` mark, and the policy single-sources the criterion: an assertion is smoke-test when its failure leaves the system useless for its main purpose, or when the behavior charges, pays, moves, or computes money. A `**Test assertions**` field in the earlier prose form stays valid and carries no mark.
- `openspec/schemas/sai-workflow/templates/interfaces.md` shows the list form with one marked and one unmarked item.
- `sai/commands/design/steps/interfaces.md` writes each step's assertions as the policy's list and marks every assertion that meets the criterion. When at least one assertion is marked, it adds a `**Smoke-test tagging**` field to `## Implementation Context` in `tasks.md`, after `**Test Command**`, naming the project's native tag mechanism with its syntax, `[smoke-test]` in the test name, or that the tests stay untagged. With no marked assertion, or with the `None — no step contracts` sentinel, `tasks.md` carries no such field and a field an earlier run wrote is removed.
- `sai/commands/design/steps/tasks.md` notes that the `interfaces` step may add the `**Smoke-test tagging**` field after `**Test Command**`.
- `sai/commands/implement/steps/red-step.md` applies the tag that `**Smoke-test tagging**` names to every test RED writes or modifies from a marked assertion, including a test written from several assertions when any of them is marked. RED never removes an existing smoke-test tag, adds no tag without the field or when it says the tests stay untagged, reads the earlier prose form as before, and leaves tests written for audit findings untagged.
- `sai/commands/implement/coordinator.md` extends the step review's structural check: a test written from a marked assertion that lacks the tag `**Smoke-test tagging**` names is a spec-fidelity finding; a step without the field, or whose field says the tests stay untagged, owes no tag.
- `sai/tools/check-cited-paths.js` reads cited paths of the `interfaces.md` `**Test assertions**` field from its label line and from the list items below it, up to the next heading or `**Label**` field line, so paths cited in list items are checked like those of the prose form. `test/check-cited-paths.test.js` covers marked and unmarked list items, the earlier prose form, and the end of the list at the next field line.

## Capabilities

### New Capabilities

- `smoke-test-assertion-tagging`: design marks smoke-test assertions and fixes the tagging mechanism in `tasks.md`; RED tags the tests written from marked assertions; the implement step review checks the tag.

### Modified Capabilities

- `shared-step-contract-section-format`: `**Test assertions**` becomes a list with an optional `[smoke-test]` mark and a single-sourced criterion; the earlier prose form stays valid.
- `tasks-implementation-context`: `## Implementation Context` may carry the `**Smoke-test tagging**` field after `**Test Command**`, written by the `interfaces` design step only when an assertion is marked.
- `cited-path-existence-check`: `interfaces.md` test-assertion paths are read from the field's label line and its list items.

The change only tags tests: it does not change which tests run or when, and it adds no `sanity` or `regression` tag. Claude Code and opencode read the same harness-neutral cards; no wrapper changes. `sai/tools/lint.js` `step-contract` is unchanged, since it checks only the heading and the field labels and accepts both forms. A framework with neither native tags nor flexible test names keeps the mark only in `interfaces.md`.
