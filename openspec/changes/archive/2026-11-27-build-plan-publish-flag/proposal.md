> **⚠ POST-HOC RECORD** — This proposal was backfilled after implementation against a user-supplied statement of intent. It describes a decision already made, not one being proposed.

## Why

`/sai-plan` and `/sai-build` already accept `--publish yes|no` and resolve that answer at the start of a run, before any worker exists. Three gaps remained: `/sai-build` could not keep a request as a draft for a shared slice set, `--publish` had no bare form, and the closing hints did not carry the next command's flag. A user who had already chosen an answer rebuilt the next command from the documentation, and `/sai-build` never pointed to `/sai-archive`.

## What Changes

- `/sai-build` accepts `--publish` with an optional value in the separate and attached forms: a bare `--publish` equals `yes`, `yes` publishes a ready request, `draft` creates or keeps a draft, and `no` publishes nothing. An invalid value or a second flag ends the run before anything is written.
- `/sai-build` records and reuses `draft` in `implement-run@1`, and hands the unattended publication `publish_pr_as_draft: true` for `draft` and `false` for `yes`.
- `/sai-build` asks a three-option publication question when no argument, recorded answer, or setting answers it, and its completed close names `/sai-archive {name} --push yes` only when the answer is `yes` or `draft` and the push was confirmed, otherwise `--push no`.
- `/sai-plan` accepts `--publish` with an optional value, normalizes `draft` to `yes` because its request is always a draft, and accepts `--build-publish <yes|no|draft>` on any invocation as the override of its closing build hint.
- The plan's `Plan done` line carries the build publication flag, resolved from `--build-publish` when given and otherwise from `pr.publishAfterRun`; on the Explore Plan route the flag comes from the set's `publication`, `branch_strategy`, and `pending` slices, and the Explore close refers to that one printed command.
- The shared run core takes each machine's accepted publication values, so `implement-run@1` accepts `yes`, `no`, and `draft` while `plan-run@1` keeps rejecting `draft`.
- The wrappers, the command documentation, the project-settings documentation, `README.md`, and `AGENTS.md` describe the new forms; `docs/commands/sai-archive.md` is unchanged.

## Capabilities

### New Capabilities

- None

### Modified Capabilities

- `build-publication`: `/sai-build` parses the optional value and the bare flag, resolves and stores `draft`, and publishes a draft request while leaving a ready request ready.
- `plan-terminal-close`: the plan coordinator prints the only build hint, carrying the build publication flag, and the Explore close refers to it without printing a second command.
- `sai-build-command`: the completed build close prints the archive hint with its `--push` value, and the no-changes close prints none.
- `explore-publication`: the Plan route hands `--build-publish` to the plan coordinator from the set's publication answer, branch strategy, and pending slices.
- `plan-command`: `/sai-plan` accepts the optional `--publish` value and `--build-publish`, and its closing line carries the build publication flag.
- `explore-pipeline-supervision`: the Plan - Unattended route hands the derived `--build-publish` value to the plan coordinator.
- `to-pr`: the unattended mode accepts a recorded `draft` answer for the build and sends the caller's `publish_pr_as_draft` value.
- `project-settings`: `pr.publishAfterRun` also supplies the standalone plan build-hint recommendation and never takes `draft`.
- `plan-segment-cycle`: the shared run core takes each machine's publication values, so `implement-run@1` accepts `draft` while `plan-run@1` rejects it.
