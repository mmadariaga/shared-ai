> **⚠ POST-HOC RECORD** — This proposal was backfilled after implementation against a user-supplied statement of intent. It describes a decision already made, not one being proposed.

## Why

A user who enabled automatic publication in the shared `.sai/settings.jsonc` saw the agent refuse to apply it, because under ADR 0224 a granting value of `publication.autoApprove` or `pr.publishAfterRun` counted only from the personal `.sai/settings.local.jsonc` (`CONSENT_IDS` and `consentWarning` in `sai/tools/project-settings.js`). The setting had no effect from the shared file and the behavior was surprising. The team wants one shared grant that holds for every contributor.

## What Changes

- `sai/tools/project-settings.js`: `readSettings` merges a granting value of `publication.autoApprove` and `pr.publishAfterRun` from `.sai/settings.jsonc` like any other key, with `.sai/settings.local.jsonc` still overriding key by key. `CONSENT_IDS`, `grants`, `consentWarning`, the `consentWarnings` result, and `readAutoApprove` are removed; `get` carries no consent warning, and `autoApprove` returns `true` for a stored boolean `true` from either file.
- `sai/tools/to-pr.js` and `sai/tools/to-backlog.js`: the consent warning is no longer added to `warnings`; the auto-approval value is still read by the tool and bound into the confirmation tokens.
- `bin/project-settings-writer.js`: `saveSettings` treats the two keys like every other key: they go to the local file only when it already holds the key, otherwise to `.sai/settings.jsonc`; the local file is never created, and the git-not-ignored warning (`localFileNotIgnored`) is removed.
- `bin/project-settings-screen.js`: the Auto-approve publication row shows and saves through the ordinary base/local override rules, with no consent-specific branch, and no consent warning is printed when a screen opens or after a save.
- `skills/universal/safe-operations/SKILL.md` and `AGENTS.md` (§ Optional plan publication, § Safe Operations): a granting value of either key, from either file, is a held confirmation for the publication that key covers.
- `skills/universal/to-pr/SKILL.md`, `skills/universal/to-backlog/SKILL.md`, `docs/project-settings.md`, `docs/commands/to-pr.md`, `docs/commands/to-backlog.md`: the local-only rule and its warning are removed from the prose; the Publication consent section of `docs/project-settings.md` is deleted.
- `docs/adr/0227b-publication-consent-comes-from-either-settings-file.md`: new ADR that supersedes ADR 0224 and records the accepted risk; `docs/adr/0000-INDEX.md` lists it and moves ADR 0224 to the superseded section. The ADR 0224 file is not edited.
- Tests updated to the shared rule: `test/project-settings.test.js`, `test/project-settings-screen.test.js`, `test/to-pr.test.js`, `test/to-backlog.test.js`.

Unchanged: the unattended refusals of `to-pr.js` (force push, default branch, detached HEAD, merged or closed request), the confirmation token binding the setting, the approval question after a `stale-baseline` or `divergent` renewal or an explicit request to review, and `pr.publishAfterRun` having no setup menu row. Claude Code and opencode apply the rule identically.

## Capabilities

### New Capabilities

None

### Modified Capabilities

- `project-settings`: a granting value of the two publication consent keys in `.sai/settings.jsonc` merges like any other key; the consent warning, `CONSENT_IDS`, and `readAutoApprove` are removed.
- `project-settings-writer`: the two consent keys are saved under the ordinary base/local rule; the local file is never created and the git-not-ignored warning is removed.
- `project-settings-screen`: the Auto-approve publication row uses the ordinary base/local display and save rules.
- `to-pr`: a shared `publication.autoApprove: true` binds `auto_approve` into both tokens; no consent warning is reported.
- `backlog-publication`: a shared `publication.autoApprove: true` binds `auto_approve` into every backlog proposal; no consent warning is reported.
