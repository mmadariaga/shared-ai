> **⚠ POST-HOC RECORD** — This proposal was backfilled after implementation against a user-supplied statement of intent. It describes a decision already made, not one being proposed.

## Why

Design writes `**Existing Tests Broken**` per Step (`sai/commands/design/steps/tasks.md`), and nothing reads it, so a Step that breaks a pre-existing test reaches apply with no plan-level owner for that test. GREEN may not touch tests and RED could only retire them, so those Steps ended in `blocking-contradiction` (11% of GREEN dispatches). Design's restricted `Manual Verification` and conditional `Migration Plan` likewise reached no plan. This change follows `implement-plan-slimming`: it carries the three unconsumed design fields into fixed locations of `implementation.md` and lets RED own the update of exactly the plan-named existing tests.

## What Changes

- The RED block of `sai/commands/implement/implementation-plan.template.md` gains an `**Existing tests to update:**` line beside `**Retirements:**`, listing each file by exact repository-relative path with its `compile` or `runtime` mode. The Verify RED checkbox also accepts that declared failure.
- `sai/commands/implement/steps/common.md` and `plan-generation.md` carry the rules: each `Existing Tests Broken` entry becomes an update line (a test that no longer makes sense becomes a retirement), a non-empty field forces a RED block and a green-direct Step requires `None`, each `Manual Verification` item becomes a `- [ ]` checkbox under the `**Functional (...)**` header of the first Step where it is observable (or the last Step), and a `Migration Plan` shapes Step order or an italic `*(...)*` note. An absent field or section counts as `None`.
- `sai/commands/implement/steps/validation.md` checks that every entry of the three design fields is carried or explained in one line; absent entries never fail it.
- `sai/commands/apply/red-worker.md` lets RED modify exactly the plan-named existing tests (declared in field 8, kept across recovery continuations) and counts their declared `compile` or `runtime` failure as a valid RED; `sai/commands/apply/coordinator.md` judges RED failure class the same way.
- `sai/tools/apply-step.js` parses the update line and adds those paths to the RED allowed set; a RED dispatch touching any other existing test, and a GREEN dispatch touching a plan-named test, are out of the allowed set. GREEN keeps its absolute test-file prohibition.
- `AGENTS.md` § RED → GREEN states the widened RED ownership. Tests pin the new wording and the tool behavior.

## Capabilities

### New Capabilities
- `implement-design-carry-through`: the implementation plan carries Existing Tests Broken, Manual Verification, and Migration Plan, and validation checks each is carried or explained.
- `apply-red-existing-test-update`: RED may update exactly the plan-named existing tests, their declared failure is a valid RED, and `apply-step.js verify` enforces the allowed set.

### Modified Capabilities
- `apply-test-retirement`: RED write authority is no longer retirement-only.
- `apply-step-verification`: a declared compile or runtime failure of a plan-named updated test is a valid RED.
- `apply-red-green-worker-model`: the RED worker contract admits plan-named existing tests to update.
- `implement-red-phase-contract`: the RED block may carry the `**Existing tests to update:**` line.

## Impact
