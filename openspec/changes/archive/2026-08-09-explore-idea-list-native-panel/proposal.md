**Complexity**: medium (1 capability, 4 requirements, no breaking change)

## Why

In a long explore session the plain-text idea list scrolls out of view, so the user loses the only surface that tracks the explored idea across turns; opencode already exposes a native task panel and the experience there is better, so the goal is parity on Claude Code. The render contract in `sai/instructions/explore.md` (item 11, Idea Progress List) explicitly forbids any harness task-list tool or panel, so it is the blocking site.

## What Changes

- The idea progress list renders through a new per-harness render binding that follows the existing worker-binding pattern (`sai/orchestration/workers/bindings/{claude,opencode}/`), and panel availability is declared by the binding, never detected at runtime: the two supported harnesses (Claude Code and opencode) declare a native task panel, on which the binding renders the list — replacing plain in-conversation text, never both surfaces — expressing a marked item as `completed` and a cleared item back to `pending` (no item carries `in_progress`), carrying each slice's `**Change name**` key in a machine-readable panel entry field for stable item identity, and keeping the slice's change name in the label so items of different slices stay visually distinguishable; a binding that declares no native task panel renders plain in-conversation Markdown checkbox text as the declared fallback, an extension point no supported harness exercises today.
- The item 11 (Idea Progress List) render contract drops the "no harness task-list tool or panel" prohibition and routes rendering through the binding; the timing rules survive unchanged — no render while the list holds only the research item, first render at the first slice identification, and exactly one render per turn after all of that turn's additions and state changes.
- Explore's own contract states that while an explore chat is active, the native task panel's declared owner is the idea progress list — an ownership rule, not a suppression rule, with an operative consequence: the list never coexists with other surfaces' entries, its renders displace the panel wholesale, and a future surface that needs the panel renegotiates ownership rather than deleting a prohibition or writing alongside. The supervised run is the illustrative case: no plan-based list renders during supervision, while dispatched workers' progress events are processed for their plan-independent obligations exactly per the coordinator contract (`changed_files` unioning and `continue_after_progress` unchanged; step marking has no application because no adapter-declared plan is in force in the supervised flow), so this change alters no observable supervised-run behavior. Standalone `/sai-1-spec` and `/sai-2-design` progress rendering remains unchanged.
- The "conversation only, never written" clause is reworded with the prohibition scoped to writes the session itself performs: the session never writes the list to any file, artifact, change directory, or configuration, and the list is still never derived from repository state, while harness session state (the panel) is permitted as a render surface — harness-internal persistence of the harness's own task-panel state is harness session machinery, not a session write, and is out of scope of the prohibition.
- The idea-list contract states the panel update originates exclusively from the coordinator session — the `sai-explore` session itself — never from a worker subagent (opencode disables `todowrite` for subagents by default).
- The idea-list contract defines the panel lifecycle: every render emits the full list and replaces whatever the panel holds, so the list never coexists with foreign entries — at first render it displaces any entries that re-occupied the panel (a routed phase's progress plan or `/sai-4-apply`'s step projection), a new `sai-explore` chat clears at its start only the entries a previous idea list rendered, classified by an ownership marker in the machine-readable entry field (the same field that carries the change-name key; the binding reads the marker only, never list content — a claim action distinct from list rendering, never other surfaces' entries), so a previous chat's entries never linger as current and a chat that never crystallizes leaves no idea-list entries on the panel, the entries persist as session state after the chat ends with no end-of-life cleanup, and any later surface that renders on the panel replaces them wholesale.
- `GLOSSARY.md` gains the **Native Task Panel** term and updates the **Idea Progress List** definition, its relationship line, and the flagged-ambiguity phrasing.

## Additional Notes

- Re-grounded "no-op today" premise: the routed spec/design/implement adapters DO declare progress plans (`sai/commands/spec/coordinator.md:19-25`; `openspec/specs/design-coordinator/spec.md:172`; `openspec/specs/implement-progress-plan/spec.md:11`), and the worker bindings instruct the coordinator to update the harness task list on each progress event (`sai/orchestration/workers/bindings/claude/spec-worker.md:13`, `design-worker.md:23`; opencode counterparts). Whether the supervisor de facto processes those events was ambiguous in the sources: explore's supervised contract (item 10, Supervised sai-1 pipeline) enumerates the closed lifecycle payloads without addressing progress events at all. Rather than assert an inference, this change pins the property in the least invasive form: the supervised contract is amended to state that dispatched workers' progress events are received and processed per the coordinator contract for their plan-independent obligations — `changed_files` unioning and `continue_after_progress` continuation unchanged; step marking has no application because marking is defined only against an adapter-declared plan and no adapter-declared plan is in force in the supervised flow — with no plan-based list rendering during supervised coordination, a state the existing rules already entail because the neutral task-list policy and the worker bindings govern routed phases that declare a progress plan and the supervised flow declares none; the no-op claim therefore holds without breaking the worker protocol and without carving any exception into the policy — the worker bindings stay byte-identical and `sai/policies/todo-structure.md` is untouched.
- Decisions: (1) ownership rule rather than suppression rule — identical visible behavior today, but a prohibition must be deleted later while an ownership rule is simply renegotiated; ownership carries an operative consequence (the list never coexists with other surfaces' entries, and a future surface renegotiates rather than writes alongside), scoped to the active explore chat with the supervised run as the illustrative case, which is where a future start-pipeline task list plugs in; (2) the rule lives in explore's own contract, not in the worker bindings — writing it into the bindings would also silence standalone `/sai-1-spec` and `/sai-2-design`, where no idea list competes for the panel, and would scatter one rule across three files; (3) the native panel is technically sufficient for this list's semantics — `pending` is a settable status so clearing a review item after a High finding is expressible as completed → pending, `in_progress` is optional matching a list with no active item, and a machine-readable panel entry field (identity or metadata) carries the change-name key for stable item identity so the label is not reduced to the raw key — while the label keeps the slice's change name, because the metadata field is not user-visible and multi-slice labels must stay distinguishable on screen (the concrete per-harness field is resolved at design); (4) the panel replaces plain text where a panel exists rather than rendering both, to avoid maintaining the same list on two surfaces; (5) the never-written prohibition is scoped to writes the session itself performs — harness-internal persistence of the harness's own task-panel state is harness session machinery, not a session write, and remains out of scope, because the prohibition's original intent was to keep the pipeline from persisting the list as an artifact or config, never to police the harness's session store; (6) panel availability is declared by the per-harness binding, never runtime-detected — both supported harnesses declare a panel, so the plain-text fallback is a declared extension point for a future harness without a panel rather than a branch an implementer must keep live through runtime detection; (7) panel entries are session-level render state with replacement semantics, not chat-scoped data — each render emits the full list and displaces whatever the panel holds, the list never coexists with foreign entries, each new explore chat clears at its start only the entries a previous idea list rendered, classified by an ownership marker in the machine-readable panel entry field (the same field that carries the change-name key; the binding is authorized to read panel entry state for that classification, marker only and never list content — a claim action distinct from list rendering, which stays forbidden while the list holds only the research item; other surfaces' entries bear no marker and are never cleared by it), and explore performs no end-of-chat cleanup because the harnesses provide no end-of-chat hook, so last-rendered entries persist only until the next writer (a render, another surface, or the next chat's start clear of the idea list's own entries) replaces them.
- Rejected alternatives: worker takes the panel during a supervised run and the idea list is restored afterwards (builds save/restore machinery for a progress plan that does not exist yet; still available later); one merged list with worker steps nested beneath idea items (same reason); keep plain text and re-render it more often (does not deliver parity with opencode's native panel); extend the neutral task-list policy with a non-monotone state (unnecessary — the policy's scope line already excludes a list with no declared `progress_plan`).
- Trade-offs accepted: rendering leaves the transcript, so the per-turn audit trail of the list — notably a review item being cleared after a High finding — is no longer preserved inline; the panel shows current state only. The idea list's panel entries can outlive the explore chat as last-rendered session state until another surface renders or the next explore chat's start clear removes them — accepted, because the harnesses expose no end-of-chat hook, and cleanup machinery would be the save/restore complexity the design rejects; the start clear closes the window where a foreign chat's list could otherwise present as current, and it is deliberately scoped to the idea list's own entries, so it never destroys another command's surface (a routed plan or `/sai-4-apply`'s step projection); those surfaces are displaced only by the idea list's ordinary first-render full-list replacement — the single-slot, latest-render-wins semantics every surface already subjects the panel to. A future task list for the supervised pipeline will still have to renegotiate panel ownership; this change deliberately does not pre-solve that.
- Framing: the panel is a single-slot resource with one declared owner at a time, not a surface each producer writes to independently; the idea progress list and a routed phase's progress task list are different data types — marked/unmarked with reversal, versus a declared, ordered, monotone plan.
- Non-goal: giving the supervised pipeline its own task list.
- Explore stays read-only; the change touches contract, binding, and spec files only — no production code.
