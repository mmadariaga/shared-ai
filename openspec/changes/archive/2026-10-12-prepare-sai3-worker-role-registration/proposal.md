## Why

Implementation registration previously encoded one canonical sai-3 worker directly in phase-level identity and contract tables. Separating phase membership from the closed worker-role definition prepares the registration extension point while keeping the current installed roster and outputs unchanged.

## What Changes

- Added an immutable implementation registration definition that owns the implementation phase, sai-3 command identity, and ordered supported worker identities and contracts.
- Updated worker-matrix validation and installer validation to resolve implementation identities and contracts from that definition.
- Derived implementation registration cardinality and ordered phase entries from the supported role list while retaining duplicate-worker and ordering checks.
- Updated implementation worker projection to use the registered role contract and updated model-customizer grouping to use the same role definition.
- Added tests for the closed current role set, invalid identities and contracts, duplicate and reordered registrations, both harnesses' rendered output equivalence, binding collisions, and unchanged customizer grouping.
- Kept the supported implementation role set limited to sai-3-implementation-worker. This preparation adds no five-agent planning behavior.

## Capabilities

### New Capabilities

- `implementation-role-registration-seam`: One authoritative definition separates implementation-phase membership from the closed set of registered implementation worker roles and supplies validation, projection, and model-customizer grouping.
- `existing-installation-equivalence`: Regression coverage preserves current rendered worker content and destinations, implementation identity and contract checks, binding collision rejection, and sai-3 customizer grouping for Claude Code and opencode.

### Modified Capabilities

None. The selected diff is a behavior-preserving registration refactor and adds no changes to existing capability requirements.
