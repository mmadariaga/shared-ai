## Why

`az devops invoke` picks the endpoint by area and resource name, so `git/pullrequests` resolved to the project-scoped, GET-only location: every Azure DevOps pull-request creation of `to-pr` failed with "does not support http method 'POST'" after the branch push, and the pull-request list read the pull requests of every repository in the project. The `to-pr` skill also did not name the field that carries the push token, and an observed run blocked `push` twice.

## What Changes

- `api()` in `sai/tools/azure-publication.js` sends every `git/pullrequests` call (`GET`, `POST`, `PATCH`) through the installed-SDK bridge with the repository-scoped location id `9946fd70-0d40-406e-b686-b4744cbbcc37` and API version `7.1`, in place of `az devops invoke`. The call sites keep their route keys: `project` and `repositoryId` on every call, `pullRequestId` on update only.
- The SDK request replaces the boolean `identity` with a `client` selector whose value is `location`, `wit`, or `git`. `SDK_SCRIPT` in `sai/tools/from-backlog.js` builds `get_location_client`, `get_work_item_tracking_client`, or `get_git_client` from it. `sai/tools/from-next-backlog-item-azuredevops.js` sends `client: 'wit'` in place of `identity: false`.
- Pull-request bodies travel as UTF-8 JSON on the SDK bridge's standard input, so pull-request calls no longer write a temporary payload file.
- `git/repositories` and the other unambiguous resources keep the `az devops invoke` path.
- `skills/universal/to-backlog/providers/azuredevops-transport.md` documents the pull-request ambiguity, the `client` selector, and the pull-request SDK location, and states that `git/repositories` keeps invoke.
- `skills/universal/to-pr/SKILL.md` § 4 states that `push` receives the push token in the `confirmation` field and rejects any other field name.
- Tests cover the `git` selector in the SDK routing fixture, the repository-scoped route values and methods, the absence of a payload file, the failure-reason classification, and the push-token field name.
