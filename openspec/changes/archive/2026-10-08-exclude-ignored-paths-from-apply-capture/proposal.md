> **⚠ POST-HOC RECORD** — This proposal was backfilled after implementation against a user-supplied statement of intent. It describes a decision already made, not one being proposed.

## Why

In a real `/sai-build` run on a .NET project, the Step 1 test command rebuilt the git-ignored `bin/` and `obj/` outputs, and `apply-step.js verify` returned `ok: false` for a valid RED dispatch. The run had no way to recover, because the baseline stores only content fingerprints. The cause was the state capture: it enumerated files with `git ls-files --cached --others` and no ignore filter, so every ignored file was fingerprinted and every change to one counted as an out-of-scope change. This blocked apply in any project whose test command writes ignored files.

## What Changes

- `captureState` in `sai/tools/apply-step.js` now enumerates with `git ls-files -z --cached --others --exclude-standard`. The capture holds tracked files plus untracked files that git does not ignore. Ignored paths are outside the baseline, checkpoint, settled, and current-state captures, so creating, changing, or deleting one produces no discrepancy.
- A new `declaredPaths` helper reads the change's `tasks.md` and collects the exact paths every Step declares in `**Files Affected**`, plus the resolved files of declared generated families. Every `captureState` caller (`baseline`, `dispatch-check`, the execution-state comparison behind `verify` and `close`, the settled receipt, and `restore-unrelated-index`) passes that list, and the capture adds those paths even when git ignores them. A worker that writes and reports a declared ignored file therefore causes no false discrepancy, and one that writes it without reporting it is still listed in `unreported`.
- Ignore status is evaluated at every capture. A file that moves between visible and ignored between two captures appears as a change.
- A generated family that cannot be resolved does not stop a capture: the capture keeps that Step's exact declared paths, and verify and close continue to report the family error. A missing `tasks.md` yields no declared paths.
- The verdict shape is unchanged: no new field, no new option, and no mode that restores the previous behavior.
- `test/apply-step-tool.test.js`: the test that pinned ignored outputs as discrepancies now asserts the opposite and also covers an out-of-scope `.gitignore` edit and an untracked visible file as discrepancies. Five tests are added: an ignored file created after the checkpoint is no discrepancy; a Step command that creates, changes, and deletes ignored paths passes verification; a tracked file matching an ignore pattern is still a discrepancy; a file that becomes ignored between captures is a discrepancy; an ignored path declared by the plan is compared.

Known limitation accepted with this change: a worker write into an ignored path that the plan does not declare (for example a local environment file) is no longer detected by the tool. Ignored paths cannot reach a commit through the tool's ownership and commit decisions, which start from `git status`.

## Capabilities

### New Capabilities

- None

### Modified Capabilities

- `apply-step-tool`: the state capture excludes git-ignored paths unless the plan declares them, and scope verification passes when a Step's commands regenerate ignored outputs and its declared files are the only visible changes.

## Impact

- Modified: `sai/tools/apply-step.js`
- Modified: `test/apply-step-tool.test.js`
- No command card, policy, or step file changes. Claude Code and opencode share the tool, and its input and output contract is unchanged.

Out of scope: design.md, tasks.md, implementation.md — not generated by /sai-backfill
