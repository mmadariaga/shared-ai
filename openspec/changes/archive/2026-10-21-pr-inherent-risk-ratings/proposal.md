## Why

Human reviewers of a pull request get no explicit signal of how risky the change inherently is, so they cannot tell where to look with extra care. Fixed findings and completed audits do not prove that nothing was missed. `/to-pr` now publishes four independent inherent-risk ratings in the pull request description, so the reviewer sees where the change carries risk by its nature.

## What Changes

- New shared policy `sai/policies/inherent-risk.md`: the single source of the computation. It defines four independent ratings (security, reversibility, critical sections, blast radius), the `low` / `medium` / `high` scale, the rule that a published level is the higher of the judgment and its floor, a one-line justification with `path:line` evidence per rating, the rule that a lower level than a previous block needs the motivating surface to be gone from the final diff, and the ratings block format between `sai-inherent-risk` HTML comment markers carrying the merge-base and the code fingerprint. The ratings measure the change itself: fixing findings, hardening, validating, or testing lowers no level, and they change no review depth, start no audit, and carry no global score.
- New deterministic tool `sai/tools/risk-signals.js` (`compute --parent <branch> [--cwd <project-root>]`): resolves the merge-base with the parent branch, hashes the diff from the merge-base to HEAD excluding `openspec/` as the code fingerprint, and sets floors from generic signals — sensitive paths (high) and exposed route/controller paths and user-input lines (medium) for security; migrations and schemas (high), CI/container/infrastructure files and dependency manifests (medium), and file deletions (by count) for reversibility; changed-file count, changed-line count, and CodeGraph dependents when a `.codegraph/` index exists for blast radius. Critical sections have no floor. Test and documentation files raise no security or reversibility floor, and a rename is not a deletion. It prints one JSON object (`status: ok` with `merge_base`, `fingerprint`, `floors`, `signals`, `stats`, `codegraph`, or `status: blocked` with a `message` for an invalid or unknown parent).
- `skills/universal/to-pr/SKILL.md` §2 computes the ratings on the current tree with the policy and the tool, using the collection ref as the parent branch, with or without an OpenSpec change, and places the block in the draft. On update it replaces everything between the block markers (or inserts the block at its fixed position) without a separate approval, keeps the rest of the description under the existing retention rule, and still presents the full result for publication approval.
- `skills/universal/to-pr/description-format.md` fixes the block position: after `## Audits`, or after `## Test plan` when `## Audits` is omitted, and before `## Out of Scope / Follow-ups`.
- `sai/policies/tool-resolution.md` documents the `risk-signals.js` invocation form (scope drift: implemented, but not named in the intent statement).
- `docs/commands/to-pr.md` describes the Inherent Risk block.
- `test/risk-signals-tool.test.js` covers the floors, the fingerprint, the CodeGraph-less path, and the blocked outcome.

## Capabilities

### New Capabilities

- `inherent-risk-ratings`: the shared computation of four independent `low` / `medium` / `high` ratings with deterministic floors, a `path:line` justification per rating, and the ratings block format.

### Modified Capabilities

- `to-pr`: the pull request description carries the ratings block, computed on the current tree, at a fixed position, and replaced between its markers on update.
- `shared-tool-resolution`: the shared tool-resolution instructions declare the `risk-signals.js` invocation form (`compute --parent <branch> [--cwd <project-root>]`).

## Impact

New files:
- `sai/policies/inherent-risk.md`
- `sai/tools/risk-signals.js`
- `test/risk-signals-tool.test.js`

Modified files:
- `sai/policies/tool-resolution.md`
- `skills/universal/to-pr/SKILL.md`
- `skills/universal/to-pr/description-format.md`
- `docs/commands/to-pr.md`

Known limitations: floors come from generic path, extension, and diff-size heuristics, so they can over- or under-estimate risk in a given stack; the judgment can only raise them.

Out of scope: design.md, tasks.md, implementation.md — not generated by /sai-backfill
