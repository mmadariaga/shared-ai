**Complexity**: high (2 capabilities, 19 requirements, 3 local files, no breaking change)

## Why

The Step 3 index-maintenance hook in `sai/instructions/implement.md` and the `adr-index-maintenance` capability spec already parameterize **one** axis of the index — the `<domain unit>` H2 noun is substituted at cold-build time from the project's own ADR vocabulary, and the same template is therefore usable across projects whose ADRs reference commands, modules, endpoints, packages, or services. But the parameterization stops there. Every other parameter of the index machinery is still hardcoded inside `openspec/specs/adr-index-maintenance/spec.md` and inside the hook text itself: the mapping rules and their precedence, the fallback noun, the cross-cutting thresholds, the canonical five-section skeleton, the relationship-token rules, the link-form rules, and the four index-output invariants (language, links, record titles, index H1) — all of which are also implicit — spread across the spec and the hook — rather than named as one contract. This change extracts the shared machinery into a parameterizable `decision-record-index-machinery` capability, pins the framework values (mapping list, fallback noun, thresholds) in that spec as the contractually-defined defaults for unconfigured projects, and lets `adr-index-maintenance` delegate to the abstract surface for every currently-hardcoded value. The framework values produce a byte-for-byte equivalent of today's live `docs/adr/0000-INDEX.md` (modulo new ADRs added after the change lands), so a project that does nothing sees no behavioral change. This slice ships the abstract surface instantiated for the ADR family only; the cross-family rules (a `supersedes` family-boundary restriction and a `refs` / `amends` / etc. cross-family link form) are part of the abstract surface and bind this slice from this point forward; their observed effect differs in this slice — the `supersedes` family-boundary restriction is dormant (no cross-family supersede exists in the corpus), while the cross-family link form `../<family>/NNNN-slug.md` and the `<family>:NNNN` encoding codify behavior already present in the live ADR index, which already links to DDR records, so the byte-for-byte equivalence holds because the abstract surface's formats match the existing links.

## Additional Notes

- **Why no project-level config block in this slice (per M1).** A future slice that wants per-project overrides of the framework values can introduce a `decision_record_indexes:` block in `openspec/config.yaml` with a closed pattern vocabulary, precedence semantics, threshold overrides, and a validation contract. This slice does not introduce that block. The framework values are pinned in the abstract spec as the contractually-defined defaults; they apply to every project that does not opt in to a future override mechanism. This keeps the change scoped to "extract the abstract surface and instantiate it for adr" without speculative generality.
- **Why the `<domain unit>` noun is a derived value, not a per-index binding (per M4).** The cold build's procedure reads the mapping list and the records' content, applies the rules in precedence order, and produces the noun as its output. Pinning the noun in a per-index binding would freeze it at the spec level and break the cold build's derivation across projects with different ADR vocabularies. Three per-index bindings (storage directory, index filename, index H1) plus two type-specific section headings is the correct granularity.
- **Why DDR is not in this slice (per H1).** The crystallized change scoped slice 0 to "instantiate the abstract surface with exactly one family, adr". Adding the DDR family in the same change collapses slice 0 and slice 1, which would prevent the ADR-behavior regression surface from being isolable in the diff. The DDR family is a separate slice that adds a second concrete capability against the same abstract surface; that slice also introduces the ADR-vs-DDR routing rule, which is out of scope here. The abstract surface's "Relationship tokens respect family boundaries" requirement binds this slice from this point forward, so the DDR slice does not have to re-derive the cross-family rules.
- **Why the abstract surface's cross-family rules are present even though DDR is not (per H2, H4).** The cross-family rules — `supersedes` is family-bound; `refs` / `pair-with` / `amends` / `reframes` / `reverses` may cross; cross-family link form `../<family>/NNNN-slug.md` — are part of the abstract surface because they constrain the maintenance cycle's behavior at the family boundary. The `supersedes` family-boundary restriction is dormant in this slice (no cross-family supersede exists in the corpus); the cross-family link form and `<family>:NNNN` encoding, by contrast, codify behavior already present in the live ADR index, which already links to DDR records. Binding them from this slice forward means the DDR slice (or any later slice that adds a second family) does not have to re-derive them, and the abstract surface stays a stable contract. A `supersedes` relationship that crosses a family boundary is a classification error (per the abstract surface's scenario) — the source record is not moved, the target family's index is not touched, and the error is surfaced so the user can reclassify the source or target record.
- **Why the canonical section skeleton is in the abstract surface, not the per-index binding (per M3).** The five section positions (H1, Conventions, By <domain unit>, Cross-cutting categories, then the two type-specific section headings) are invariant across all decision-record indexes; only the last two headings' TEXT varies by family. Putting the skeleton in the abstract surface fixes the positions, and the per-index binding names the two type-specific texts. This split is consistent with the other abstract invariants (language, links, record titles, index H1) and keeps the abstract surface a stable contract.
- **Why the byte-for-byte equivalence claim is restricted to the ADR index in this slice (per H4).** The live `docs/adr/0000-INDEX.md` is the only index file the change touches. The framework mapping list, fallback noun, and threshold values produce a `## By command` H2 and the same threshold structure (2 / 8–12 / 8) for this repository's ADRs, so the cold-build output is byte-for-byte equivalent to the live file. The cross-family link form `../<family>/NNNN-slug.md` is part of the abstract surface and codifies behavior already present in the live ADR index — which already links to DDR records via that form — so the byte-for-byte equivalence holds because the abstract surface's format matches the existing hand-curated links. The `supersedes` family-boundary restriction, by contrast, is dormant in this slice (no cross-family supersede exists). When the DDR slice adds the DDR capability spec, the equivalence claim is re-evaluated against the live `docs/ddr/0000-INDEX.md` separately.
- **Why no parity-guard test in this slice (per M2, with the precedent correctly identified).** The `test/report-template-parity.test.js` test established the parity-guard category for two-family skeletons (review / security / performance / accessibility templates). That category applies between the abstract surface and a single concrete instantiation only when there are at least two concrete instantiations to compare; this slice ships exactly one. When the DDR slice adds the second family, it should add a parity guard following the report-template-parity precedent — asserting that the two index families' skeletons stay structurally aligned, the mapping list and thresholds are shared, and the per-index bindings differ only in the documented places. The `test/orchestration-source-layout-step-2.test.js` and `test/orchestration-source-layout-step-6.test.js` tests cover instruction-tree content for unrelated subsystems, not the index maintenance cycle; they are not the right precedent here.
- **Why no GLOSSARY.md change in this slice.** The abstract surface does not introduce a new domain term — `GLOSSARY.md` has no existing `adr-index-maintenance` coverage (its scope is the pipeline's own domain language, and it excludes general concepts such as ADRs and indexes), and the abstract surface's own requirements carry the meaning. A future slice that adds a second family (or that introduces the project-level config block) may need to add a glossary term; that decision belongs to that slice.
- **Why the ADR/DDR recommendation is deferred to slice 1 (per L1, H3).** The current change's only architecture decision is the extraction of the abstract surface. Per the existing routing discipline, an architecture decision independent of business rules is an ADR, not a DDR. The decision is recorded in this proposal's Additional Notes, which is archived with the change. The DDR-side decision (adding the second family, introducing the routing rule) belongs to slice 1 and is not a consequence of this slice.
- **No `instruction-output-templates` change.** The `sai/instructions/_templates/adr-index.md` template stays. The abstract surface's contract lives in the spec, not in a new template — the template continues to be the cold-build section skeleton, and the substitution of `<domain unit>` is now driven by the abstract surface's framework values instead of the hardcoded rule set in the spec text.
- **No `installer-and-documentation-alignment` change.** No docs/ADRs or docs/DDRs are being marked superseded in this change.
