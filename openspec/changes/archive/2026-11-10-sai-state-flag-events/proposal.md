> **⚠ POST-HOC RECORD** — This proposal was backfilled after implementation against a user-supplied statement of intent. It describes a decision already made, not one being proposed.

## Why

Every identifier-only `sai-state` event cost two tool calls (write the event file, then emit), although such events need no JSON quoting. The `emit` argument parser accepted only a closed set of boolean flags and let a repeated flag overwrite the earlier one, so there was no way to build an event on the command line.

## What Changes

- `bin/sai-state.js` `emit` builds an identifier event from flags: `--set <field>=<id>` sets one value, repeatable `--add <field>=<id>` appends to a list (`--add <field>=` records an empty list), and `--set-path <field>="<path>"` sets a path. The parser collects these flags in order instead of overwriting a repeated flag.
- Field names start with a letter followed by letters, digits, or `_`. `--set` and `--add` values must match `ID_PATTERN`, which `sai-state/machines/run-core.js` now exports and `bin/sai-state.js` imports, so the flag parser and the run machines share one identifier rule. A `--set-path` value must be non-empty and hold no `"`, `$`, backtick, or control character.
- Any violation, a field set twice with `--set`, a field named by both `--add` and `--set`/`--set-path`, or a flag combined with `--input-file`, stdin `-`, `--progress`, or `--ready-to-propose` is a usage error (exit 2) that changes no state; the stderr message shows the flag form, and a rejected path names `--input-file` as the alternative. The CLI usage text lists the flag form.
- The flag form becomes the default event delivery: `sai/policies/stage-machine.md` (Emit verb entry, canonical example, § Event delivery), the `bin/sai-state.js` bullet of `sai/policies/tool-resolution.md`, `sai/commands/implement/coordinator.md`, `sai/commands/plan/cycle.md` (run events and step-id emits), `sai/commands/merge/coordinator.md`, and the explore event steps (`sai/commands/explore/instructions.md`, `steps/common.md`, `steps/poc-lane.md`) now prescribe flags. The input file stays the transport for events with free text or a path the flags reject; Ready to Propose blocks and worker progress reports keep their file transports.
- Tests: `test/sai-state.test.js` covers the flag form, its usage errors, and runs it through Bash and PowerShell 7; `test/explore-step-reachability.test.js`, `test/step-machine-wiring.test.js`, and `test/worker-report-transport.test.js` follow the new card wording.

## Capabilities

### New Capabilities

None

### Modified Capabilities

- `stage-machine-cli-interface`: `emit` accepts identifier events built from `--set`, `--add`, and `--set-path` flags, with their validation and usage errors.
- `stage-machine-emit-delivery`: the stage-machine policy documents the flag form as the default delivery of identifier events, keeping the input file for free text and rejected paths.
- `merge-run-state`: the merge coordinator states `merge-run@1` events as flags whose `kind` names the event.
- `block-file-delivery`: non-block identifier events (intents, recorded lists, `step_ids`) travel as flags; free text and progress payloads keep the input file.
- `tool-input-file-delivery`: an identifier event of `sai-state emit` travels as flags and is not structured input under the input-file rule; free text and rejected paths keep the input file.
