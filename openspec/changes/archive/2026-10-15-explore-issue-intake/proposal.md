> **⚠ POST-HOC RECORD** — This proposal was backfilled after implementation against a user-supplied statement of intent. It describes a decision already made, not one being proposed.

## Why

Explore had no defined behavior for an incoming issue, so runs improvised: one observed session wasted three turns before treating the issue as the candidate idea, and another emitted a Ready to Propose block with invented fields because the block emit accepted a block at any stage of the exploration.

## What Changes

- New step file `sai/commands/explore/steps/issue-intake.md` defines one source-agnostic intake for any issue, bug, or ticket whose content is in the conversation. Intake starts on issue-format text (the headings `## Problem`, `## Goal`, `## Scope`, `## Non-goals`, `## Open questions`, `## Maturity`) or on an explicit user statement that the text is an issue; a link triggers nothing, and the intake names no skill.
- The intake asks a work question (`work` / `context`) through the harness-native picker (`AskUserQuestion` on Claude Code, `question` on opencode) once the complete issue is in the conversation, and the question closes that turn. Several unrelated issues get one `work` option each plus `context`; a message that already states the intent to work on the issue answers `work`; an issue in the Ready to Propose form shows a `Change name` proposed from its `Goal`; `--fast-track` skips nothing.
- On `work`, in the same turn, the issue becomes the candidate idea, `Explore change` begins, and the issue's `E#` and `I#` lists become the starting lists of `Review edge cases` and `Implementation details`; related issues may be explored for context while the work stays on the first issue. On `context`, no candidate idea is created.
- `sai/commands/explore/steps/common.md` fetches the intake file when an issue enters the conversation, before the direct-looking request rule applies; `sai/commands/explore/instructions.md` lists it in the step map.
- `sai/commands/explore/steps/review-edge-cases.md` and `sai/commands/explore/steps/implementation-details.md` take a carried `E` or `I` list as the stage's starting list and add items only from that stage's checks.
- `bin/sai-state.js` (`commandEmitReadyToPropose`) rejects a block emit while the same session's `explore-idea@1` stage is not `crystallize` (an absent state counts as `explore-change`): it records nothing, exits 1, and answers `INVALID_EVENT` with `reason: "STAGE_NOT_CRYSTALLIZE"`, the found `stage`, and the `explore-idea@1` pointer. A single-slice amendment (`--amend`) is outside this check. `sai/policies/stage-machine.md` documents the guard.
- Tests cover the new step file and the block guard at every pre-crystallize stage, its acceptance at `crystallize`, and the unchecked amendment.

## Capabilities

### New Capabilities

- `explore-issue-intake`: the intake trigger, the work question, and the carried edge-case and implementation-detail starting lists for an issue entering Explore.

### Modified Capabilities

- `stage-machine-cli-interface`: the Ready to Propose block emit is accepted only at the `crystallize` stage of `explore-idea@1`, and the closed error vocabulary gains the `STAGE_NOT_CRYSTALLIZE` reason.
- `validated-block-recording`: an emit outside the `crystallize` stage records nothing.
