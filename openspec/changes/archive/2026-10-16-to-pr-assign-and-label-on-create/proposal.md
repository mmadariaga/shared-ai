## Why

Requests opened through `to-pr` carried only a title and a description, because the skill put labels and assignees out of scope. The user therefore had to assign and triage every GitHub pull request or GitLab merge request by hand after publication.

## What Changes

- When `query` prepares the creation of a GitHub pull request or GitLab merge request, it reads the current user and every page of the project's labels through two new adapter methods (`currentUser`, `labels`) in `sai/tools/to-pr-github.js` and `sai/tools/to-pr-gitlab.js`, and returns the label names as `available_labels`.
- `query` accepts an optional `labels` list, keeps only names that exactly match the project's label list without duplicates, and drops every other name with a warning. On creation the proposal carries the current user as `assignee` and the kept `labels`, so both enter the confirmation digest.
- GitHub creation sends `POST pulls`, then one `PATCH issues/{number}` with `assignees` and `labels`, skipped when both are empty; a failure of that second call returns the created request with a warning naming its URL and what was not applied, never the `uncertain` status. GitLab creation sends `assignee_ids` and a comma-separated `labels` value in the same `POST merge_requests`.
- After a creation, `publish` compares the request's actual assignee and labels with the approved proposal and adds a warning for every missing or unapproved entry. Provider identities now carry `assignees` and `labels`, so `recover` reports them without applying anything.
- A failure to read the current user or the labels is a warning that removes only that part from the proposal. When such a read fails again at publication, `publish` uses the assignee and labels the caller echoes back only when they reproduce the approved confirmation digest exactly, and adds a warning that they could not be re-read.
- An update reads and sends no assignee or labels. For Azure Repos, `query` reads neither and returns the warning `no assignee or labels: the provider does not support them`.
- `skills/universal/to-pr/SKILL.md` removes labels and assignees from the out-of-scope sentence, adds the label selection step (zero or more type or area labels from `available_labels`, never state or workflow labels, never an invented name, then `query` again with `labels`), shows the assignee, the labels, and their warnings before approval and after publication, and passes the chosen `labels` and the unchanged `assignee` to `publish`. `docs/commands/to-pr.md` and the GitHub, GitLab, and Azure DevOps provider references describe the same contract.

## Additional Notes

- Known limitations accepted: the label choice is model judgment, bounded by the tool to existing names and shown in the approval presentation; requests updated through `to-pr` and every Azure Repos request receive no assignee or labels; on GitHub the assignee and labels need a second call after creation, so a request can exist without them, which is reported as a warning.
- Labels are never created, and state or workflow labels (`wontfix`, `duplicate`, `needs review`, `good first issue`) are never selected.
- `publish` compares the actual assignee and labels with the approved ones only when the GitHub second call did not already report a failure, so one failure is not reported twice.
