> **⚠ POST-HOC RECORD** — This proposal was backfilled after implementation against a user-supplied statement of intent. It describes a decision already made, not one being proposed.

## Why

A `budget-executor` dispatched for a long command could leave its coordinator without the command's result. In a Direct Build run of `/sai-explore` on Claude Code, the executor started `npm test` (about 224 seconds, above the 120-second default shell timeout) in the background and handed back a report with `exit_code: pending` and no tallies. When the suite later finished, the harness rejected the executor's second hand-back because its single report had already been delivered, and the coordinator learned the result only by reading the executor's log file itself. `sai/policies/executor-agent.md` said a run is done when every requested command has an entry, but said nothing about long-running commands, background execution, or the single-report rule.

## What Changes

- `sai/policies/executor-agent.md`, section `## Choosing the command`: the executor reports once, after every requested command has exited, whatever its duration, and a report is never a progress update. A command within the shell's timeout runs in the foreground with the longest timeout the active harness's shell allows; a command expected to outlast that timeout runs in the background with its output going to a log file, and the executor waits for it to exit through the harness's own wait mechanism before reporting; a command the executor cannot bring to completion (no wait mechanism, or the shell kills it at its timeout) is reported as Failed with that reason and the path of its output log. Harness mechanisms are named only generically, as examples (a shell tool timeout of up to 600000 ms, a fixed shell timeout, the task notification of a background run).
- `sai/policies/executor-agent.md`, section `## Report`: one report per task message; `pending`, `running`, or a promise of later results is never an entry, and the report is the executor's only delivery.
- `skills/claude/budget-executor/SKILL.md` and `skills/opencode/budget-executor/SKILL.md`, section `## Spawn prompt`: one identical dispatcher line makes a report without a final result for a requested command (`pending`, `running`, or no entry) an obstacle under `sai/policies/obstacle-escalation.md`, resolved by reading the result from the evidence the report names, such as its output log, or by dispatching again, never by waiting for a later message from that executor.
- `test/executor-single-final-report.test.js` (new) asserts the completion rule inside `## Choosing the command` (no separate long-running section), the report rule, the unchanged existing executor rules, the absence of any resend-by-`SendMessage` rule, the identical dispatcher line in both skills, and that the dispatching cards stay free of the wait rule.
- `test/canonical-opencode-agent-behavior.test.js`: the assertion that the Claude budget skills retain no retired escalation tier ignores the literal `sai/policies/obstacle-escalation.md` path, so the new dispatcher line does not trip it.

The cards that dispatch the executor (`sai/commands/explore/direct-build-coordinator.md`, `sai/commands/implement/coordinator.md`, `sai/commands/plan/cycle.md`) are unchanged; they inherit the rule through the executor policy and the binding skills. The executor's existing rules (exact command, narrowest command, no retry or fix, low-output report, `warming: false`) are unchanged, and no rule tells the executor to resend an already-delivered result.

## Capabilities

### New Capabilities

None.

### Modified Capabilities

- `executor-universal-behavior`: the executor reports once per task message, after every requested command has exited, with a final Succeeded, Failed, or Skipped entry for each; long commands run in the background and are awaited, and a command that cannot be completed is reported as Failed with its log path.
- `executor-claude-skill`: the Claude Code `budget-executor` skill tells the dispatcher to treat a report without a final result as an obstacle and resolve it from evidence or by dispatching again.
- `executor-opencode-skill`: the opencode `budget-executor` skill carries the same dispatcher line, word for word.
