**Complexity**: high (5 files, cross-route lifecycle recovery)

## Why

A harmless runtime error can stop an unattended SAI run and ask the user how to proceed even when the active worker has a bounded, reversible, and verifiable correction. The staged change adds one route-scoped recovery policy so Plan - Unattended and Direct Build - Unattended resume only when their existing contracts prove the correction safe.

## What Changes

- Add `sai/policies/unattended-runtime-recovery.md` as the shared rule for post-disclosure runtime interruptions on the selected Plan - Unattended and Direct Build - Unattended routes.
- Apply existing dispatch, startup, replacement, validation, accepted-result, review, feedback, and one-shot execution handling before considering generic runtime repair.
- Permit repair only when the same worker is resumable, current effects are fully verifiable, the cause and correction are inside the worker boundary, no effect is replayed, existing consent remains sufficient, and the shared diagnosis allowance is unused.
- Charge the existing Plan or Direct Build diagnosis allowance before continuation, without refund, stacking, or counter reset.
- Keep Plan workers on their existing recovery continuation and give the Direct Build implementer a narrow same-worker verification note; keep backfill and archive execution orders one-shot and unreplayable.
- Validate every repaired result before trusting status, progress, changed files, or advancement; stop affected work without a routine question when recovery is unsafe, unavailable, invalid, or interrupted.
- Preserve existing Plan approval/review, Direct Build selected-scope, validated-order, and one-local-commit gates.
- Add seven static tests covering route scope, precedence, budget accounting, worker compatibility, validation, stopping, and gate preservation.
