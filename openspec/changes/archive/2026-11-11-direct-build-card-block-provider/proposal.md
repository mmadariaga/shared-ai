## Why

A standalone, non-interactive Direct Build entry point has no explore session and no `sai-state` store. The Direct Build coordinator card (`sai/commands/explore/direct-build-coordinator.md`) always re-exported its block from that store, so another caller could reuse the card only by editing it in place. This enabling refactor opens the one seam such a caller needs: the card obtains its block through its caller instead of reading the explore store itself. It adds no user-facing value on its own.

## What Changes

- `sai/commands/explore/direct-build-coordinator.md` defines the card's **block provider**: the caller-side source of the verified block file and hash that the card sends to its workers. The invocation's `arguments_value` comes from the provider's first block.
- The former `Stored block` paragraph becomes `Block provider`. Before each dispatch that consumes the block (Step 1 and Step 3, including a retry or a replacement), the card obtains the `--block-file`/`--block-hash` pair from the provider. Explore provides it by exporting from the `sai-state` store each time, as before; another caller provides the path of an already verified block file with its hash, and that pair serves every dispatch. The card's own readings in Steps 2, 4, and 5 use the verified block file.
- Start step 2 verifies the argument lines against the block file; the run-state `Identity` entry states that only the block provider holds the block text; Step 3 takes its block lines from the block provider; the issue-origin handoff passes the block's own `Backlog origin` and `Explore origin`.
- `sai/commands/explore/steps/pipeline-direct-build.md` names explore as the card's block provider: explore exports anew for the card's request before the backfill preparation and before any replacement worker, for a fresh Direct Build selection, and after an amendment.
- The slice transition, the route entries, and the slice machine stay with explore. The explore Direct Build route behaves as before.
