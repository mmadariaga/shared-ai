> **⚠ POST-HOC RECORD** — This proposal was backfilled after implementation against a user-supplied statement of intent. It describes a decision already made, not one being proposed.

## Why

In `/sai-4-apply`, only `RED result: valid` unlocks GREEN. Recovery cannot legitimately make a passing test fail, and `apply-step.js close` blocked the untouched production files of such a Step as `DEVIATION`. A Step whose RED returned `passes` therefore had no way to finish. A passing RED means one of two things: the behavior already exists, or the test checks nothing real. Only a human can reliably tell them apart.

## What Changes

- New disclosed step file `sai/commands/apply/steps/already-satisfied.md`, loaded only when a RED return reports `passes`. It runs the evidence verify in already-satisfied mode, shows the written tests, the Step test command and its result, and the untouched production files. It then asks the human, through the native picker and never auto-answered (also under `--fast-track`, `session_commit_authorized`, and `/sai-build`): "The behavior already exists" or "The test checks nothing real".
  - Already exists: the Step closes without a GREEN dispatch. The RED tests are committed, `GREEN result` stays `n/a`, an `> ALREADY SATISFIED:` notice is printed, and a `### Step N — Already satisfied: <behavior>` block is added to `Plan vs Final Implementation`.
  - Checks nothing real: the same RED worker continues through `continue_after_recovery` to harden the test. This spends a `recovery-ledger@1` worker attempt, and an exhausted budget leads to the exhausted-Step choice.
  - An evidence verify that returns `ok: false` voids the stop and routes to Known-False Report Recovery.
- `sai/commands/apply/steps/routing-split-flow.md`: the RED gate gains a one-line pointer for RED `passes`. Known-False Report Recovery now covers the other non-clean returns.
- `sai/commands/apply/runner.md`: `Plan vs Final Implementation` names the already-satisfied block. In an already-satisfied close, a `DEVIATION` or `scope-blocked` refusal means a production file changed, and it is handled by `steps/already-satisfied.md`, never by `steps/plan-amendment.md`.
- `sai/tools/apply-step.js`: new `--already-satisfied` flag for `verify --dispatch red` and `close` (including `--dry-run` and `--mark-only`). In this mode:
  - the Step test command is expected to pass and every Automated item runs;
  - the allowed files and the add-list scope are the Step's test files only;
  - declared production files left untouched raise no `DEVIATION` and are reported as `untouched`, while any production change is still `DEVIATION` or `scope-blocked`;
  - a generated output the Step never produces is not a declaration discrepancy;
  - the flag is a usage error outside red verify and close, and for a Step without a RED block naming test files.
- `test/apply-step-tool.test.js`: coverage for the mode's acceptance, its failures, close reporting and commit scope, the contrast with ordinary mode, and the usage errors.

## Capabilities

### New Capabilities

- None

### Modified Capabilities

- `apply-test-impl-split`: RED `passes` gains a human-confirmed completion path (already-satisfied close or vacuous-test hardening) and never unlocks GREEN.
- `apply-coordinator-verification`: `apply-step.js verify` and `close` accept an already-satisfied mode.
- `apply-pre-commit-file-report`: in an already-satisfied close, the `Plan cross-check` lists untouched declared production files on their own line, not as `Missing`.
- `apply-plan-amendment`: an already-satisfied close is excluded from the close amendment trigger.

## Impact

- New: `sai/commands/apply/steps/already-satisfied.md`
- Modified: `sai/commands/apply/runner.md`, `sai/commands/apply/steps/routing-split-flow.md`, `sai/tools/apply-step.js`, `test/apply-step-tool.test.js`
- Accepted trade-off: one new human question per RED `passes`, never auto-approved.

Out of scope: design.md, tasks.md, implementation.md — not generated by /sai-backfill
