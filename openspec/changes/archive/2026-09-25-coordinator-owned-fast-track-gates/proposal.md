## Why

In an observed `/sai-build` run, implementation asked for permission to perform bounded lookups and apply asked for permission to create a Step commit, despite the build's fast-track banner. The prompts left state delivery and activation timing ambiguous: the implementation coordinator had no validated typed gate for lookup approval, the worker could conflate fast-track state with authorization, and apply activated its local-commit grant at run start rather than explicitly before the first Step. The change makes authorization coordinator-owned, delivery explicit, and timing pre-Step while preserving all existing bounds and safety gates.

Known limitations carried from intent: a typed lookup request required a small validation-contract change in addition to prompt edits; missing or invalid authorization state stops safely rather than falling back to an interactive or broader approval path.

## What Changes

- The implementation coordinator validates every lookup permission as a typed `bounded-project-lookup` request with `worker-report-validator.js` before any decision, never from question wording. Under build or fast-track standalone implementation it approves every valid item without the picker; otherwise it presents per-item yes/no decisions. Denial preserves the convention-question fallback.
- The implementation worker returns lookups only as the typed request (1–5 ordered items with `id`, `area`, `reason`, `step`; matching ordered yes/no `questions`), never auto-approves even under fast-track, awaits ordered `lookup_decisions`, and reconstructs pending state from typed history on replacement without re-asking.
- The apply coordinator sets invocation-scoped `session_commit_authorized=true` at segment entry — after the standalone parse or the chained injected signal is known and before Run-Start Step Projection or first Step work — if and only if fast-track is active, retaining visibility reports, proposed messages, exact staging, and all stops.
- Fast-track state travels as an explicit boolean alongside the envelope (never the raw `--fast-track` token), delivered in the post-ready disclosure and replacement reconstruction and preserved across continuations for the worker's other defined behaviors. Standalone absence sets the signal explicitly false.
- Specifications aligned and both harness paths covered; first-Step and replacement paths tested.

## Capabilities

### New Capabilities

- `implement-lookup-authorization` — coordinator-owned validated approval of bounded project lookups with typed requests, per-mode decisions, worker request discipline, and replacement history.
- `apply-commit-activation` — pre-first-Step activation of the existing local-commit grant with retained visibility, exact staging, and grant exclusions.
- `fast-track-state-delivery` — explicit boolean delivery and preservation of fast-track state separate from lookup authorization.

### Modified Capabilities

- None — no existing capability behavior was modified outside the new gates; overlapping main specs are updated via delta requirements at archive.
