**Complexity**: high

## Why

The `start-pipeline` supervised pipeline today stops at spec-phase convergence and reports that sai-2 was not run, leaving the user to hand-carry the reviewed specs into a separate `/sai-2-design` invocation — the same manual proxying step the pipeline already removed for the spec phase. The design worker and its Claude Code and opencode bindings already exist and already expose the closed worker lifecycle, so chaining the design phase behind the same token is mostly reuse of the coordinator behavior already proven on sai-1.

## What Changes

- Chain the supervised pipeline into the design phase: after the spec phase converges, the same `start-pipeline` invocation dispatches the existing sai-2 design-planning worker without a second token.
- Apply the same supervised treatment to the design artifacts (`design.md`, `tasks.md`, `interfaces.md`) that the spec phase already receives: bounded independent-review convergence loop, the closed `High`/`Medium`/`Low` review severity contract, machine-feedback through the design worker, question autonomy with escalation, and a per-phase autonomy audit log. Because the existing pipeline review, convergence, autonomy, escalation, and audit-log capabilities are textually scoped to the spec worker and spec artifacts, `pipeline-design-phase-chaining` owns these contracts for the design phase directly — mirroring the spec-phase behavior for the design worker and its artifacts — and reuses only the genuinely phase-generic `pipeline-review-severity` contract and the coordinator contract unchanged.
- Inherit the spec phase's three-pass iteration-cap semantics for the design review loop rather than defining a separate design-phase cap.
- Gate chaining on spec-phase convergence only: when the spec phase ends by cap exhaustion (outstanding `High` findings), reviewer failure/cancellation/severity-contract violation, or a `failed` or `cancelled` spec worker, the pipeline SHALL NOT dispatch the design worker, so design never consumes specs that still carry high-severity findings.
- Emit a phase-transition report of the completed spec-phase outcome — including the spec-phase autonomy audit log — before dispatching the design worker, as the user's main visibility checkpoint for the now long-lived single-token run.
- Consume the existing design worker, its bindings, and its design-notice protocol unchanged; the design-notice extension and its fixed acknowledgement continue to be handled per the coordinator contract.
- Emit design-phase supervised completion at the end of the chained design phase, suppressing the standalone `/sai-2-design` navigation sentence for the supervised run, and report that sai-3 was not run.

## Capabilities

### New Capabilities
- `pipeline-design-phase-chaining`: After spec-phase convergence, the single `start-pipeline` run dispatches the existing sai-2 design worker through its existing binding and defines, for the design worker and design artifacts, a bounded independent-review convergence loop, the three-pass cap, question autonomy with escalation, and a design-phase autonomy audit log — mirroring the spec-phase behavior and reusing the phase-generic review severity and coordinator contracts — then emits design-phase supervised completion without chaining any later phase.
- `pipeline-phase-transition`: The pipeline reports the completed spec-phase outcome before entering design, dispatches the design worker only when the spec phase converged, and terminates the supervised run without design on any non-convergent spec ending.

### Modified Capabilities
- `explore-pipeline-token`: Extends the active-supervision interval so a single `start-pipeline` run spans both the spec phase and the chained design phase, ending only when the design phase terminates or when a non-convergent spec ending stops the run before design.
- `explore-pipeline-supervision`: Two requirements are amended. "Supervised completion replaces standalone navigation" fired supervised completion at spec convergence — the same moment `pipeline-phase-transition` needs — so it is amended so that, where `start-pipeline` supervision is available, spec convergence emits the phase-transition report and proceeds to the chained design phase rather than terminating the run, while cap exhaustion and reviewer/worker failure remain terminal and chain no design phase. "Explore supervises the routed sai-1 phase" carried the tracked-set "uncompleted change" definition, which keyed completion on the spec phase alone; it is amended into a phase-aware state machine: a change reaches supervised completion when its terminal worker returns `completed` (including cap exhaustion, and following the worker's result on reviewer failure), so cap-exhausted or reviewer-failed phases complete and are not re-offered; only a `failed` or `cancelled` spec or design worker leaves the change uncompleted and retryable, and a retry resumes at the phase whose worker did not complete — a design-phase retry re-dispatches the design worker over the existing converged spec artifacts rather than re-running sai-1, so it never discards reviewed, user-approved spec work.

## Additional Notes

- This change depends on `add-pipeline-review-convergence-loop` (archived), which established the spec-phase convergence loop this change chains behind.
- The pipeline is reframed as phase-generic: any phase exposing the closed worker lifecycle can be chained. sai-3 is a deliberate non-goal here; the design draws the automation boundary at the design phase.
- Chaining lands after spec-phase convergence deliberately. Cap exhaustion is a non-failure terminal outcome for the spec phase, but its outstanding `High` findings mean the specs are not fully reviewed, so it does not chain into design.
- The design phase's review, convergence, autonomy, escalation, and audit-log contracts are defined by `pipeline-design-phase-chaining` itself (the existing pipeline-* capabilities are worded around the spec worker/artifacts and do not cover the design case), mirroring the spec-phase behavior: the independent reviewer is a fresh isolated subagent per pass, the design worker owns all design-artifact edits and per-finding legitimacy evaluation, and pipeline supervision never edits artifacts or suppresses findings. Only the phase-generic `pipeline-review-severity` and coordinator contracts are reused unchanged.
- The permitted grounding sources for design-phase auto-answers are the design phase's bounded set — the design worker's `needs_input` payload, the crystallized block, the approved spec artifacts (`proposal.md`, `specs/**`), and the design artifacts written so far — and still exclude the surrounding explore conversation.
- The autonomy audit log is presented per phase: the spec-phase log accompanies the phase-transition report, and the design-phase log accompanies design-phase supervised completion. Neither is written to any file, artifact, or configuration.
- The single-token run is long-lived, so the phase-transition report is the deliberate mid-run visibility checkpoint; the design phase inherits the spec phase's iteration-cap semantics rather than defining its own.
- Completion/retry state machine (for the designer): a change leaves the token's uncompleted set only when its terminal worker returns `completed`. Convergence, cap exhaustion, and reviewer failure (which follows the worker's `completed` result) all complete the change; only a `failed`/`cancelled` worker keeps it retryable. Retry is phase-aware — it resumes at the phase whose worker did not complete, so a design failure re-runs only the design worker over the already-converged, user-approved specs and never regenerates `proposal.md`/`specs/**`. This implies the tracked-set state must record, per change, whether its spec phase has converged in this chat.
