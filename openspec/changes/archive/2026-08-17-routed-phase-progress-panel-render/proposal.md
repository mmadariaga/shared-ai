## Why

Routed phase progress panels stayed frozen at their dispatch state because coordinators marked progress steps and continued workers without performing a separate panel render. The implementation makes state-changing progress events update the panel while preserving the existing deterministic step derivation and coordinator-only rendering ownership.

## What Changes

- `sai/policies/todo-structure.md` defines a conditional progress-event rendering action and its stamp behavior.
- `sai/command-runner.md` detects whether a progress event newly marks a declared step, renders only after state-changing events, and then continues the worker.
- The seven routed phase coordinators delegate progress-event panel updates to the shared runner and policy.
- Worker-matrix templates inject the matching Claude Code or opencode panel-render instructions for routed bindings, while apply bindings remain unchanged.
- Tests cover conditional rendering, stamp behavior, routed harness bindings, and the no-plan explore path.

## Capabilities

### New Capabilities

- `progress-render-act`: State-changing progress events re-render the routed phase task list using the existing deterministic derivation.
- `routed-phase-panel-binding`: Routed worker bindings load the matching harness panel-render mechanics without adding them to apply bindings.
- `stamp-on-progress`: Newly completed steps receive the worker-authored progress-event timestamp, while no-op events receive no stamp.

### Modified Capabilities

- `todo-list-progress-rendering`: Progress rendering is conditional on a newly marked declared step rather than occurring for every progress event.
- `coordinator-progress-ownership`: The shared command runner and harness binding own panel rendering; workers continue to emit progress data only.
