> **⚠ POST-HOC RECORD** — This proposal was backfilled after implementation against a user-supplied statement of intent. It describes a decision already made, not one being proposed.

## Why

A `/sai-build` run in opencode stopped before its first RED worker. Azure DevOps rejected the selected-child assignment as an "unknown identity", because the tool wrote the authenticated identity GUID to `System.AssignedTo`. The implementation-start gate offered only Retry or Stop, so a backlog bookkeeping failure blocked implementation. The same run also failed with `Invalid assignment choice`: `propose-assignment` emitted `choice: "assign"` for an unassigned child, and `assign` rejected that value. A provider rejection that proved no change was applied was also reported as `uncertain`, so the gate recommended a retry that could not succeed.

## What Changes

- `sai/policies/backlog-implementation-start.md`: the step-3 approval now asks **Approve / Stop / Skip**. After any failed or unverified assignment, the step-4 stop asks **Retry / Skip / Stop**, and Skip is the recommended option after `rejected`. Skip performs no remote operation and holds for the implementation stretch (worker correction, resumption, and replacement). A new slice or a new invocation asks again. Skip comes only from a user answer: fast-track, `/sai-build`'s injected fast-track, and Direct Build consent never choose it. After a Skip, the closing report states that the work item stayed unassigned by user choice and lists the assignees last verified. Step 2 (Keep / Replace / Stop for an already-assigned child) is unchanged. `assign` receives the `confirmation` and `choice` that `propose-assignment` returned, unchanged.
- `sai/tools/backlog-provider-assignment.js`: `propose-assignment` and `assign` accept `choice: "assign"`. `assign` maps a provider error marked `rejected: true` to `status: "rejected"` with the message "No change was applied" and no `next_operation`. Every other failure stays `uncertain` and leads to `verify-assignment`.
- `sai/tools/azure-publication.js`: `inspect` returns the authenticated user's unique name from `authenticatedUser.properties.Account.$value` in the `connectionData` response it already reads.
- `sai/tools/to-backlog-azuredevops.js`: the assignment PATCH writes that unique name to `System.AssignedTo`. Identity checks keep comparing identity ids. When no unique name is available, `assign` fails as a rejection before the PATCH, and the work item is not changed.
- `sai/tools/from-backlog.js`: the Azure SDK bridge records the HTTP status of a service error at the SDK's error handler. An "unknown identity" 400 therefore reaches `api` with `rejected: true`. 5xx, timeouts, and transport errors are not marked rejected.
- `skills/universal/to-backlog/providers/azuredevops.md` and `docs/backlog.md`: document the unique-name write, the `rejected` / `uncertain` split, and the Skip option.
- Tests: the Azure fake in `test/backlog-slice-provider-parity.test.js` accepts only the unique name in `System.AssignedTo`. New cases cover the choice round-trip, unique-name writing, `rejected` versus `uncertain`, the missing-unique-name rejection, three-provider outcome parity, and identical Skip wording for every provider. `test/azure-publication-corrections.test.js` covers the SDK bridge status capture.
