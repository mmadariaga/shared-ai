> **⚠ POST-HOC RECORD** — This proposal was backfilled after implementation against a user-supplied statement of intent. It describes a decision already made, not one being proposed.

## Why

`/to-pr` always drafted the PR/MR title and description in English unless the user asked for another language in the conversation, so a team that writes its requests in another language had to repeat the request on every publication. The unattended publications of `/sai-plan`, `/sai-build`, and the `/sai-explore` Plan and Direct Build routes have no conversation in which to ask, so they could only publish in English. `explore.readyToProposeLanguage` was also easy to mistake for a setting that covers the PR/MR.

## What Changes

- New project setting `pr.language` in `.sai/settings.jsonc`, registered in the catalogue of `sai/tools/project-settings.js`: a free-form language name, trimmed and normalized like `explore.readyToProposeLanguage` and `explore.chatPublicLanguage` (`english` reads as `English`), with `none`, an empty string, and a non-string value invalid. It is not a `/to-pr` destination field, so `readPr` does not return it. It carries the menu label `PR/MR language`, the section `Pull requests`, and the absence text `English`.
- An invalid `pr.language` value is dropped with a warning that says the draft falls back to English; the catalogue gains an optional `fallback` wording used by that warning, and every other key keeps the warning ending "its question stays normal".
- `sai/tools/to-pr.js collect` returns a `language` field in both output shapes (with and without `base`): the normalized `pr.language` value, or `English` when the key is absent or invalid, together with the settings `warnings` when there are any.
- `skills/universal/to-pr/description-format.md` replaces the "Draft in English unless the user requests another language" rule with the resolved language: an explicit request for the PR/MR language in the conversation, else `collect`'s `language`, else English. The `type(scope):` title prefix stays English, the title rules apply to the subject in any language, the section headings follow the resolved language, and the closing keywords, the tool's closing block, and the inherent-risk ratings block stay verbatim. On update only SAI-drafted content follows the language. The language the user chats in and `explore.chatPublicLanguage` are not a request.
- `skills/universal/to-pr/SKILL.md` prints the `warnings` of both `collect` calls verbatim and drafts in the language `description-format.md` resolves.
- The closing reports of `sai/commands/plan/publication.md` and `sai/commands/build/publication.md` list the warnings of `collect` beside those of `query`, `publish`, and `recover`, so an invalid value reaches the run's publication outcome; they gain no language logic of their own.
- `bin/project-settings-screen.js` lists `pr.language` as the fourth row of the `Language settings` submenu, offering `English` and `Other language...`; choosing `English` removes the key, because an absent key reads as `English`.
- `docs/project-settings.md` documents the key (settings table row, validation notes, a `PR/MR language` section with the squash-merge consequence, and the submenu row), and `docs/commands/to-pr.md` names the setting.

## Capabilities

### New Capabilities

None

### Modified Capabilities

- `to-pr`: the PR/MR title subject and SAI-drafted description follow a resolved language (explicit conversation request, else `pr.language`, else English); `collect` returns that language with the settings warnings; unattended publications use the setting and report its warnings.
- `project-settings`: the catalogue holds the validated, normalized `pr.language` key with its presentation fields.
- `project-settings-screen`: the `Language settings` submenu lists and edits `pr.language`.

## Impact

- Modified: `sai/tools/project-settings.js`, `sai/tools/to-pr.js`, `bin/project-settings-screen.js`, `skills/universal/to-pr/SKILL.md`, `skills/universal/to-pr/description-format.md`, `sai/commands/plan/publication.md`, `sai/commands/build/publication.md`, `docs/project-settings.md`, `docs/commands/to-pr.md`, `test/project-settings.test.js`, `test/project-settings-screen.test.js`, `test/to-pr.test.js`.
- New files: none.
- Without `pr.language`, every publication drafts in English as before. The language of commit messages, OpenSpec artifacts, and the `Ready to Propose` block does not change. Claude Code and opencode share the same tool and skill contract.
- Known limitation: after a squash merge, the commit subject that the provider takes from the request title is in the resolved language.
- Out of scope: design.md, tasks.md, implementation.md — not generated by /sai-backfill
