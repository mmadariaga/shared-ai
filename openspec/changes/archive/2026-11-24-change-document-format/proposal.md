## Why

SAI keeps the same agreement in two formats: the backlog issue format and the `Ready to Propose` block. Publishing a crystallized change makes the model rewrite the block as an issue, which spends output tokens and can drift from the agreed text, and re-importing an issue loses the block-only fields. A single format needs a validator and a verifiable file form before any consumer can read it.

## What Changes

- `sai/policies/issue-format.md` defines the **change document**: the issue format extended with the optional sections `Capabilities`, `Terms`, `Out-of-scope implementation notes`, `Alternatives considered`, `Trade-offs accepted`, and `Additional notes` (in the agreed order between Non-goals and Open questions) and a last `## Change` section that carries the change metadata as visible `Key: value` lines (`Change name`, `Depends on`, `Specs`, `Explore origin`, `Backlog origin`). It also defines the file form (one document per file, first line `# <title>`), the hash over the whole LF-normalized file, the dispatchable checks, the hygiene judgment over the whole document, and the file transport.
- New `sai/tools/change-document.js` parses a change document with a fence-aware section parser and exposes the sub-commands `check` (dispatchable validation that names each failed check, with an optional verdicts file and `--slice`), `check-set` (slice-set validation), `hash`, `verify-file`, `compare` (metadata-only versus content amendment), and `sections` (the section reading of the issue intake).
- `sai/tools/ready-to-propose.js` keeps working as the tool of every consumer; its issue optional-section constants list the new optional sections so they match the policy.
- New `test/change-document.test.js` covers the tool; `test/to-backlog-issue-format.test.js` checks the new section order.
- `AGENTS.md` documents `change-document.js` in the `sai/tools/` row.

No consumer of the block switches to the change document in this change.

### Modified Capabilities

- `to-backlog-issue-format`: the issue format gains the new optional sections, the `## Change` metadata section, and the change document definition.
- `ready-to-propose-detection`: a change-document tool validates a document's dispatchability, validates a slice set, compares amendments, and reads issue sections, next to the unchanged block detector.
- `block-integrity-verification`: a change document has a sha256 hash over the whole LF-normalized file and a `verify-file` check.
- `bounded-hygiene-judgment`: the lexical pre-filter and the verdicts run over the whole change document.
