## Why

After a failed or interrupted Step, a new apply run captured a baseline in which that Step's own partial files were already dirty. `apply-step.js dispatch-check` treated every initially dirty path as protected pre-existing work and refused the dispatch, even though the files were the Step's own unfinished work. The stop report nevertheless described the tree as retryable, so the re-entry it recommended could not work. The tool could not tell a file the Step itself wrote from earlier uncommitted work of the user or of another Step.

## What Changes

- `apply-step.js verify` saves or overwrites an attempt receipt for the unclosed Step at every call. The receipt lives in the system temp directory, outside the repository, under a name derived from the project root, the change, and the Step number. It holds every path the Step wrote, planned or not, with each path's content fingerprint. A foreign file that a dispatch touched is left out of the receipt.
- `apply-step.js baseline` reads the receipts of the change's Steps and returns `own` (path to Step number): a dirty path whose fingerprint matches a receipt is that Step's own file. `dispatch-check`, `verify`, `close`, `inspect`, and `restore-unrelated-index` treat an own file as the Step's work for the whole run. Every other dirty file is a foreign file and stays protected, including a file changed after its receipt was saved and a file that is own to a different Step.
- `apply-step.js dispatch-check` refuses only over foreign files in the dispatch scope, and a refusal now returns the two `exits`: `commit the listed files` and `discard the changes in the listed files`.
- `apply-step.js close` deletes the Step's receipt on a committing close and on a `--mark-only` close; a `--dry-run` close keeps it. The close add-list includes the Step's own files from the baseline's `own`.
- `apply-step.js inspect` accepts `--step <N>` and then reports `next_dispatch` (`step`, `would_pass`, `conflicts`, `exits`): whether a new run could dispatch that Step.
- The apply coordinator runs `inspect --step N` when a Step stopped and keeps its `next_dispatch`; its dispatch stop message names both exits. The stopped closing report states whether the Step can be retried from that result only, lists the conflicts and the two exits on `would_pass: false`, and says the retry state is unknown when the call could not run.
- Known limitations: an attempt interrupted before its first `verify` leaves no receipt, and the Step stays blocked until the user commits or discards the files. The receipt lives in the system temp directory; when the system clears it, the same blocked path applies. The receipt grants no commit and marks no checkbox.

## Capabilities

### New Capabilities

- None

### Modified Capabilities

- `apply-step-tool`: adds the attempt receipt saved at every `verify`, own-file recognition in `baseline`, receipt deletion at `close`, and `inspect --step` with `next_dispatch`; changes the dispatch check to refuse only foreign files and return the two exits; changes the statelessness requirement to name the receipt as the tool's only state between runs.
- `implementation-closing-report`: the stopped report states whether a stopped Apply or Build Step can be retried from the tool's `next_dispatch`, through one read-only `inspect` call that is part of the stop.
