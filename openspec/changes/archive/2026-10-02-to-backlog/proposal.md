> **⚠ POST-HOC RECORD** — This proposal was backfilled after implementation against a user-supplied statement of intent. It describes a decision already made, not one being proposed.

**Complexity**: medium (four new capabilities, three existing capability updates, and remote publication recovery)

## Why

Agreed work in an agent conversation otherwise requires manual rewriting into GitHub. This change captures one reviewed work item directly while separating the conversation workflow from provider-specific mechanics.

## What Changes

- Added `/to-backlog` entry points for Claude Code and OpenCode that retain the current conversation instead of entering the clean-start SAI boot.
- Added one provider-neutral skill for extracting a title and Markdown description, clarifying ambiguity, resolving the destination, presenting visibility, and obtaining explicit confirmation.
- Added a Node resolver using explicit destination fields, optional `.to-backlog.json` configuration, and Git remotes in that order.
- Added an external provider registry, plain GitHub instructions, and an isolated Node GitHub adapter using gh.
- Added read-only repository and Project inspection with pagination, destination ambiguity handling, and independent Project ownership.
- Added confirmed issue creation and Project insertion, private local publication receipts, and recovery that never recreates an issue.
- Added checks for changed content, visibility, identity, and destination before pending insertion or recovery.
- Extended installation projections and command capability assignments for both harnesses.
- Updated command-directory and command-enumeration regression expectations to retain nineteen SAI commands alongside the new command.
- Added simulated Git and gh tests for resolution, confirmation, publication, failures, recovery, privacy boundaries, and installation.

## Capabilities

### New Capabilities

- `to-backlog-conversation-capture`: Capture one proposed work item from the retained conversation and require exact review and confirmation.
- `to-backlog-provider-resolution`: Resolve a registered provider and destination deterministically without substituting an unsupported provider.
- `to-backlog-github-publication`: Inspect GitHub destinations, publish approved content, and recover partial or uncertain outcomes without issue recreation.
- `to-backlog-harness-installation`: Install the invocation, skill, provider references, registry, and tools for Claude Code and OpenCode.

### Modified Capabilities

- `command-wrapper-body`: Preserve the nineteen SAI wrappers while adding the separate conversation-preserving to-backlog wrapper.
- `contract-tool-capabilities`: Include the new command in canonical capability assignments.
- `sai-1-command-inventory`: Enumerate twenty shipped commands, including sai-review and to-backlog, on both harnesses.

## Impact

- New files: `commands/claude/to-backlog.md`, `commands/opencode/to-backlog.md`, `skills/universal/to-backlog/SKILL.md`, `skills/universal/to-backlog/providers/github.md`, `skills/universal/to-backlog/providers/registry.json`, `sai/tools/to-backlog.js`, `sai/tools/to-backlog-github.js`, and `test/to-backlog.test.js`.
- Modified files: `sai/install-manifest.json`, `README.md`, `test/command-launcher-card.test.js`, and `test/model-customization-menu.test.js`.
- Runtime dependencies: Node, and installed authenticated gh with repository issue and Project access for GitHub publication.
- Optional destination configuration: `.to-backlog.json` in the target working directory.
- Publication receipts contain approved content and require an existing private local directory outside the repository.
- GitHub is the only implemented provider; github.com is the supported GitHub host.
- Issue creation and Project insertion are separate operations. Partial publication preserves the issue; uncertain creation requires verification rather than automatic recreation.
- Out of scope: design.md, tasks.md, implementation.md — not generated by /sai-backfill

## Request Additional Notes

Future providers may include Jira and GitLab. Their exact integration mechanics are intentionally undecided; the extension seam is in scope, their implementation is not. The destination configuration schema and storage location remain design decisions, not an agreed requirement for a particular new configuration file.
