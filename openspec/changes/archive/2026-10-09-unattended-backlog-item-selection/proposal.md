## Why

Selecting the next backlog item required unnecessary user intervention: the provider could already be determined from Git, while missing GitLab manual positions blocked otherwise valid issues. The implementation resolves available destination information before asking and permits selection within the highest available priority group.

## What Changes

- Reuse the existing Git destination resolver to complete missing provider and destination information from supplied context and Git remotes.
- Retain known selection context when information remains unresolved, and ask only for missing components.
- Default GitLab selection to open project issues while preserving explicit destinations and supported filters.
- Return all GitLab candidates at the smallest valid manual position, or all matching members when none has a valid position.
- Let the AI choose any returned candidate without a tie-breaking question, then use the existing import flow.
- Keep unsupported GitLab boards, lists, and views pending. Reject non-importable or inconsistent highest-priority members without silently skipping them.
- Update shared and GitLab-specific instructions and tests for destination resolution, filters, candidate membership, and import compatibility.
- **BREAKING**: successful GitLab selection now returns `status: candidates` with a candidate array instead of a single `selected` reference. The selector CLI treats this outcome as success.

## Capabilities
