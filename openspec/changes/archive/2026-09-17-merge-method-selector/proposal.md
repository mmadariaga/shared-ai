## Why
Let the user choose the integration strategy explicitly at the start instead of assuming `git merge`. Rebase replays the current branch onto the selected branch, and pre-unifying squash bounds conflicts to a single point instead of N commits.

## What Changes
- Add Step 1B method-first gate (`Merge` / `Rebase`) before branch selection in `sai/commands/merge/instructions.md`; pin to `Merge` under `--fast-track` with no squash question.
- Make branch selection method-aware: `Which branch do you want to merge?` for merge, `Which branch do you want to rebase onto?` for rebase; selected branch is merge source / rebase target.
- Add Step 2B conditional squash gate (`Yes` / `No`) shown only for `Rebase` in normal mode; `Yes` unifies `merge_base..HEAD` into one local commit, `No` replays commit by commit.
- Add rebase execution paths: plain `git rebase` and squash-unify then `git rebase`, reusing the existing resolution, verification, and commit-authorization flow; conflicts reuse the merge resolution flow.
- Add E2b in-progress rebase guard (`.git/rebase-merge`, `.git/rebase-apply`, `REBASE_HEAD`) alongside the existing merge guard.
- Update coordinator, worker, lifecycle, presentation, and TODO seams for method/squash state, method-aware summaries, adaptive TODO, and coordinator-owned integration launch, squash unification, rebase continuation, and finalization.
- Update `commands/claude/sai-merge.md` and `commands/opencode/sai-merge.md` descriptions to merge-or-rebase.

## Capabilities
### New Capabilities
- method-selection: initial `Merge` / `Rebase` gate before branch selection
- conditional-squash: `Yes` / `No` squash gate shown only for `Rebase` in normal mode
- rebase-paths: plain and pre-squashed rebase execution reusing the existing resolution and commit flow
### Modified Capabilities
- None — all behavior is introduced as new capabilities; the `Merge` path behavior is unchanged.
