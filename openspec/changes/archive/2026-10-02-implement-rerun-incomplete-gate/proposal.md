## Why

`/sai-build` re-entry is contractually required to pass through implement (`sai/commands/meta-build/coordinator.md`), but the implement re-run gate failed whenever any Step was INCOMPLETE (`sai/commands/implement/steps/rerun-preservation.md`), so a re-entered build could never reach apply. The gate's own rationale (audit steps generated on the false premise that pending Steps' code exists) only applies when audit steps are appended. This was observed in an opencode `/sai-build` run on a change with no audit artifacts.

## What Changes

- The INCOMPLETE gate moves from the classify phase to the append-audit-derived-steps phase of `rerun-preservation.md`. It now fails only when at least one audit artifact needs a new audit step; the `failed` summary names each INCOMPLETE Step, the artifacts needing a step, and the next action (`/sai-4-apply <change>`, then re-plan).
- With no audit artifact needing a new step, a re-plan over INCOMPLETE Steps preserves `implementation.md` byte-for-byte and ends `completed`, listing the pending Steps (and any VERIFY-PENDING warnings) in the summary, so `/sai-build` continues into apply.
- An audit artifact whose latest audit step is still pending is not re-appended; the pending step already carries it.
- The audit step heading is pinned as `#### Step N: Address <kind> findings` (`<kind>` one of `review`, `security`, `performance`, `accessibility`) in `rerun-preservation.md` and `plan-generation.md`; a pending audit step is that heading plus at least one `[ ]` in its section.
- The Audit-append invariant in `steps/validation.md` counts only artifacts needing a new audit step, and the Durable Artifact Completion Gate in `sai/commands/implement/worker.md` points to that invariant instead of restating it.
- The Re-entry section of `sai/commands/meta-build/coordinator.md` becomes a positive pointer to implement's re-run contract and no longer names APPLIED / VERIFY-PENDING / INCOMPLETE.
- Tests: `test/build-coordinator.test.js` asserts the new Re-entry sentence; `test/implement-coordinator-worker.test.js` asserts the gate sits inside the audit-append section, the pinned heading literal, and the validation scoping.
