**Complexity**: medium (2 modified capabilities, 3 requirements, 6 affected paths)

## Why
The flat `worker:<name> [model]` target list in the installer's model-customization checklist is hard to scan and grows unwieldy as projected targets grow (12 workers on opencode today); fixed columns make type, target, and effective setting legible at a glance.

## What Changes
- The model-customization target checklist now renders as an aligned three-column table view: TYPE (uppercase family padded to seven characters), TARGET (padded to the longest displayed name of the current scope), and SETTING (plain text, no brackets or ANSI styling), separated by two-space gutters.
- A two-line English header (TYPE/TARGET/SETTING titles above U+2500 separator dashes, indented six spaces over the option prefix, sized to the row column widths) renders between the question and the option rows.
- The shared navigator accepts an optional `header` threaded through `promptChecklist` navigatorOptions and rendered by `runNavigator.frameLines()`; header rows are non-selectable decoration excluded from cursor movement and toggling while included in redraw bookkeeping.
- The empty-scope check runs before any label or header construction, so the notice path never renders a header or opens a checklist.
- Checklist selection values, key handling, other navigator screens, and manifest/enumeration data are unchanged; non-TTY input paints nothing.
- Tests updated for the new display format plus header coverage (navigator rendering/redraw accounting, promptChecklist forwarding, non-TTY behavior, unavailable-setting plain text, empty-scope path).
