## Why

Nothing measures whether cache warming pays off. Each wake costs short requests that re-read the whole cached context, and no report showed how many wakes a run spent or what they cost. Counting wakes and measuring their requests and tokens per agent and per run lets the warming timings be tuned against measured cost.

## What Changes

- The shared transcript readers detect cache-warming wakes. A wake is the turn of an agent that the completion of its own `wait.js … warm` background wait opens, the main session included. Detection matches the wait command, never the background task description and never an `ok` reply:
  - `sai/tools/claude-transcripts.js` (Claude Code): `claudeWaitTasks` collects the background task ids returned for shell (`Bash`/`PowerShell`) `tool_use` calls whose command runs `wait.js` with `warm`; `claudeWakes` opens a wake at each `<task-notification>` whose task id is one of them and lists the distinct `message.id` of every model request until the next record that opens a turn. Requests of a wake turn are flagged `wake`, and `openClaudeSource` exposes `wakes(session, from, to)`.
  - `sai/tools/opencode-db.js` (opencode): `opencodeWakes` opens a wake at each `synthetic` `session_message` with `metadata.source: "shell"` whose `<shell … command="…">` header runs `wait.js` with `warm`, and lists every `assistant` message until the next message that opens a turn. The shell state is not read, so a wait that returned `finished` is still a wake.
- `sai/tools/retrospective.js` gives the coordinator and every agent row of the index `wakes` and `wake_usage` (the requests and usage fields of the wake turns, a subset of `usage`). An agent whose data could not be read has `wakes: null` and `wake_usage: unavailable`, distinct from zero. A Claude Code wait armed in one execution and completed in a later one is still matched, because the wait tasks come from the whole session. The `cost` report adds the figures per agent, per segment row, and per run (`totals.wakes`, `wake_requests`, `wake_tokens`, `unavailable_wake_agents`). The markdown baseline adds `Wakes`, `Wake requests`, and `Wake tokens` columns to the segment table, `Wakes` and `Wake tokens` to the mean table, a per-run wake table, and a note defining a wake; its baseline format becomes `2`.
- `sai/tools/change-telemetry.js` adds a `Wakes` column to its per-agent tables and the change total, and a `Cache-warming wakes` table at the end of each execution section and of each exploration segment, with requests, input, output, reasoning, cache read, cache write, and cost of the wake requests per agent and for the run or exploration total. A subagent session that is not recorded shows the existing unavailable marker and makes the total partial (`≥`); a section written before the column existed counts as unknown in the change total.
- `sai/policies/change-telemetry.md`, `docs/commands/sai-retrospective.md`, `docs/project-settings.md`, and `sai/commands/retrospective/body.md` describe the wake figures and the wake definition.
- `test/retrospective-tool.test.js` and `test/change-telemetry.test.js` cover wake counting and wake cost with hand-built fixtures for both harnesses.

## Capabilities

### New Capabilities

None

### Modified Capabilities

- `change-telemetry`: per-agent wake counts and a wake-cost table per execution section and exploration segment, per agent and for the total.
- `sai-retrospective`: wake counts and wake usage per agent in the index, and per agent, per segment, and per run in the cost report.
