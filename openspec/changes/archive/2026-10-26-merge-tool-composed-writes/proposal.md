## Why

In a retrospective `/sai-merge` run, the worker retyped a 4.5 KB glossary region into a PowerShell here-string piped to `merge.js write`; every U+2014 em dash reached the tool as `?`, and the coordinator misdiagnosed the resulting rejection as editorial edits. `write` accepted only authored text on standard input, although the conflict snapshot already holds each side's text, so the model had to reproduce bytes the tool owned and pass them through a shell whose transport can change non-ASCII characters. The rejection itself gave no hint of where the bytes diverged. Separately, the stage step's whole-index `git diff --cached --check` flagged, during a rebase, whitespace the replayed commit already carried, although `write` and `resolution` already reject leftover conflict markers.

## What Changes

- `merge.js write` accepts, per payload entry, exactly one of `text` (authored replacement) or `segments` (an ordered list of pieces, each `{"side": "ours" | "theirs" | "base"}` or `{"text": "..."}`). Side pieces are copied from the snapshot's decoded conflict sides, the same versions `bundle` returns, and pieces are concatenated with nothing between them. An entry with both forms, an empty or malformed segment list, an unknown side, or a side the region lacks (including `base` when the region has no base version) is rejected and the call writes nothing. Composed text goes through the same marker, encoding, line-ending, and BOM handling as authored text.
- `merge.js write` gains `--input <payload-file>`: the payload is read from that file as UTF-8, with or without a BOM, and an invalid UTF-8 byte is an error rather than a replacement character. `--input` applies to `write` only. Standard input remains accepted; supplying a non-empty redirected file on standard input together with `--input` is a usage error, while a pipe, socket, device, or terminal on standard input is ignored and never read when `--input` is given.
- `merge.js resolution` accepts a region reported as `segments`, composing it again from the snapshot, and, when a file's content differs from the expected resolution, names the first differing byte offset and the expected and actual characters as code points (or `end of file`, or the invalid byte).
- `sai/commands/merge/steps/apply.md` instructs the worker to write the payload as a UTF-8 JSON file in the run directory with its own file-write tool and pass it with `--input`, never piping it through a shell, to use `segments` for every region that equals a side or a concatenation of sides, and authored `text` only for line-level synthesis. The apply report may carry `segments` for a region.
- `sai/commands/merge/coordinator.md` conflict-stop step 6 stages the resolved paths with `git add` and runs no `git diff --cached --check`.
- Tests in `test/merge-conflict-bundle.test.js` cover composition, file input, the input-conflict rule, and the rejection diagnostic; `test/merge-goal-driven.test.js` follows the new stage-step wording.

## Capabilities

### New Capabilities

None.

### Modified Capabilities

- `merge-resolution-write`: composition of regions from conflict sides, file input for the write payload, and the first-difference rejection diagnostic of the `resolution` check.
- `sai-merge-command`: the conflict-stop cycle stages resolved paths without a whole-index whitespace check.

## Impact

- Modified: `sai/tools/merge.js`, `sai/commands/merge/steps/apply.md`, `sai/commands/merge/coordinator.md`, `test/merge-conflict-bundle.test.js`, `test/merge-goal-driven.test.js`.
- Existing `{conflict_id, text}` payloads on standard input keep working. Binary, deleted, renamed, and undetermined-encoding files keep their whole-side coordinator checkout; composition applies to text regions only. Claude Code and opencode workers follow the same write path.
- `merge.js write` gains a new payload form, widening the tool contract and its tests.
