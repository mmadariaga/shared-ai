> **⚠ POST-HOC RECORD** — This proposal was backfilled after implementation against a user-supplied statement of intent. It describes a decision already made, not one being proposed.

## Why

Backfill detected a crystallized `Ready to Propose` block with a prose rule that the model applied by inference (the nine-literal quorum in `sai/commands/backfill/instructions.md`). Separately, `sai/tools/lint.js` carried its own list of required block sections, and that list differed from the canonical format in `sai/policies/ready-to-propose-format.md`: it omitted `**Change name**`, `**What**`, `**Why**`, `**Terms**`, and `**Overview language**`. Two definitions of a valid block could drift apart. One shared deterministic detector removes this risk and is the prerequisite for later gating explore's crystallization close.

## What Changes

- New tool `sai/tools/ready-to-propose.js`. `check --profile loose|strict` reads text on stdin, accepts one or more blocks, and always prints one JSON verdict (`ok`, `profile`, `names`, `blocks` with per-block violations, set-level `violations`). Exit 0 means valid, exit 1 means violations, exit 2 means a usage or I/O error.
- The `loose` profile is backfill's quorum: the nine plain literals are present as case-sensitive substrings after `**` is stripped, in any order, with no heading required.
- The `strict` profile is the full canonical format: every field label in order, inline values for `Change name`, `What`, `Why`, and `Overview language`, a kebab-case change name, non-empty mandatory sections (or `- None`), an optional `**Request Additional Notes**` with real content, `**Overview language**` as the last line, a `---` line ending each block, and unique change names across the set. Set-level distribution rules are excluded. Every strict-valid block also passes `loose`.
- `lint.js ready-to-propose` now delegates to the detector's `strict` profile and no longer keeps its own section list.
- Backfill's crystallized-block intake now pipes the request body to the detector with `--profile loose`, resolved under `sai/policies/tool-resolution.md`. Exit 0 skips intent capture, exit 1 falls through to the generic flow, and exit 2 or a missing tool stops the run.
- `sai/policies/tool-resolution.md` documents the detector's invocation shape. `AGENTS.md` registers the tool. The validator comment in `sai/policies/ready-to-propose-format.md` names the detector.
- New unit tests for both profiles and the CLI. The lint tests now cover the delegation, and the valid-block fixture gains `**Terms**`.

## Capabilities

### New Capabilities

- `ready-to-propose-detection`: one deterministic stdin detector, with `loose` and `strict` profiles, that decides whether text is a valid `Ready to Propose` block.

### Modified Capabilities

- `backfill-unattended-intake`: crystallized-block detection runs through the detector's `loose` profile instead of model inference.
- `format-linting`: the `ready-to-propose` check delegates to the detector's `strict` profile and therefore requires the full canonical field set.
