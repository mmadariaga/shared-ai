> **⚠ POST-HOC RECORD** — This proposal was backfilled after implementation against a user-supplied statement of intent. It describes a decision already made, not one being proposed.

## Why

A standalone GitLab work item could never be assigned at implementation start. The shared `bind()` inspection in `sai/tools/backlog-provider-assignment.js` required a verified parent and written correspondence, and the GitLab read path saw hierarchy only through written SAI markers. A real run on a parentless GitLab work item failed with `Assignment requires a verified child and parent; parent responsibility is preserved`, and retries could not succeed because the failure was a contract gap, not a transient error. GitHub already accepted a standalone leaf; GitLab now follows the same pattern, proven by a complete native hierarchy read rather than by the absence of a written marker.

## What Changes

- `sai/tools/to-backlog-gitlab.js`: GitLab responsibility inspection reads the native work-item hierarchy with one GraphQL query (`parent` and the first page of `children` from the hierarchy widget) over the adapter's existing authenticated transport, only when the selected work item carries no written SAI marker.
  - A complete response with no parent and no children makes the work item a standalone leaf; the adapter hands `bind()` explicit standalone evidence with the item URL and current assignees.
  - A complete response with no parent and at least one child rejects the item with `Selected work item has child items; parent responsibility is preserved`.
  - A complete response with a native parent falls back to the existing written-correspondence flow, which keeps rejecting it.
  - A GraphQL error, a transport failure, a missing work item or namespace, a missing hierarchy widget, or a missing `parent` or `children` field fails inspection with `GitLab work item hierarchy could not be verified`; no standalone leaf is accepted from incomplete evidence.
  - Marked work items skip the native read and keep the existing flow.
  - The standalone-leaf read and the `assign` re-read of current assignees accept any GitLab work-item type, not only ordinary issues.
- `sai/tools/from-backlog-gitlab.js`: `issue()` takes an optional flag that skips the ordinary-issue type restriction; import callers keep the restriction.
- `sai/tools/backlog-provider-assignment.js`: shared `bind()` accepts adapter-proven standalone evidence in place of the parent and written-correspondence requirements and returns `parent: null` for it. `verify` now requires `expected_parent` to equal the currently inspected parent for every provider bound through it (GitLab and Azure DevOps), and `assign` verifies against the parent of its approved proposal. Azure DevOps supplies no standalone evidence, so an Azure item without a parent keeps being rejected.
- `sai/policies/backlog-implementation-start.md`: step 1 accepts the standalone leaf on GitHub and GitLab, states that GitLab proves it with a complete native hierarchy read, and keeps the child-and-parent requirement for Azure DevOps.
- `test/backlog-slice-provider-parity.test.js`: GitLab fixture answers GraphQL hierarchy reads; new tests cover an accepted leaf of issue and task type, rejection with native children, each incomplete-read cause, unchanged rejection with a native parent, marked items skipping the native read, `expected_parent` verification on GitLab and Azure DevOps, and continued Azure rejection of a parentless item.
