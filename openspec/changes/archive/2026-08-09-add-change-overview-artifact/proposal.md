## Why

Reviewing a proposed change currently requires navigating several artifacts — `proposal.md`, `specs/**`, `design.md`, `tasks.md`, and `interfaces.md` — while `interfaces.md` itself mixes implementation-facing step contracts with a target-state snapshot. This change adds `change-overview.md`, a single derived review projection that consolidates those completed sai-2 source artifacts into one comprehensible PR review surface, without replacing the normalized artifacts the pipeline consumes.

## What Changes

- `sai-2-design` produces a new per-change artifact, `change-overview.md`, alongside `design.md`, `tasks.md`, and `interfaces.md` — a single structured review projection consolidating `proposal.md`, `specs/**/*.md`, `design.md`, `tasks.md`, and `interfaces.md`.
- **Target State relocation**: `## Target State` — with its `### Architecture Snapshot` and `### File Manifest` subsections — moves out of `interfaces.md` into `design.md`, where the design worker authors and persists it as the authoritative snapshot. `interfaces.md` retains only the implementation-facing per-step `## Step N` interface contracts and test assertions, resolving the mixing identified in the Why. `change-overview.md` projects the snapshot from `design.md` (and recomputes the File Manifest from `tasks.md`), so regeneration never synthesizes the snapshot anew.
- The overview is organized **by capability and behavior**, presenting scope, target architecture, requirements, scenarios, interfaces, method-level test assertions, file changes, delivery steps, and end-to-end traceability — not a concatenation of the source documents. The traceability and method-level assertion content SHALL be the content the source artifacts already encode (Step N keys, assertion→requirement anchors, requirement→scenario structure); mappings the sources do not encode are reported as gaps, never synthesized.
- **Deferred materialization**: no overview is generated during the initial sai-2 feedback loop while the source artifacts are still converging; first materialization occurs exactly once at the feedback gate's `Continue` processing after all source artifacts verify successfully; failure, cancellation, or abandonment materializes nothing.
- **Post-materialization synchronization**: once materialized, exactly one regeneration occurs after each later source-modifying transaction, owned solely by the writable design-worker transactions (re-invoked `/sai-2-design`, supervised design phase); the `sai-explore` artifact-review loop is a read-only origin of handoff payloads, never a regeneration surface; the sai-2 coordinator terminates at `Continue`, so no same-chat transaction exists after it; transactions that produce no effective source changes cause no regeneration; out-of-band modifications are detectable as stale, not auto-regenerated.
- **Persisted materialization state**: the change's `overview.state` (`unmaterialized` | `materializing` | `failed` | `current` | `stale`) is persisted in `.openspec.yaml` by the design worker; every generation is a recoverable two-phase transition — `materializing` before generator dispatch, then commit `current` after a successful closed result, so a process lost between file write and commit leaves `materializing` for reconciliation by the next writable design-worker transaction (the read-only review loop never commits state); `stale` is marked **before the first effective source write** of every post-materialization transaction so abandonment or process loss conservatively leaves `stale`; a failed first materialization sets `failed`, suppresses the success terminal, and is retried by a later invocation; `sai-status` and `sai-archive` consume the state key AND the CLI-reported artifact presence, so current metadata with a missing file — or any file paired with a non-`current` state — is treated as inconsistent.
- **Budget-routed generation**: the overview is generated by a budget-routed subagent executing a shared overview-generation instruction — no new numbered SAI phase, worker lifecycle, or feedback loop.
- The overview is a **derived projection, not a source of truth**: source artifacts stay authoritative, normative requirements and scenarios are preserved faithfully, and contradictions or missing relationships are reported rather than fabricated.
- The overview is registered in `openspec/schemas/sai-workflow/schema.yaml` (`requires: [interfaces]`, whose transitive closure covers proposal, specs, design, tasks, and interfaces), **excluded from `apply.requires`** — `sai-3-implement` and `sai-4-apply` keep consuming the authoritative source artifacts and never read the overview.
- The generated overview is validated for completeness and consistency against its sources, so human reviewers may use it as the sole PR review surface; the `sai-explore` artifact-review loop's new read-only `Review change-overview` action re-validates it against its sources on demand.

Non-goals:
- No consumer wiring: `sai-3-implement` and `sai-4-apply` remain unchanged and never depend on the overview.
- No change to `interfaces.md`'s per-step `## Step N` contracts: they remain the authoritative step-contract surface for `sai-3` and `sai-4`; only the review snapshot (`## Target State` and its `### Architecture Snapshot` / `### File Manifest` subsections) relocates, into `design.md` (authoritative) and `change-overview.md` (projection).
- No new numbered SAI phase, coordinator, worker, question lifecycle, or feedback loop for generation.
- No new source-level traceability identifier scheme in this slice: the overview presents the traceability the current sources already encode, and method-level mapping enrichment is reserved for a later capability.
- No overview for backfilled changes: a backfilled change produces no design-stage sources, so no overview is generated or expected for it and no `overview.state` key is written; on ordinary designed changes the persisted state distinguishes the expected pre-`Continue` absence from a stale overview (AUDIT warning in archive, flagged in status).

## Capabilities

### New Capabilities

- `change-overview-artifact`: `change-overview.md` consolidates the five completed sai-2 source artifacts into one review-oriented document organized by capability and behavior; source artifacts remain authoritative and normative content stays faithful; contradictions and gaps are reported, not fabricated; the overview is validated for completeness and consistency against its sources; it is registered in the schema (`requires: [interfaces]`) but excluded from `apply.requires`, and is never a prerequisite or input for sai-3 or sai-4.
- `change-overview-synchronization`: generation is deferred until the sai-2 feedback gate's `Continue` processing; the change's `overview.state` is persisted in `.openspec.yaml` (`unmaterialized` | `materializing` | `failed` | `current` | `stale`) with design-worker-owned transitions; every generation is a recoverable two-phase transition (`materializing` before dispatch, `current` commit after success), with interrupted `materializing` reconciled only by a writable design-worker transaction; `stale` is marked before the first effective source write of every post-materialization transaction and `failed` on an unsuccessful first materialization (success terminal suppressed, later invocation retries); exactly one regeneration per later source-modifying transaction, owned solely by the writable design-worker transactions; no regeneration without effective source changes; failed regeneration from a generator that ran leaves a stale record carrying contradiction details, while dispatch failure or process loss preserves the prior file and relies on `overview.state: stale`.
- `change-overview-generation-routing`: generation runs in a budget-routed subagent executing a shared overview-generation instruction — no new numbered SAI phase or worker lifecycle; the generator writes only `openspec/changes/{change-name}/change-overview.md` and returns a closed result contract (status, changed files, validation outcome, contradiction details, failure kind) that the design worker maps deterministically; Claude Code and opencode maintain parity for dispatch permissions (including the opencode design-worker `permission.task: budget: allow` allowance), bindings, managed agent projections, installation projections, and behavior.

### Modified Capabilities

- `design-interfaces-artifact`: `interfaces.md` no longer admits a leading `## Target State` section — every top-level section SHALL be a `## Step N` contract, with the single `None — no step contracts` sentinel admitted when no step has an interface surface; the Target State admission relocates to `design.md`.
- `design-target-state`: the `## Target State` section (with `### Architecture Snapshot` and `### File Manifest`) moves from `interfaces.md` to `design.md` as the authoritative snapshot, and is projected into `change-overview.md`; the finished-shape, snapshot, and net-fold contracts keep their normative content and change only their host artifact.
- `sai-archive-soft-warn-audits`: the CORE/AUDIT/EXEMPT Classification Check extends to the 11th artifact — `change-overview` joins the AUDIT group (informational missing warning) for ordinary changes, and backfilled changes skip it alongside `interfaces`.
- `sai-status-progress-panel`: the panel covers the 11 sai-workflow artifacts; `change-overview.md` is flagged when missing on ordinary changes and treated as EXEMPT only when backfilled.
- `explore-post-crystallization-review-loop`: the per-change picker gains a read-only `Review change-overview` action that validates the overview against its sources only when the overview is the current review surface (`overview.state: current` plus CLI-reported done); non-current states produce an availability/integrity report with no findings tally and no review-evidence change; the loop stays strictly read-only and is a payload origin, not a regeneration or reconciliation surface; acceptance iterates one `Accept`/`Decline` picker per finding in deterministic order (High → Medium → Low, then numeric within severity), and the handoff protocol routes design-artifact findings to the design worker and consent-gated proposal/spec findings through the design phase's spec-amendment path (no spec-worker continuation exists at review time); regeneration follows only when the overview is already materialized — before first materialization, corrections update sources only.
- `explore-review-evidence-marking`: a completed no-High `Review change-overview` marks the slice's reviewed-sai-2 item, a High finding clears it, the most recent completed review over the sai-2 slice decides precedence, an absence report for a missing overview leaves the item unchanged, and an availability/integrity report for a non-current overview leaves the item unchanged (no findings tally).

## Additional Notes

- Source-artifact authority is unchanged: `interfaces.md` keeps its per-step `## Step N` contracts, which remain the authority for step attribution; the `## Target State` review snapshot (with `### Architecture Snapshot` and `### File Manifest`) is authored and persisted in `design.md` and projected into `change-overview.md`, so regeneration reads it from persisted sources and never synthesizes it.
- The `### File Manifest` is recomputed at projection time by the deterministic net fold over `tasks.md` and validated against the persisted manifest in `design.md`; on divergence the generator reports the source contradiction and fails the transactional validation rather than preferring either side.
- The change's `overview.state` lives in `.openspec.yaml` — a per-change metadata write the design worker already owns (approval metadata precedent) — so `sai-status` and `sai-archive` distinguish never-attempted (`unmaterialized`), in-progress or interrupted (`materializing`), failed-first-attempt (`failed`), current, and stale overviews without inspecting file contents. Every generation is a two-phase transition (`materializing` before dispatch, `current` commit after a successful closed result), and an interrupted `materializing` is reconciled only by a writable design-worker transaction (re-invoked `/sai-2-design` or supervised design phase); the read-only review loop reports but never commits state. The worker marks `stale` before the first effective source write of every post-materialization transaction, so abandonment or process loss after the first write conservatively leaves the stale state with no further execution point required. Currentness is the conjunction of the state key and the CLI-reported artifact presence, so current metadata with a missing file — or any file paired with a non-`current` state — is surfaced as inconsistent. A failed first materialization sets `failed`, suppresses the design completion sentence, and is retried by a later re-invoked `/sai-2-design` at its own `Continue`.
- The generator returns a closed result contract (status, changed files, validation outcome, contradiction details, mandatory `failure_kind`) that the design worker maps deterministically. A stale-record file write is required only when the generator actually ran and returned a coherent failed envelope; on dispatch failure or process loss the prior file is preserved and `overview.state: stale` alone prevents it from being presented as current. A malformed or empty envelope is an output-contract violation: whatever file state exists is preserved unmodified (the parent never writes `change-overview.md`), the state is set `stale` (regeneration) or `failed` (first materialization), and the file becomes current only through a later writable reconciliation transaction.
- The opencode design-worker managed agent currently permits only `explore` task dispatch (`permission.task: "*": deny, explore: allow`); this change adds `budget: allow` so the budget-routed generator is dispatchable, with the parity test asserting the allowance. The Claude agent's `Agent` tool already permits the dispatch; no permission change is needed there.
- Post-materialization synchronization is owned solely by two writable design-worker transactions (re-invoked `/sai-2-design`, supervised design phase); the `sai-explore` review loop is a read-only origin of handoff payloads, so no two transactions can claim the same regeneration; the sai-2 coordinator terminates at `Continue` with no continuation question, so no same-chat transaction exists after it; `/sai-1-spec` cannot consume an existing change and no spec-worker continuation is live at review time, so consented proposal/spec amendments route through the design phase's consent-gated spec-amendment path; manual or unintegrated edits are out-of-band and detectable as stale by review validation, never auto-regenerated. Regeneration after accepted corrections occurs only when the overview is already materialized — before first materialization, corrections update sources only. A completed no-High `Review change-overview` marks the slice's reviewed-sai-2 item per the shared evidence rule, with most-recent-review precedence.
- Blocking source contradictions (for example a persisted File Manifest diverging from the deterministic fold) fail the transactional validation, and the failure payload — the stale record on regeneration, the blocking result on initial generation — names both conflicting sources, their locations, and the one-line disagreement; non-blocking gaps are recorded in the overview itself without failing it.
- The alternative "keep Target State inside interfaces.md" is rejected by the change's own decisions because it mixes PR-review information with implementation-facing step contracts; the relocation resolves the mixing directly.
- The exact fetch sites of the shared instruction (design invocation vs worker binding) and the exact budget subagent binding are design-phase decisions; the specs pin the routing class and the single-source shared instruction, not a specific agent keyword.
- The schema header comment ("full 10-artifact graph") becomes stale once the 11th artifact is registered; the design phase updates it.
- Backfilled and legacy changes never produce design-stage sources, so no overview is generated for them and no `overview.state` key is written; for those changes the overview is silently skipped (matching the `interfaces` backfill treatment), while ordinary designed changes surface a stale overview (AUDIT warning in archive, flagged in status) and treat pre-`Continue` absence as expected.
