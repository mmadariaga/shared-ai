> **⚠ POST-HOC RECORD** — This proposal was backfilled after implementation against a user-supplied statement of intent. It describes a decision already made, not one being proposed.

## Why

A committed base settings file acted as push and publication consent for every contributor and for anyone who cloned a repository that set it. `publication.autoApprove: true` or `pr.publishAfterRun: yes` in the shared `.sai/settings.jsonc` removed the publication question of `/sai-plan`, `/sai-build`, and `/sai-explore` and the approval question of `/to-pr` and `/to-backlog`, although none of those people decided it. That contradicted the held-confirmation rule of `skills/universal/safe-operations/SKILL.md` and AGENTS.md § Safe Operations (issue #486, finding F1).

## What Changes

- `readSettings` in `sai/tools/project-settings.js` applies a consent rule to `publication.autoApprove` and `pr.publishAfterRun` (exported as `CONSENT_IDS`): a granting value (`true`, `yes`) held by `.sai/settings.jsonc` stays out of the merged `values` and out of `baseValues`, and restricting values (`false`, `no`, `ask`) merge as before. A key held by `.sai/settings.local.jsonc` still wins over the base key. `get`, `autoApprove`, the `get` CLI, and the setup menu inherit the rule.
- A granting base value produces one consent warning per key, returned in a new `consentWarnings` map instead of `warnings`: `get` of that key and the new `readAutoApprove` read return it, and a read of any other key does not. The warning reads `Setting <id> in .sai/settings.jsonc grants consent only from .sai/settings.local.jsonc, so that value is ignored; move it to .sai/settings.local.jsonc to grant consent.` It appears whether or not the local file also holds the key.
- `to-pr.js` adds the auto-approve consent warning to the `warnings` of its `query`, `push-query`, `push`, and `publish` output, and `to-backlog.js` (`withAutoApprove`) adds it to the `warnings` of every adapter dispatch, through the new `addWarnings` helper that drops duplicates.
- `saveSettings` in `bin/project-settings-writer.js` always writes the two consent keys to `.sai/settings.local.jsonc`, creating it when absent, and never to `.sai/settings.jsonc`, also under `baseOnly`. When it writes a granting value and `git check-ignore` reports the local file as not ignored, it returns a warning that committing the file shares the grant with every clone and that the menu never edits `.gitignore`.
- The `Auto-approve publication` row of the setup menu shows the value that takes effect, saves `On` as `true` and `Off` as `false` in the local file, prints the writer's warnings after a save, and prints the consent warnings when a screen opens. The menu gains no `pr.publishAfterRun` row.
- `docs/project-settings.md` gains a `Publication consent` section and corrects the exception list, the setting table, the local-override rules, and the menu write rule; `docs/commands/to-pr.md`, `docs/commands/to-backlog.md`, the `to-pr` and `to-backlog` skills, and AGENTS.md § Optional plan publication name the local-only grant. ADR 0224 amends ADR 0222 and ADR 0223 and is listed in the ADR index.

## Capabilities

### New Capabilities

None

### Modified Capabilities

- `project-settings`: the base/local merge keeps a granting consent value of the base file out of the merged values and reports it per key.
- `project-settings-writer`: the two consent keys always save to `.sai/settings.local.jsonc`, which is created when absent, with a warning when git does not ignore it.
- `project-settings-screen`: the `Auto-approve publication` row saves to the local file and shows the value that takes effect.
- `to-pr`: the auto-approval setting grants only from the local file, and a base-file grant is reported in `warnings`.
- `backlog-publication`: the auto-approval setting grants only from the local file, and a base-file grant is reported in `warnings`.
