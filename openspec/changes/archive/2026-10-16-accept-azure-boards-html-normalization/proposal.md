> **⚠ POST-HOC RECORD** — This proposal was backfilled after implementation against a user-supplied statement of intent. It describes a decision already made, not one being proposed.

## Why

Azure Boards publication verification compared the sent and the received work-item description byte for byte. Azure re-serializes a stored description: it adds formatting whitespace between block tags and drops the `backlog-id-counters` comment. An otherwise successful Azure publication therefore ended as divergent or uncertain and forced needless reconciliation and renewed approval.

## What Changes

- The Azure DevOps backlog adapter (`sai/tools/to-backlog-azuredevops.js`) gains a hand-written, dependency-free directional comparison `equivalent(sent, received)`. Received content is equivalent to sent content only when it equals the sent content plus whitespace inserted between block tags (`p`, `li`, `ul`, `ol`, `h1`-`h6`, `pre`, `blockquote`), immediately before a block closing tag, or at the start or end of the description next to a block tag, optionally without the exact `backlog-id-counters` comment. Whitespace removed anywhere, whitespace added before an inline closing tag, any whitespace change inside `<pre>` or `<code>`, any other comment, a counters comment with different values, and any change to text, links, or structure stay differences.
- The Azure adapter uses the comparison for the description in the update `no_changes` check, in the `complete` check of update and creation outcomes, and in the creation recovery candidate filter. Titles stay strictly compared, and the comparisons between two Azure reads (the stale-baseline digest and the `pending` digest) stay strict.
- The shared set workflow (`sai/tools/backlog-provider-set.js`) compares descriptions through an optional provider `equivalent` mechanic, defaulting to strict equality. It applies to the creation readback, the accepted-content check before writing slice references, the decision to write references, the readback after writing them, and the set recovery candidate match and existing-result check. Only the Azure adapter supplies `equivalent`; GitHub and GitLab stay byte-exact.
- The Azure provider documentation (`skills/universal/to-backlog/providers/azuredevops-content.md` and `azuredevops-update.md`) states that verification and no-change detection accept this harmless normalization, and that because Azure drops the counters comment, an identifier removed from the description can be reused on Azure Boards.
- Regression tests cover harmless normalization (no-change update, update outcome, creation recovery, set publication and set recovery readback), meaningful differences that stay visible, and the GitLab set path staying byte-exact.
