## Why

The `/sai-merge` command was the only phase whose worker was strictly read-only while its coordinator wrote resolution content. This created an architectural inconsistency: the component that materialized the resolution (coordinator) was also the one that would have to judge it. This separation of concerns is maintained in every other SAI phase (`apply`, `review`, etc.), where each worker performs technical writes and the coordinator verifies the work against the approved strategy. Restoring this pattern to merge keeps the authorization gate (coordinator approval) distinct from the execution gate (worker implementation).

## What Changes

**Worker scope expansion:** The merge worker transitions from read-only analysis to include authored-content resolution writing. After the coordinator confirms the selected global strategy (`apply-strategy`), the worker writes the resolution to the working tree by:
- Splicing conflict-region replacement text (from the JSON payload) into each conflicted file at its marked conflict region
- Updating ADR/DDR references within files (family-aware canonical tokens, index-label replacements)
- Applying verification-loop corrections in the same manner (splice corrected text, update references)

The worker continues to avoid all state-changing git commands (`git merge`, `git checkout`, `git add`, `git commit`, etc.) and file renaming.

**Coordinator scope refinement:** The coordinator's git-command ownership remains unchanged. After the worker writes content, the coordinator performs a post-resolution review:
- Validates the materialized working tree against the approved global strategy held in context
- Performs cheap deterministic validation: byte-identity checks for git-sourced files (via `git show :2:` / `:3:` stages) and correctness checks for authored splices
- Detects divergences (unapproved changes, unresolved regions, out-of-scope writes)
- On divergence, returns the named issue to the worker under bounded round count (max 3 rounds)
- On successful review, proceeds to staging

This adds a post-resolution review gate that never existed before, making the coordinator's verification authoritative and informed by the complete approved strategy.

**Git-command ownership unchanged:** The coordinator retains exclusive ownership of:
- Merge launch (`git merge`)
- Git-sourced materialization (`git checkout --ours/--theirs`)
- File renames (`git mv`) for ADR/DDR collision repair
- Staging (`git add`)
- Commit execution (`git commit`)

**Fast-track does not skip review:** The `--fast-track` flag continues to bypass only the runtime scope question; it does not skip the coordinator's post-resolution review.
