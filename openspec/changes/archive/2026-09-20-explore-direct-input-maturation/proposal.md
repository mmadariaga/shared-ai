## Why

A detailed imperative request can currently be misclassified as an instruction to implement, causing Explore to recommend leaving the mode and skipping its edge-case and implementation-detail phases. Treating it as idea content preserves the intended read-only exploration workflow and keeps the scope explicit before any route is selected.

Direct-looking requests take longer because they must pass the exploration gates. Detailed requests may receive concise confirmation prompts rather than a full re-discovery interview. Explore remains read-only, imperative wording cannot bypass mandatory gates, the crystallization-close selector remains the only route-selection gate, explicit artifact-review behavior is unchanged, and the shared behavior stays equivalent on Claude Code and opencode.

## What Changes

- `sai/commands/explore/instructions.md`: added rule 11, Direct-looking request classification (sai-explore only). Imperative inputs ("Implement …", "Fix …", "Add …", "Apply …") are treated as the initial content of a candidate idea, never as authorization to implement, dispatch, or leave Explore. Stated objectives, constraints, and acceptance criteria are preserved; only unresolved substantive questions are asked. Imperative wording alone never triggers handoff to `/sai-4-apply` or `/sai-build`, never advises exiting Explore, and never dispatches implementation before the crystallization-close route selector. `Explore change`, `Review edge cases`, `Implementation details`, and `Crystallize` (including final route selection) remain mandatory. Explicit artifact-review deliverables keep their review path; mentioning a change authorizes nothing; destructive or shared actions remain unperformed.
- `test/explore-pre-crystallization-stages.test.js`: added contract assertion `direct-looking imperative inputs mature as ideas without early implementation handoff` covering the classification sentence, preservation sentence, no-handoff, no-exit-advice, mandatory four stages, sole selector gate, and artifact-review path.
- No OpenSpec skills modified. No product code modified. Both harnesses share the single instruction source.
