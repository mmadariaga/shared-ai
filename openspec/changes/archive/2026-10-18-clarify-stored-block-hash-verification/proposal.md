## Why

Workers in a run that predated the stored-block file transport re-typed long, non-ASCII stored blocks by hand to hash them and failed (a dropped closing `---`, altered characters). The current transport already verifies a stored block with `ready-to-propose.js verify-file` on the file exported by `sai-state block … --export`, but several normative surfaces still described `ready-to-propose.js hash` as the receiving worker's hash recomputation and invited the old manual step back. This change rewords those surfaces so `verify-file` on the exported file is the only transport verification and `hash` is a diagnostic hash.

## What Changes

- `sai/policies/stage-machine.md` (`Block` verb): the receiving worker now runs `verify-file` on the exported `block_file`, per `sai/policies/ready-to-propose-format.md` § Stored block transport, instead of "recomputing the hash of the block it received".
- `sai/policies/issue-origin-preservation.md`: the re-read of an amended imported-issue block now names `sai-state block <id> <change-name> --export --harness <claude|opencode>`, checks the refreshed `hash` that export returns, and stops before dispatch when the export returns `BLOCK_EXPORT_FAILED` or `BLOCK_NOT_FOUND`.
- `AGENTS.md` (`sai/tools/` row, `ready-to-propose.js` entry): `hash` is described as a diagnostic hash for investigating a mismatch, never transport verification, whose result never authorizes a dispatch; transport verification is `verify-file` on the exported block file.
- `sai/tools/ready-to-propose.js` header comment: the `hash` sub-command is described the same way. The executable code, usage text, interface, and tests of `hash` and `verify-file` are unchanged.
- The hashed block range (which includes the closing `---`), the Manual route, and the `--no-specs` POC profile are unchanged; they keep carrying no hash check where they had none.
