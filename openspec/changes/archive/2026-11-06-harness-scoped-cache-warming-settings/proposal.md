## Why

The `Cache warming` screen mixed the provider and model pairs of Claude Code and opencode in one list, because pair discovery deduplicated the pairs without keeping the harness they came from. One global `warming` value could not express a difference between the harnesses either, so a user could not tell which settings applied to which harness and could not edit one harness without affecting the other.

## What Changes

- The `Cache warming` screen asks which harness to configure first (`Claude Code` or `OpenCode`) and lists only that harness's role defaults and rules.
- Guided pair discovery keeps the harness and deduplicates within it, so a pair used by both harnesses appears in both groups.
- The `warming` setting accepts one `{defaults, rules}` block per harness under `claude` and `opencode`, and still accepts the top-level `defaults` and `rules` as the legacy global value that a harness without a block reads.
- The effective-warming resolver takes a required `--harness claude|opencode` and reads that harness's block, or the global value when it has none. **BREAKING** for callers of `project-settings.js warming`, which now fails with a usage error when the flag is absent.
- Saving writes only the edited harness's block, keeps the other block and the legacy global keys, and never deletes user configuration.
- The warming policy, the explore hand-off step, the benchmark override's verify path, and the project settings documentation name the harness whose timings they resolve.

## Capabilities

### New Capabilities

None

### Modified Capabilities

- `warming-setup`: the `Cache warming` screen selects a harness first, lists only that harness's pairs, and saves the selected harness's block.
- `cache-warming-settings`: the `warming` setting accepts per-harness blocks with a global fallback, and the resolver resolves a value for an explicit harness.
- `explore-handoff-warming`: the hand-off warming lookup names the active harness when it resolves the `agent` timings.
