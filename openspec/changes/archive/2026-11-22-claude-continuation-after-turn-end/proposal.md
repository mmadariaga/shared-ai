> **⚠ POST-HOC RECORD** — This proposal was backfilled after implementation against a user-supplied statement of intent. It describes a decision already made, not one being proposed.

## Why

On Claude Code, a subagent's handback (its `ready` reply or a report reference) reaches the coordinator before the subagent's turn has ended. A `SendMessage` sent on the handback alone can land in the ending turn: a `haiku` archive worker refused such a message and looped on `ready`, which stalled a Direct Build route. The implement, review, audit, and plan coordinators and every opencode dispatch source already wait for the subagent's completion notification before a continuation, but the Claude Code routed-worker binding template, the three Claude Code budget skills, the `/sai-explore` explorer startup, and the progress-event exception of the Claude panel adapter did not.

## What Changes

- `sai/orchestration/workers/bindings/claude/standalone-worker-template.md` § Continue: every later message goes to the captured handle only after the worker's `task-notification` with `status: completed` for the turn that returned the message being answered has arrived, matched by task ID, whatever its summary. A new paragraph states that a handback alone never marks the turn as ended, that a `completed` notification whose summary says the worker waits on its own background work (its armed cache-warm wait) ends the turn, that a `completed` notification saying the worker has not reported yet is not a result, and that a stop call at a dispose point is not a continuation and never waits.
- `skills/claude/budget-explorer/SKILL.md`, `skills/claude/budget-executor/SKILL.md`, and `skills/claude/budget-subagent/SKILL.md` § Dispatch mode: the sentence "Capture and await the continuation on the dispatcher's own turn." is replaced by the same rule: capture the agent ID, await the completion notification on the dispatcher's own turn, match notifications to subagents by task ID when several run at once, never sleep or poll, and send a `SendMessage` continuation only after the previous turn's `completed` notification, whatever its summary.
- `sai/commands/explore/body.md` § Explorer two-phase startup: on Claude Code each explorer continuation, after the ready reply and for every later search, goes only after that explorer's `completed` task notification, matched by task ID.
- `sai/adapters/claude/panel-render.md` § Order: the routed progress-event exception keeps its panel updates in the turn that registers the event, while the `SendMessage` continuation follows the worker's `completed` task notification, never the handback alone.

The opencode dispatch sources, `sai/policies/opencode-dispatch.md`, the worker contracts and ready prompt, and the coordinators that already carry the rule are unchanged.

## Capabilities

### New Capabilities

- `claude-continuation-timing`: when a Claude Code coordinator or dispatcher may send the next message to a routed worker, a budget helper, or the `/sai-explore` explorer.

### Modified Capabilities

- `harness-panel-render-binding`: the Claude Code progress-event continuation no longer shares the panel-update turn; its `SendMessage` waits for the worker's `completed` notification.
- `non-blocking-runtime-panel-tool-degradation`: the progress-event exception to render-first ordering keeps the Claude Code continuation behind the worker's `completed` notification.
- `todo-list-progress-rendering`: the same-turn pairing of the list update and the continuation keeps the Claude Code continuation behind the worker's `completed` notification.
- `explore-two-phase-startup`: Claude Code explorer continuations wait for that explorer's `completed` notification.
- `opencode-subagent-calls`: the Claude Code worker binding template no longer stays unchanged; it keeps no `running` exception and carries its own `completed`-notification rule.
- `worker-dispatch-prompt-template`: Claude binding continuations go only after the worker's `completed` notification.
- `dispatch-safety-invariant`: the Claude Code `## Dispatch mode` declaration states the `completed`-notification rule for continuations.

## Request Additional Notes

The probe behind the Q1 decision simulated the cache-warm wait with a background `sleep 120` instead of `wait.js`, used one `general-purpose` agent per case and one run each, and did not reproduce the original `haiku` failure. In the same probe the first `ready` of the agent with a live background child was not delivered as a handback; the ready dispatch carries no warming switch today, so this does not affect the handshake, but a later change that arms warming before `ready` would meet it.
