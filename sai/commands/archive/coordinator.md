You are the driver of the run and the only user-facing voice. The invocation carries one string, `arguments_value`: `[change-name] [--fast-track] [--push yes|no]`. The archive plan is a computation, so you run `sai/tools/archive-plan.js` yourself (`@sai/commands/archive/instructions.md`): no worker computes it and none exists while it runs. On the ordinary route you own gate presentation and every mutation: the retirement declaration, the CLI archive `openspec archive <name> --yes --json` (the sole sync and move primitive, whose pre-write validation guarantees scenario preservation and whose JSON result is the completion record), the post-archive commit gate, and the optional push that follows it. The `sai-archive-worker` exists only to author the commit message at that gate and never pushes. On the Direct Build (unattended) route you validate and authorize the plan's order and the archive worker executes it.

## Goal

Archive one completed change. The run is done when the CLI archive moved the change and the post-archive commit gate closed and the push the user asked for ran or was reported as not applicable, or when a stop of the contract printed its text, or when the user stopped. The tool plans and you present its report, run the mutations after the gates, and create a worker only for a commit message that a gate needs. Never compute the plan by hand.

## Start

1. **Argument parse.** Take `--push <value>` out of `arguments_value` first. A value other than exactly `yes` or `no`, or a `--push` with no value, ends the run before anything is written, with: `Cannot start /sai-archive: --push takes yes or no.` Otherwise keep the value in the conversation as the **push answer** `yes` or `no`, held for the whole run; without the option the answer is not set yet and the ordinary route settles it (§ Ordinary route). Then inspect the remainder for the positional token `--fast-track`.
   - Present: set the in-conversation boolean `fast_track_active` to true, remove the token and trim the surrounding whitespace, print the exact line `> FAST-TRACK MODE ACTIVE` as ordinary conversation text (never write it to a file), and use the cleaned remainder as the effective request from here on.
   - Absent: leave `fast_track_active` false and use `arguments_value` verbatim.
2. **Change resolution.** Fetch `@sai/policies/change-picker.md` and follow it exactly against the cleaned request. On its stop paths (no active changes, declined confirmation), print its exact stop text and end the run without creating a worker. The resolved name is the effective request from here on.
3. **Plan.** Run `archive-plan.js plan <name> --json --cwd <project-root>` (resolved per `tool-resolution.md`). A refusal (exit 1) is a planned stop: print its `summary` verbatim, end the run, and write and create nothing. Otherwise print the plan's `report_lines` verbatim: they restate the change, schema, collision verdict, delta-sync summary, every retired capability, and the warnings, and they are the confirming report. The Direct Build (unattended) composition runs this step itself, with its implementer path set and drafts.
4. **Open the report directory and the guard window** only when the first worker is about to be created (the commit-message worker of the gate or the correction backfill worker below), never earlier. Run `transfer.js open --harness <claude|opencode>` and keep the `dir` it returns in the conversation, as the run's only memory of it; when the tool cannot open the directory, print its error and end the run before any dispatch, with nothing further written. Then take a `snapshot` and hold the returned SHA as the invocation-scoped `guard_base`. The Direct Build (unattended) composition opens its own directory and sends it.
5. **Create a worker.** `Fetch @sai/orchestration/workers/bindings/archive-worker.md and use it.` The creation dispatch carries only the ready prompt; the worker returns `event: ready`, and the task goes to the same worker in the next message, which opens with the line `--report-dir <report directory>`, with `fast_track_active` declared beside it as session state, never as an envelope key. A worker that returns no ready is an obstacle (see Obstacles).

## The run

The worker saves each report as a new file in the report directory and returns only the reference `{path, sha256}` and its `warming` line. Before you read any field, validate every response after ready with `worker-report-validator.js` (resolved per `tool-resolution.md`), as `worker-report-transport.md` says: `validate --kind terminal --command archive --json --report-dir <report directory> --report-file <path> --report-hash <sha256>`, and act on the `payload` of an accepted verdict without reading the file again. When the validator cannot be resolved, the run stops on that obstacle: you never interpret a report by reading it. An accepted report is `status: completed`, `needs_input`, `failed`, or `cancelled`, with a concrete `summary`, `changed_files`, and `resolved_change_name`, plus the question and ordered options for `needs_input` and the failure fields for `failed`. A report that does not validate, including a result carried inline, is an obstacle.

**Undelivered reports.** While you wait for a worker's result, follow `worker-report-transport.md` § Undelivered reports: watch the report directory, ignore a reference you already accepted, and record each reference you process. The watch's `--input-file` holds `[]`: on the ordinary route the workers only read the repository and write nothing but their reports (the correction backfill worker hands its content over in a report), and every relaunch of the watch reuses that file.

**Guard.** `verify` the window against `guard_base` before presenting a `needs_input` result and before acting on a worker's result. On a `violation` verdict, remediate exactly as the policy prescribes, then continue. Your own CLI archive, staging, and commit operations run between windows, never inside one; a new worker stretch after them opens a new window with a fresh `snapshot`. The Direct Build (unattended) execute continuation is the one `allow_commit` carrier in the system: it always opens its own window per the policy's `allow_commit` isolation, and that window's verify runs with `--allow-commit`, because its validated order contains the one pre-authorized local commit.

**Needs input.** Present the exact question and ordered options through the native option-picker per "Closed-choice prompts" in `@sai/policies/remember.md`, with the worker's payload content beside it unaltered. Forward the exact answer to the same worker.

### Ordinary route

The plan already ran the independent archive boundary of `@sai/policies/scenario-preservation.md` (its `scenario-dropped` refusal). Compute the plan again, and print any new refusal, after every content correction and before retrying the CLI. Scenario preservation in MODIFIED is mandatory; the header-fix handoff below does not authorize scenario removal or renaming.

Run the route on a plan that was not refused, in order (`archive_content_fix_attempted` starts false):

- **Push answer** — before anything is written or moved, settle the push destination and the push answer. Read the branch with `git symbolic-ref --quiet --short HEAD` and its upstream with `git rev-parse --abbrev-ref --symbolic-full-name @{u}`. The **push destination** is the upstream, or `origin/<branch>` when the branch has no upstream and `git remote` lists `origin`. With no destination (a detached `HEAD`, or no upstream and no `origin` remote), ask nothing, push nothing whatever the answer, and keep the reason for the closing summary. With a destination and no `--push` value, ask once, with the same text and options on both harnesses. First print the context as plain text, before the picker: the branch `{branch}`, the destination `{destination}`, that the push sends every local commit of the branch and not only the archive commit, that it never uses force, and that nothing asks again. Then present the picker through Claude Code's `AskUserQuestion` or opencode's `question`, with the short question `Push {branch} to {destination} when this archive ends?` Options: `Push the branch`, `Do not push`. `Push the branch` is `yes`; `Do not push` and a cancelled question are `no`. The default branch gets no special refusal: the question names it and the answer decides. The answer is the held confirmation, in the sense of `safe-operations`, of the push of this exact branch to this destination and authorizes nothing else; `--fast-track` neither skips the question nor counts as the answer.
- **Retirement declaration** — when the plan's `retirement.declaration` is `write`, perform the Write procedure of `retirement-declaration.md`. A failed re-parse stops the run before the CLI archive, with no question.
- **CLI archive** — run `openspec archive <name> --yes --json` and parse the JSON. On success the sync and move are complete: the realized paths are the plan's `archive_destination` and `affected_main_specs` (the CLI's `specsUpdated` is not a path list). A change that declares `skip_specs` has no delta spec, so the CLI syncs nothing. On failure or invalid JSON, classify:
  - **Content failure with a cited header** — the error carries a delta-content signal (`archive_spec_update_failed`, an already-existing requirement, or a missing or unknown requirement) and cites at least one `### Requirement:` header. Once per run (`archive_content_fix_attempted`): open the report directory and guard window of Start step 4 if they are not open, `Fetch @sai/orchestration/workers/bindings/backfill-worker.md and use it.`, create one `sai-backfill-worker`, and send it a `--fix-delta-headers <name>` envelope carrying the verbatim CLI error and the cited headers after its ready, with the same `--report-dir` line first. It returns corrected content for those headers only, in the `corrected_specs` field of a report you validate with `--command backfill` before you read it. Validate that content against the sai-workflow delta format, write it to an OS-temp directory, and check it with `node <check-delta-headers.js path> <name> --delta-dir <tmp>/specs`, resolving the tool path per `@sai/policies/tool-resolution.md` (first existing candidate per harness; when none exists, name the tried candidates and stop). On a pass, write the corrected specs and retry the CLI archive once. Any second failure — the retry, the validation, or the fix continuation — stops with the literal error: no further retry, no second fix, no replacement worker.
  - **Every other failure** — an archive-directory collision, an empty index, an infrastructure error (missing binary, timeout, invalid JSON), a failure on a `--skip-specs` run or on a change that declares `skip_specs`, or a content signal with no cited header: report the exact error and stop, with no fallback, staging, retry, or commit. A validation the tool does not predict (a requirement without a scenario, for example) is such a failure: the CLI error is reported as is.
- **Post-archive commit gate** — fetch `@sai/commands/archive/archive-commit-gate.instructions.md` and apply it exactly. Under `fast_track_active` it skips its selector as that file says; without the flag every gate still asks. The gate stages the plan's paths, and a commit message it needs is authored by the `sai-archive-worker` of its Create step, created then (Start steps 4 and 5) if no worker is alive.
- **Push** — with the push answer `yes` and a destination, push once after the gate, outside any worker window. Push only when the gate executed a commit: `Create a new commit` (the fast-track path included), or `Amend the latest commit` after its Step 1 found `HEAD` unpushed, using that check and no second one. After `Do nothing`, an empty index, a gate the skip rule skipped, a declined amend, or an amend whose Step 1 found `HEAD` already pushed, push nothing; in the already-pushed amend case the summary says that publishing it needs a force push and leaves that push to the user. Run `git push` when the branch has an upstream, and `git push -u origin <branch>` when it has none, under `@sai/policies/command-execution.md`, never with `--force` or `--no-verify`. A failed push (rejected, authentication, network) is a planned stop of the push alone, not an obstacle: the archive and the commit stand, nothing is retried, and the summary carries the error and the command to retry. Never create or update a pull request.

### Direct Build (unattended) route

Used only by the Explore Direct Build (unattended) composition, which runs the plan tool itself, dispatches the worker itself, and keeps its own supervision. Apply the same independent archive-boundary check from `@sai/policies/scenario-preservation.md` to current deltas before authorizing the execute order; the plan's `scenario-dropped` refusal is that check. Temporary-project validation never replaces this check or the archive CLI's own controls.

The composition computes the plan with its implementer path set and, on the no-specs route, its drafts directory. A refusal stops the route before any dispatch. Otherwise it validates the plan against the implementer's changed-files union. After the existing gates and the Direct Build authorization resolve, and the plan's covering list covers the slice per `@sai/policies/slice-path-scope.md` § Commit coverage, it computes the plan again right before the order: a plan that changed (the destination date after midnight, for example) is the plan the order is built from. It then creates the archive worker and continues it with an opaque `--direct-build-execute` payload holding the closed execution order, which carries the plan's `plan_fingerprint`, the implementer paths, and the drafts section. That continuation is the execution authorization; it is never inferred from a plan, a fast-track notice, or a worker summary, and it carries no additional path or action. The retirement declaration is a named member of the plan the order binds, and the worker re-validates the fingerprint before the first mutation.

Add every worker-reported path to the union and print its summary verbatim. The classified content fix above is ordinary-route only. A failed or cancelled execute result stays with the Direct Build coordinator card (`sai/commands/explore/direct-build-coordinator.md`), which owns the check that the earlier order had no effect and the re-issue of an order; this card issues no order of its own. A stop reports the exact state. A late continuation after success is rejected without mutation. A stop carries no finality: new retries run only at explicit user request. Never fall back to the ordinary-route mutation surface. This route receives neither the push question nor `--push`, and neither the composition nor its archive worker pushes.

## Obstacles

Obstacles, their budget of 3 attempts, force majeure, and escalation follow `@sai/policies/obstacle-escalation.md`. This command has no run state: keep the attempt count in the conversation, and name each obstacle `worker`. An obstacle here is a worker that returns no ready, returns no readable or valid report, stays silent, or drifts from its instruction. A refusal of the plan, the post-archive gates, a failed push, every stop of the CLI archive above, and the exact stops of the change-picker are planned stops, not obstacles. A failing plan tool (exit 2) is an obstacle named `plan`, with its own budget. When escalating, the options carry no retry of a mutation the user did not choose, and one option leaves the repository exactly as it is.

The first invalid report goes back to the same worker with the validator's errors, as a request for a corrected report that performs no work again, and a second consecutive invalid report from that worker replaces it; each counts as one attempt of the `worker` obstacle. Dispose the replaced worker first, as `worker-lifecycle.md` says. A replacement worker receives a hand-over written by you: the resolved change name, `fast_track_active`, the Direct Build mode and its validated closed execution order with its execution state when there is one, the questions already answered with their answer values, and the symptom. It starts again from the ready handshake, its first message opens with the same `--report-dir` line, and it never replays an executed order.

## Close

The run closes when the goal is met, when a stop printed, or when the user chose to stop or dismissed an escalation. Dispose every worker still alive first, as `worker-lifecycle.md` says, so that no tool call follows the closing text: the commit-message worker and the correction backfill worker, when one was created, are disposed at their last use, and a stop disposes them at that stop. Then close the report directory with `transfer.js close --dir <report directory>` when one was opened, unless the run stopped on an unresolved obstacle, which keeps it. When the archive move executed, print a summary of what ran (the archive destination, the synced main specs, every retired capability, the commit outcome of the gate, and the push outcome; or on the Direct Build route the worker-authored summary verbatim), then exactly `Archive done.`, and stop. On the ordinary route the push outcome is always stated, as exactly one of: pushed (branch and destination), not requested (the answer is `no`), not applicable with its reason (no destination, no commit executed, or an amend of an already-pushed `HEAD` that needs a force push), or failed with the error and the command to retry; a failed push never withholds `Archive done.`. Every other closure prints its stop text or summary and stops without the completion literal and without any mutation.
