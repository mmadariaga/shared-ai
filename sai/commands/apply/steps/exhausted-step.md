# Apply Step — Exhausted-Step Choice

Loaded when a `recovery-ledger@1` response reports a budget `exhausted`, the worker pool or the coordinator attempts. The block that `steps/recovery.md` puts on marking, commit, and advance holds until the user decides; the only path to a fresh whole-Step budget is the choice below.

Applies to standalone `/sai-4-apply` and to the apply segment of `/sai-build`. When an un-lifted `unrecoverable: true` veto or a safe-operations denial also applies, no choice is offered: `steps/veto-override.md` or the stop report governs.

## Procedure

1. **Read.** Take both tallies, the exhausted budget, and all prior cycles from the ledger response.
2. **Recommend.** Before the picker, recommend the safe, viable option with the least further human work. Recommend a fresh attempt only when a concrete authorized correction resolves the known cause, and explain what the agent will correct and verify, the explicit retry authorization the user must give, and any approvals still needed. Otherwise recommend manual correction and name the user's work. The recommendation grants no budget, changes no option or order, and never treats repeating an unresolved cause as unattended recovery.
3. **Present** through the active harness's native picker, following `@sai/policies/question-context.md`. The text before the picker names the active command (`/sai-4-apply` or `/sai-build`), the change, the blocked Step, what failed, both spent tallies, and the prior attempt history when present. It defines in plain words each term it uses: the Step, the recovery budgets and their limits, a new attempt, and explicit authorization. It states that the Step stays blocked, that the retry option authorizes exactly one new attempt for the whole Step and does not authorize a commit or bypass a check, and that the manual option stops apply for human correction.
   - Question: `How do you want to proceed with Step N?`
   - Options, in order: `Authorize one fresh attempt` (`authorize-step-retry`); `I will correct it manually` (`manual-correction`).
4. **Wait.** The retry option, or an unequivocal order naming this exact Step, is the only authorization. A question, a request for help, silence, or a free-text reply that picks no option authorizes nothing: show the same picker again, unchanged. `manual-correction` closes this apply run with the Step still blocked. Never auto-select either option under `--fast-track`.
5. **Grant.** After explicit authorization, re-read the current `implementation.md` Step contract and verification scope. When the plan changed, the Step contract is missing or ambiguous, the correction is not viable, a worker veto applies, or safe-operations denied the action, grant nothing and report the exact stop. Otherwise send `{kind: authorized-step-retry, step: "Step N", authorized: true}` and require `retry_grant: granted`. The ledger archives the exhausted cycle in `attempt_history` before clearing both budgets; report the retained history and the new cycle.
6. **Retry.** Start one new worker-level invocation of only this Step, reusing the current worktree and plan. Its ordinary `step-entry` is a re-entry, not another grant, and its first dispatch opens a new no-commit-guard window with a fresh snapshot. Re-select routing and the current plan, then run the normal verification and commit gates. The grant covers the whole Step, not only the original failure. When either fresh budget is exhausted again, ask for a new explicit decision; never chain a grant.
