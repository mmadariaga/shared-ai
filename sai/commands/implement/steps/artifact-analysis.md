# Implement Step — Artifact Analysis

Active step: artifact-analysis. Parse all change artifacts, classify audit findings, and validate design decisions for ADR/DDR, then report the `artifact-analysis` progress event per the worker contract.

### Step 2: Parse the Artifacts

Read the full content of `proposal.md`, `design.md`, `tasks.md`, and all `specs/**/*.md` before applying the workflow steps below.

- Extract change metadata (name, affected files)
- Parse all implementation steps from `tasks.md` in order
- Identify affected files and intended actions per step
- Extract and internalize the Expertise Profile from `## Implementation Context` in `tasks.md`
- If `## Implementation Context` is missing entirely, STOP per the STOP condition above.

**Exception (audit artifacts):** Check whether any of `review.md`, `security.md`, `performance.md`, or `accessibility.md` exist in `openspec/changes/{change-name}/`. For each one that exists, read it and apply the **Judgment Rubric for Audit Findings** (see below) to every finding, classifying each as Apply, Discard, or Escalate. The classified results are evaluated for escalations first (see **Escalation Detection and Handoff** below); if escalations exist, the run stops. Otherwise, the Apply/Discard classification results are appended as audit-derived steps by Step 5 ("Append audit-derived steps") — the append description lives at that execution site; this step only reads and classifies.

### Judgment Rubric for Audit Findings

The rubric is defined normatively in `openspec/specs/audit-artifact-ingestion/spec.md`; this section is its operational restatement. Both Step 2's audit-reading exception and Step 5's first-run generation path / "Append audit-derived steps" sub-section invoke this rubric before appending any audit-derived step.

For every finding in an existing audit artifact (`review.md`, `security.md`, `performance.md`, `accessibility.md`), evaluate all five criteria and classify the finding as **Apply**, **Discard**, or **Escalate**:

1. **Severity** — does the finding rise to Critical/High (the shared audit severity vocabulary used by review, security, performance, and accessibility), or is it a non-issue?
2. **Actionability** — is the proposed fix specific enough to implement as a concrete file:line change, or is it a vague suggestion?
3. **Spec-decision consistency** — does the finding contradict a decision in `design.md` or a requirement in `specs/**/*.md`?
4. **Duplication** — does the finding repeat another finding already addressed in an earlier step of `implementation.md`?
5. **Scope** — does the finding stay within the change's declared scope, or does it propose out-of-scope work?

The Apply/Discard/Escalate classification SHALL follow from the rubric outcome, not from gut feel.

- **Apply** findings are rendered as concrete code-writing checkboxes (file:line location + specific change) inside the appended audit step — the same kind of code-writing checkboxes the implementation plan template uses elsewhere in `implementation.md`.
- **Escalate** findings are those that contradict an existing decision or requirement (criterion 3 fails) or propose work that exceeds the change's declared scope and would require new acceptance criteria not yet established (criterion 5 fails). When any finding is classified as Escalate, the run stops before `plan-generation` appends any audit-derived steps, and instead emits a `Ready to Propose` block for a new change derived from the escalated findings. No Escalate findings are appended as code actions. Each escalated finding that stops the run records the artifact source (`review.md`, `security.md`, etc.) and finding id for research-leads population in the emitted proposal.
- **Discard** findings appear in a **Discarded findings sub-block** inside the same appended step (not a separate step). Each entry uses the format:
  `**{id}** — {one-sentence reason} (source: {artifact} § {category} {id})`
- **Question (Q) findings** (only `review.md` has a Questions category) are auto-discarded with the reason `requires user response, not a code change`. The full Q text SHALL be transcribed verbatim beneath the entry line so the user can answer in chat. Q findings SHALL NOT be rendered as Apply code actions under any circumstance.
- **Informational findings** in `security.md` / `performance.md` / `accessibility.md` are NOT auto-discarded — they go through the normal rubric like any other finding. (Only `review.md` Questions are auto-discarded; `security.md` has no Informational tier, while `performance.md` and `accessibility.md` do.)

**Escalation Detection and Handoff**: After classifying each finding in all audit artifacts, check whether any finding was classified as **Escalate**. If escalations exist:
  1. Do NOT generate any appended audit step.
  2. Do NOT continue to `plan-generation`.
  3. Group escalated findings by the scope of work they imply: two findings from different artifacts belong in the same group when they describe the same missing change or overlapping capability gap. Each group represents one proposed change (e.g., findings from `review.md` and `security.md` that both reveal a missing authentication requirement belong together; a finding about a missing configuration file would be a separate group).
  4. For each group of escalated findings, emit a `Ready to Propose` block from `sai/policies/ready-to-propose-format.md` with:
     - **Change name**: a kebab-case suggestion derived from the escalated work (e.g., `add-authentication-requirement`, `missing-config-file-handling`). Derive the name from the substance of the missing work, not from its source artifacts. When the work is genuinely too ambiguous to name, acknowledge the ambiguity in **What** and use the most concrete descriptor available from the findings.
     - **What**: a 1–2 sentence summary of the escalated work.
     - **Why**: describing the gap, issue, or constraint revealed by the escalated findings, citing the source artifacts and finding ids as evidence (e.g., `Finding C1 in review.md and finding S2 in security.md both reveal that the current change's scope does not cover authentication, which contradicts the requirement in specs/auth.md.`).
     - **Research Leads**: populated from the repository-relative paths the escalated findings point to in the codebase (e.g., `specs/auth.md`, `sai/commands/config/auth-handler.md`, any source files the findings cite). Do NOT use artifact offsets or finding id suffixes; Research Leads are pointers to code and documentation the findings reference, not the audit artifact itself.
     - **Edge Cases**: `- None` (only explore can agree on edge cases with the user).
     - **Implementation Details**: `- None` (only explore can agree on implementation details with the user).
     - All other sections populated to the best of the agent's ability from the escalated findings' text.
  5. Return a terminal status (with `summary` containing all emitted blocks as chat output — one block per escalation group) and stop the run.

After generating an appended audit step (when no escalations exist), the agent SHALL print the list of Discarded findings to chat (one line per Discard, plus the verbatim Q text for any Q Discard) and ask the user to confirm or override before `/sai-4-apply` starts. Confirmation is conversational in chat only — the agent SHALL NOT write any approval key to `.openspec.yaml` and SHALL NOT introduce a new approval gate for Discards.

When every finding in an artifact is Discard, the appended step SHALL still exist, containing only the Discarded findings sub-block and a single `- [ ] No code changes from this audit` checkbox (no Apply code actions). The user closes the step by checking that box.

### Step 3: Validate Design Decisions for ADR/DDR

Read the `## Decisions` section from `design.md`. Fetch @sai/policies/adr-ddr-criteria.md and evaluate each recorded decision against the three ADR/DDR criteria it defines.
- **Resolve the record family first**: only when all three criteria hold, resolve the decision's record family (`adr` or `ddr`) before deciding record creation. Read the decision's `**Record family**: adr|ddr` marker from `design.md` when present — do NOT re-decide a family the design already recorded. When the marker is absent (the design predates this requirement, or the decision surfaced only at implementation time), apply the ordered routing test defined in that policy.
- **Culture check before any ask**: only after all three criteria hold and the record family is resolved, use the resolved family's physical `0000-INDEX.md` as the sole culture signal: `docs/adr/0000-INDEX.md` for `adr` or `docs/ddr/0000-INDEX.md` for `ddr`. Do not infer culture from any other ADR/DDR records, from the other family's index, or from records/files outside these recognized locations; a missing index means no culture whether the resolved family has records or no records at all. If the resolved-family index exists, create the `docs/<family>/NNNN-slug.md` file directly without asking, then use the warm-splice branch below. If it is absent, ask the user a closed yes/no on creation that names the resolved family (e.g. "This decision qualifies as a DDR. Do you want me to create it?") and create the file only upon explicit approval, then use the cold-build branch below. Never offer an ADR-vs-DDR choice in the ask. If the decision does not meet all three criteria, create nothing and ask nothing.
- When the record being created declares a relationship to another record (amends, supersedes, reverses, reframes, refs, or pair-with), append a structured, parseable relationship line to the record file itself, in addition to any prose. Use an HTML comment form keyed on the prefix `adr-index:` listing each `<relationship> <NNNN>` pair separated by `;`, e.g. `<!-- adr-index: supersedes 0002; amends 0003 -->`. The structured-line relationship token set is: `amends|supersedes|reverses|reframes|refs|pair-with`. For pair semantics, writers SHALL emit `pair-with` in the structured line. A relationship target in the same family is encoded as a bare number (`0002`); a target in the other family carries the explicit family prefix (`ddr:0014`, `adr:0069`). Records with no relationship carry no such line. The index-maintenance hook below reads this structured line deterministically; prose parsing is a best-effort fallback for hand-written records that predate this convention.
- **Maintain each family's index once at the end of Step 3**: after the record-creation pass above completes (whether it created zero, one, or many records this run), run exactly one index-maintenance cycle per family that received records in the current run — `docs/adr/0000-INDEX.md` for the ADR family, `docs/ddr/0000-INDEX.md` for the DDR family. Each cycle covers only the records of its own family that the CURRENT Step 3 run created and writes only its own family's index; when a family created zero records, its cycle is a no-op — do not touch that family's index and do not print any index-maintenance instruction into `implementation.md`.
- **Branch selection**: per family, choose the branch by the absence or presence of that family's index file (`docs/adr/0000-INDEX.md` / `docs/ddr/0000-INDEX.md`):
  - **Cold build** (index absent): construct the family's index from its project-agnostic template — `sai/commands/implement/adr-index.template.md` for the ADR family, `sai/commands/implement/ddr-index.template.md` for the DDR family (read it by exact path — do NOT inline its boilerplate into `implement.md`). The template carries only the canonical section skeleton with `## By <domain unit>`. The cold build derives the `<domain unit>` noun deterministically from the family records' domain-unit references by applying the abstract surface's framework mapping list and fallback noun (`decision-record-index-machinery`), and substitutes the derived noun into that H2 (for example, `## By command` in this repository, `## By module` in a module-based consumer project). The mapping list, its precedence, and the fallback rule are the abstract surface's contract — referenced by name here, not restated.
  - **Cold build derivation rules**: derive domain-unit references and cross-cutting categories from the family records' own content at cold-build time; create `### <domain unit reference>` subsections under `## By <domain unit>` and `### <category>` subsections under `## Cross-cutting categories` from that derived set; do not assume any fixed list of commands, modules, endpoints, or categories.
  - **Cold-build delegation (cost discipline)**: the cold build's bulk read of every `docs/<family>/NNNN-*.md` file is delegated to a `budget-explorer` subagent per `sai/policies/remember.md`; the main `sai-3` agent MUST NOT read every record in bulk. The subagent returns RAW per-record context only: exact H1 title (`{Title}`), parsed structured `<!-- adr-index: ... -->` relationship declarations, domain-unit references mentioned verbatim, the first paragraph of `## Context` (raw text, capped at ~80 words), and best-effort prose relationship candidates for records without a structured line (normalized relationship token, target record number, source section label, short evidence snippet). The subagent MUST NOT return pre-decided cross-cutting categories. The main `sai-3` agent performs cross-cutting categorization and threshold judgments from that raw context.
  - **Relationship annotation rules (both branches)**: for every relationship declared by a structured line (or by best-effort prose fallback for hand-written records), annotate entry lines using these exact token forms: `— Pair with NNNN`, `— Refs NNNN`, `— **Amends** NNNN`, `— **Reframes** NNNN`, `— **Reverses** NNNN`, `— Supersedes NNNN`, with the family-prefixed encoding for cross-family targets (`— Refs adr:0069`, `— **Amends** ddr:0014`). Do not invent alternate token styles. `*Superseded by [NNNN]*` is reserved for the moved historical entry in the supersede-move rule, not for the superseding record's entry. Family-boundary behavior — which tokens may cross families and the cross-family target encoding — follows the abstract surface's relationship-token rules (`decision-record-index-machinery`), referenced by name here rather than restated.
  - **Correction-table population rules (both branches)**: the correction-table section heading and header are per-family bindings — `## ADRs that extend or correct prior ones` with `| ADR | Action | Over |` for the ADR family, `## DDRs that extend or correct prior ones` with `| DDR | Action | Over |` for the DDR family; for each relationship of type `amends|supersedes|reverses|reframes`, add one row using `[NNNN_source] | <action> | [NNNN_target]` where `<action>` is exactly `amends`, `supersedes`, `reverses`, or `reframes`; cross-family `amends | reframes | reverses` target cells use the cross-family link form `[NNNN](../<family>/NNNN-slug.md)` and the row is written only to the source record's own family index. Do not add correction-table rows for `refs` or `pair-with`.
  - **Cold-build supersede move**: move EVERY superseded record project-wide (not session-scoped) out of `## By <domain unit>` and `## Cross-cutting categories` into the family's historical section (`## Superseded ADRs (historical)` / `## Superseded DDRs (historical)`), appending `*Superseded by [NNNN_superseding]*` to each moved entry line and adding correction-table rows for each supersede relation. When the supersede target is NOT a decision record (e.g. ADRs 0080 and 0089 in this repository, whose supersede declarations name the change `simplify-routed-phase-coordination` rather than an ADR number), preserve the note text verbatim (`— *Superseded by simplify-routed-phase-coordination*`, no numeric link, no rewrite) so the byte-for-byte equivalence claim holds.
  - **Threshold recomputation scope**: the cold build is the SOLE branch that recomputes the cross-cutting threshold structure, per the abstract surface's threshold contract (`decision-record-index-machinery`); the warm path does NOT recompute thresholds. The threshold values are the abstract surface's framework values, referenced by name here rather than restated. The threshold contract applies only to `## Cross-cutting categories`. The `## By <domain unit>` axis has NO threshold: each distinct domain-unit reference gets its own subsection.
  - **Warm splice** (index exists): splice ONLY the family records the current Step 3 run created into the existing index structure, leaving all hand-curated content for records not created this session byte-for-byte unchanged EXCEPT where a session record supersedes one (a supersede-move is the only permitted mutation of a non-session entry).
  - **Warm placement rules**: insert each session record into every correct `### <domain unit reference>` subsection under `## By <domain unit>` based on its content, creating a new `### <domain unit reference>` subsection on demand when missing. For `## Cross-cutting categories`, do NOT create a new `### <category>` subsection unless it already exists in the structure (warm path does not recompute cross-cutting thresholds); when the category subsection is missing, append the entry to the collapsed single list under `## Cross-cutting categories` in place.
  - **Warm supersede-move**: when a session record supersedes a prior record in the same family, move the superseded record's entry out of `## By <domain unit>` and `## Cross-cutting categories` into the family's historical section, append `*Superseded by [NNNN_superseding]*` to its entry line, preserve its exact title and any pre-existing relationship annotations, and add correction-table row `[NNNN_superseding] | supersedes | [NNNN_superseded]` to the family's correction-table section. The move SHALL NOT clobber, reword, reorder, or delete unrelated hand-curated entries. A `supersedes` whose target is in the other family is a classification error per the abstract surface's family-boundary rule: it is NOT executed, the source record is NOT moved, the other family's index is NOT touched, and the error is surfaced in chat so the user can reclassify the source or target record.
- **Idempotent on rerun**: per family, before inserting a session record `NNNN`, check whether an entry line for `NNNN` already exists in its own family's index — i.e. a line beginning with the literal form `- [NNNN —`. If it does, that record is a no-op for the rerun: skip it entirely (no new entry line in any placement, no new correction-table row, no new supersede-move). The detection key is the record number matched against an actual entry line — do NOT key on the bare link target `./NNNN-slug.md` appearing anywhere in the file (that link string legitimately appears in the correction table's `[NNNN](./NNNN-slug.md)` cells and in `*Superseded by [NNNN](./NNNN-slug.md)*` supersede notes, which would false-positive). The skip is per-record and covers all placements — an interrupted prior run that placed `NNNN` in only some of its sections leaves it permanently under-placed by this rule (accepted limitation; the fix-up path is a cold rebuild by deleting that family's `0000-INDEX.md` and re-running Step 3 with a record-creating decision). A present index forces the warm branch for that family — NEVER re-cold-build, even when the warm splice produces no new entries.
- **Index-output invariants** (both branches): the index output SHALL follow the abstract surface's five index-output invariants (`decision-record-index-machinery`) — language, links, record titles, index H1, and the canonical section skeleton (the H1 plus five `## ` sections in fixed order; the section positions are fixed by the abstract surface, and the two type-specific section-heading texts are the family bindings) — referenced by name, not restated. The link forms are the within-family `./NNNN-slug.md` and, for relationship targets in another family, the cross-family `../<family>/NNNN-slug.md`. Each entry line uses the form `- [NNNN — {Title}](./NNNN-slug.md)` with the verbatim `{Title}` from the record's H1 (without the `# ADR NNNN:` / `# DDR NNNN:` prefix in the entry text). Preserve the index's own H1 (`# ADR Index` / `# DDR Index`) verbatim as the first line of the file across both branches.
