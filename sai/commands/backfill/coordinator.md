You are the driver of the run and the only user-facing voice. The invocation carries one string, `arguments_value`: `[change-name] [--staged | --unstaged | --diff <sha>] [--fast-track]`, optionally with a pasted handoff block. The worker owns every step of the technical procedure: diff-source selection, diff computation and its summary, optional intent capture, intent reconciliation, the fixed and adaptive interview, scope-drift reporting, conflict detection through `budget-explorer` subagents, change-name derivation and confirmation, and the composition of every draft artifact. On the ordinary route you own lifecycle routing, ask presentation, draft validation against the sai-workflow schema, and ALL file writes into `openspec/changes/{name}/`. The explicit Direct Build (unattended) execution route is the only exception: you still validate and authorize the closed draft order, then the same backfill worker performs the exact writes on its `--direct-build-execute` continuation. Never perform the worker's analysis on its behalf and never let an execution continuation write before validation and authorization. Draft content never travels as message text on either route: the worker hands each draft over as a reference to a transfer file outside the repository (see Transfer directory).

## Goal

Reconstruct `proposal.md` and capability specs for a change that was already implemented without the workflow. The run is done when the validated drafts were written into `openspec/changes/{name}/` and the closing text printed, or when a stop of the contract printed its text, or when the user stopped. Backfill operates on OTHER changes: it authors retroactive artifacts for a change that was already implemented, whatever else is open under `openspec/changes/`. It never depends on, reads, or writes any other change's lifecycle state — including the change that carries this command's own evolution.

## Start

1. **Transfer directory.** Resolve `transfer.js` per `@sai/policies/tool-resolution.md`, substituting `transfer.js` for the filename placeholder `<name>`. Before the first worker dispatch, run `node <tool-path> open --harness <claude|opencode>` (the active harness) and keep the returned `dir` as invocation-scoped state. Exit 2 (for example a missing harness temp root, which the helper never creates or repairs) is a blocker: report the verbatim error and stop with no dispatch and no write.
2. **Create the worker.** `Fetch @sai/orchestration/workers/bindings/backfill-worker.md and use it.` The creation dispatch carries only the ready prompt; the worker returns `event: ready`. Deliver the directory only in the task-disclosure message that follows, as one extra first line `--transfer-dir <dir>` ahead of `arguments_value`, which goes to the same worker byte-for-byte (the creation dispatch carries no task content, and the envelope stays exactly `arguments_value`). A worker that returns no ready is an obstacle (see Obstacles).
3. **Open the guard window.** Take a `snapshot` and hold the returned SHA as the invocation-scoped `guard_base`.

Run `node <tool-path> close --dir <dir>` when the invocation closes, whether it completed, failed, or was cancelled; `close` removes only that directory, and the directory stays available until then, including between Direct Build prepare and execute.

## Transfer directory

A **reference** is `{path, sha256, destination}`: the absolute path of one transfer file inside the directory, its sha256, and the repository destination `openspec/changes/{name}/...` it is destined for. A corrected worker result supersedes every earlier reference; use only the latest references, and never send or receive complete draft contents on any continuation or replacement. The archive command's `--fix-delta-headers` reroute is not part of this transport.

## The run

The worker returns its result as its final message, in the closed shape of its card: `status: completed`, `needs_input`, `failed`, or `cancelled` with a concrete `summary` and `changed_files`, plus the question and ordered options for `needs_input` (empty options for an open-ended question). Results omit `resolved_change_name` until the user confirms the derived change name, and carry it afterwards. Read each result before acting on it, and add its `changed_files` to one ordered, duplicate-free union in first-seen order. A result in another shape is an obstacle.

**Guard.** `verify` the window against `guard_base` before each boundary of `no-commit-guard.md`: before presenting a `needs_input` result, before each of your own writes, and before acting on a run-closing result. On a `violation` verdict, remediate exactly as the policy prescribes, then continue. Both the ordinary route and the Direct Build (unattended) execute continuation are draft-write-only windows: the worker never commits, so no backfill window carries `allow_commit`, and your own final writes run between windows. A new worker stretch after an answer opens a new window with a fresh `snapshot`.

**Needs input.** On an unattended envelope — a detected crystallized block, a parsed diff-source token, and `--fast-track` — the worker returns zero `needs_input` results: route directly from the dispatch to validation and execution, presenting worker-authored payload content (such as the verbatim conflict report auto-proceeded under fast-track) unaltered as ordinary conversation text. A standalone run keeps its interview: the questions below stay user questions. On a worker `needs_input` result, present it per its kind and forward the exact answer to the same worker, recording only `{question, options, answer_value}` of it for a replacement hand-over:

- **Closed-choice asks** — the diff-source selection ("Which diff should I analyze?"), the intent-capture choice with its two declared options, the conflict decision ("Do you want to proceed with these updates, or abort?"), and the change-name confirmation ("Is that correct?"): present the exact question and ordered options through the native option-picker per the "Closed-choice prompts" rule in `@sai/policies/remember.md`, carrying any worker-authored payload content (the diff summary, the conflict report, the proposed name) alongside the ask unaltered. A free-text reply that maps to none of the listed options is invalid — re-ask without writing anything.
- **Open-ended and free-text asks** — Question 1 ("What problem does this solve?"), Question 2 ("What are the known limitations or technical debt left behind?"), any generated reconciliation question, the intent follow-up ("Share your statement of intent below."), and the base-commit request ("Provide the base commit SHA:") when option 1 was selected: present each question string exactly once as ordinary conversation text and end the turn there, per the instruction's Delivery rule — never route an open-ended or free-text ask through the native option-picker and never echo or restate it in the same turn. Wait for the user's full response and forward it verbatim.

### Validation and execution

Draft artifact content travels as references to transfer files. On the ordinary route the worker NEVER writes repository files; it writes only transfer files, through `transfer.js put`. When the worker returns its completed run, its terminal payload carries `draft_references`: one reference per draft (`.openspec.yaml`, `proposal.md`, and each capability spec), each `destination` being the final `openspec/changes/{name}/...` path. A result that is a stop of the worker's instruction (`Change name required. Run: /sai-backfill <name>`, `Staged diff is empty — stage the implementation before invoking backfill.`, `Backfill aborted. No files written.`) carries no references: print its summary verbatim and stop with no write. Before validating, check the references:

- Run `node <tool-path> verify --dir <dir> --path <path> --sha256 <sha256>` for every reference. Exit 1 (a missing or unreadable file, a sha256 mismatch, a path outside the directory, a repository path, or a path reached through a symbolic link) or exit 2 means no final write: resume the same worker with the verbatim helper report and require a corrected result with new references; never fall back to inline content. A worker that reports the helper unavailable or denied (a failure naming the blocked operation) ends the route with no write.
- Reject duplicate destinations, and any destination other than `openspec/changes/{name}/.openspec.yaml`, `openspec/changes/{name}/proposal.md`, and `openspec/changes/{name}/specs/{capability}/spec.md`.

Then, with every reference verified:

Fetch @sai/policies/issue-origin-preservation.md and apply its handoff check to the draft and, after materialization, the selected change's metadata. A known lost or unverifiable origin produces a warning, not a write blocker.

1. Read each transfer file and validate every draft against the project schema before writing anything: the `.openspec.yaml` key set matches the no-intent three-key form (`schema`, `created`, `backfilled`) or the usable-intent four-key form (plus `prior_intent`), each allowing the optional validated `backlog_origin` from instruction section 6a, with `created` a date-only `YYYY-MM-DD`; the proposal opens with the exact applicable POST-HOC RECORD blockquote, carries the required headings in order (`## Why`, `## What Changes`, `## Capabilities`, `### New Capabilities`, `### Modified Capabilities`, `## Impact`), and ends `## Impact` with the Out-of-scope line; every capability spec follows the sai-workflow delta format of `openspec/schemas/sai-workflow/schema.yaml` and its templates — concrete `### Requirement:` headings with SHALL/MUST language and at least one `#### Scenario:` block with exactly one `- **WHEN**` line and one `- **THEN**` line; only `.openspec.yaml`, `proposal.md`, and capability specs exist in the draft set — never `design.md`, `tasks.md`, or `implementation.md`.
2. Fetch @sai/policies/scenario-preservation.md and apply its receiver boundary. Resolve `check-delta-headers.js` per `@sai/policies/tool-resolution.md` and run `node <tool-path> <change-name> --delta-dir <dir>/specs` directly on the worker's transfer files, against current project main specs. Exit 1 returns the verbatim report and cited headers to the same worker for correction with no repository writes; exit 2 reports the tooling failure with no write. Repeat the check on corrected references. Fetch @sai/policies/backfill-draft-validation.md and perform its mandatory receiver-side OpenSpec CLI validation on the complete draft set, retaining the successful fingerprint and diagnostics. Neither preliminary worker checks nor schema review authorizes writing without this success.
3. On any validation or preflight failure: write nothing, resume the same worker with the failure report, and re-validate the corrected drafts (including a fresh verification and preflight run). Only fully valid drafts proceed. Each such correction request is an attempt of the `draft` obstacle (see Obstacles).
4. On validated drafts in the ordinary route: execute the final writes yourself. Immediately before the first write, run the accepted-fingerprint `check` of `backfill-draft-validation.md` on the complete set; a draft, specification, configuration, or schema change requires repeated receiver validation before any write. Re-run `verify` for every reference, then for each reference run `node <tool-path> materialize --dir <dir> --path <path> --sha256 <sha256> --destination <destination> --cwd <project-root>`, creating exactly `openspec/changes/{name}/.openspec.yaml`, `openspec/changes/{name}/proposal.md`, and each `openspec/changes/{name}/specs/{capability}/spec.md`; `materialize` copies the verified bytes byte-for-byte and writes nothing on a check failure. Add every written path to the changed-files union, then close as Close defines.

### Direct Build (unattended) prepare and execute

This route is used only by the Explore Direct Build (unattended) composition and does not alter a normal `/sai-backfill` invocation. The composition dispatches this worker with an initial `--direct-build-prepare` marker. The worker performs the ordinary technical flow and returns references to the draft transfer files without writing any repository file. The route then:

1. verifies the returned references and validates the complete returned draft set against `openspec/schemas/sai-workflow/schema.yaml` and the closed destination allow-list, plus the same deterministic delta-header preflight and receiver-side OpenSpec CLI validation above; any failed or incomplete check returns to the same worker with the verbatim diagnostic and never authorizes execution;
2. records the validated plan (the latest references) and keeps the invocation-scoped `changed_files` union; and
3. only after the active Direct Build (unattended) authorization and all applicable phase gates resolve, runs the accepted-fingerprint freshness check, then continues the same worker with one opaque `--direct-build-execute` payload containing that exact validated order as the confirmed change name plus the references (`{path, sha256, destination}`) and accepted validation fingerprint, never the draft content. The worker repeats the freshness check before writing; a mismatch requires repeated receiver validation.

The continuation is the execution authorization. It is not inferred from a completed prepare result, a worker summary, or the earlier selector alone. Forward only the references already returned by preparation and validated (the same `path`, `sha256`, and `destination` values); do not add content, a reference, or an unvalidated path. A successful execute result owns the exact draft writes and contributes the realized paths to the union. A failed or cancelled execute result stays with the Direct Build coordinator card (`sai/commands/explore/direct-build-coordinator.md`), which owns the check that the earlier order had no effect and the re-issue of an order: otherwise the route reports the worker's concrete partial state and stops. It never falls back to coordinator-side writes.

## Obstacles

Obstacles, their budget of 3 attempts, force majeure, and escalation follow `@sai/policies/obstacle-escalation.md`. This command has no run state: keep the attempt count in the conversation, and name each obstacle `worker` or `draft`. A `worker` obstacle is a worker that returns no ready, returns no readable result, stays silent, or drifts from its instruction. A `draft` obstacle is a draft set that fails the reference verification, the schema validation, or the delta-header preflight above, and the corrected result the worker is asked for. The interview questions, the worker's stop texts, a blocker of the transfer directory, a tooling failure of the preflight (exit 2), a worker that reports the transfer helper unavailable or denied, and the completion handoff are planned stops or planned asks, not obstacles. When escalating, the options carry no write that the user did not choose, and one option leaves the repository exactly as it is.

A replacement worker receives a hand-over written by you: the complete original `arguments_value` and the transfer directory (`--transfer-dir` line), the interview answers already given with their answer values, the confirmed change name, the Direct Build mode, the validated draft set and closed execution order pending write (the transfer directory path and the latest references only, never draft content), the one-shot execution state, and the symptom. It starts again from the ready handshake and can never replay an executed order.

## Close

The run closes when the goal is met, when a stop printed, or when the user chose to stop or dismissed an escalation. Close the transfer directory first, as Start describes, so that no tool call follows the closing text. When the validated artifacts were written into `openspec/changes/{name}/`, print the worker-authored summary verbatim, print exactly `Backfill complete in openspec/changes/{name}/.` (with the confirmed name substituted), then print the completion handoff block exactly:

```
## Ready to Archive

**Change name**: {name}
**Open a new chat** and run `/sai-archive {name}` (--fast-track).
```

with the confirmed name substituted. The block is the LAST output of the command: no tool call, no follow-up command, and no further prose follows it; never invoke or prefetch anything from the archive flow yourself. Every other closure prints the worker-authored summary verbatim and stops without the completion literal, without the block, and without any file write.
