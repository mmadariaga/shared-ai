# `/sai-build` coordinator

Fetch `@sai/policies/public-chat.md` and follow it exactly.
Fetch `@sai/policies/tool-resolution.md`
Fetch `@sai/policies/finding-state.md`
Fetch `@sai/policies/cache-warming.md`
Fetch `@sai/policies/change-telemetry.md`

You chain the segments of one build run in a single session. The invocation carries one string, `arguments_value`: the change name, with the optional `--publish [yes|no|draft]`, `--parent-branch <branch>`, and `--expert-review [no|auto|ask]`.

## Start

Drop every `--fast-track` token from `arguments_value`, and take `--publish` out of it and keep its value for the publication answer below. The value is consumed only when it is exactly `yes`, `no`, or `draft`, from the separate form or the attached `--publish=<value>` form; when the next token is anything else, the bare `--publish` equals `yes` and leaves that token in place. A value other than `yes`, `no`, or `draft`, or a second `--publish`, ends the run before anything is written with: `Cannot start /sai-build: --publish takes yes, no or draft.` Take `--expert-review` out of it too and keep its value for the expert review answer below, in the separate form or the attached `--expert-review=<value>` form, where a bare `--expert-review` is `auto`: a value other than `no`, `auto`, or `ask`, or a second `--expert-review`, ends the run before anything is written with: `Cannot start /sai-build: --expert-review takes no, auto or ask.` Take `--parent-branch <branch>` out of it too and keep the branch for the segments; a missing branch, or a second option, ends the run before anything is written with: `Cannot start /sai-build: --parent-branch takes one branch name.` The remainder is the change name, or empty, and goes to segment 1 as its `arguments_value`, followed by `--parent-branch <branch>` when one was given and `--expert-review no` always, because the checkpoint belongs to this command and never to a segment. The publication answer is resolved inside segment 1, as § Publication answer says, and so is the expert review answer, as § Expert review answer says.

## Publication answer

A run publishes a request when it holds a `yes` or a `draft` answer, and it asks the user at most once, so nothing after the question waits for a human. A `yes` publishes a request that is ready for review; a `draft` creates a draft request or keeps an open request in its draft or ready state; `no` publishes nothing. The answer is the held confirmation for the two remote operations of `@sai/commands/build/publication.md` on this exact branch and request, in the sense of `safe-operations`: the non-force push of the branch, and the creation or update of its request, which includes marking a draft request ready for review on a `yes`. It authorizes nothing else.

Resolve it once, inside segment 1, after that segment's Start step 4 has accepted the change (so a run that ends at the prerequisite check or at the startability check asks nothing) and before its step 5 opens the run, so no worker exists yet. The first of these that yields a value is the answer, and nothing after it is asked. An explicit `--publish` value wins over the recorded answer and replaces it:

1. The `--publish [yes|no|draft]` argument; a bare `--publish` is `yes`.
2. The answer recorded in the run state: spawn the `sai-state` session of key `implement-{name}` (the same session that segment 1's Start step 5 uses), emit `status` to `implement-run@1`, and read the `publication` field of its `run` view, which holds `yes`, `no`, or `draft`. Without a `--publish` argument a resumed run reuses it, whatever segment it resumes in, and asks nothing. A run with no recorded answer goes on to the next source.
3. The `pr.publishAfterRun` setting, read with `node <tool-path> get pr.publishAfterRun --json --cwd <project-root>` (`project-settings.js`, resolved per `tool-resolution.md`) when it returns `yes` or `no`. Print its `warnings` verbatim, one line each. `ask`, an absent key, an invalid value, and a tool that cannot run leave the question normal.
4. The question below.

Keep the answer in the conversation, and keep the id of that `sai-state` session. The session stays open across the segments: the implement coordinator's Close step 7 skips its session `close` inside this command, because closing the session would delete the recorded answer and a build interrupted in segment 2, in the Assessment pass, or after segment 3 would ask again. You close the session at your own Close (§ Close, after the publication step). **Record it** with `node <sai-state-path> emit --note "record the publication answer" <id> implement-run@1 --set kind=publication --set value=<yes|no|draft>` as soon as the run of a segment that opens one exists, so every later read of the run state returns it: right after segment 1's Start step 5 has opened its run or taken up an interrupted one, and again right after segment 3's Start step 5 has opened its new run, before its first step, because a completed implement run starts fresh under the same key and drops the answer. A build whose segment 3 does not run publishes with the answer of segment 1. When `--publish` differs from the answer already recorded by an earlier session of this run, the emit replaces the recorded answer, and the closing report says that the argument replaced it. When it equals the recorded answer, nothing is said. A resumed run takes the answer from the run state again, and asks only when none was recorded, for example when the run stopped before segment 1 opened its run.

**The question.** Ask it through Claude Code's `AskUserQuestion` or opencode's `question`, with the same text and options on both. Read the current branch (`git symbolic-ref --quiet --short HEAD`) and its remote (`git config branch.<branch>.remote`, else the only remote that `git remote` lists), and name them, so that an answer confirms that exact operation: `Publish the PR/MR of the build of {name} when this run ends? Branch {branch}, remote {remote}. The branch is pushed without force. A new request is created ready for review or as a draft; an open request of this branch is updated, and a ready choice marks an open draft request ready for review. Nothing asks you again.` Options: `Publish ready request`, `Publish draft request`, `Do not publish`. `Publish ready request` is `yes`, `Publish draft request` is `draft`, and `Do not publish` and a cancelled question are `no`. A detached HEAD has no branch to name: ask nothing, record no answer, and say in the closing report that nothing is published because HEAD is detached. When the remote cannot be read, say so in the question instead of a remote name.

**No answer is a no.** A run that fails, is stopped, or ends on an unanswered escalation publishes nothing, whatever the answer.

## Expert review answer

A run reviews its built code with an independent expert only when it holds an `auto` or an `ask` answer; `ask` adds one reconciliation question the user chose at Start, so nothing else waits for a human. Fetch? `@sai/policies/adversarial-expert-review.md` and resolve the answer by its § The answer: the `--expert-review` argument, the recorded `expert_review` field of `implement-run@1`, the `expertReview.build` setting, then its Start question. Resolve and record it at the same points and the same way § Publication answer resolves and records the publication answer — after segment 1's Start step 4 has accepted the change and before any worker exists for the question, right after the run of a segment that opens one exists for the record, and again right after segment 3's Start step 5 has opened its new run. Print the setting's `warnings` verbatim whenever you read it, and when it answers, one line naming it and its value. Record it with `emit <id> implement-run@1 --set kind=expert_review --set value=<no|auto|ask>`. Pass `--expert-review no` to segments 1 and 3: the checkpoint is this command's.

## Segments

1. `/sai-3-implement`: Fetch `@sai/commands/implement/coordinator.md` and follow it exactly as the first segment, with the change name of Start as `arguments_value`, followed by `--parent-branch <branch>` when one was given and `--expert-review no` always. It resolves the change and runs the whole implementation; keep the name it resolves (`{name}`) for the rest of the run. Resolve the publication answer between its Start step 4 and step 5, and record it right after step 5 (§ Publication answer), and do the same for the expert review answer (§ Expert review answer). Like any `/sai-3-implement` run, it also applies the open fixable findings of the audit reports already in the change directory. No wrapper is entered again and no approval is asked between segments.
2. `/sai-4-review`: Fetch `@sai/commands/review/coordinator.md` and follow it exactly as the second segment, with `{name}` as `arguments_value`, followed by `--parent-branch <branch>` when one was given, so it reviews the change segment 1 resolved instead of resolving one again. It reviews the diff in a fresh worker and writes `review.md`. It fixes nothing.
3. `/sai-3-implement` again, for the findings you select: follow `sai/commands/implement/coordinator.md` exactly as the third segment, with `{name}` as `arguments_value`, followed by `--parent-branch <branch>` when one was given and `--expert-review no` always, and hand it `review.md` as its only Composition report. Right after its Start step 5 has opened its new run, record the publication answer again (§ Publication answer) and the expert review answer again (§ Expert review answer). It applies every open fixable finding of `review.md` that carries no ` (EXCLUDED: …)` mark and marks each one it fixes. It starts only when the Assessment pass leaves at least one such finding. When it fixes a finding, it closes by storing the inherent-risk ratings block in `review.md` and committing it, as its own Close says.

No review runs after segment 3: one review pass runs per run, and the next `/sai-build` run reviews again. Segments 1 and 3 create no decision records; this command creates them at its Close.

Each segment disposes its own workers when it ends, in every outcome, as `worker-lifecycle.md` says, so no worker of a finished segment stays alive when the next segment starts; segment 3 creates new workers. A segment starts only when the previous one completed, including a segment 1 that completed with no new work. When segment 1 or segment 3 ends blocked (an escalation the user did not resolve), stopped, or with a failed precondition, print its report and end the run without a closing line, and do not start any later segment.

## Assessment pass

You run this pass yourself, once, after segment 2 completes and wrote `review.md`. It never runs when `review.md` holds no fixable finding (zero findings, or Questions only), and never in a worker.

1. Read `openspec/changes/{name}/review.md`. Read the code behind a finding whenever the heading and body do not let you judge it.
2. Judge each fixable finding (every finding except a Question) on its own: select it for fixing or exclude it. Use your judgment. Impact, the cost of the correction, and the risk of the correction are things you may weigh, never mandatory checks. No fixed selection rule, threshold, or severity cutoff applies: a High finding may be excluded and a Low one selected.
3. Append the exclusion mark to the end of each excluded finding's heading line: the literal ` (EXCLUDED: <reason>)` of `finding-state.md`. The reason is concrete, one line, and says why the fix is unwarranted. Change nothing else: the body, identifier, severity, and `Summary:` tally stay as they are. Never mark a Question.
4. When you wrote at least one mark, commit `review.md` alone under the Commit rule of `sai/commands/review/coordinator.md` § Close: check the path with `git check-ignore -q` first, `git add` it alone only when it is not ignored, and `git commit -m "<subject>" -- <path>`. The subject is a Conventional Commits message of at most 50 characters, for example `docs(review): mark excluded findings`. Authorship credits follow that same Commit rule. When the path is ignored, the marks stay on disk uncommitted. Never force-add with `-f`, never push, and commit nothing else. Invoking the command authorizes this one local commit.
5. Count the fixable findings with no mark. Start segment 3 only when that count is above zero. When you excluded every fixable finding, run no fix and go to the Close.

The assessment keeps no memory: a rerun regenerates `review.md` without earlier marks and judges every finding again.

## Expert review checkpoint

Run this once, only when the answer is `auto` or `ask`, after the last implementation segment that ran completed (segment 3 when it ran, otherwise segment 1) and before § Close, so it lands after the segment's commits and before the decision records, the telemetry, and the publication. Follow `@sai/policies/adversarial-expert-review.md` § The checkpoint, with this run's product:

- **Product and allowed write paths.** The files the change modifies against its change base, test files excluded: the paths `git diff --name-only <change-base>..HEAD` reports, minus everything under `openspec/` (so `review.md` and the plan artifacts stay as their segments wrote them), `SAI_LEARNINGS.md`, and every test path: the tests `tasks.md` records in its `**Tests**` fields, the tests the fix RED wrote in segments 1 and 3, and any other path the project's test conventions mark as a test (its test directories and the file-name patterns its test command collects). Read the change base as the implement coordinator does (§ Close of `sai/commands/implement/coordinator.md`, `change-base.js` resolved per `tool-resolution.md`). The worker writes production files only: a finding about a missing or weak test is reported without a correction, for a later `/sai-3-implement` run (E6), and a worker change outside these paths, a test file included, is reverted and reported (E4).
- **Checks.** The check the checkpoint re-runs after kept corrections is the tests related to them, run once under `@sai/policies/test-execution.md` (`test-select.js`, resolved per `tool-resolution.md`), with the command line that policy has you build. A failing test reverts every worker change and the product equals its state before the checkpoint (E5), with the pre-existing-failure classification of that policy applying as usual.
- **Commit.** After the kept corrections pass, commit them in one local commit under the commit authorization the invocation gives: each path checked with `git check-ignore -q` first and staged only when it is not ignored, the subject a Conventional Commits message of at most 50 characters such as `fix(expert-review): apply adversarial expert review corrections`, `git commit -m "<subject>" -- <paths>`, no force-add, and nothing pushed. An ignored path keeps its correction on disk, uncommitted, and the closing report names it; the commit carries the remaining paths. When the checkpoint kept no correction, commit nothing.
- **Inherent-risk block.** When the checkpoint kept a correction and `review.md` already carries an inherent-risk block, refresh it in its own local commit exactly as `@sai/policies/inherent-risk.md` and the implement coordinator's Close step 1 direct, so the stored ratings describe the corrected code. When it carries none, create none: `/to-pr` computes them as before.

Record the handled checkpoint with `emit <id> implement-run@1 --set kind=expert_review_checkpoint --set value=<done|skipped>`: `skipped` when it ran nothing, `done` otherwise. Report the checkpoint lines § Closing report of that policy defines, before this command's finding lists, and say that `review.md` was written before the corrections, so they are absent from it.

## Close

**Decision records.** After the last segment that ran ends and before the report, Fetch? `@sai/policies/decision-record-creation.md` and create the decision records when every segment that ran completed (a segment 2 whose accepted report carries `outcome: no-changes` counts as completed). Work from the final code and the deviations that the closing reports of segments 1 and 3 list, which are the only record of them once those runs end, and add the records to the report as that policy says. Its one local commit falls under the commit authorization the invocation gives. When a segment failed, was stopped, or ended blocked, create none.

**Telemetry.** After the decision records and before the report, record the change telemetry as `change-telemetry.md` says, with `--command sai-build` and no `--run-dir`; its one line, when it has one, goes into the report.

**Publication.** After the telemetry commit and before the report and any closing line, publish only when the answer is `yes` or `draft` and every segment that ran completed (a segment 2 whose accepted report carries `outcome: no-changes` counts as completed): Fetch? `@sai/commands/build/publication.md` and follow it with the change name, the `publish_pr_as_draft` value (`false` for `yes`, `true` for `draft`), and the findings that stay unresolved: as pending, the findings the report lists as **Left open by the fix segment** and the step-review findings that the closing reports of segments 1 and 3 list as pending after the third fix round; as excluded, the findings the report lists as **Excluded**. It runs unattended and asks nothing, and the build publishes once, here, never between segments. Print its one-paragraph outcome with the reports: the request URL it verified with its ready or draft state, or the reason nothing was published (detached HEAD, default branch, no provider or remote, failed authentication, a rejected push, a merged or closed request of the branch), and, when marking a draft request ready failed or its readback did not show it ready, that the request stays a draft and why. A publication that fails or is skipped never stops the run and never changes its outcome: the build stays completed, any confirmed push stays, and nothing is retried with force. With the answer `no`, or without an answer, nothing is published and nothing is asked. A run that fails, is stopped, or ends blocked publishes nothing.

**Session.** When the run completed (the publication step included, whatever its outcome), `close` the `sai-state` session of key `implement-{name}` that the segments left open (§ Publication answer), after the publication step and before the report. A run that fails, is stopped, or ends blocked leaves it open, so a rerun finds the recorded answer.

After the last segment that ran ends, print the report of each segment. A segment's own closing line is replaced by this command's.

- **Segment 2 completed** (it wrote `review.md`): read `openspec/changes/{name}/review.md` again (segment 3 and the Assessment pass changed its headings) and print the finding counts from its `Summary:` tally by category (Critical, High, Medium, Low, Questions) and the `## Recommended Audits` block of segment 2's report. Run no audit. Then print, each only when it has entries:
  - **Fixed**: the findings whose heading carries ` (FIXED)`, with identifier and title.
  - **Excluded**: the findings whose heading carries ` (EXCLUDED: …)`, with identifier, title, and reason, followed by the recovery instruction: to apply one, remove its ` (EXCLUDED: …)` mark from the heading in `review.md` and run `/sai-3-implement {name}`.
  - **Left open by the fix segment**: each selected finding that segment 3 did not fix and left without a mark (its fix rounds ran out, it judged the finding mistaken, or the run stopped on an obstacle), with the reason from segment 3's report. Never list it as excluded.
  - **Questions**: say that Questions stay open until the user answers them, because the fix segment applies only fixable findings.
  - With zero findings, report the zero counts and print none of these lists.

  Then close by the outcome of segment 3, whatever the findings:
  - **Segment 3 completed or did not run**: print the **Archive hint**. End with exactly `Build done.` The **Archive hint** is the next command for a new chat: `/sai-archive {name} --push yes` when the answer is `yes` or `draft` and the publication step confirmed the push of this branch; otherwise `/sai-archive {name} --push no`. The push counts as confirmed only when the publication step's result reports the branch pushed; an answer of `no`, a skipped publication, a refused or failed push, and a `draft` whose push did not complete give `--push no`.
  - **Segment 3 failed, was stopped, or ended blocked**: print segment 3's report and end the run with no archive hint and no closing line.
- **Segment 2 found no changes against the parent branch** (its accepted report carries `outcome: no-changes`; read the field, never the summary text): say that no review ran, because there was nothing to review, and end with exactly `Build done.`
- **Segment 2 failed, was stopped, or could not start**: print both reports and end the run without a closing line.
