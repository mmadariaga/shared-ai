# Unattended completed-build publication

The build is complete and its run holds the answer `yes` to the publication question of its Start (`@sai/commands/build/coordinator.md` § Publication answer). That answer is the held confirmation for the operations below on the current change branch: the non-force push of the branch and the creation or update of one request that is ready for review. This action never creates a commit, asks the user nothing, and never stops the run: every failure is a skipped or incomplete publication with its reason in the closing report.

Load the `to-pr` skill and follow its destination, content and recovery workflow with its § Unattended publication, with the completed change name and an explicit `ready:true` request, never `draft:true`. Use the same installed `to-pr.js` and provider registry that the skill resolves. The build's commits are already local commits of the branch, so no plan-commit step runs and no ignored file is included: a change artifact the project ignores stays on disk and out of the request.

1. **Destination.** Run `collect`, `resolve` and `destination` as the skill's § Resolve the destination says, without asking: an unresolved provider, an ambiguous remote or target branch, or a destination that needs a question skips the publication and names the missing fact. The target branch is the one `destination` returns for the provider's default branch unless the run was given another. A detached HEAD, missing access, or an unavailable provider skips the publication the same way.
2. **Request content.** Continue the skill with fresh collection against the same destination and branch: the title, the description (every committed change on this branch enters the request, so the description does not claim a request for the build alone), the ratings block, `query` with `ready:true`, and `push-query`. The unattended publish with `ready:true` creates a missing request ready for review, updates an open request, and marks an open draft request ready for review; an open request that is already ready stays ready. Multiple matches skip the publication; never create a duplicate.
3. **Push and publish.** Run `push --unattended`, then `prepare`, then `publish --unattended` with `ready:true` and the receipt, as the skill's § Unattended publication says. A refusal (`refusal` in the blocked result: `default-branch`, `detached-head`, `not-published`, `request-merged`, `request-closed`) skips the publication; for a merged or closed request, name it from the result's `request`. No force push, no automatic retry of a refused or rejected push, no authentication change or installation. On `uncertain` or `partial_failure`, run `recover` once, which is read-only, and report what it verified; never repeat a creation.
4. **Ready state.** The result of `publish` or `recover` carries `ready` with `requested: true` and its `status` whenever the request was asked to be ready. A `ready.status` of `pending`, a `rejected` or `uncertain` publish whose message says that marking the request ready failed, or a readback that shows the request still as a draft means the request stays a draft: the push and the content update stand, nothing is retried, and the report says that the request stays a draft and gives the reason from the result's message. The build still counts as completed.

Report, in one short paragraph, the branch push, the request URL with its verified ready or draft state, and every warning of the `query`, `publish` and `recover` results. When the publication was skipped or ended uncertain, report the completed steps separately from the failed one, keep the completed build and any confirmed push, and say how to continue by hand with `/to-pr` on this same branch; when only the ready state failed, say that the request can be marked ready for review by hand.
