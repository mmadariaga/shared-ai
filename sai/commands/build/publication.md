# Unattended completed-build publication

The build is complete and its run holds the answer `yes` or `draft` to the publication question of its Start (`@sai/commands/build/coordinator.md` § Publication answer). That answer is the held confirmation for the operations below on the current change branch: the non-force push of the branch and the creation or update of one request whose state the caller's `publish_pr_as_draft` value sets: ready for review for `false` (the `yes` answer), a draft for `true` (the `draft` answer). This action never creates a commit, asks the user nothing, and never stops the run: every failure is a skipped or incomplete publication with its reason in the closing report.

Load the `to-pr` skill and follow its destination, content and recovery workflow with its § Unattended publication, with the completed change name and an explicit `publish_pr_as_draft` value: the one the caller hands over, or `false` when it hands none, so `/sai-build` publishes a request that is ready for review. Use the same installed `to-pr.js` and provider registry that the skill resolves. The build's commits are already local commits of the branch, so no plan-commit step runs and no ignored file is included: a change artifact the project ignores stays on disk and out of the request.

1. **Destination.** Run `collect`, `resolve` and `destination` as the skill's § Resolve the destination says, without asking: an unresolved provider, an ambiguous remote or target branch, or a destination that needs a question skips the publication and names the missing fact. The target branch is the one `destination` returns for the provider's default branch unless the run was given another. A detached HEAD, missing access, or an unavailable provider skips the publication the same way.
2. **Request content.** Continue the skill with fresh collection against the same destination and branch: the title, the description (every committed change on this branch enters the request, so the description does not claim a request for the build alone), the ratings block, `query` with `publish_pr_as_draft`, and `push-query`. When the caller hands over findings that stay unresolved, the description you write (for a new request, or for an open request you update or mark ready) gains a `## Pending findings` section, headed in the resolved language and placed right before `## Out of Scope / Follow-ups`, so a reviewer of a request that is ready for review sees what the run left: one line per finding with its identifier, title, and reason, under **Pending** for the findings left without a fix (their fix rounds ran out, the fix segment judged them mistaken, or it stopped on them) and under **Excluded** for those whose heading in `review.md` carries ` (EXCLUDED: …)`. With neither, the description has no such section. The unattended publish with `publish_pr_as_draft: false` creates a missing request ready for review, updates an open request, and marks an open draft request ready for review; an open request that is already ready stays ready. With `publish_pr_as_draft: true` it creates a missing request as a draft and updates an open request without changing its state, so a request someone marked ready by hand stays ready. Multiple matches skip the publication; never create a duplicate.
3. **Push and publish.** Run `push --unattended`, then `prepare`, then `publish --unattended` with `publish_pr_as_draft` and the receipt, as the skill's § Unattended publication says. A refusal (`refusal` in the blocked result: `default-branch`, `detached-head`, `not-published`, `request-merged`, `request-closed`) skips the publication; for a merged or closed request, name it from the result's `request`. No force push, no automatic retry of a refused or rejected push, no authentication change or installation. On `uncertain` or `partial_failure`, run `recover` once, which is read-only, and report what it verified; never repeat a creation.
4. **Request state.** The result of `publish` or `recover` carries `publish_pr_as_draft` with `value` and its `status`. When the value is `false`, a `status` of `pending`, a `rejected` or `uncertain` publish whose message says that marking the request ready failed, or a readback that shows the request still as a draft means the request stays a draft: the push and the content update stand, nothing is retried, and the report says that the request stays a draft and gives the reason from the result's message. The build still counts as completed.

Report, in one short paragraph, the branch push, the request URL with the state it published the request in (ready for review, or a draft, and for a draft the caller's count of slices still pending when it handed one), and every warning of the `collect`, `query`, `publish` and `recover` results. When the publication was skipped or ended uncertain, report the completed steps separately from the failed one, keep the completed build and any confirmed push, and say how to continue by hand with `/to-pr` on this same branch; when only the ready state failed, say that the request can be marked ready for review by hand.
