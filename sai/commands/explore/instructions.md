11. **Idea Progress List (sai-explore only)**: The session maintains a chat-scoped idea progress list tracking the explored idea rather than the command's own steps. The list is held in the session: in conversation and, where a native task panel is bound, in the harness's task-panel session state. The session never writes the list to any file, artifact, change directory, or configuration, and its contents are never derived from repository state — no `openspec list --json`, no disk enumeration, no artifact reads. Harness-internal persistence of the harness's own task-panel state is harness session machinery, not a session write, and is out of scope of that prohibition (`specs/explore-idea-list/spec.md` requirement `idea-list-scope-and-state`).

   **Item catalog.** The list holds exactly one research item, created unmarked at the start of the chat, plus per crystallized slice a set of three items — slice-crystallization, reviewed-sai-1, reviewed-sai-2 — added unmarked at that slice's block emission, keyed by its authored `**Change name**`, in the order the slicing assessment (item 4) identified the slices. A crystallized slice is one `**Change name**` value emitted by a crystallization turn (items 5/6): block emission is therefore the first identification of a slice, and the key binds to that slice's items at that moment. A duplicate later identification of a change name already present in the list adds no items, mirroring the tracked crystallized set discipline (item 9). The list contains no implementation item and no other item kind (`idea-list-item-catalog`).

   **Render contract.** Rendering is performed through the per-harness idea-list render binding, which references the per-harness panel-render binding for native-panel availability and mechanics. Panel availability is declared by the panel binding, never determined at runtime. The two supported harnesses (Claude Code and opencode) declare a native task panel, and their bindings render the list on it, replacing plain in-conversation text — the same list state never renders on both surfaces. On the panel, a marked item renders `completed`, a cleared item renders back to `pending`, and the slice's active review item renders `in_progress` while the post-crystallization review loop processes that slice — `in_progress` is carried only by the reviewed-sai-1 and reviewed-sai-2 items (per `idea-list-review-in-progress-state`), never by the research item or a slice-crystallization item. Each item's slice `**Change name**` key rides the machine-readable panel entry field pinned by the binding (opencode `priority`, Claude Code `description`, both carrying the value `sai-idea-list:<change-name>`), while the label keeps the slice's change name, so a slice's items stay visually distinguishable from every other slice's items. A binding that declares no native task panel renders the list as plain in-conversation Markdown checkbox text — `- [ ]` for an unmarked item, `- [~]` for the active in-progress review item, `- [x]` for a marked item — as the declared fallback; no supported harness exercises that branch today, so it is a declared extension point for a future harness, never a runtime-detected path. The panel update originates exclusively from the coordinator session, never from a worker subagent. The list is NOT rendered while it holds only the research item.     **Review-in-progress state.** While the post-crystallization review loop (item 9) processes a change, the slice's active review item renders `in_progress` — the item selected once at loop-processing start as the slice's first review item not marked completed, in fixed order (reviewed-sai-1 first, else reviewed-sai-2; when both are marked completed no item of the slice renders `in_progress`).
