## Goal

Turn the crystallized change document of the first pending slice into implemented, reviewed code, backfilled specs, an archived change, and two local commits, in one session and with no human in the loop. The run is done when the archive worker's execute order returned a clean `completed` result and both commits are confirmed, or when a stop was reported. A human is needed only for force majeure. Selecting the route consented to delegated writes AND pre-authorized exactly two local commits for this slice: the archived change and its change telemetry. It is consent to selection and dispatch only. Never push, except the one publication that a recorded `yes` answer authorizes at Close (**Publication**): the same slice commits stay local until then, and an answer of `no`, no answer, or a caller that supplies none leaves the run pushing nothing.

The workers are `sai-direct-build-worker`, `sai-backfill-worker`, and `sai-archive-worker`. Each runs one role for the whole slice. You read every result before acting on it; a result in another shape, or a report that does not validate, is an obstacle. The route identity is `direct-build-unattended`.

Following `cache-warming.md`, end every task message and continuation to a worker with the warming switch the policy defines. Under `worker-lifecycle.md`, dispose the implementer when Step 5 ends (its last continuation is the decision-record order of Step 5), the backfill worker (worker route only) when Step 6 completes, the archive worker when Step 8 completes (it is created for Step 8 only), a worker whenever a new worker replaces it, each executor after its result, and each explorer of the Step 2 functional fix loop at the latest when Step 2 converges, or at Close in every outcome. An escalation question that waits for the user keeps its worker alive until the answer. The `warming` declaration gates no dispose.

The `--no-specs` POC profile is dispatched by the POC lane, never by this card's route: it runs only Step 1 and Step 2 below, never the suite gate, and spends no attempt, because a POC failure is the experiment's observation (`pipeline-direct-build.md`).

## Start

1. On a new slice, initialize the run state below with every counter at zero (on the explore route its store entry opens at step 3, once the run directory exists). On `{intent: resume-direct-build}`, follow Resume instead.
2. Verify both argument lines against the document file per `@sai/policies/issue-format.md` § Change document (Transport). A missing line, or a file that does not verify, dispatches nothing and escalates at once as force majeure (Obstacles).
3. Open the report directory for the slice per `@sai/policies/worker-report-transport.md` § Receiver boundary and keep its `dir` in the run state. Any failure to open it, such as a missing harness temp root, stops before any dispatch with the verbatim error. Then open the slice's run directory with `node <tool-path> mkdtemp --harness <claude|opencode> --prefix direct-build-{name}-` (`temp-root.js`, resolved per `@sai/policies/tool-resolution.md`) and keep its `dir` in the run state; an `ok: false` result stops before any dispatch with its verbatim `error`. The implementer's scratch folder is the path `scratch-implementer` in the run directory: you only name it, and the worker creates it. While you wait for the result of any worker of this route, follow `@sai/policies/worker-report-transport.md` § Undelivered reports: watch the report directory, ignore a reference you already accepted, and record each reference you process. The implementer's writable paths are the directories of the repository paths the verified document cites (taken without their `:line` ranges), so a new test or module beside a cited file counts as activity, plus its scratch folder: a cited path at the repository root is listed as that file alone, never the root directory, and a cited path whose directory does not exist yet is listed through its nearest existing parent directory below the root, or as the path itself when that parent would be the root (a listed path that does not exist yet is never an error); write them as the JSON array of the watch's `--input-file` in the run directory, and reuse that file for every relaunch of the watch and for a replacement implementer. The backfill worker's writable paths are its transfer directory and the archive worker's are `[]`, each in its own file. The archive worker is created at Step 8, so its watch starts there.
4. Fetch `@sai/orchestration/workers/bindings/direct-build-worker.md` and use it. The creation dispatch carries only the ready prompt; the worker returns `event: ready`, and the task goes to the same worker in the next message (Step 1). A worker that returns no ready is an obstacle.

## Run state

Two modes hold it. On the explore route the identifiers and paths below are also kept in the `sai-state` store as `direct-build-run@1` (**Store** below), so a context compaction or a stop mid-route leaves them readable and a parked slice can rewind to any step whose state is stored; the conversation holds the rest. On `/sai-direct-build`, and on the explore route after a store failure, the conversation holds all of it and nothing is persisted. In both modes this is the single authority for resumption.

- **Identity.** `active_change` (never the document text, which only the document provider holds), the route entries and their accepted completion states, and `pending_step` (Step 1, 2, 2b, or 3–8, including the current check or continuation).
- **Workers.** Each role's captured handle while its work may need continuation: implementer, backfill, archive, and any in-flight verification agent, with its original envelope and the messages it received.
- **Evidence.** The first-seen changed-path union, the fix loop's round files and findings ledger, draft validation evidence, the route of Step 3 (`no-specs` or `worker`), the backfill transfer directory path and the latest draft references (never draft content), suite results, `report_dir`, `run_dir`, and the verification references that justified accepted steps.
- **References and counters.** `base_sha` (HEAD before the initial implementer dispatch), `slice_snapshot` (the initial snapshot reference of `@sai/policies/slice-path-scope.md`), `order_snapshot` (its No-effect check reference for the order in flight), `fix_rounds`, `review_snapshot` (the tree identifier of the latest functional-review pass, per `@sai/policies/incremental-review.md`; lost on a compaction, which makes the next pass a full review), `gate_rounds`, `direct_build_mode` (`prepare` or `execute` for the backfill worker; the archive worker has the execute order only), `validated_execution_order`, `execution_state` (`pending`, `executed`, or `failed`), `direct_build_commit_authorized` with its consumption evidence (the authorized order and the confirmed commit references: the archived change and its change telemetry), and `attempts`, one budget of 3 per step.
- **Window-local guard state.** Retain `guard_base` only within its live window. Apply `@sai/policies/no-commit-guard.md` § Window pairing at every boundary, including a user interruption: close and verify the running window. After the human turn, open a fresh window under that policy before forwarding worker work. `guard_base` is never carried across a boundary. Preserve the immutable slice references `base_sha` and `slice_snapshot` through resumption; a fresh guard snapshot replaces only the window-local baseline, not those slice references.

Only a new slice resets the counters, captures the initial snapshots, starts at Step 1, and receives the two-local-commit grant. No progress plan is declared: the idea progress list owned by explore keeps panel ownership.

**Store.** The explore session holds `direct-build-run@1` beside `explore-slice@1`, under the same session `<id>`; emit to it per `@sai/policies/stage-machine.md` (flags for identifiers, `--set-path` or an input file for a path). It holds identifiers and paths of ONE slice at a time and no free text: `change`, `step` (`step-1` … `step-8`, with `step-2b`), `base_sha`, `slice_snapshot`, `route`, `fix_rounds`, `gate_rounds`, the in-flight `order` with its `order_snapshot` and `order_state`, the checkpointed route items, the consumed orders and grants, each worker handle, and the paths of the report directory, the transfer directory, the evidence files (the first-seen changed-path union, the fix loop's round and ledger files, the draft references and accepted fingerprint, the draft validation evidence), the backfill validation projects, and the confirmed commits. The files stay in the run directory. Emit each event right after the fact it records, before the next dispatch:
- `start` (`dir`, `change`) at Start step 3, once the run directory exists, and then the `record` of the report directory; `record` with `ref` `report-dir`, `transfer-dir`, `evidence`, `project-dir`, or `commit` for each such path as it appears, and `record` with `ref` `worker`, `role` (`implementer`, `backfill`, or `archive`), `handle`, and `reason` (`create`, `replace`, or `resume`) for each worker handle;
- `field` (`field`, `value`) for `base_sha` and `slice_snapshot` at Step 1, `route` (`no-specs` or `worker`) at Step 3, and `fix_rounds` and `gate_rounds` after every round; `step` whenever `pending_step` changes;
- `checkpoint` (`item`) states that a rewind may re-enter that route item from the store: `build-implement` once Step 1's references and the report directory are stored, `backfill` when Step 2b converges and the changed-path evidence is recorded, `archive` when Step 4 accepts the drafts and the route, the transfer directory, and the draft evidence are recorded. The machine refuses a checkpoint whose state is incomplete and answers with what is missing;
- `order` (`order`: `backfill-execute` or `archive-execute`, `snapshot`) immediately before sending an execute order, and `order-result` (`result`: `done` for its clean result, `no-effect` when the No-effect check verified none, `uncertain` when that check is inconclusive or the state is completed, partial, or unknown) once its outcome is read; `consume` (`grant`: `archive-commit` or `telemetry-commit`) for each commit confirmed;
- `attempt`, `escalate`, and `answer` for the obstacles below, and `close` (`completed`, `escalated`, or `stopped`) when the run closes. `status` returns the run view.

A rejected event changes nothing and names what to fix. A failed write (`STORE_WRITE_FAILED`, `STORE_CONFLICT`) or a store that cannot be reached prints one line naming the failure and continues with the whole run state in the conversation; never retry a conflicting write before reading `status`. The store then holds no checkpoint past the last one it accepted, so every rewind past the first step is rejected with `missing: [run-state]`. `/sai-direct-build` emits none of it.

## The run

**No-commit guard windows.** Every dispatch of the run is guarded by `no-commit-guard.md`. The run has three windows. (1) The implementer window opens at the Step 1 snapshot, whose head is recorded as BOTH `base_sha` and the window's `guard_base`, and is verified after the implementer stretch closes (the fix loop converged or its cap exhausted, and the Step 2b suite gate green, skipped, or stopped) and before the Step 3 staging, or before the stop report when the suite gate stops the route. (2) On the worker route, the backfill window opens immediately before the Step 3 prepare dispatch, after the path-scoped staging so that your `git add` runs outside every window, and opens per § Window pairing; it spans the findings and execute continuations and is verified after the Step 6 execute terminal, before you act on it. (3) The archive window is the one of the Step 8 execute continuation: it carries `allow_commit`, opens its own window per the policy's `allow_commit` isolation, and is verified with `--allow-commit`. No archive worker stretch precedes it, because the plan of Step 7 is a tool run. A question inside any window is a human-turn boundary of § Window pairing. On a `violation` verdict, remediate exactly as the policy prescribes, then continue.

**Document provider.** The document provider is the only source of document text. Before each dispatch that consumes the document (Step 1 and Step 3, including a retry or a replacement), obtain the document pair from the provider and send its `--document-file <path>` and `--document-hash <hash>`, never inline text, following `issue-format.md` § Change document (Transport) for verification, amendment refresh, and file lifetime. Explore provides it by exporting from the `sai-state` store with `sai-state block <id> <change-name> --export --harness <claude|opencode>` each time and sending the returned `document_file` and `hash` as the pair. Another caller provides the path of an already verified document file with its hash, and that pair serves every dispatch. The provider also supplies the publication answer: Explore reads it from `explore-slice@1` (`route-selector.md` § Publication question), where the first round 3 of the set recorded it, and another caller supplies none, so the run publishes nothing. Your own readings in Steps 2, 4, and 5 use the verified document file, not the conversation. Execute continuations (Steps 6 and 8) carry validated draft references, not the document.

1. **Implement** — Fetch `@sai/policies/backlog-implementation-start.md` and complete it for this slice before any technical dispatch; for a slice started by `auto_continue` it applies the set's assignment answer from `route-selector.md` without a question, and a question it raises (other assignees, a failed assignment) is asked here and waited on, with its answer or a Retry or Skip continuing this slice and the chain and only Stop ending it. Fetch `@sai/policies/slice-path-scope.md` and take its initial snapshot as `slice_snapshot`. Capture `base_sha` by running the guard's `snapshot` step (the snapshot's head is `base_sha` and the implementer window's `guard_base`), then dispatch the `sai-direct-build-worker` through its binding: the task-disclosure message opens with the `--report-dir <dir>` line, followed by `--direct-build`, `--document-file <path>`, and `--document-hash <hash>` on separate lines, and then a `Scratch folder: <path>` line naming the implementer's scratch folder. The verified file is its ONLY substantive input: no conversation context and no inferred requirement. Accept only closed lifecycle statuses and union the returned `changed_files` first-seen.

2. **Functional fix loop** — Fetch `@sai/policies/incremental-review.md` and follow it for the passes, with `base_sha` as the starting point; the ignored paths the implementer changed go to its snapshots as arguments. The first pass is full: review the resulting diff (`git diff` from `base_sha`) against the document's Capabilities and Edge cases. Every later pass runs the same two checks on the delta since the previous pass's snapshot and on the direct consumers of the code it changed, nothing else. Run both: (a) always a structural check (every capability maps to changed paths; every Edge Case is addressed or explicitly contradicted by a constraint; and the excess-scope check: the diff implements no item listed under the document's `## Out-of-scope implementation notes` and contains no anticipatory implementation, meaning no whole item, stub, hook, "for later" abstraction, or reference whose only purpose is to serve a later slice, and each such occurrence is a finding that requires reverting it); (b) empirical verification that the requested behavior works whenever feasible, by exercising the affected flow through the project's runnable surface (tests, CLI, script, or app) rather than inferring it from the diff. Write every pass to `reviews/implement-round-{k}.md` in the run directory, with each finding's state (`open`, `fixed`, or `scope`) and the snapshot identifier in `reviews/implement-round-{k}.tree`, ending with the line `Summary: High=<n> Medium=<n> Low=<n>`, the base form of `artifact-review-contract.md` § Summary tally, counting the findings whose state in that file is `open`; `k` starts at 1 for the first full pass and increments for every later pass, and the change's telemetry reads its found and pending counts from these files. Write them through the budget executor, because this session gains no direct write tool. Form findings under `@sai/policies/artifact-review-contract.md`; its § Scope observations classifies every observation of this step and of Step 4, and each scope observation is held for the terminal report. A round with open findings continues THE SAME implementer with exactly the ordered open-finding list and increments `fix_rounds`; a `Pre-existing` finding is never sent to the worker and is held for the terminal report; a pass with no open finding converges. After the third fix round, run one final pass over the round-3 delta and its consumers, which only reports: findings it still reports are a non-failure cap exhaustion (E1). Write it as the next round file, emit one line with that pass's exact base-form tally, report it, and continue forward without further rounds. The fix loop is its own loop: its findings are not obstacles and spend no attempt.

   2b. **Suite gate** — mandatory on the full route. Its completion criterion is binary: **green** (continue) or **stop**. It is a substep of `Build/Implement`, not a new step or panel entry.
   - **Suite run.** Dispatch an executor subagent through the loaded budget executor binding, opening with its `ready` handshake, with the task "run the project's full test suite" and an output contract of exactly: the chosen command, whether it ran, the exit code, and the identifiers of the failing tests. The executor never moves HEAD and never touches the working tree beyond running the suite.
   - **Green.** The suite ran and no test failed: continue to Step 3.
   - **No suite.** The executor finds no test suite: print exactly `> Suite gate: skipped — no test suite found` and continue to Step 3.
   - **Cannot run.** The command fails before running any test (missing dependencies, broken environment, runner error): stop, reporting the command and the error.
   - **First red: classification.** On the first red run only, and before any gate round, dispatch a second executor (same binding, same `ready` handshake) that runs only the failing tests at `base_sha` in a temporary detached `git worktree` created outside the working tree, and removes it when done, even when the check fails. It returns each test as `pass`, `fail`, or `unrunnable`. `fail` is a pre-existing failure: reported in `Verification`, never sent to the implementer, never blocking. `pass` and `unrunnable` are new failures, and when in doubt they block. HEAD and the working tree stay untouched, so the guard sees no movement. When every red test is pre-existing, no gate round runs and the route continues to Step 3.
   - **Gate round.** One gate round is one continuation of THE SAME implementer with the new failures as an ordered finding list, plus one suite rerun through a fresh executor dispatch; increment `gate_rounds`. A test that fails for the first time in a later round is a new failure directly, with no `base_sha` check, because it already passed with the change. A gate round never reopens the Step 2 review and never touches `fix_rounds`. Record every test file the implementer touched in a gate round for `Verification`.
   - **Stop** — new failures remaining after the third completed gate round, or a suite that cannot run, stop the route at the terminal suite gate: the command and the failure are reported, nothing after the gate is run or marked, and Steps 3–8 do not run (no backfill, archive, or commit); verify guard window 1; the changes stay unstaged in the working tree. The gate rounds are this step's attempts, so its budget is spent and the stop escalates: the report is the shared stopped Direct Build terminal report below (What you need to know states the run is incomplete and names the verification limitation; Execution details lists the red tests), and the options follow it as a separate decision prompt. The slice is marked failed and stays retryable, and a retry runs the suite gate afresh; no later slice starts.

   When the gate is green or skipped, `Build/Implement` converges: explore completes that route item (`pipeline-direct-build.md`).

3. **Sibling backfill preparation** — stage exactly the implementer's owned paths (path-scoped `git add`; unrelated dirty files never enter) and open the transfer directory (**Transfer directory** below). **Route choice.** Then run `node <tool-path> compose --document-file <path> --document-hash <hash> --change-name <name> --transfer-dir <dir> --cwd <project-root>` (`backfill-no-specs.js`, resolved per `@sai/policies/tool-resolution.md`), which reads the document's own `Backlog origin:` and `Explore origin:` lines itself (add `--backlog-origin` only to carry the valid `backlog_origin` of an existing change's `.openspec.yaml`, which the issue-origin policy preserves). It answers `eligible: true` only for a document that declares `Specs: none — <reason>` in `## Change` while `openspec/changes/{name}/specs/` holds no file; the **no-specs route** (last paragraph of this step) then applies, and every other answer takes the **worker route**, which is the rest of this step. A compose error is an obstacle of `step-3`. **Worker route.** Dispatch the EXISTING `sai-backfill-worker` through its existing binding and Direct Build (unattended) prepare route with `arguments_value` beginning `--direct-build-prepare`, then `--document-file <path>` and `--document-hash <hash>` lines from the document provider, then `--fast-track --staged`. The verified file supplies the complete document; no document text travels in the message. Fetch `@sai/orchestration/workers/bindings/backfill-worker.md` and use it before this dispatch. The dispatch requests the backfill worker to compose the draft set including `openspec/changes/{name}/.openspec.yaml` in the canonical form specified at `sai/commands/backfill/instructions.md` section 6a, in addition to `proposal.md` and capability specs. Interview asks resolve through the grounded auto-answer-or-escalate rule: the same qualitative confidence threshold, ambiguity resolving toward escalation, permitted grounding extended only by this run's document, fix-loop findings, staged diff summary, and captured `base_sha`: the diff-source ask resolves to the staged-changes option grounded in `base_sha`; Question 1 grounds in the document's Goal and Problem; Question 2 grounds in the fix-loop findings; anything ungrounded escalates unchanged. A foreign-spec conflict auto-proceeds per the delta-sync/fast-track precedent (E2), reported as a notice. Preparation performs no draft write into the repository. **Transfer directory:** before the prepare dispatch, resolve `transfer.js` per `@sai/policies/tool-resolution.md` and run `node <tool-path> open --harness <claude|opencode>`, keeping the returned `dir` in the run state (exit 2, such as a missing harness temp root, stops the route before any dispatch and any final write, reported with the verbatim error). Carry it to the worker only in the task-disclosure continuation as `--transfer-dir <dir>` after the outermost `--report-dir` line and before the envelope above, never in the initial dispatch. The worker hands each draft over as a reference `{path, sha256, destination}` to a transfer file in that directory (`sai/commands/backfill/worker.md` § Draft transfer); drafts never travel as message text on any continuation, replacement, or execute order, and a corrected result supersedes every earlier reference. Keep the directory through archive and any unresolved validation or recovery; cleanup follows `@sai/policies/worker-report-transport.md`. This draft directory is separate from report storage and the stored-document export directories, whose lifetime follows the change document transport policy.

   **No-specs route.** When `compose` answered `eligible: true`, no backfill worker is created or bound, no backfill window opens, and no prepare dispatch happens: its `draft_references` (`.openspec.yaml` and `proposal.md`, written with `transfer.js put` into the transfer directory) are the draft set, and its `warnings` are reported as notices; a lost or unverifiable origin warns without blocking. The tool derives both drafts from the verified document alone, so a correction round has nothing to change.

4. **Spec review** — explore runs `transfer.js verify` on every returned reference (a failure, a path outside the directory, or a duplicate or non-allow-listed destination returns to the same worker as a corrected-result request, with no execute order) and then validates the draft content read from those transfer files read-only against `openspec/schemas/sai-workflow/schema.yaml` (pure reading, the validation/writer split: explore writes nothing) and accepts `openspec/changes/{name}/.openspec.yaml` as part of the returned draft set, validating it against the canonical forms of `sai/commands/backfill/instructions.md` section 6a rather than against the capability schema: the three-key form (`schema`, `created` as a YYYY-MM-DD date only, `backfilled: true`) for a run with no usable intent context, and the four-key form (those three plus `prior_intent: true`) for a run with usable intent context. Either form validates under its own condition; both allow the optional validated `backlog_origin` and `explore_origin` of section 6a and, when the document declares `Specs: none — <reason>` in `## Change` and `specs/` holds no file, the optional `skip_specs: true` (a no-specs draft set carries no capability spec), and no other key. Compare that value with the document's selected origin; a known lost or unverifiable origin warns without blocking the remaining work. It reviews the drafts against the document under `@sai/policies/artifact-review-contract.md`, and continues any findings once to the SAME backfill worker within the remaining `fix_rounds` budget; schema-invalid or still-failing drafts are an obstacle of `step-4`.
   **No-specs route.** On this route the paragraph above applies to the two generated drafts only: run its `transfer.js verify` check, its read-only schema review of the draft content (the `.openspec.yaml` against the four-key form plus `skip_specs: true`), and the mandatory `validate-backfill-drafts.js validate` of the paragraph below, with no scenario-preservation check, no review round, and no correction request: a draft set that fails any of them is an obstacle of `step-4` that escalates under `@sai/policies/obstacle-escalation.md` and writes nothing to the repository, because the tool would repeat its output. `openspec-cli-unavailable` stays force majeure. When the drafts are accepted, retain the accepted fingerprint and the references in the run state, and the `Backfill` route item converges here.

   MODIFIED-delta completeness: Fetch `@sai/policies/scenario-preservation.md` and apply its receiver boundary to the temporary drafts before accepting them. Run the shared checker and route missing scenarios as High completeness findings to the same backfill worker. A failed or incomplete comparison cannot be accepted through review-round cap exhaustion. Fetch `@sai/policies/backfill-draft-validation.md` and perform its mandatory receiver-side OpenSpec CLI validation on the complete draft set. Retain its accepted fingerprint and diagnostics in run state; rejection or incomplete validation authorizes no write and returns the diagnostic to the same worker for correction, except the distinct validation reason `openspec-cli-unavailable`: it is force majeure that escalates at once under `@sai/policies/obstacle-escalation.md`, requests no correction from the worker, spends no `step-4` attempt, and wins even when the drafts are also invalid. Repeat all checks for corrected drafts, including archive-failure corrections.

5. **ADR/DDR pass** — fetch `@sai/policies/adr-ddr-criteria.md` and run its ordered routing test over the document's Decisions; never offer a choice. When `adr|ddr` resolves for at least one decision, Fetch `@sai/policies/decision-record-creation.md` and prepare its order: the inventory and numbers through the executor, the already-cited check, and the `git check-ignore` check of each record and index path. Then continue THE SAME implementer with exactly that order. It writes the records and their index entries, creates a missing folder or index, and returns the closed lifecycle result; the paths it reports join the first-seen changed-path union of Step 1, minus the ignored ones, which stay on disk and are reported. The records enter the route's change commit through the implementer path set of Steps 7 and 8. The pass adds no commit, and the backfill artifact set gains no record: that set is restricted to the schema-validated OpenSpec drafts plus the `.openspec.yaml` metadata file in the canonical form specified at `sai/commands/backfill/instructions.md` section 6a. Record the resolved family, the records written, and the pass outcome in one line and proceed. When no decision qualifies, say so in that line, order nothing, and leave the indexes untouched.

6. **Backfill execution** — on the no-specs route there is no backfill worker, so no order goes out and nothing is written here: the references and the accepted fingerprint pass to Step 7 and the archive worker writes them in its execute order. On the worker route: after the schema validation, successful receiver-side CLI validation, and ADR/DDR decisions above, run the accepted-fingerprint freshness check of `backfill-draft-validation.md` before authorizing any writes. A mismatch requires repeated receiver validation. Take the `order_snapshot`, then generate the order with `node <tool-path> order --input-file <path>` (`validate-backfill-drafts.js`, resolved per `@sai/policies/tool-resolution.md`; the input file holds the change name, the accepted fingerprint, the validated `draft_references`, and the worker's latest `prepared_references`) and continue the SAME `sai-backfill-worker` with exactly its output as the one `--direct-build-execute` closed order containing the validated draft references (`{path, sha256, destination}`, never content) and accepted validation fingerprint, including the reference whose destination is `openspec/changes/{name}/.openspec.yaml`; `sai/commands/backfill/worker.md` § Direct Build (unattended) execution continuation defines its format. References that do not match the worker's latest prepared set produce no order, and that failure is an obstacle of `step-6`. This continuation is the coordinator's explicit execution authorization; the worker repeats the fingerprint check before its first write, verifies each reference and materializes it byte-for-byte to its destination, and writes nothing else. It stops before archive preparation. Keep the transfer directory through archive for corrections, then close it at terminal cleanup as described under Step 3. When it returns a clean result, `Backfill` converges.

7. **Archive preparation** — a computation, so no worker computes it: run `node <tool-path> plan <change-name> --json --cwd <project-root> --implementer-paths-file <path>` (`archive-plan.js`, resolved per `@sai/policies/tool-resolution.md`) yourself, as `@sai/commands/archive/instructions.md` describes. The path file is the first-seen changed-path union of Step 1, deletions included, one repository-relative path per line, kept in the run directory. A path set missing from run state (for example, after a compaction) stops the route before the tool runs and escalates under `@sai/policies/obstacle-escalation.md`; never rebuild it from the git index. On the no-specs route the call adds `--drafts-dir <transfer directory>` (the transfer directory holds the draft `.openspec.yaml` and `proposal.md` under those names), because the change directory holds none of its files yet; the tool reads the drafts in their place, and its covering list includes the change directory that holds both draft destinations. The plan is the closed archive plan: the CORE gate verdict, the AUDIT line, the delta-sync summary, the retired capabilities and the retirement declaration, the date-prefixed destination and its collision verdict, the affected main specs, the owned staging paths, the already staged deletions, the omitted ignored paths, and the lines of the commit message (the closing line and the retirement lines). A refusal (exit 1: the CORE stop literal, a collision, a dropped scenario, a declaration refusal, an unreadable `.openspec.yaml`) is a planned stop, not an obstacle: print its `summary` verbatim, stop the route with no dispatch and no mutation, and verify guard window 1 first if it is still open. A tool failure (exit 2) is an obstacle of `step-7`. Print the plan's `report_lines` as notices. This is the read-only pre-flight, a tool run with no archive worker and no archive window.

   7b. **Prepare-time coverage check** — after the plan is read and before any execute order, run the `verify` check of `@sai/policies/slice-path-scope.md` § Commit coverage with `slice_snapshot`, the slice paths of Step 8, and the plan's `covering_paths` as the covering list. An empty `uncovered` continues to Step 8. A non-empty `uncovered` sends no execute order and a gap in the plan is not patched by hand: it names a path the plan does not own, so compute the plan again (a path file that lacks a path is the usual cause, and a path set missing from run state follows Step 7), spend one `step-7` attempt per repetition, and repeat this check on the new plan. An exhausted budget escalates under `@sai/policies/obstacle-escalation.md`.

8. **Archive execution and pre-authorized commit** — after coordinator validation, gate resolution, and the commit-authorization state are all present, and the plan covers the slice per `@sai/policies/slice-path-scope.md` § Commit coverage (slice paths: the implementer's unioned changed paths, the backfill-written draft paths, and the plan's archive destination and synced main specs), compute the plan again with the same inputs right before the order (a clock or index change since Step 7 changes it: the order is built from the new plan, and the new plan repeats the Step 7b check), apply the independent archive-boundary check of `scenario-preservation.md` (the plan's `scenario-dropped` refusal is that check), take the `order_snapshot`, then Fetch `@sai/orchestration/workers/bindings/archive-worker.md` and use it. The creation dispatch carries only the ready prompt, and a worker that returns no ready is an obstacle. After its ready, continue the SAME `sai-archive-worker` with exactly one `--direct-build-execute` closed order, in the format `sai/commands/archive/worker.md` defines: the change name, the plan's `plan_fingerprint`, the implementer paths (the path set of Step 7, one per line, under the `--implementer-paths` marker line), and on the no-specs route a `--drafts` marker line and the draft section printed by `node <tool-path> order --target archive --input-file <path>` (`validate-backfill-drafts.js`: the input of Step 6 plus `transfer_dir`, with the compose output as both `draft_references` and `prepared_references`), once the fingerprint freshness check of `backfill-draft-validation.md` has held. The task-disclosure message opens with `--report-dir <dir>`. On the no-specs route both draft destinations are among the order's target paths for the `order_snapshot`. The order carries no path or action beyond those lines: the worker recomputes the plan from them, rejects the order when its fingerprint differs from the order's (executing nothing), materializes the drafts before `openspec archive`, runs `openspec archive <name> --yes --json` as the sole sync + move primitive, stages only the plan's OWNED paths (reconstructed artifacts, synced main specs, and the implementer's unioned changed paths — unrelated dirty files never enter the commit, E4; an implementer deletion that is already staged is not added again and stays in the commit), authors the commit message from staged state under `@sai/policies/commit-rules.md`, adds the plan's retirement lines and closing line, and passes the message literally on standard input to `git commit -F -` under `@sai/policies/command-execution.md`; never push, amend, retry, or add an action outside the order. The worker's plan check stops the order on a changed fingerprint before any mutation, and a changed fingerprint or a failed materialization stops before archive and commit, with any file already written left uncommitted and named in the terminal report. A path set missing from run state stops the route before this continuation and escalates under `@sai/policies/obstacle-escalation.md`. A clean terminal `completed` makes `Archive` converge and consumes the order and the archive-commit grant.

**Execute orders.** Take the `order_snapshot` immediately before sending any execute order, and record it with `order` first. When one fails, first restore any pending foreign index entries under `@sai/policies/foreign-index-preservation.md` § Recovery (a restore that stops ends recovery and is reported), then run the No-effect check of `slice-path-scope.md`. With no effect verified, the step is an obstacle like any other, and a new order goes to its owner after a different correction. A completed, partial, or unknown state issues no order: it is force majeure. A delivery or validation failure after independently confirmed operations is a pending report check, not a failed order: recover the report of the existing effects and never replay the order. A confirmed archive move or commit stays confirmed, and a consumed order or commit grant is never renewed. A late continuation after success is rejected without mutation.

## Resume

On `{intent: resume-direct-build}`, take the parked stage `explore-slice@1` returns and reuse that slice's run state: on the explore route emit `resume` (`change`) to `direct-build-run@1`, which reopens the parked run (stopped, escalated, or interrupted) with its counters, attempts, and handles, and rebuild the run state above from the `run` view of its response and the files it names, asking the user nothing that the store already holds. Continue at the stored pending step. A rejected `resume` (`no run state for that change`), or a store that cannot be read, leaves the conversation as the only holder: use it while it still holds the run state. Steps 1–2b belong to `build-implement`, Steps 3–6 to `backfill`, and Steps 7–8 to `archive`. A missing handle history, counter, authorization state, or verification reference that the pending operation needs keeps the route stopped and names what is missing, and the stop names its exit: a slice that never dispatched has no run state to resume, so the pending-execution branch of `route-selector.md` offers `goto` to pending or to the first step in place of a stop with no way out. A `goto` to a later item (`backfill` or `archive`) is accepted only when the store holds that item's checkpoint, and the store then keeps the checkpoints up to that item with `step` at its first step: resume it as above, rebuild the state of the items after it, and never renew a consumed order or commit grant or replay an execute order whose effect is uncertain (`GOTO_ORDER_CONSUMED` and `GOTO_ORDER_UNCERTAIN` refuse such a rewind). After a `goto` to the first step the store holds no run state: initialize the run state as for a new slice, with every counter at zero and `base_sha` taken from the current working tree at the implementer dispatch: files an earlier run wrote stay and nothing is reverted. A stage mismatch is reconciled from accepted checks before any work, never by initializing a new run.

1. Recheck the evidence of accepted steps against the current repository state. Preserve accepted work whose evidence still holds, review the work whose evidence changed, and keep counters and scope. Enter at the first pending internal step, not at Step 1 merely because this card loaded again. A completed worker stretch alone does not accept a step: acceptance takes a validated report and all that step's checks. Update `pending_step` only after acceptance, and converge a route item only when all its checks passed.
2. For pending worker work, continue the retained handle first. Each step continues its own role and never starts a new implementer for backfill or archive. A new worker (an obstacle approach) gets the hand-over of Obstacles below and the ready handshake.
3. Deliver every report to the validator exactly as received; never rewrite or re-serialize it. On an invalid report, preserve existing changes, keep the step pending, and ask the authoring worker for a fresh valid report as an obstacle of that step. Accept no status or changed-path claim from rejected output. At an exhausted budget, keep the step pending and report the cause; a resume choice alone does not reopen any budget.
4. Before resuming an uncertain execute operation, run the No-effect check with the retained `order_snapshot`. If the authorized commit is confirmed to have occurred, record its reference and consumption once, and accept route closure only when the archive result and the remaining checks are accepted. If it is confirmed absent, continue only the pending work the no-effect check permits; the absence of a commit does not authorize replay of a partially applied archive order. An inconclusive check keeps execution stopped. A consumed order or commit grant is never renewed by resumption; never push.

Resumption preserves every value above and grants no extra attempt or authorization.

## Obstacles

Obstacles, their budget of 3 attempts, force majeure, and escalation follow `@sai/policies/obstacle-escalation.md`. Keep the attempts in the run state, one budget per step, named by the step it blocks (`step-1`, `step-2`, `step-2b`, `step-3` through `step-8`). A step's attempts never draw on another step's budget, they persist across a same-slice resume, and a review round, a question answer, a continuation, a replacement, and a step transition leave them as they are. An obstacle here is a non-clean outcome after dispatch: a worker that returns no ready, an unreadable or invalid report, a silent or drifting worker, a valid `failed` or `cancelled` result, a draft set that still fails Step 4, a failing tool (`transfer.js`, `sai-state`, the CLI archive), or a failed step check. The three gate rounds of Step 2b are that step's attempts. `failure_class` and `unrecoverable` are evidence for the response, never an eligibility gate.

A correction is steered by the failed step's check and by three invariants that hold for every attempt: agreed content (Goal, Problem, Edge cases, Implementation notes, scope) passes through unchanged; writes land only on the slice paths; and the step sequence stays as planned, skipping nothing. After each attempt, run the foreign-change check of `slice-path-scope.md` § Foreign changes, and run the failed step again through its owner before anything advances.

Force majeure, which escalates at once without spending an attempt, also covers: an argument line that is missing or a document file that does not verify; `BLOCK_NOT_FOUND` or `BLOCK_EXPORT_FAILED` at an export (dispatch nothing; the options offer retrying the export and re-emitting the document with `--amend` for one pending or stopped slice); a correction that needs a change to the Goal, the Problem, or the Edge cases; a `foreign` path after an attempt (report the exact paths and revert nothing); an execute order left in a completed, partial, or unknown state; and any push other than the publication of Close, deletion of files foreign to the slice, or shared-infrastructure change.

A stop reports the exact draft paths written or the exact CLI, staging, and commit state, and a partial plan is never committed. A stopped slice carries no finality: new retries or changes run only at explicit user request, and the manual `/sai-backfill`, `/sai-archive`, and `/sai-commit` guidance is reported where it applies. Preserve the report and draft evidence at a non-clean closure per the report transport; a helper that is unavailable or denied has no inline-content fallback.

A new worker receives a hand-over written by you: the change name, the role and step, the retained references (never draft content and never the old worker's history), the validated closed order and its execution state when there is one, the findings already sent, and the symptom. It starts again from the ready handshake and never replays an executed order.

## Close

The run closes when the goal is met, when a stop was reported, or when the user chose to stop or dismissed an escalation.

**Run state.** Emit `close` to the store when the run closes, in every outcome; a closed run stays readable for its report and for a rewind or resume, and a new slice, a discard, or the next invocation's reset clears it.

**Change telemetry.** When the archive worker returned a clean `completed` result, record the change telemetry as `change-telemetry.md` says, with `--command sai-explore-direct-build`, `--status completed`, and `--run-dir <run directory>`, then make its local commit. Its outcome changes neither the route outcome nor the transition; a skipped collection adds its one line to the report. A run that stopped before that result records nothing.

**Publication.** After the telemetry commit (or, when its collection was skipped, right after the archive worker's clean result) and before the slice transition, publish when the answer of the set is `yes`: Explore reads it from the `publication` field of the `run` view of `explore-slice@1` (`node <tool-path> emit <id> explore-slice@1 --set intent=publication` returns it and records nothing); a document provider that supplies no answer means `no`, and so does a set whose publication `route-selector.md` § Branch creation point withholds. A run that stopped before the archive worker's clean `completed` result, with the archive commit unconfirmed, publishes nothing, whatever the answer. Otherwise Fetch `@sai/commands/build/publication.md` and follow it with the archived change's name: the answer is the held confirmation it names, in the place of the build's publication answer, and the run's route grant carries it, so nothing is asked. The push and the request are coordinator operations after the guard windows, never the archive worker's, whose order keeps its no-push rule, and the publication creates no commit. Its failures and refusals (a skipped destination, a refused push, a request that stays a draft) are reported and never stop the slice, the slice transition, or the chain of slices. An answer of `no` and a missing answer run nothing.

Explore then applies the slice transition of `pipeline-direct-build.md`. Before the report, dispose every worker and helper still alive under `worker-lifecycle.md` in one same-turn batch, in every outcome. A resumed slice continues the retained handle when it still answers, or creates a new worker with the hand-over of Obstacles. Close with the Direct Build terminal report, following `@sai/policies/implementation-closing-report.md` as the single format authority; reporting changes no completion or authorization rule.

- **What you need to know** — summarize the material repository changes; on success, name the archive destination and the local commit references (short SHA and subject for the archived change and for its change telemetry), and state the publication outcome: the request URL with its verified ready or draft state after a publication, the skip or failure reason when the answer was `yes` and the publication was skipped, refused, or incomplete (with the confirmed push, when there is one), and `Nothing was pushed.` when the answer was `no`, when none was recorded, or when no publication ran. If archiving or the commit did not complete, state what completed and what remains; use the stopped status. Include every relevant verification limitation, pre-existing or new failure, and incident with its known effect here so the reader can stop before the technical record.
- **Next step** — retain the outcome-appropriate navigation and retry guidance. After an escalation, the options of `@sai/policies/obstacle-escalation.md` follow after `Execution details` as a separate question, not as another report section. Cancellation and a stop the user chose get no options.
- **Execution details** — preserve the work and commit record, original tool-generated commit reports, and these route-owned diagnostic records:
  - **Verification** — always state the Step 2b suite-gate command and its observed result (green, red with the failing tests, cannot run with the error, or `no test suite found`); distinguish test failures known before this run from failures introduced or worsened by it by listing the pre-existing failures classified at `base_sha`; and list every test file the implementer touched in a gate round. A pre-existing test failure is a verification limitation, not an incident. Say `No known verification issues.` only when the suite gate ran green, no pre-existing failure was found, and no test file was touched in a gate round.
  - **Incidents** — briefly name each run-caused execution problem or contract violation and its known effect, even when the functional result is correct. Name the violated rule for a contract violation. If an expected generated file is excluded from the commit, name it and the reason. Say `None` only when no incident is known.
  - **Pre-existing findings** — every `Pre-existing` finding of the functional fix loop, one line each with its location and issue. Omit this record when there is none.
  - **Scope observations** — every scope observation of this run, in the line form of `@sai/policies/artifact-review-contract.md` § Scope observations. Omit this record when there is none.

Omit routine rounds without findings, cap tallies, checks without alerts, automatic answers that caused no problems, other execution telemetry, and verbatim worker summaries. For autonomy-audit display, follow the Direct Build - Unattended final-report exception in `sai/policies/autonomy-audit-log.md`. After accepted route closure, with no continuation or recovery that still needs them, close the report directory with `transfer.js close`; remove the run directory with `temp-root.js remove --harness <claude|opencode> --dir <run directory>`; close the transfer directory at the same point, and remove the temporary backfill validation projects (each `project_dir` retained in run state) with `temp-root.js remove --harness <claude|opencode> --dir <project_dir>`, resolved per `@sai/policies/tool-resolution.md`. These closes and removals are independent: issue them in one same-turn batch, as `worker-lifecycle.md` § Same-turn batch says. A failed or escalated closure keeps them as evidence.
