## Goal

Turn the crystallized block of the first pending slice into implemented, reviewed code, backfilled specs, an archived change, and one local commit, in one session and with no human in the loop. The run is done when the archive worker's execute order returned a clean `completed` result and the commit is confirmed, or when a stop was reported. A human is needed only for force majeure. Selecting the route consented to delegated writes AND pre-authorized exactly one local commit for this slice; it is consent to selection and dispatch only. Never push.

The workers are `sai-direct-build-worker`, `sai-backfill-worker`, and `sai-archive-worker`. Each runs one role for the whole slice. You read every result before acting on it; a result in another shape, or a report that does not validate, is an obstacle. The route identity is `direct-build-unattended`.

Following `cache-warming.md`, resolve each worker's timings at every message to it and end the message with the warming line the policy defines. Dispose the implementer when Step 2b ends and the backfill worker when Step 6 completes, a worker whenever a new worker replaces it, and the archive worker and every worker still armed at Close. An escalation question that waits for the user keeps its worker armed until the answer. An executor is disposed as soon as its result is read.

The `--no-specs` POC profile is dispatched by the POC lane, never by this card's route: it runs only Step 1 and Step 2 below, never the suite gate, and spends no attempt, because a POC failure is the experiment's observation (`pipeline-direct-build.md`).

## Start

1. On a new slice, initialize the run state below with every counter at zero. On `{intent: resume-direct-build}`, follow Resume instead.
2. Verify both argument lines against the stored block per `@sai/policies/ready-to-propose-format.md` § Stored block transport. A missing line, or a file that does not verify, dispatches nothing and escalates at once as force majeure (Obstacles).
3. Open the report directory for the slice per `@sai/policies/direct-build-report-transport.md` § Receiver boundary and keep its `dir` in the run state. Any failure to open it, such as a missing harness temp root, stops before any dispatch with the verbatim error.
4. Fetch @sai/orchestration/workers/bindings/direct-build-worker.md and use it. The creation dispatch carries only the ready prompt; the worker returns `event: ready`, and the task goes to the same worker in the next message (Step 1). A worker that returns no ready is an obstacle.

## Run state

Conversation-only, never persisted. This is the single authority for same-conversation resumption.

- **Identity.** `active_change` (never the block text, which only the store holds), the route entries and their accepted completion states, and `pending_step` (Step 1, 2, 2b, or 3–8, including the current check or continuation).
- **Workers.** Each role's captured handle while its work may need continuation: implementer, backfill, archive, and any in-flight verification agent, with its original envelope and the messages it received.
- **Evidence.** The first-seen changed-path union, the fix loop's findings ledger, draft validation evidence, the backfill transfer directory path and the latest draft references (never draft content), suite results, `report_dir` and the verification references that justified accepted steps.
- **References and counters.** `base_sha` (HEAD before the initial implementer dispatch), `slice_snapshot` (the initial snapshot reference of `@sai/policies/slice-path-scope.md`), `order_snapshot` (its No-effect check reference for the order in flight), `fix_rounds`, `review_snapshot` (the tree identifier of the latest functional-review pass, per `@sai/policies/incremental-review.md`; lost on a compaction, which makes the next pass a full review), `gate_rounds`, `direct_build_mode` (`prepare` or `execute` for backfill and archive), `validated_execution_order`, `execution_state` (`pending`, `executed`, or `failed`), `direct_build_commit_authorized` with its consumption evidence (the authorized order and the confirmed commit reference), and `attempts`, one budget of 3 per step.
- **Window-local guard state.** Retain `guard_base` only within its live window. Apply `@sai/policies/no-commit-guard.md` § Window pairing at every boundary, including a user interruption: close and verify the running window. After the human turn, open a fresh window under that policy before forwarding worker work. `guard_base` is never carried across a boundary. Preserve the immutable slice references `base_sha` and `slice_snapshot` through resumption; a fresh guard snapshot replaces only the window-local baseline, not those slice references.

Only a new slice resets the counters, captures the initial snapshots, starts at Step 1, and receives the one local-commit grant. No progress plan is declared: the idea progress list owned by explore keeps panel ownership.

## The run

**No-commit guard windows.** Every dispatch of the run is guarded by `no-commit-guard.md`. The run has three windows. (1) The implementer window opens at the Step 1 snapshot, whose head is recorded as BOTH `base_sha` and the window's `guard_base`, and is verified after the implementer stretch closes (the fix loop converged or its cap exhausted, and the Step 2b suite gate green, skipped, or stopped) and before the Step 3 staging, or before the stop report when the suite gate stops the route. (2) The backfill window opens at a fresh snapshot immediately before the Step 3 prepare dispatch, taken after the path-scoped staging so that your `git add` runs outside every window; it spans the findings and execute continuations and is verified after the Step 6 execute terminal, before you act on it. (3) The archive window opens at a fresh snapshot immediately before the Step 7 prepare dispatch and closes immediately before the Step 8 execute continuation; that continuation carries `allow_commit`, opens its own window per the policy's `allow_commit` isolation, and is verified with `--allow-commit`. A question inside any window is a human-turn boundary of § Window pairing. On a `violation` verdict, remediate exactly as the policy prescribes, then continue.

**Stored block.** The `sai-state` store is the only source of block text. Before each dispatch that consumes it (Step 1 and Step 3, including a retry or a replacement), export it again with `sai-state block <id> <change-name> --export --harness <claude|opencode>` and send the paired `--block-file <block_file>` and `--block-hash <hash>`, never inline text, following `ready-to-propose-format.md` § Stored block transport for verification, amendment refresh, and file lifetime. Your own readings in Steps 2, 4, and 5 use the stored block, not the conversation. Execute continuations (Steps 6 and 8) carry validated draft references, not the block.

1. **Implement** — Fetch @sai/policies/backlog-implementation-start.md and complete it for this slice before any technical dispatch; for a slice started by `auto_continue` it applies the set's assignment answer from `route-selector.md` without a question, and a question it raises (other assignees, a failed assignment) is asked here and waited on, with its answer or a Retry or Skip continuing this slice and the chain and only Stop ending it. Fetch @sai/policies/slice-path-scope.md and take its initial snapshot as `slice_snapshot`. Capture `base_sha` by running the guard's `snapshot` step (the snapshot's head is `base_sha` and the implementer window's `guard_base`), then dispatch the `sai-direct-build-worker` through its binding: the task-disclosure message opens with the `--report-dir <dir>` line, followed by `--direct-build`, `--block-file <path>`, and `--block-hash <hash>` on separate lines. The verified file is its ONLY substantive input: no conversation context and no inferred requirement. Accept only closed lifecycle statuses and union the returned `changed_files` first-seen.

2. **Functional fix loop** — Fetch @sai/policies/incremental-review.md and follow it for the passes, with `base_sha` as the starting point; the ignored paths the implementer changed go to its snapshots as arguments. The first pass is full: review the resulting diff (`git diff` from `base_sha`) against the block's Capabilities and Edge Cases. Every later pass runs the same two checks on the delta since the previous pass's snapshot and on the direct consumers of the code it changed, nothing else. Run both: (a) always a structural check (every capability maps to changed paths; every Edge Case is addressed or explicitly contradicted by a constraint; and the excess-scope check: the diff implements no item listed under the block's `**Out of scope Implementation Details**` and contains no anticipatory implementation, meaning no whole item, stub, hook, "for later" abstraction, or reference whose only purpose is to serve a later slice, and each such occurrence is a finding that requires reverting it); (b) empirical verification that the requested behavior works whenever feasible, by exercising the affected flow through the project's runnable surface (tests, CLI, script, or app) rather than inferring it from the diff. Form findings under `@sai/policies/artifact-review-contract.md`; its § Scope observations classifies every observation of this step and of Step 4, and each scope observation is held for the terminal report. A round with open findings continues THE SAME implementer with exactly the ordered open-finding list and increments `fix_rounds`; a `Pre-existing` finding is never sent to the worker and is held for the terminal report; a pass with no open finding converges. After the third fix round, run one final pass over the round-3 delta and its consumers, which only reports: findings it still reports are a non-failure cap exhaustion (E1). Emit one line with that pass's exact base-form tally, report it, and continue forward without further rounds. The fix loop is its own loop: its findings are not obstacles and spend no attempt.

   2b. **Suite gate** — mandatory on the full route. Its completion criterion is binary: **green** (continue) or **stop**. It is a substep of `Build/Implement`, not a new step or panel entry.
   - **Suite run.** Dispatch an executor subagent through the loaded budget executor binding, opening with its `ready` handshake, with the task "run the project's full test suite" and an output contract of exactly: the chosen command, whether it ran, the exit code, and the identifiers of the failing tests. The executor never moves HEAD and never touches the working tree beyond running the suite.
   - **Green.** The suite ran and no test failed: continue to Step 3.
   - **No suite.** The executor finds no test suite: print exactly `> Suite gate: skipped — no test suite found` and continue to Step 3.
   - **Cannot run.** The command fails before running any test (missing dependencies, broken environment, runner error): stop, reporting the command and the error.
   - **First red: classification.** On the first red run only, and before any gate round, dispatch a second executor (same binding, same `ready` handshake) that runs only the failing tests at `base_sha` in a temporary detached `git worktree` created outside the working tree, and removes it when done, even when the check fails. It returns each test as `pass`, `fail`, or `unrunnable`. `fail` is a pre-existing failure: reported in `Verification`, never sent to the implementer, never blocking. `pass` and `unrunnable` are new failures, and when in doubt they block. HEAD and the working tree stay untouched, so the guard sees no movement. When every red test is pre-existing, no gate round runs and the route continues to Step 3.
   - **Gate round.** One gate round is one continuation of THE SAME implementer with the new failures as an ordered finding list, plus one suite rerun through a fresh executor dispatch; increment `gate_rounds`. A test that fails for the first time in a later round is a new failure directly, with no `base_sha` check, because it already passed with the change. A gate round never reopens the Step 2 review and never touches `fix_rounds`. Record every test file the implementer touched in a gate round for `Verification`.
   - **Stop** — new failures remaining after the third completed gate round, or a suite that cannot run, stop the route at the terminal suite gate: the command and the failure are reported, nothing after the gate is run or marked, and Steps 3–8 do not run (no backfill, archive, or commit); verify guard window 1; the changes stay unstaged in the working tree. The gate rounds are this step's attempts, so its budget is spent and the stop escalates: the report is the shared stopped Direct Build terminal report below (What you need to know states the run is incomplete and names the verification limitation; Execution details lists the red tests), and the options follow it as a separate decision prompt. The slice is marked failed and stays retryable, and a retry runs the suite gate afresh; no later slice starts.

   When the gate is green or skipped, `Build/Implement` converges: explore completes that route item (`pipeline-direct-build.md`).

3. **Sibling backfill preparation** — stage exactly the implementer's owned paths (path-scoped `git add`; unrelated dirty files never enter), then dispatch the EXISTING `sai-backfill-worker` through its existing binding and Direct Build (unattended) prepare route with `arguments_value` beginning `--direct-build-prepare`, then `--block-file <path>` and `--block-hash <hash>` lines from a fresh export, then `--fast-track --staged`. The verified file supplies the complete block; no block text travels in the message. Fetch @sai/orchestration/workers/bindings/backfill-worker.md and use it before this dispatch. The dispatch requests the backfill worker to compose the draft set including `openspec/changes/{name}/.openspec.yaml` in the canonical form specified at `sai/commands/backfill/instructions.md` section 6a, in addition to `proposal.md` and capability specs. Interview asks resolve through the grounded auto-answer-or-escalate rule: the same qualitative confidence threshold, ambiguity resolving toward escalation, permitted grounding extended only by this run's block, fix-loop findings, staged diff summary, and captured `base_sha`: the diff-source ask resolves to the staged-changes option grounded in `base_sha`; Question 1 grounds in the block's What/Why; Question 2 grounds in the fix-loop findings; anything ungrounded escalates unchanged. A foreign-spec conflict auto-proceeds per the delta-sync/fast-track precedent (E2), reported as a notice. Preparation performs no draft write into the repository. **Transfer directory:** before the prepare dispatch, resolve `transfer.js` per `@sai/policies/tool-resolution.md` and run `node <tool-path> open --harness <claude|opencode>`, keeping the returned `dir` in the run state (exit 2, such as a missing harness temp root, stops the route before any dispatch and any final write, reported with the verbatim error). Carry it to the worker only in the task-disclosure continuation as `--transfer-dir <dir>` after the outermost `--report-dir` line and before the envelope above, never in the initial dispatch. The worker hands each draft over as a reference `{path, sha256, destination}` to a transfer file in that directory (`sai/commands/backfill/worker.md` § Draft transfer); drafts never travel as message text on any continuation, replacement, or execute order, and a corrected result supersedes every earlier reference. Keep the directory through archive and any unresolved validation or recovery; cleanup follows `@sai/policies/direct-build-report-transport.md`. This draft directory is separate from report storage and the stored-block export directories, whose lifetime follows the stored-block transport policy.

4. **Spec review** — explore runs `transfer.js verify` on every returned reference (a failure, a path outside the directory, or a duplicate or non-allow-listed destination returns to the same worker as a corrected-result request, with no execute order) and then validates the draft content read from those transfer files read-only against `openspec/schemas/sai-workflow/schema.yaml` (pure reading, the validation/writer split: explore writes nothing) and accepts `openspec/changes/{name}/.openspec.yaml` as part of the returned draft set, validating it against the canonical forms of `sai/commands/backfill/instructions.md` section 6a rather than against the capability schema: the three-key form (`schema`, `created` as a YYYY-MM-DD date only, `backfilled: true`) for a run with no usable intent context, and the four-key form (those three plus `prior_intent: true`) for a run with usable intent context. Either form validates under its own condition; both allow the optional validated `backlog_origin` of section 6a and no other key. Compare that value with the block's selected origin; a known lost or unverifiable origin warns without blocking the remaining work. It reviews the drafts against the block under `@sai/policies/artifact-review-contract.md`, and continues any findings once to the SAME backfill worker within the remaining `fix_rounds` budget; schema-invalid or still-failing drafts are an obstacle of `step-4`.
   MODIFIED-delta completeness: Fetch @sai/policies/scenario-preservation.md and apply its receiver boundary to the temporary drafts before accepting them. Run the shared checker and route missing scenarios as High completeness findings to the same backfill worker. A failed or incomplete comparison cannot be accepted through review-round cap exhaustion. Fetch @sai/policies/backfill-draft-validation.md and perform its mandatory receiver-side OpenSpec CLI validation on the complete draft set. Retain its accepted fingerprint and diagnostics in run state; rejection or incomplete validation authorizes no write and returns the diagnostic to the same worker for correction, except the distinct validation reason `openspec-cli-unavailable`: it is force majeure that escalates at once under `@sai/policies/obstacle-escalation.md`, requests no correction from the worker, spends no `step-4` attempt, and wins even when the drafts are also invalid. Repeat all checks for corrected drafts, including archive-failure corrections.

5. **ADR/DDR pass** — fetch `@sai/policies/adr-ddr-criteria.md` and run its ordered routing test over the block's Decisions & Rationale; never offer a choice. When `adr|ddr` resolves, record the resolved family and pass outcome in one line and proceed. The Direct Build (unattended) route does not add a decision-record file to the backfill artifact set: that set is restricted to the schema-validated OpenSpec drafts plus the `.openspec.yaml` metadata file in the canonical form specified at `sai/commands/backfill/instructions.md` section 6a, and persistent ADR/DDR creation remains owned by the normal implementation flow.

6. **Backfill execution** — after the schema validation, successful receiver-side CLI validation, and ADR/DDR decisions above, run the accepted-fingerprint freshness check of `backfill-draft-validation.md` before authorizing any writes. A mismatch requires repeated receiver validation. Take the `order_snapshot`, then continue the SAME `sai-backfill-worker` with exactly one `--direct-build-execute` closed order containing the validated draft references (`{path, sha256, destination}`, never content) and accepted validation fingerprint, including the reference whose destination is `openspec/changes/{name}/.openspec.yaml`. This continuation is the coordinator's explicit execution authorization; the worker repeats the fingerprint check before its first write, verifies each reference and materializes it byte-for-byte to its destination, and writes nothing else. It stops before archive preparation. Keep the transfer directory through archive for corrections, then close it at terminal cleanup as described under Step 3. When it returns a clean result, `Backfill` converges.

7. **Archive preparation** — Fetch @sai/orchestration/workers/bindings/archive-worker.md and use it. Then dispatch the EXISTING `sai-archive-worker` through its binding with an `--direct-build-prepare` envelope for the resolved name, declaring `fast_track_active` and `direct_build_mode: prepare` as session state alongside the envelope; the task-disclosure message opens with `--report-dir <dir>`. Run the read-only pre-flight over the materialized artifacts. The worker returns the validated CLI archive, staging, and commit plan without mutating.

8. **Archive execution and pre-authorized commit** — after coordinator validation, gate resolution, and the one-commit authorization state are all present, and the order covers the slice per `@sai/policies/slice-path-scope.md` § Commit coverage (slice paths: the implementer's unioned changed paths, the backfill-written draft paths, and the prepared plan's archive destination and synced main specs), take the `order_snapshot`, then continue the SAME `sai-archive-worker` with exactly one `--direct-build-execute` closed order. Apply the independent archive-boundary check of `scenario-preservation.md` to the current deltas first. The worker runs `openspec archive <name> --yes --json` as the sole sync + move primitive, stages only the supplied OWNED paths (reconstructed artifacts, synced main specs, and the implementer's unioned changed paths — unrelated dirty files never enter the commit, E4), authors the commit message from staged state under `@sai/policies/commit-rules.md`, and passes it literally on standard input to `git commit -F -` under `@sai/policies/command-execution.md`; never push, amend, retry, or add an action outside the order. A clean terminal `completed` makes `Archive` converge and consumes the order and the commit grant.

**Execute orders.** Take the `order_snapshot` immediately before sending any execute order. When one fails, first restore any pending foreign index entries under `@sai/policies/foreign-index-preservation.md` § Recovery (a restore that stops ends recovery and is reported), then run the No-effect check of `slice-path-scope.md`. With no effect verified, the step is an obstacle like any other, and a new order goes to its owner after a different correction. A completed, partial, or unknown state issues no order: it is force majeure. A delivery or validation failure after independently confirmed operations is a pending report check, not a failed order: recover the report of the existing effects and never replay the order. A confirmed archive move or commit stays confirmed, and a consumed order or commit grant is never renewed. A late continuation after success is rejected without mutation.

## Resume

On `{intent: resume-direct-build}`, take the parked stage `explore-slice@1` returns and reuse that slice's run state. Steps 1–2b belong to `build-implement`, Steps 3–6 to `backfill`, and Steps 7–8 to `archive`. A missing handle history, counter, authorization state, or verification reference that the pending operation needs keeps the route stopped and names what is missing. A stage mismatch is reconciled from accepted checks before any work, never by initializing a new run.

1. Recheck the evidence of accepted steps against the current repository state. Preserve accepted work whose evidence still holds, review the work whose evidence changed, and keep counters and scope. Enter at the first pending internal step, not at Step 1 merely because this card loaded again. A completed worker stretch alone does not accept a step: acceptance takes a validated report and all that step's checks. Update `pending_step` only after acceptance, and converge a route item only when all its checks passed.
2. For pending worker work, continue the retained handle first. Each step continues its own role and never starts a new implementer for backfill or archive. A new worker (an obstacle approach) gets the hand-over of Obstacles below and the ready handshake.
3. Deliver every report to the validator exactly as received; never rewrite or re-serialize it. On an invalid report, preserve existing changes, keep the step pending, and ask the authoring worker for a fresh valid report as an obstacle of that step. Accept no status or changed-path claim from rejected output. At an exhausted budget, keep the step pending and report the cause; a resume choice alone does not reopen any budget.
4. Before resuming an uncertain execute operation, run the No-effect check with the retained `order_snapshot`. If the authorized commit is confirmed to have occurred, record its reference and consumption once, and accept route closure only when the archive result and the remaining checks are accepted. If it is confirmed absent, continue only the pending work the no-effect check permits; the absence of a commit does not authorize replay of a partially applied archive order. An inconclusive check keeps execution stopped. A consumed order or commit grant is never renewed by resumption; never push.

Resumption preserves every value above and grants no extra attempt or authorization.

## Obstacles

Obstacles, their budget of 3 attempts, force majeure, and escalation follow `@sai/policies/obstacle-escalation.md`. Keep the attempts in the conversation, one budget per step, named by the step it blocks (`step-1`, `step-2`, `step-2b`, `step-3` through `step-8`). A step's attempts never draw on another step's budget, they persist across a same-slice resume, and a review round, a question answer, a continuation, a replacement, and a step transition leave them as they are. An obstacle here is a non-clean outcome after dispatch: a worker that returns no ready, an unreadable or invalid report, a silent or drifting worker, a valid `failed` or `cancelled` result, a draft set that still fails Step 4, a failing tool (`transfer.js`, `sai-state`, the CLI archive), or a failed step check. The three gate rounds of Step 2b are that step's attempts. `failure_class` and `unrecoverable` are evidence for the response, never an eligibility gate.

A correction is steered by the failed step's check and by three invariants that hold for every attempt: agreed content (What, Why, Edge Cases, Implementation Details, scope, Key constraints) passes through unchanged; writes land only on the slice paths; and the step sequence stays as planned, skipping nothing. After each attempt, run the foreign-change check of `slice-path-scope.md` § Foreign changes, and run the failed step again through its owner before anything advances.

Force majeure, which escalates at once without spending an attempt, also covers: an argument line that is missing or a block file that does not verify; `BLOCK_NOT_FOUND` or `BLOCK_EXPORT_FAILED` at an export (dispatch nothing; the options offer retrying the export and re-emitting the block with `--amend` for one pending or stopped slice); a correction that needs a change to the What, the Why, or the Edge Cases; a `foreign` path after an attempt (report the exact paths and revert nothing); an execute order left in a completed, partial, or unknown state; and any push, deletion of files foreign to the slice, or shared-infrastructure change.

A stop reports the exact draft paths written or the exact CLI, staging, and commit state, and a partial plan is never committed. A stopped slice carries no finality: new retries or changes run only at explicit user request, and the manual `/sai-backfill`, `/sai-archive`, and `/sai-commit` guidance is reported where it applies. Preserve the report and draft evidence at a non-clean closure per the report transport; a helper that is unavailable or denied has no inline-content fallback.

A new worker receives a hand-over written by you: the change name, the role and step, the retained references (never draft content and never the old worker's history), the validated closed order and its execution state when there is one, the findings already sent, and the symptom. It starts again from the ready handshake and never replays an executed order.

## Close

The run closes when the goal is met, when a stop was reported, or when the user chose to stop or dismissed an escalation. Explore then applies the slice transition of `pipeline-direct-build.md`. Close with the Direct Build terminal report, following `@sai/policies/implementation-closing-report.md` as the single format authority; reporting changes no completion or authorization rule.

- **What you need to know** — summarize the material repository changes; on success, name the archive destination and local commit reference (short SHA and subject), and state `Nothing was pushed.` If archiving or the commit did not complete, state what completed and what remains; use the stopped status. Include every relevant verification limitation, pre-existing or new failure, and incident with its known effect here so the reader can stop before the technical record.
- **Next step** — retain the outcome-appropriate navigation and retry guidance. After an escalation, the options of `@sai/policies/obstacle-escalation.md` follow after `Execution details` as a separate question, not as another report section. Cancellation and a stop the user chose get no options.
- **Execution details** — preserve the work and commit record, original tool-generated commit reports, and these route-owned diagnostic records:
  - **Verification** — always state the Step 2b suite-gate command and its observed result (green, red with the failing tests, cannot run with the error, or `no test suite found`); distinguish test failures known before this run from failures introduced or worsened by it by listing the pre-existing failures classified at `base_sha`; and list every test file the implementer touched in a gate round. A pre-existing test failure is a verification limitation, not an incident. Say `No known verification issues.` only when the suite gate ran green, no pre-existing failure was found, and no test file was touched in a gate round.
  - **Incidents** — briefly name each run-caused execution problem or contract violation and its known effect, even when the functional result is correct. Name the violated rule for a contract violation. If an expected generated file is excluded from the commit, name it and the reason. Say `None` only when no incident is known.
  - **Pre-existing findings** — every `Pre-existing` finding of the functional fix loop, one line each with its location and issue. Omit this record when there is none.
  - **Scope observations** — every scope observation of this run, in the line form of `@sai/policies/artifact-review-contract.md` § Scope observations. Omit this record when there is none.

Omit routine rounds without findings, cap tallies, checks without alerts, automatic answers that caused no problems, other execution telemetry, and verbatim worker summaries. For autonomy-audit display, follow the Direct Build - Unattended final-report exception in `sai/policies/autonomy-audit-log.md`. After accepted route closure, with no continuation or recovery that still needs them, close the report directory with `transfer.js close`; close the transfer directory at the same point, and remove the temporary backfill validation projects (each `project_dir` retained in run state) with `temp-root.js remove --harness <claude|opencode> --dir <project_dir>`, resolved per `@sai/policies/tool-resolution.md`. A failed or escalated closure keeps them as evidence.
