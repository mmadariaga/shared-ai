# Item 4: Slicing assessment (before crystallizing)

Before emitting any proposal block, run TWO assessments in order — a **size** judgment (is the change too big?) and an **integration-point friction** judgment (is the code the change lands in hostile at the exact site the feature must plug into?). They are orthogonal axes and compose: either can add slices to the crystallized set.

Technical uncertainty belongs to the POC lane, not to this assessment. The lane's trigger is evaluated at the close of stage 1 (`common.md`, **POC trigger**), and the lane runs between `Explore change` and `Review edge cases` (`poc-lane.md`), so any POC has been decided, run, and discarded before this assessment runs: size and friction always judge the original repository. A user who explicitly asks for a POC during this stage leaves for the lane (`common.md`, **Late explicit POC entry**) and returns through `Review edge cases`, and this assessment then runs again on the repository the lane left as it found it.

**Size judgment.** A change is "too big" when it would likely produce a diff too large to review carefully in one sitting (review fatigue hides defects). You cannot see the diff yet, so judge from these scope signals:
- several distinct user tasks with orthogonal concerns (not facets of one behavior);
- no end-to-end path achievable in ~1–3 days;
- touches more than one module boundary with no shared integration point.

**Integration-point friction judgment (refactor-first).** After the size judgment, judge whether the *exact site* where the imminent feature would integrate is hostile — a qualitative judgment in the same tone as "too big", and distinct from it: size asks whether the *change* is too big; friction asks whether the *code the change lands in* is hostile at the integration point. The assessment **fires** when, at that specific site, either signal holds:
- **mixed responsibilities** — the site conflates concerns, so the feature cannot be added without touching unrelated behavior; or
- **no clean extension seam** — the feature can only be added by modifying existing code in place, not by extending it.

Judge friction **locally and concretely**, at the integration point of the feature at hand — a site judgment, not a tech-debt audit of the surrounding module or repository (unrelated debt elsewhere does not fire it). Blast-radius metrics from a code graph MAY be cited as supporting evidence; the trigger stays qualitative, with no metric threshold. When friction fires, a behavior-preserving **slice 0** (the preparatory refactor) is prepended to the crystallized set per the slice-0 machinery in item 6.

**Routing** (both axes combined):
- **Fits one change AND friction does not fire** → single-block protocol (item 5).
- **Fits one change BUT friction fires** → sliced protocol (item 6) as a 2-block set: slice 0 (refactor) → slice 1 (the feature).
- **Too big** → identify one **Walking Skeleton** (the simplest end-to-end path covering every user task, reversible) plus the remaining work grouped into review-sized slices (dependency-ordered), then crystallize via the sliced protocol (item 6); when friction also fires, slice 0 is prepended ahead of the Walking Skeleton (refactor → skeleton → backlog). Describe each slice as a user-facing outcome, leaving layer decomposition and delivery planning to `sai-2-design`/`sai-3-implement`. (Outcome-description exception: slice 0 is marked enabling / behavior-preserving, not user-facing value — see item 6.)

Each identified slice adds no panel entries. The assessment identifies slices by role and outcome description only and leaves them unnamed; the authored `**Change name**` is recorded for the later deferred route choice — keyed records only, so every list item carries a key. When the user keeps a large feature as a single change after the assessment recommended a split, only the emitted block's change is recorded for the later choice.

**Clarifying questions.** Ask one only when the answer would change where the cuts fall; otherwise state your assumptions and proceed. Shape it per `@sai/policies/question-context.md`: what is being decided (where the slicing cuts fall), why it matters (the cuts set the change boundaries and their dependency order), and the essential state of the candidate idea being sliced, in plain wording.

When ambiguity materially affects where to cut, surface your assumptions explicitly inside the proposal block(s) so the user can correct them. Recommending a split or a refactor-first slice 0 is guidance, not a gate: if the user prefers to keep a large feature as a single change, or to land the feature directly in the tangle without slice 0, state the risk once, briefly, then proceed — with the single-block protocol (item 5) when no slice remains, and WITHOUT slice 0 when friction was declined. Do not re-litigate.

**Crystallize stage (stage 4).** Advancing into `Crystallize` is itself an explicit crystallization request: immediately run the slicing assessment (size and friction), then proceed to the crystallization language gate (item 8) and then to `Ready to Propose` block printing; the overview-language decision (gate 9) runs only at a later supervised **Plan - Unattended** activation after deterministic selection confirms a dispatchable change. From `Implementation details`, `next-step`, `crystallize`, natural-language advancement, semantic list confirmation, and deterministic empty-set advancement are equivalent ways to enter this stage. A direct crystallization request from an earlier stage first runs the mandatory edge-case review with no skip path; after agreement, the pending request enters crystallization directly and the emitted block carries `**Implementation Details**: - None` when stage 3 was skipped. `--fast-track` bypasses only the language questions (the item-8 gate here and the overview-language ask at a subsequent **Plan - Unattended** activation) and never skips, weakens, or auto-completes a stage. At block emission, clear the stage TODO and leave the panel empty until the deferred route choice resolves; never re-render the stage TODO afterward.
