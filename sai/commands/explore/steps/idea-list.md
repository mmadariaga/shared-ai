   **Route-owned entries (authoritative).** The list holds only the chosen route's entries; no baseline evidence entries exist. Clear stage TODO at block emission and first render only at selector resolution. Panel stays empty from block emission until selector resolution (E5). The list first renders in the turn that resolves the deferred route choice — choice resolution is the first identification of the route — exactly once after that turn's additions and state changes; after that, a turn that adds, marks, or clears a route entry re-renders the list exactly once, after all of that turn's changes have been applied. The neutral task-list minimum threshold (`sai/policies/todo-structure.md`) is not applied: the list has no declared progress plan, no canonical step ids, and its length is known only when the route is chosen.

   **Render contract.** Rendering is performed through the per-harness idea-list render binding, which references the per-harness panel-render binding for native-panel availability and mechanics. Panel availability is declared by the panel binding, never determined at runtime. The two supported harnesses (Claude Code and opencode) declare a native task panel, and their bindings render the list on it, replacing plain in-conversation text — the same list state never renders on both surfaces. On the panel, a marked entry renders `completed` and an unmarked entry renders `pending`; no entry renders `in_progress` from review state because review items do not exist in this list. Each entry's slice `**Change name**` key rides the machine-readable panel entry field pinned by the binding (opencode `priority`, Claude Code `description`, both carrying the value `sai-idea-list:<change-name>`), while the label keeps the slice's change name, so a slice's entries stay visually distinguishable from every other slice's entries. A binding that declares no native task panel renders the list as plain in-conversation Markdown checkbox text — `- [ ]` for an unmarked entry, `- [x]` for a marked entry — as the declared fallback; no supported harness exercises that branch today, so it is a declared extension point for a future harness, never a runtime-detected path. The panel update originates exclusively from the coordinator session, never from a worker subagent. The list is NOT rendered while it holds no route entries. Old `reviewed-sai-1` and `reviewed-sai-2` references mark, clear, or render nothing; each path owns its entries (E7).

    **Panel tool degradation.** If a declared native-panel tool is rejected as unavailable at runtime, record exactly one visible notice — `> Panel rendering unavailable; continuing without task-panel updates.` — disable panel calls for the rest of the chat, and continue exploration without panel rendering. Do not probe for availability, retry the failed call, or switch dynamically to the declared no-native-panel Markdown branch; the logical idea-list state and its marking rules remain unchanged.

   **Panel ownership.** The panel's declared owner splits into two phases while a `sai-explore` chat is active. Phase A: before block emission, the panel's declared owner is the pre-crystallization stage TODO per the single source in `steps/common.md` — paint rule, stage ids, marker carriers, and clear semantics live there only and are not restated here. Phase B: from the idea progress list's first render (deferred route-choice resolution), the panel's declared owner is the session's idea progress list — exclusive in that the list never coexists with entries from any other surface and after every render the panel holds exactly the full idea list with no foreign entries, realized through the per-harness binding's render mechanism (in-place convergence on Claude Code, full-array replacement on opencode) — and the stage TODO is cleared at block emission and never re-renders. A new `sai-explore` chat's start clear removes entries bearing either marker prefix (`sai-explore-stage:` or `sai-idea-list:`), leaving other surfaces' entries in place. A future surface that needs the panel during an active explore chat renegotiates the ownership rule rather than writing alongside the current owner. The rule lives in explore's own contract and in no routed worker binding file. The supervised run is the illustrative case: during supervised coordination no adapter-declared progress plan is in force, so no plan-based list renders on the panel, and the ownership rule changes no observable supervised-run behavior; standalone `/sai-1-spec` and `/sai-2-design` progress rendering remains unchanged (`idea-list-panel-ownership`).

   **Panel lifecycle.** Every render leaves the panel holding exactly the full idea list with no foreign entries — the full-list outcome, achieved per the per-harness binding's mechanism (in-place convergence on Claude Code, full-array replacement on opencode). The first render displaces any pre-existing panel entries — a routed phase's progress plan or another `sai-explore` chat's earlier list — with the full idea list. A new `sai-explore` chat starts with a fresh chat-scoped list, and its start clears exactly the entries a previous idea list or stage TODO rendered, classified by the ownership markers in the machine-readable panel entry field (the same field that carries the `**Change name**` key; the two marker prefixes are `sai-idea-list:` and `sai-explore-stage:`) — a claim action distinct from rendering the list, which remains forbidden while the list holds no route entries; the read covers the markers only and never derives list content, and entries rendered by other surfaces, which bear no such marker, remain on the panel until the idea list's first render displaces them wholesale. When the explore chat ends, its last-rendered entries remain on the panel as session state — the ended chat performs no end-of-life cleanup — and any later surface that renders on the panel, including the next explore chat's start clear, replaces them wholesale (`idea-list-panel-lifecycle`).

   **Route entries.** The chosen route creates its own entries with no baseline items:
   - **Plan:** exactly `sai-1`, `sai-2`, `Implement`. `sai-1` starts `in_progress`; only clean spec convergence completes it and starts `sai-2` as `in_progress`; a clean terminal design result completes `sai-2` and starts `Implement` as `in_progress`. `Implement` has no worker; it completes only on `next-slice` (or equivalent natural language). The route never exposes or claims `sai-3`, `/sai-3-implement`, or code implementation.
   - **Direct Build:** exactly `Build/Implement`, `Backfill`, and `Archive`, in that order. `Build/Implement` is the user-facing display label for the implementer plus functional-fix work; it is not `/sai-build`, `meta-build`, or a claim that the `/sai-build` composition ran. Backfill covers its preparation, spec review, ADR/DDR pass, and execution substeps; Archive covers its preparation, CLI archive invocation, staging, and pre-authorized commit substeps. Those internal substeps remain authoritative in the Direct Build contract but never expand the panel route.
   - **Manual:** exactly `Manual handoff`. It becomes `completed` when the path-specific handoff is emitted. Manual creates no delegated route steps, dispatches no worker, and does not authorize delegated work.

   Route state is conversation-only and scoped to the chosen slice: retain the chosen `**Change name**`, the chosen mode, the ordered route steps, each step's `pending | in_progress | completed` state, and the active step. Reset route state when a new slice is chosen; preserve completed slices and all pending slices. Route state is emitted only by the explore coordinator, is never authored by a worker, is never persisted, and creates no milestone stamps. A failed, cancelled, STOP-bearing, coordinator-disproved, or unrecovered route result leaves the active route step `pending` and the route retryable; previously completed route steps remain completed, no later step starts, and the route is not completed. Only a clean terminal result completes the active route. On retry, the route is rebuilt for the same chosen slice from its mode's fixed ordered steps.
