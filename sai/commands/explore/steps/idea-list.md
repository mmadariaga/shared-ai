   **Item catalog.** The list holds exactly one research item, created unmarked at the start of the chat, plus per crystallized slice a set of three items — slice-crystallization, reviewed-sai-1, reviewed-sai-2 — added unmarked at that slice's block emission, keyed by its authored `**Change name**`, in the order the slicing assessment (item 4) identified the slices. A crystallized slice is one `**Change name**` value emitted by a crystallization turn (items 5/6): block emission is therefore the first identification of a slice, and the key binds to that slice's items at that moment. A duplicate later identification of a change name already present in the list adds no items, mirroring the tracked crystallized set discipline (item 9). The list contains no implementation item and no other item kind (`idea-list-item-catalog`).

   **Render contract.** Rendering is performed through the per-harness idea-list render binding, which references the per-harness panel-render binding for native-panel availability and mechanics. Panel availability is declared by the panel binding, never determined at runtime. The two supported harnesses (Claude Code and opencode) declare a native task panel, and their bindings render the list on it, replacing plain in-conversation text — the same list state never renders on both surfaces. On the panel, a marked item renders `completed`, a cleared item renders back to `pending`, and the slice's active review item renders `in_progress` while the post-crystallization review loop processes that slice — `in_progress` is carried only by the reviewed-sai-1 and reviewed-sai-2 items (per `idea-list-review-in-progress-state`), never by the research item or a slice-crystallization item. Each item's slice `**Change name**` key rides the machine-readable panel entry field pinned by the binding (opencode `priority`, Claude Code `description`, both carrying the value `sai-idea-list:<change-name>`), while the label keeps the slice's change name, so a slice's items stay visually distinguishable from every other slice's items. A binding that declares no native task panel renders the list as plain in-conversation Markdown checkbox text — `- [ ]` for an unmarked item, `- [~]` for the active in-progress review item, `- [x]` for a marked item — as the declared fallback; no supported harness exercises that branch today, so it is a declared extension point for a future harness, never a runtime-detected path. The panel update originates exclusively from the coordinator session, never from a worker subagent. The list is NOT rendered while it holds only the research item. It first renders in the turn that first emits a slice's block — block emission is the first slice identification, since a crystallized slice is a `**Change name**` value — exactly once after that turn's additions and state changes; after that, a turn that adds, marks, or clears an item, or sets or resolves an item's in-progress state, re-renders the list exactly once, after all of that turn's changes have been applied (`idea-list-rendering`). The neutral task-list minimum threshold (`sai/policies/todo-structure.md`) is not applied: the list has no declared progress plan, no canonical step ids, and its length is unknown until slices crystallize.

    **Panel tool degradation.** If a declared native-panel tool is rejected as unavailable at runtime, record exactly one visible notice — `> Panel rendering unavailable; continuing without task-panel updates.` — disable panel calls for the rest of the chat, and continue exploration without panel rendering. Do not probe for availability, retry the failed call, or switch dynamically to the declared no-native-panel Markdown branch; the logical idea-list state and its marking rules remain unchanged.

    **Review-in-progress state.** While the post-crystallization review loop (item 9) processes a change, the slice's active review item renders `in_progress` — the item selected once at loop-processing start as the slice's first review item not marked completed, in fixed order (reviewed-sai-1 first, else reviewed-sai-2; when both are marked completed no item of the slice renders `in_progress`). The active item renders `in_progress` from loop entry, before any review transaction for the change has run, and keeps rendering it through every later per-change picker re-show until it is marked completed; when the state resolves (`Skip`, the active-loop `exit` token, or loop close), the item renders `pending` again, without marking or clearing any evidence. The state is render-only: setting, advancing, or resolving it never marks or clears an item, and the evidence-based marking hooks apply unchanged (`idea-list-review-in-progress-state`). The supervised in-session review rounds (item 10) drive the same items only on ordinary supervised review entry: during supervised spec rounds reviewed-sai-1 renders `in_progress`, and during supervised design rounds reviewed-sai-2 renders `in_progress`. A Diagnosis Round or same-worker re-dispatch never sets either item `in_progress`, adds a diagnosis-specific list item/row/entry, marks or clears review evidence, or counts as a Supervised Review Round. A round reporting `High=0` marks the corresponding item; cap exhaustion or worker failure/cancellation (or any other diagnosis-eligible result) resolves an unmarked active item to `pending`. If diagnosis stops, re-dispatch fails, or the worker fails/cancels again, the phase item remains/resolves to `pending`. This remains render-only and never marks or clears by state transition alone.

   **Panel ownership.** The panel's declared owner splits into two phases while a `sai-explore` chat is active. Phase A: before the first slice identification, the panel's declared owner is the pre-crystallization stage TODO — each stage-TODO entry carries the stage-ownership marker `sai-explore-stage:<stage-id>` (stage ids `explore-change`, `review-edge-cases`, `implementation-details`, `crystallize`) in the machine-readable panel entry field pinned by the per-harness idea-list render binding (opencode `priority`, Claude Code `description`), so stage entries stay visually distinct from every other surface's entries. Phase B: from the idea progress list's first render (the first slice block emission), the panel's declared owner is the session's idea progress list — exclusive in that the list never coexists with entries from any other surface and after every render the panel holds exactly the full idea list with no foreign entries, realized through the per-harness binding's render mechanism (in-place convergence on Claude Code, full-array replacement on opencode) — and the stage TODO is cleared at that transition and never re-renders. A new `sai-explore` chat's start clear removes entries bearing either marker prefix (`sai-explore-stage:` or `sai-idea-list:`), leaving other surfaces' entries in place. A future surface that needs the panel during an active explore chat renegotiates the ownership rule rather than writing alongside the current owner. The rule lives in explore's own contract and in no routed worker binding file. The supervised run is the illustrative case: during supervised coordination no adapter-declared progress plan is in force, so no plan-based list renders on the panel, and the ownership rule changes no observable supervised-run behavior; standalone `/sai-1-spec` and `/sai-2-design` progress rendering remains unchanged (`idea-list-panel-ownership`).

   **Panel lifecycle.** Every render leaves the panel holding exactly the full idea list with no foreign entries — the full-list outcome, achieved per the per-harness binding's mechanism (in-place convergence on Claude Code, full-array replacement on opencode). The first render displaces any pre-existing panel entries — a routed phase's progress plan or another `sai-explore` chat's earlier list — with the full idea list. A new `sai-explore` chat starts with a fresh chat-scoped list, and its start clears exactly the entries a previous idea list or stage TODO rendered, classified by the ownership markers in the machine-readable panel entry field (the same field that carries the `**Change name**` key; the two marker prefixes are `sai-idea-list:` and `sai-explore-stage:`) — a claim action distinct from rendering the list, which remains forbidden while the list holds only the research item; the read covers the markers only and never derives list content, and entries rendered by other surfaces, which bear no such marker, remain on the panel until the idea list's first render displaces them wholesale. When the explore chat ends, its last-rendered entries remain on the panel as session state — the ended chat performs no end-of-life cleanup — and any later surface that renders on the panel, including the next explore chat's start clear, replaces them wholesale (`idea-list-panel-lifecycle`).

   **Marking hooks.** The research item marks at the chat's first `Ready to Propose` block emission and is never re-marked; no other event marks it (`research-item-marking`). A slice's slice-crystallization item marks when that slice's block is emitted, leaving its two review items unmarked (`slice-crystallization-item-marking`). A slice's reviewed-sai-1 item marks exactly when the most recent completed review over that slice's available sai-1 artifact set reports no High findings and clears exactly when it reports at least one High finding; its reviewed-sai-2 item follows the same rule over the sai-2 artifact set — where a completed change-overview review transaction supplies the same reviewed-sai-2 evidence (item 9: the most recent completed review over the sai-2 slice, whether a sai-2 or a change-overview transaction, decides). The evidence comes from either entry path — the manual review loop's base-form `Summary: High=<count> Medium=<count> Low=<count>` tally (item 9) and the supervised pipeline's in-session review rounds (item 10) — with the severity vocabulary, finding shape, and tally form applied by reference to `@sai/policies/artifact-review-contract.md`, never restated inline. A review transaction that ends without a completed review — an absence report for a missing change directory or missing artifact set, a review blocked by missing specs, or a `failed` or `cancelled` phase worker — leaves the item unchanged. A supervised round or manual review over one slice's change marks or clears only that slice's items; every other slice's items stay unchanged. No item is ever marked or cleared from artifact existence, repository state, plan progression, or the completion of any other command or session (`specs/explore-review-evidence-marking/spec.md` requirements `review-item-no-high-pass-marks`, `review-item-per-slice-targeting`, and `review-item-evidence-only-marking`).
   **Crystallization route projection (temporary, coordinator-owned).** The baseline catalog above remains the evidence ledger. After the crystallization-close selector resolves one slice and one mode, the coordinator may temporarily replace only that selected slice's three baseline evidence entries with a mode-specific route projection; it never appends route items to the catalog, changes another slice, or renders a generic `Implementation` item. The research item and every non-selected slice remain in the baseline list. The projection uses the same per-harness idea-list render binding, the same `sai-idea-list:<change-name>` ownership marker, and the same exclusive panel ownership, so it is one idea-list render rather than a second task list.

   Route state is conversation-only and scoped to the selected slice: retain the selected `**Change name**`, the selected mode, the ordered route steps, each step's `pending | in_progress | completed` state, and the active step. Reset route state when a new slice is selected; preserve completed slices and all pending slices. Route state is emitted only by the explore coordinator, is never authored by a worker, is never persisted, and creates no milestone stamps. Route items are progress claims only: they never mark or clear `slice-crystallization`, `reviewed-sai-1`, or `reviewed-sai-2` evidence.

   - **`plan-unattended` route (Plan (unattended)):** expose exactly two steps, `sai-1` followed by `sai-2`. `sai-1` starts `in_progress`; only clean spec convergence completes it and starts `sai-2` as `in_progress`; only a clean terminal design result completes `sai-2`. The route never exposes or claims `sai-3`, `/sai-3-implement`, or code implementation. The reviewed evidence items may change their underlying evidence state according to the existing marking hooks, but they are temporarily replaced by the route and are never duplicated beside it.
   - **`direct-build-unattended` route (Direct Build (unattended)):** expose exactly the high-level stages `Build/Implement`, `Backfill`, and `Archive`, in that order. `Build/Implement` is the user-facing display label for the implementer plus functional-fix work; it is not `/sai-build`, `meta-build`, or a claim that the `/sai-build` composition ran. Backfill covers its preparation, spec review, ADR/DDR pass, and execution substeps; Archive covers its preparation, sync, move, staging, and pre-authorized commit substeps. Those internal substeps remain authoritative in the Direct Build (unattended) contract but never expand the panel route.
   - **`manual` route (Manual):** expose only `Manual handoff`. It becomes `completed` when the path-specific handoff is emitted. Manual creates no delegated route steps, dispatches no worker, and does not authorize delegated work.

   A failed, cancelled, STOP-bearing, coordinator-disproved, or unrecovered route result leaves the active route step `pending` and the route retryable; previously completed route steps remain completed, no later step starts, and the route is not completed. Only a clean terminal result completes the active route. On retry, the route is rebuilt for the same selected slice from its mode's fixed ordered steps. A route terminal state never fabricates review evidence, and a multi-slice route changes only the selected slice; completed slices retain their completed states and pending slices remain selectable.
