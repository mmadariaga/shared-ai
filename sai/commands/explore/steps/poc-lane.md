**POC lane (conditional stage, between `Explore change` and `Review edge cases`).** This step owns the lane from candidate agreement onward: the `C1..Cn` agreement stop, the POC execution, the verdict, and the verdict menu. The trigger itself — the two motives, the no-fire test, and the go/no-go ask — is evaluated at the close of stage 1 and is stated once in `common.md` (**POC trigger**); this file never re-states it and never re-litigates it.

The lane is a **conditional stage** of `explore-idea@1` (stage id `poc-lane`) between `explore-change` and `review-edge-cases`. It is reached only through `next.follow` after an entry intent — `{"intent":"poc-lane"}` from the stage-1 close, or `{"intent":"poc-lane-late"}` from an explicit user request at stages 2 through 4 (`common.md`, **Late explicit POC entry**) — and it is left only through the ordinary `next-step` advancement into `Review edge cases`. Ordinary advancement never enters it: an idea whose trigger did not fire, or whose user declined the go/no-go, goes from stage 1 straight to stage 2 and enters the lane later only if the user asks. While the lane runs, the stage TODO carries its five entries (`common.md`, Phase A stage TODO paint rule) and `POC` renders `in_progress`.

The lane behaves identically whichever entry brought it here: the same candidate agreement, the same pinned profile, the same verdict vocabulary, the same verdict menu, and the same return into `Review edge cases`. A late entry carries no trigger re-evaluation and no go/no-go — the user's explicit request has already answered that — and it never skips, weakens, or re-opens an already agreed `E1..En` or `I1..In` list (`common.md`, **Agreed lists survive the lane**).

The lane is never a slice of the crystallized set, never appears on the Idea Progress List, and never renumbers friction or skeleton slices. It clears no stage TODO.

While the lane is the current stage, the pre-crystallization closure (`common.md`) is satisfied by the lane's own pending stop — the candidate-list agreement question or the verdict menu — and no stage-aware reminder is appended.

**Candidate (`Cn`).** A candidate is one thing the POC can confirm or rule out: for the **viability** motive a strategy to prove, for the **diagnosis** motive a root-cause theory. A single lane run may mix both kinds when both motives fired on the same idea (E1) — one POC, never one per motive.

**Stop 2 — candidate list agreement (before the POC runs).** Propose the candidates as a numbered list `C1` through `Cn`, each one plain sentence naming what would be observed if that candidate were the right one. Then ask one plain conversational question whether the list captures the competing candidates or needs adjustment, following `@sai/policies/question-context.md` in the ambient conversation language: state that the POC will be built to discriminate exactly these candidates, that agreement comes first so a full POC cycle is not spent on the wrong hypotheses, and the two paths — confirm the list as written, or describe additions, removals, or changes. Preserve the literal `Cn` identifiers, use no native yes/no picker, and require no fixed agreement phrase.

Evaluate the answer by dominant semantic intent with the same mechanics the `E1..En` gate uses (`common.md`, edge-case review gate): clear confirmation records the ordered list as agreed and runs the POC in the same turn; a bare `next-step` turn with a non-empty list is confirmation; a disagreement, removal, addition, or material revision — including a same-turn revision paired with `next-step` — updates and renumbers the list, keeps the stop open, and re-asks without running the POC; an ambiguous answer stays discussion. Record the agreed list with a `recordedList` emit to `explore-idea@1` per `@sai/policies/stage-machine.md`; recording the candidate list never advances the stage.

**POC execution (pinned profile).** Run one POC through the **Direct Build (unattended) `--no-specs` profile** (`pipeline-direct-build.md`), whose scope is implementer-only: no backfill, no OpenSpec specs, no artifact archive, dirty code acceptable, minimal tests or human observation as the verdict authority. The profile is pinned: the POC is never routed through **Plan** or **Manual**, the deferred crystallization route choice never offers it (`route-selector.md`). The POC is scoped to the smallest experiment that discriminates the agreed candidates — it is not an implementation of the change. The POC implementer's last use is the end of its Step 2: dispose it then, as `@sai/policies/worker-lifecycle.md` says, and on any lane exit that ends the POC earlier, before the destroy question can remove the worktree it works in.

**Reversible isolation.** Before the POC runs, `sai-explore` creates the **POC isolation** as the coordinator: a dedicated sibling worktree on an exclusive branch, so the lane never modifies the user's checkout, its branch, or its uncommitted changes. Resolve `worktree.js` per `@sai/policies/tool-resolution.md` § `sai/tools/*.js` copies and run `node <tool-path> create <repo>.poc-<idea-slug> --json --cwd <invoking-directory>`, where `<repo>` is the main repository directory name and `<idea-slug>` is a short kebab-case slug of the idea. The tool yields the sibling worktree `<repo>.poc-<idea-slug>` on the exclusive branch `poc-<idea-slug>`. Record the `path` and `branch` that its JSON output returns. They live in the conversation only, like the hand-off wait state, and never in the `sai-state` store or a repository file. These recorded values are the only targets of a later destruction.

The worktree starts from the user's current committed `HEAD`: `create` passes no start point, so uncommitted changes in the user's checkout are not carried into the POC. Tell the user this before the POC runs. The POC runs only under the recorded path (`pipeline-direct-build.md`, `--no-specs` profile).

A `create` refusal (`directory-exists`, `branch-exists`, `invalid-branch`, `git-refused`) stops the lane before the POC runs. Report the tool's reason and ask no destroy question, because nothing was created. An existing branch is never reused as the POC branch.

Only the verdict survives the lane. The POC code is discarded only by the confirmed destruction of the POC isolation below, **never** by deletion of the user's working tree, `git reset --hard` on the user's branch, or removal of files the user owns. Because the user's checkout is never modified, the size and integration-point friction judgments at stage 4 evaluate the original repository and never one contaminated by throwaway POC code.

**Destroy question (every lane exit).** A **lane exit** is any way the lane ends: `Continue with <Cn>`, a `none` verdict, an execution failure, a cancellation, or a discard of the idea from inside the lane. At every lane exit, once the POC isolation exists, ask whether to destroy the POC through the harness-native picker per the "Closed-choice prompts" rule in `sai/policies/remember.md`, with exactly two options in this order: `Destroy the POC` and `Keep the POC`. The question context names the recorded path and branch. `Stay here` keeps the lane open and asks nothing. On `Continue with <Cn>`, the question is answered before `{"intent":"next-step"}` is emitted. When a POC run is interrupted mid-turn, ask the question on the next turn of the lane; a chat that never resumes leaves the POC on disk, and no later automatic cleanup exists. The verdict and the lessons learned stay in the conversation whatever the answer is.

- **`Destroy the POC`.** First confirm the recorded targets: run `worktree.js inventory --json` and require a registered worktree whose `path` equals the recorded path and whose `branch` equals the recorded branch. On any mismatch, run nothing, remove nothing, and report the mismatch. Otherwise run `worktree.js remove <path> --force`, then `worktree.js delete-branch <branch> --force`, in that order, because git does not delete a branch that a worktree still has checked out. `--force` passes the uncommitted-changes and unmerged-branch safeguards because the POC implementer never commits and its branch is never merged; it acts only on the recorded targets, so it never reaches the user's own work. A failure in the first step skips the second. On a partial cleanup (for example, the worktree is removed but the branch deletion fails), report what was removed, what remains, and the exact command that finishes it by hand, with no automatic retry.
- **`Keep the POC`.** Keep the worktree and the branch, and report their exact path and branch name.

**Verdict.** The verdict names the winning **agreed** candidate or names none — exactly `<Cn> wins` or `none`. It is never a judgment of the POC's code quality, and it never names a candidate outside the agreed list: a cause or strategy the POC reveals that was not on the list makes the verdict `none`, not a new winner.

**Stop 3 — verdict menu.** Report the verdict with the concrete observation that produced it, then take exactly one of two branches.

- **`<Cn> wins` (E4).** Present the harness-native picker per the "Closed-choice prompts" rule in `sai/policies/remember.md` — `AskUserQuestion` on Claude Code, the `question` tool on opencode — with exactly two options in this order:
  - `Continue with <Cn>` — ask the destroy question and take its answer, then advance to `Review edge cases`. What enters stage 2 is the **proven change** when the winning candidate was a strategy (viability motive), or the **proposed fix** for the confirmed root cause when it was a theory (diagnosis motive). Emit `{"intent":"next-step"}` to `explore-idea@1` per `@sai/policies/stage-machine.md` and follow the returned `next.follow`.
  - `Stay here` — do not advance; keep discussing the verdict in the lane. The idea is not discarded and no crystallization runs.
- **`none` (E5).** Present no advancement option. Stop the lane, ask the destroy question, report what was learned — including any cause or strategy the POC revealed that was not among the agreed candidates — and wait for instructions. No auto-advance, no progression reset, and no crystallization happen on this branch.

**Return is not a material change (E6).** The advancement out of this lane into `Review edge cases` is automatic stage progression, not a change of the idea: it does not reset the staged progression and does not start a new `active-uncrystallized` lifecycle. A genuine material change authored by the user still resets the progression exactly as always (`common.md`, material-change detection).
