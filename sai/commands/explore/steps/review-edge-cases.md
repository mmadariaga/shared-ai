# Review edge cases (stage 2)

The shared list-stage question, answer evaluation, and `- None` rule live in **List stages** in `steps/common.md`.

**Edge-case review gate (stage 2 — before readiness and crystallization).** The edge-case review is the second stage of the staged progression. It runs when the user advances into `Review edge cases`, or when the user explicitly asks to crystallize before the review has reached agreement. The review state is conversation-only and contains the ordered proposed list, its agreement state, and any pending explicit crystallization request. The review runs at most once while the idea remains substantially unchanged.

- **Terminology agreement (pre-edge-cases, conversation-only).** Before the edge-case review, fix ambiguous terms in conversation. Agreed terms travel as the block's `Terms`. Explore performs no file writes; it never writes `GLOSSARY.md`.
- **The list.** Only include behaviors that define a behavior or scope boundary for this proposed change. Do not invent `E` items from unrelated possibilities; cases outside the change remain Non-Goals. Number the proposed behaviors consecutively as `E1` through `En`, then run the lightweight probes, then ask whether the complete list accurately captures the relevant edge cases or needs adjustment. The emission is one message: the formal list first, then the probes, then the question — nothing sits between them. The question also names the list and current change context, explains that agreement is required before crystallization so the handoff preserves the intended scope boundaries, and states the two paths: confirm the list as written, or describe additions, removals, or changes. An empty list (`- None`) runs no probes.
- **Lightweight probe (post-list sub-step, conversation-only).** After the formal edge-case list has been drafted and before the agreement question, systematically probe candidate scenarios against the proposed list. Exercise at least 2 scenarios before anything is shown; holes a probe uncovers are fixed in the list privately, so the list is published already coherent, with no change marks and no explanations. Only material probes are shown: a probe is material when its outcome adds, removes, or modifies an `E` item, or clarifies a non-obvious consequence of an existing one. The search stops when no remaining scenario is material; the floor is a search duty, not a quota to pad with noise. When fewer than 2 material scenarios exist, show what the probes produced and state explicitly that there are no more material scenarios. Each shown probe is a plain direct question in the ambient conversation language — no fixed formula — immediately followed by a self-sufficient prose answer whose `E(N)` citations trail at the end as reference. Probes serve only this change's edge-case list; they do not open Implementation details or crystallization decisions. The probe does not replace the formal list.
- **Feedback ripples.** Explanations of side effects are owed only when user feedback drags changes into `E` items other than the one the feedback addressed (ripples); feedback aimed at a shown probe binds to the `E` item that probe illustrates.
- **Pending crystallization.** Do not emit a `Ready to Propose` block while the review is unresolved. If the user explicitly asks to crystallize before agreement, retain that request as pending and run this same review with no skip path. After semantic agreement or exact empty-set recording, ordinary stage advancement proceeds to `Implementation details`; a pending premature crystallization request instead enters `Crystallize` directly and runs slicing and the crystallization language gate, with `**Implementation Details**: - None` when that stage was skipped. `--fast-track` does not approve, skip, or weaken this gate; it bypasses the crystallization language question here. The overview-language gate has its own supervised **Plan (unattended)** activation timing and fast-track rule.
