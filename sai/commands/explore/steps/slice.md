**Post-crystallization slice machine (`explore-slice@1`).** After crystallization, explore consumes `explore-slice@1` in the same store session as `explore-idea@1`. The wire stays `{stage, next, rejected?, warnings?}`: `stage` is the slice inventory cursor (`idle` before a complete inventory, `waiting` for a route choice, then Direct Build `build-implement` → `backfill` → `archive` or Plan `sai-1` → `sai-2` → `implement`). Inventory readiness, `set` / `active` / `done`, parked steps, and TODO mode live in store-owned state and never travel on the wire; slice names come from the Ready to Propose blocks in chat. The `recordedList` holds the emitted `**Change name**` values in emission order and replaces `set` without moving a running slice's cursor. The crystallization close never composes it by hand: its block emit (`--ready-to-propose`) validates the block set and derives the `recordedList` from the extracted names.

Every `/emit` and `/restore` names `machineId: "explore-slice@1"`. An omitted or mistyped id is a closed error (`INVALID_EVENT` / `UNKNOWN_MACHINE`); nothing falls back to the first machine. Crystallize does not `/close`; `explore-idea@1` stays at `crystallize` in the map.

**Picker presentation and route gate.** A successful `recordedList` marks the whole ordered set complete, moves the machine to `waiting`, and returns the `route-selector.md` pointer when no slice is active. Follow the authoritative shared crystallization close in `crystallization-protocol.md` for inventory recording and block display, then `route-selector.md`'s optional pre-route actions and completion gate before presenting its native route picker. Opening the picker does not choose a route or authorize work. The machine keeps route intents blocked until the picker has returned one valid answer and the coordinator emits `{intent: route-choice}`. That event unlocks route processing and returns the selector pointer; only then may the matching Plan or Direct Build intent start. If a slice remains active during re-crystallization, its own pointer stays authoritative, and the new inventory's questions wait until the active slice closes. Before a complete inventory exists, Plan and Direct Build intents are rejected as `INVENTORY_NOT_READY`. Every slice finish or park re-locks the initial-selection gate. The selector distinguishes a pending Direct Build execution (resumption below) from a fresh choice for the first pending slice; a fresh choice follows the optional-action completion gate and never reuses an earlier answer. `{intent: auto-continue}` is accepted only right after a clean Direct Build finish; emit it only when `route-selector.md` resolves the continuation to `auto_continue`. With no pending slice, dispatch nothing and never restart a route. Another choice while `active` is set is already running: dispatch nothing.

**First pending slice only.** Plan and Direct Build route emits carry only their route intent, never a slice name or `pick`. `explore-slice@1` starts the first pending name in `recordedList` order (`set` minus `done`); no route may skip ahead. Manual handoff uses that same first pending slice. If the first pending slice is parked in the other route, the machine rejects the route with `PARKED_IN_OTHER_MODE`; later pending slices remain blocked until the first one resumes and completes.

**Parked slices.** Every E4 non-clean route ending (`route-selector.md`) emits `{intent: fail}` after its outcome report. When the user tells you to abandon or stop the running route, stop any worker still running for it (`TaskStop` on its captured handle on Claude Code; on opencode the user's interruption has already ended the blocking `task` call), then emit `{intent: cancel}` and wait for the applicable decision. Either intent parks the active slice at its current step: `active` is released, `stage` returns to `waiting`, and the slice stays first-pending. Preserve the Direct Build execution references defined in `pipeline-direct-build.md`, including handles, accepted checks, counters, and authorization consumption; releasing the machine's `active` is not clearing conversation execution state. The waiting pointer selects `route-selector.md`'s pending-execution branch for Direct Build. `{intent: resume-direct-build}` consumes only the first pending Direct Build parked cursor, returns its saved stage and route pointer, and grants no new authorization. Plan keeps its fresh picker and resumes only in its own mode at its parked step — a Plan slice parked on `sai-2` resumes design over its existing specs. Selecting the other route is rejected with `PARKED_IN_OTHER_MODE`; a parked Direct Build rejects initial selection with `RESUMPTION_REQUIRED`. No later slice may bypass it. A `recordedList` discards every parked step, so a re-crystallized slice restarts at its route's first step over its new block and requires new selection, rather than consuming an old execution's authorization.

**Plan and Manual close (`next-slice`).** Plan and Manual close the active slice only on the literal token `next-slice` — recognized by the same bare-token/dominant-intent machinery as the `next-step` token (item 9 / the stage-progression rule in `common.md`), firing when the turn is a bare token (optionally with trivial punctuation or a greeting) or when closing the current slice is the turn's dominant intent. Mere containment of the string `next-slice` SHALL NOT fire the token, and a turn that negates, defers, quotes, or discusses the token SHALL NOT close the slice. Direct Build never uses `next-slice`: completing Archive marks the slice done and clears active. The Plan `next-slice`-on-implement rule lives in `pipeline-plan-unattended.md`; `next-slice` while Plan is still on sai-1 or sai-2 does not complete Implement and does not mark the slice done. Manual has no TODO; the user closes the slice with `next-slice`.

**Slice branch chain.** With the `per-slice` branch strategy, each slice starts on its own local branch, created from the previous completed slice's branch under `route-selector.md` `## Slice branch chain`. A slice is completed for that chain when Direct Build archive completes, or when `next-slice` fires at `implement` in Plan or Manual; the slice machine, its inventory, and its transitions stay unchanged and carry no branch data. Wherever a Plan or Manual message prompts the user for `next-slice`, say that `next-slice` confirms the slice is implemented and committed.
