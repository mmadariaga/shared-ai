# Crystallization-close route choice (sai-explore only)

**Same-turn choice served at crystallization close, re-presented by `explore-slice@1` idle via `next.follow` while pending slices remain.** The first presentation runs in the same turn as the `Ready to Propose` block emission — Closure State is `crystallized`, the stage TODO is cleared, the `recordedList` for the emitted set is emitted, and the panel stays empty from block emission until this choice resolves. It runs before any route dispatch. A successful slice may start the next pending slice automatically only under the Direct Build continuation authorization below. Fast-track never auto-selects this choice; the choice is always asked. The `inline-refusal` path and store/panel failure keep their current behavior with no fusion.

**The POC profile is never a route option here.** This selector carries exactly the three options below. The Direct Build `--no-specs` profile (the POC lane's pinned execution profile, `pipeline-direct-build.md`) is never offered as **Plan - Unattended**, never offered as **Manual**, and never appears as a fourth option or as a variant of **Direct Build - Unattended**: it is reachable only from inside the POC lane, which runs before `Review edge cases` and has already closed by the time this choice is presented.

Fetch @sai/policies/stage-machine.md and follow it for every store interaction; the verbs, errors, quoting, pointer, and degraded-mode contract are single-sourced there and are not restated here.
Fetch @sai/commands/explore/steps/slice.md for inventory wiring only.
Fetch @sai/commands/explore/steps/pipeline-selector.md for supervision state only.
Fetch @sai/commands/explore/steps/idea-list.md for route-owned entries only.

**Idle distinction (no machine version bump).** The machine stays `explore-slice@1`. The first presentation runs same-turn at crystallization close; prose distinguishes two idle cases for re-presentation while pending slices remain, and the transition table is unchanged:
- **First-idle with pending** — `stage` is `idle` with at least one pending slice (`set` minus `done` non-empty). A pending set remains after a completed slice: re-present the choice below once.
- **Rest-idle without pending** — `stage` is `idle` with no pending slice (`set` minus `done` empty, `active` cleared). The slice is done: rest, present no choice, dispatch nothing, and never restart a route.

**Inventory.** Slice names come from `Ready to Propose` blocks in chat, not the wire. A `recordedList` replaces `set` without moving the cursor. Do not run `openspec list --json`, enumerate changes on disk, or re-sort emitted names.

**Crystallization-close route choice presentation.** The first presentation runs in the same turn as block emission after the final `---` with the `recordedList` emit. There is no literal pipeline token. Route execution is entered only through this choice, and no token form is recognized. Present it through the harness-native picker per the "Closed-choice prompts" rule in `sai/policies/remember.md`: `AskUserQuestion` on Claude Code, the `question` tool on opencode. Only that native picker call counts as the choice — a plain-text list does not count. Per the concise-format rule in `@sai/policies/question-context.md`, the emitted `Ready to Propose` block(s) are the preceding plain-text context; keep the picker question to the short summary `How should this change proceed?` and keep each option description ≤ ~100 chars on rendered text without markup. It carries exactly three options, in this fixed order, each carrying its fixed one-line description, with fixed English titles `Plan - Unattended`, `Direct Build - Unattended`, `Manual`. The stable machine-readable route identities are exactly `plan-unattended`, `direct-build-unattended`, and `manual`; they are not localized and are never accepted as compatibility aliases:

- **Plan - Unattended** — Runs `sai-1` and `sai-2` to create the plan and stops for pre-implementation human review.
- **Direct Build - Unattended** — Implements the change directly and updates specs afterward: ideal for fixes and simple changes.
- **Manual** — Paste the `Ready to Propose` block into a new chat with `/sai-1-spec`.

The question text and each option description render in the user's language per the crystallization language gate (crystallization-language-gates.md step-local item 8); the fixed option titles remain exactly `Plan - Unattended`, `Direct Build - Unattended`, and `Manual`. The literals `review-loop`, `/sai-1-spec`, and `/sai-2-design` stay verbatim English. Selecting **Plan - Unattended** is the explicit user act that authorizes delegated writes; it is consent to choice and dispatch only and is never consent to answer a later worker question. Selecting **Direct Build - Unattended** likewise authorizes delegated writes for the implementer, backfill, and archive workers AND pre-authorizes exactly one local commit; it too is consent to choice and dispatch only. `--fast-track` auto-selects nothing: the choice is always asked, and it is the one gate to delegated writes that fast-track never skips.

Do not fetch `pipeline-plan-unattended.md` or `pipeline-direct-build.md` at route-choice presentation. Once a route is chosen, emit `{intent: plan}` or `{intent: direct-build}` to `explore-slice@1` per `@sai/policies/stage-machine.md`; the machine starts only the first pending slice, and `slice.md` owns its parked-slice rules. Never send a slice name or `pick`. On Direct Build, after a non-rejected emit and before loading `pipeline-direct-build.md` or dispatching a worker, ask the one-time continuation question above when its condition is met. If the response carries `rejected: ALREADY_RUNNING`, dispatch nothing and acknowledge that a route is already running or that the first pending slice is parked in the other route; a later slice cannot bypass it. If the response carries `rejected: NO_PENDING_SLICE`, distinguish an empty crystallization set (no change crystallized; prompt block-first) from an exhausted set (all crystallized changes already completed); dispatch nothing in either case. Selection while `active` is already running dispatches and queues nothing (E3). After a non-rejected emit, consume `next.follow` per the same policy. Plan loads `pipeline-plan-unattended.md` at sai-1; Direct Build loads `pipeline-direct-build.md` at build-implement. Direct Build enters only through that emit plus `next.follow`; never enter via an ad-hoc Temp script or any other helper path.

A free-text answer that maps to neither route option is treated as **Manual** (`route_mode = manual`) and follows the same no-dispatch, no-state-change, no-injected-marker, and no-second-choice rules below. **Manual is not terminal** — re-present the choice whenever the user asks for it (a turn whose dominant intent is to run the **Plan - Unattended** or **Direct Build - Unattended** route or to see the choice again; no token form exists and none is recognized), with no cap on re-presentations.

**Direct Build continuation authorization (authoritative state and consent).** Keep `direct_build_continuation_prompted` and `direct_build_continuation_answer` in conversation state for the current `last_crystallization_set`. Initialize `direct_build_continuation_prompted` to `false` and `direct_build_continuation_answer` to `unasked`; the answer becomes `yes` or `no` when resolved. Reset both values and set `pending_direct_build_change` to `null` only when a new crystallization replaces that set; Manual and Plan selections do not clear them. When Direct Build is chosen with more than one pending slice and `direct_build_continuation_prompted` is `false`, ask once through the harness-native picker, even if earlier slices used Manual or Plan; a prior chat-stated answer does not suppress this picker. After the user answers, set `direct_build_continuation_prompted` to `true`. Only an explicit `yes` authorizes automatic continuation; `No`, a declined answer, or any answer that does not clearly map to `yes` resolves to `no`. If one or zero pending slices remain, do not ask. Keep the resolved answer for the whole crystallization set; never ask again for that set.

**Question context.** The picker follows `@sai/policies/question-context.md`: give the user complete, plain-language context before opening it. Localize the context, question, option labels, and descriptions. Define `{pending_count}` as all pending slices in `last_crystallization_set` minus `completed_changes`, including the current first-pending slice; render `{active_change}` as that slice's change name. Present this context before the picker:

> There are {pending_count} proposed slices still pending, in their proposed order. The current slice is {active_change}; it will finish first. I need your choice because each automatically started later slice makes a local commit. Yes starts each remaining slice in order after its predecessor succeeds and authorizes one local commit per automatically started slice; nothing is pushed. No lets this slice finish, then asks you which route to use for the next slice. If this slice fails, is cancelled, or needs intervention, no later slice starts.

Then present the concise picker question “Should later slices start automatically after each successful slice?” (about 200 characters maximum) with localized option labels and descriptions of about 100 characters maximum. Keep stable option values `yes` and `no`:

- **Yes** (`yes`) — Start each later slice in order; authorize one local commit each, never push.
- **No** (`no`) — After this slice succeeds, ask me which route to use next.

The Direct Build route choice authorizes the currently selected slice's existing single local commit. The continuation answer authorizes neither another route nor any other mutation.

**Continuation resolution (authoritative).** An explicit chat-stated `yes` or `no` outside an active slice updates `direct_build_continuation_answer` immediately, but never selects a route or dispatches a slice. While a slice is active, keep `pending_direct_build_change` in conversation state as either `null` or the latest explicit change: its requested answer (`yes` or `no`, if any) and `route_requested` (`true` only when the user explicitly asks to choose another route). Queue it without interrupting the active slice. After the current slice returns a clean terminal result, apply any queued answer, then resolve in this order: with no pending slices, return `set_complete`; with `route_requested: true`, return `route_choice`; otherwise, answer `yes` returns `auto_continue` and answer `no` returns `route_choice`. If no change was queued, resolve from the stored answer by the same yes/no mapping. Clear the queued change after consuming the resolution. A non-clean result never starts a later slice and leaves the queued change pending until the slice completes cleanly. Thus a queued change from `no` to `yes` auto-starts the next Direct Build slice; `no` offers the route choice; and an explicit request to choose another route offers the route choice regardless of the answer. This state and resolver are owned here; `pipeline-direct-build.md` consumes their result but does not redefine it.

**Deterministic choice (ordered, no name picker).** On a **Plan - Unattended** or **Direct Build - Unattended** choice, use only the pending set (`set` minus `done`, preserving crystallization order; equivalently `last_crystallization_set` minus `completed_changes`):
- If no slice has been crystallized in this chat, acknowledge that no change has been crystallized and dispatch nothing.
- If no uncompleted entry remains, acknowledge that every change of the last crystallization turn is already completed and dispatch nothing.
- If one or more uncompleted entries remain, route only the first pending slice in crystallization order. Do not present a slice-name picker, even when multiple entries remain. The same first-pending rule applies to Manual handoff, Plan, and Direct Build.
- Never re-run a completed slice. A later crystallization turn replaces the pending set with that turn's emitted names; every name in the new set leaves `completed_changes` so a re-crystallized change re-enters at the first route step over its new block. Blocks from earlier turns are assumed applied or discarded and are no longer arbitrated here. A material idea change before choice invalidates the crystallized set and restarts at `Explore change` (E6).

**Route-owned panel entries (authoritative).** The choice creates the route entries; no baseline evidence entries exist. Clear the stage TODO at block emission and first render only at choice resolution (E5). The selected path creates its own entries with no baseline items:
- **Plan** (`route_mode = plan-unattended`): exactly `sai-1`, `sai-2`, `Implement`, with `sai-1` `in_progress` and the rest `pending`, then dispatch the supervised spec worker. A clean spec convergence completes `sai-1` and starts `sai-2` as `in_progress`. A clean terminal design result completes `sai-2` and starts `Implement` as `in_progress`; it does not claim implementation ran.
- **Direct Build** (`route_mode = direct-build-unattended`): exactly `Build/Implement`, `Backfill`, and `Archive`, with `Build/Implement` `in_progress`. The display label `Build/Implement` is a Build-route label only and is never the `/sai-build` command or the `meta-build` composition. The underlying eight-step Direct Build contract remains authoritative while the panel shows only these three high-level stages.
- **Manual** (`route_mode = manual`): exactly `Manual handoff`. It becomes `completed` when the path-specific handoff is emitted. Manual creates no delegated entries, dispatches no worker, changes no supervision state, and authorizes no delegated work (E1). Emit once the path-specific handoff — including the executable `/sai-1-spec` block-paste example (paste the `Ready to Propose` block, not just the name) — plus the keep-window-open recommendation, with no second choice in that turn.

**Post-Manual handoff and recommendation (owns B7).**

1. Definitions for post-**Manual** emission only:
- **handoff**: the path-specific next-step instruction for opening a new chat with `/sai-1-spec`, choosing the wording that matches the crystallization path that just closed:
  - **Single-change path**: emit the existing `**Open a new chat**` instruction and run `/sai-1-spec` with the content above.
  - **Sliced path**: Tell the user to take the **first** block to a new chat with `/sai-1-spec`, and that each later slice becomes its own change once its predecessor is specced (the "new change per follow-up" pattern).
  - **Inline-refusal path** stays outside this close (see below).
- **recommendation**: one keep-window-open prose outside the handoff block: plain conversational free-text prose rendered in the user's language per the crystallization language gate (crystallization-language-gates.md step-local item 8) / `sai/policies/remember.md` (only the recommendation is localized — `Ready to Propose` scaffolding and next-step command lines stay English). It tells the user to keep this explore window open and return to it to review and refine the artifacts that `/sai-1-spec` and `/sai-2-design` create next (per the `explore-crystallization-block` capability). It replaces the removed auto-fired review picker (item 9) as the thing that closes the post-**Manual** turn. The recommendation names the literal token `review-loop` exactly once for the user-triggered review loop; the token is never presented through a picker and is never auto-started or auto-offered. The recommendation names no pipeline token. The standing user-triggered review path remains available while the deferred route choice governs only delegated execution.

The handoff's surrounding prose follows the selected crystallization language per the crystallization language gate (crystallization-language-gates.md step-local item 8); `/sai-1-spec`, `/sai-2-design`, and `review-loop` remain verbatim English.

2. Post-**Manual** emission: when the deferred route choice resolves to **Manual**, or gives an answer that maps to neither choice option, emit exactly once the closing path's handoff plus the recommendation, with no second choice in that turn. A deferred choice resolving to **Plan - Unattended** or **Direct Build - Unattended** never emits handoff or recommendation; their terminal texts stay untouched. The deferred route choice describes those branches by reference to this shared rule.

**Inline-refusal path**: stays outside this close and keeps its immediate handoff with no route choice: emit the existing handoff: "Creating a proposal opens a new context. The paste-ready block follows — copy it and start a new chat with `/sai-1-spec` to keep the spec session clean." Do not dispatch a proposal in-session. Present no choice on that path.

Choice re-presentations carry no prior handoff; every new deferred **Manual** resolution re-emits handoff plus recommendation once.

Route state is conversation-only and scoped to the first pending slice: retain its `**Change name**`, the chosen mode, the ordered route steps, each step's `pending | in_progress | completed` state, and the active step. Reset route state when a new slice starts; preserve completed slices and every pending slice in crystallization order. Route state is emitted only by the explore coordinator, is never authored by a worker, is never persisted, and creates no milestone stamps. Old `reviewed-sai-1` and `reviewed-sai-2` references mark, clear, or render nothing; each path owns its entries (E7).

A failed, cancelled, STOP-bearing, coordinator-disproved, or unrecovered result leaves the active route step `pending` and retryable, preserves earlier completed route steps, starts no later route step, and parks the slice in `explore-slice@1` per `slice.md`; only a clean terminal result completes the route (E4). On retry, the route is rebuilt for the same first-pending slice from its mode's fixed ordered steps. Never re-run completed slices (E2). After a clean Direct Build slice, `pipeline-direct-build.md` automatically starts the next first-pending slice only when `direct_build_continuation_answer` is `yes` and no queued change requires a route choice; otherwise, re-present this route choice once. Plan and Manual never auto-start later slices.
