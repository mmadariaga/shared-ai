# Crystallization-close route choice (sai-explore only)

**Same-turn choice served at crystallization close, re-presented by `explore-slice@1` idle via `next.follow` while pending slices remain.** The first presentation runs in the same turn as the `Ready to Propose` block emission — Closure State is `crystallized`, the stage TODO is cleared, the `recordedList` for the emitted set is emitted, and the panel stays empty from block emission until this choice resolves. It runs before any route dispatch. Fast-track never auto-selects this choice; the choice is always asked. The `inline-refusal` path, the uncertainty POC pause, and store/panel failure keep their current behavior with no fusion.

Fetch @sai/policies/stage-machine.md and follow it for every store interaction; the verbs, errors, quoting, pointer, and degraded-mode contract are single-sourced there and are not restated here.
Fetch @sai/commands/explore/steps/slice.md for inventory wiring only.
Fetch @sai/commands/explore/steps/pipeline-selector.md for supervision state only.
Fetch @sai/commands/explore/steps/idea-list.md for route-owned entries only.

**Idle distinction (no machine version bump).** The machine stays `explore-slice@1`. The first presentation runs same-turn at crystallization close; prose distinguishes two idle cases for re-presentation while pending slices remain, and the transition table is unchanged:
- **First-idle with pending** — `stage` is `idle` with at least one pending slice (`set` minus `done` non-empty). A pending set remains after a completed slice: re-present the choice below once.
- **Rest-idle without pending** — `stage` is `idle` with no pending slice (`set` minus `done` empty, `active` cleared). The slice is done: rest, present no choice, dispatch nothing, and never restart a route.

**Inventory.** Slice names come from `Ready to Propose` blocks in chat, not the wire. A `recordedList` replaces `set` without moving the cursor. Do not run `openspec list --json`, enumerate changes on disk, or re-sort emitted names.

**Crystallization-close route choice presentation.** The first presentation runs in the same turn as block emission after the final `---` with the `recordedList` emit. There is no literal pipeline token. Route execution is entered only through this choice, and no token form is recognized. Present it through the harness-native picker per `sai/policies/remember.md` (L10–15): `AskUserQuestion` on Claude Code, the `question` tool on opencode. Only that native picker call counts as the choice — a plain-text list does not count. It carries exactly three options, in this fixed order, each carrying its fixed one-line description, with fixed English titles `Plan - Unattended`, `Direct Build - Unattended`, `Manual`. The stable machine-readable route identities are exactly `plan-unattended`, `direct-build-unattended`, and `manual`; they are not localized and are never accepted as compatibility aliases:

- **Plan - Unattended** — Runs `sai-1` and `sai-2` to create the plan and stops for pre-implementation human review.
- **Direct Build - Unattended** — Implements the change directly and updates specs afterward: ideal for fixes and simple changes.
- **Manual** — Proceed manually by pasting the `Ready to Propose` block into a new chat with `/sai-1-spec` (full control over the process).

The question text and each option description render in the user's language per item 8; the fixed option titles remain exactly `Plan - Unattended`, `Direct Build - Unattended`, and `Manual`. The literals `review-loop`, `/sai-1-spec`, and `/sai-2-design` stay verbatim English. Selecting **Plan - Unattended** is the explicit user act that authorizes delegated writes; it is consent to choice and dispatch only and is never consent to answer a later worker question. Selecting **Direct Build - Unattended** likewise authorizes delegated writes for the implementer, backfill, and archive workers AND pre-authorizes exactly one local commit; it too is consent to choice and dispatch only. `--fast-track` auto-selects nothing: the choice is always asked, and it is the one gate to delegated writes that fast-track never skips.

Do not fetch `pipeline-plan-unattended.md` or `pipeline-direct-build.md` at choice presentation. On a **Plan - Unattended** choice, emit `{intent: plan}` to `explore-slice@1` per `@sai/policies/stage-machine.md`. On a **Direct Build - Unattended** choice, emit `{intent: direct-build}` to the same machine per the same policy. If the response carries `rejected: ALREADY_RUNNING`, acknowledge already running and dispatch nothing. Selection while `active` is already running dispatches and queues nothing (E3). After a non-rejected emit, consume `next.follow` per the same policy. Plan loads `pipeline-plan-unattended.md` at sai-1; Direct Build loads `pipeline-direct-build.md` at build-implement. Direct Build enters only through that emit plus `next.follow`; never enter via an ad-hoc Temp script or any other helper path.

A free-text answer that maps to neither option is treated as **Manual** (`route_mode = manual`) and follows the same no-dispatch, no-state-change, no-injected-marker, and no-second-choice rules below. **Manual is not terminal** — re-present the choice whenever the user asks for it (a turn whose dominant intent is to run the **Plan - Unattended** or **Direct Build - Unattended** route or to see the choice again; no token form exists and none is recognized), with no cap on re-presentations.

**Deterministic choice.** On a **Plan - Unattended** or **Direct Build - Unattended** choice, use only the pending set (`set` minus `done`, preserving crystallization order; equivalently `last_crystallization_set` minus `completed_changes`):
- If no slice has been crystallized in this chat, acknowledge that no change has been crystallized and dispatch nothing.
- If no uncompleted entry remains, acknowledge that every change of the last crystallization turn is already completed and dispatch nothing.
- If exactly one uncompleted entry remains, dispatch that sole change without a picker; no intermediate picker is presented.
- If multiple uncompleted entries remain, present one harness-native ordered picker containing the uncompleted names in emission order followed by `Cancel`. Dispatch at most one selected entry.
  - If the user selects `Cancel`, dispatch nothing and leave every state value unchanged.
- Never re-run a completed slice. A later crystallization turn replaces the pending set with that turn's emitted names; every name in the new set leaves `completed_changes` so a re-crystallized change re-enters at the first route step over its new block. Blocks from earlier turns are assumed applied or discarded and are no longer arbitrated here. A material idea change before choice invalidates the crystallized set and restarts at `Explore change` (E6).

**Route-owned panel entries (authoritative).** The choice creates the route entries; no baseline evidence entries exist. Clear the stage TODO at block emission and first render only at choice resolution (E5). The selected path creates its own entries with no baseline items:
- **Plan** (`route_mode = plan-unattended`): exactly `sai-1`, `sai-2`, `Implement`, with `sai-1` `in_progress` and the rest `pending`, then dispatch the supervised spec worker. A clean spec convergence completes `sai-1` and starts `sai-2` as `in_progress`. A clean terminal design result completes `sai-2` and starts `Implement` as `in_progress`; it does not claim implementation ran.
- **Direct Build** (`route_mode = direct-build-unattended`): exactly `Build/Implement`, `Backfill`, and `Archive`, with `Build/Implement` `in_progress`. The display label `Build/Implement` is a Build-route label only and is never the `/sai-build` command or the `meta-build` composition. The underlying eight-step Direct Build contract remains authoritative while the panel shows only these three high-level stages.
- **Manual** (`route_mode = manual`): exactly `Manual handoff`. It becomes `completed` when the path-specific handoff is emitted. Manual creates no delegated entries, dispatches no worker, changes no supervision state, and authorizes no delegated work (E1). Emit once the path-specific handoff — including the executable `/sai-1-spec` block-paste example (paste the `Ready to Propose` block, not just the name) — plus the keep-window-open recommendation, with no second choice in that turn.

Route state is conversation-only and scoped to the chosen slice: retain the chosen `**Change name**`, the chosen mode, the ordered route steps, each step's `pending | in_progress | completed` state, and the active step. Reset route state when a new slice is chosen; preserve completed slices and all pending slices. Route state is emitted only by the explore coordinator, is never authored by a worker, is never persisted, and creates no milestone stamps. Old `reviewed-sai-1` and `reviewed-sai-2` references mark, clear, or render nothing; each path owns its entries (E7).

A failed, cancelled, STOP-bearing, coordinator-disproved, or unrecovered result leaves the active route step `pending` and retryable, preserves earlier completed route steps, and starts no later route step; only a clean terminal result completes the route (E4). On retry, the route is rebuilt for the same chosen slice from its mode's fixed ordered steps. Re-present the choice per pending slice and never re-run completed slices (E2). Multi-slice sets re-present this choice per pending slice; completing one slice returns to first-idle with pending and presents the choice again for the next slice.
