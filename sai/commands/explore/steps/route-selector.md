# Crystallization route choice (sai-explore only)

**After printing the blocks, your one remaining action is the native route picker below (`## Native route picker`).** The inventory is already recorded; do not end the turn on the printed blocks.

**Picker presentation now; route selection after its answer.** The shared close in `crystallization-protocol.md` owns block emission, stage-panel handling, and ordered inventory recording; its block emit records the complete ordered inventory before any block is displayed, and only after that checkpoint succeeds does its `next.follow` load this selector. When no slice is active, the picker is the immediate action after the printed blocks: present the native three-option picker at the end of the same assistant turn that displayed the complete block set; the user's answer arrives in a later turn. If a slice is still active, its own pointer remains authoritative and no new picker is opened. It succeeds only when a complete inventory is in the machine's `waiting` state. A panel-unavailable notice does not block the close when inventory recording succeeds; a state-store or step-load failure stops before a choice. The `inline-refusal` path remains outside this selector.

**Route gate (single source).** Opening the picker exposes no route and authorizes no work: no route intent, panel entry, or dispatch occurs on picker presentation alone. `explore-slice@1` keeps route intents blocked until a valid picker answer is received and `{intent: route-choice}` is emitted (`ROUTE_CHOICE_REQUIRED`), and it re-locks the gate whenever a slice finishes or is parked. Every later presentation is therefore a fresh picker for the first pending slice; never reuse an earlier answer. The one exception is the Direct Build continuation below, which emits `{intent: auto-continue}` instead. Fast-track never auto-selects a route. There is no literal pipeline token.

**The POC profile is never a route option here.** This selector recognizes exactly the three route choices below. The Direct Build `--no-specs` profile (the POC lane's pinned execution profile, `pipeline-direct-build.md`) is reachable only from inside the POC lane, which runs before `Review edge cases` and has already closed by the time this choice is presented; it is never offered as a fourth route or as a variant of any route here.

Fetch @sai/policies/stage-machine.md and follow it for every store interaction; the verbs, errors, quoting, pointer, and degraded-mode contract are single-sourced there and are not restated here.
Fetch @sai/commands/explore/steps/slice.md for inventory wiring only.
Fetch @sai/commands/explore/steps/pipeline-selector.md for supervision state only.
Fetch @sai/commands/explore/steps/idea-list.md for route-owned entries only.
Fetch @sai/policies/question-context.md and follow it for the route picker.

**Waiting state (no machine version bump).** The machine stays `explore-slice@1`.
- **Before inventory** — the initial `idle` state has no complete inventory. Plan and Direct Build intents are rejected; `next.follow` is `none`.
- **Waiting with pending slices** — `stage` is `waiting`, inventory is complete, and at least one slice is pending (`set` minus `done` is non-empty). The native picker below applies to the first pending slice; route work waits for its answer.
- **Waiting with no pending slices** — `stage` is `waiting` with no pending slice and `active` cleared. The set is exhausted: acknowledge that no route can start and dispatch nothing.
- A route that fails or is cancelled parks its active slice back in `waiting`. Its returned pointer may load this selector in the same assistant turn; present a fresh native picker. A pending set remains after a completed slice: offer the picker again unless the Direct Build continuation resolves to `auto_continue`.

**Inventory.** Slice names come from `Ready to Propose` blocks in chat, not the wire. A `recordedList` replaces `set` without moving a running cursor, discards parked cursors, and makes the newest complete block set authoritative. A name in the new set is pending even if that same name completed under an older set. Do not run `openspec list --json`, enumerate changes on disk, or re-sort emitted names.

**Reply-pending state.** Keep `route_choice_reply_pending` in conversation state for the current `last_crystallization_set`. It starts `false`; the shared close sets it to `true` only after its block emit has recorded the inventory and every block has been displayed. Reset it to `false` when a new crystallization replaces the set, then set it to `true` as that new close ends. After an accepted Plan, Direct Build, or Manual picker answer, set it to `false`. If this selector is reached after a route result, set it to `true` before presenting a fresh native picker. A cancelled, absent, invalid, or ambiguous response keeps it `true` and emits no route intent. It is not persisted or sent to a worker.

## Native route picker

This is a closed choice. Present it only after a complete ordered inventory has been recorded successfully and the machine returns this selector, and only when at least one slice is pending. Before opening the picker, use the user's language for a short context that names the first-pending change, states that the complete proposal set was recorded in display order, and explains that this selection chooses only the route for that change. Explain that Plan and Direct Build authorize their existing delegated-write scopes only after the user selects them; Direct Build also authorizes its existing one local commit. Manual starts no worker and uses the block in a new `/sai-1-spec` chat. This context, question, and options follow `@sai/policies/question-context.md`; fixed route titles and command literals stay unchanged.

Use the active harness's native picker: Claude Code uses `AskUserQuestion`; opencode uses the `question` tool. Present exactly one single-select question, localized from “Which route should start for the first pending change?”, with these three options in this order. Localize descriptions, but keep the fixed option labels exactly as shown:

1. Label: `Plan - Unattended`. Description: Create the spec/design plan and stop for your review. Stable identity: `plan-unattended`.
2. Label: `Direct Build - Unattended`. Description: Implement, update specs, archive, and authorize one local commit. Stable identity: `direct-build-unattended`.
3. Label: `Manual`. Description: Take this block to a new chat with `/sai-1-spec`; start no worker. Stable identity: `manual`.

The only accepted route choices, in order, are:

- **Plan - Unattended** (`plan-unattended`) — Runs `sai-1` and `sai-2` to create the plan and stops for pre-implementation human review.
- **Direct Build - Unattended** (`direct-build-unattended`) — Implements the change directly and updates specs afterward: ideal for fixes and simple changes.
- **Manual** (`manual`) — Paste the `Ready to Propose` block into a new chat with `/sai-1-spec`.

Keep the stable identities out of the picker text; they are not localized and are selected only through their corresponding native picker options, never accepted as text aliases.

**Invalid answers.** An answer that does not map to exactly one fixed picker option is ambiguous: select no route, emit no route intent, and dispatch nothing. Map only the exact returned fixed label to its identity; a native picker answer is the only route-choice input, so a typed route name outside the picker, a cancelled picker, an absent response, an `Other`/free-text answer, or an answer that maps to zero or multiple options is ambiguous too; never infer a route from option position or free text. State that no route was selected, preserve the waiting inventory, emit no route intent (no `{intent: route-choice}`, `plan`, or `direct-build`) until one valid option is returned, keep `route_choice_reply_pending = true`, and re-present the native picker. If the user revises the proposed idea instead of selecting an option, apply `common.md`'s material-change rule and do not route the stale set.

**Consent.** The route explanation renders in the user's language per the crystallization language gate (crystallization-language-gates.md step-local item 8); the fixed route names remain exactly `Plan - Unattended`, `Direct Build - Unattended`, and `Manual`. The literals `review-loop`, `/sai-1-spec`, and `/sai-2-design` stay verbatim English. Selecting **Plan - Unattended** is the explicit user act that authorizes delegated writes; it is consent to choice and dispatch only and is never consent to answer a later worker question. Selecting **Direct Build - Unattended** likewise authorizes delegated writes for the implementer, backfill, and archive workers AND pre-authorizes exactly one local commit; it too is consent to choice and dispatch only. `--fast-track` auto-selects nothing: the native picker requires an explicit answer, and that answer is the one gate to delegated writes that fast-track never skips.

## After a valid answer

After exactly one valid picker answer, record its stable identity in conversation state, set `route_choice_reply_pending = false`, and emit `{intent: route-choice}` to `explore-slice@1`. Follow the returned pointer. This event is emitted only after the user's picker answer; it unlocks route processing but does not itself choose or start a route. Then interpret only the recorded picker identity: Plan and Direct Build emit `{intent: plan}` or `{intent: direct-build}` to `explore-slice@1` per `@sai/policies/stage-machine.md`; never send a slice name or `pick`. Manual creates no delegated route. The machine starts only the first pending slice, and `slice.md` owns its parked-slice rules.

Load `pipeline-plan-unattended.md` or `pipeline-direct-build.md` only through the route emit's `next.follow`, never at picker presentation. On Direct Build, after a non-rejected emit and before loading `pipeline-direct-build.md` or dispatching a worker, ask the continuation question (next section) when its condition is met.

Handle each rejection by dispatching nothing:
- `ALREADY_RUNNING` — acknowledge that a route is already running. Selection while `active` is already running queues nothing (E3).
- `PARKED_IN_OTHER_MODE` — explain that the first pending slice is parked in the other route and resumes only there; a later slice cannot bypass it.
- `NO_PENDING_SLICE` — distinguish an empty crystallization set (no change crystallized; prompt block-first) from an exhausted set (all crystallized changes already completed).

After a non-rejected emit, consume `next.follow` per the same policy. Plan loads `pipeline-plan-unattended.md` at sai-1; Direct Build loads `pipeline-direct-build.md` at build-implement. Direct Build enters only through that emit plus `next.follow`; never enter via an ad-hoc Temp script or any other helper path.

**Manual is not terminal** — after a Manual handoff, re-present the native route picker only when the user asks to see the choice again or to run **Plan - Unattended** or **Direct Build - Unattended**; no token form exists and none is recognized. There is no cap on re-presentations.

## Direct Build continuation

**Direct Build continuation authorization (authoritative state and consent).** Keep `direct_build_continuation_prompted` and `direct_build_continuation_answer` in conversation state for the current `last_crystallization_set`. Initialize `direct_build_continuation_prompted` to `false` and `direct_build_continuation_answer` to `unasked`; the answer becomes `yes` or `no` when resolved. Reset both values and set `pending_direct_build_change` to `null` only when a new crystallization replaces that set; Manual and Plan selections do not clear them. When Direct Build is chosen with more than one pending slice and `direct_build_continuation_prompted` is `false`, ask once through the harness-native picker, even if earlier slices used Manual or Plan; a prior chat-stated answer does not suppress this picker, because the answer exists only once the picker has asked. After the user answers, set `direct_build_continuation_prompted` to `true`. Only an explicit `yes` authorizes automatic continuation; `No`, a declined answer, or any answer that does not clearly map to `yes` resolves to `no`. If one or zero pending slices remain, do not ask. Keep the resolved answer for the whole crystallization set; never ask again for that set.

**Direct Build continuation question context.** This separate question remains a native picker and is not the route choice above. It follows `@sai/policies/question-context.md`: give the user complete, plain-language context before opening it. Localize the context, question, option labels, and descriptions. Define `{pending_count}` as all pending slices in `last_crystallization_set` minus `completed_changes`, including the current first-pending slice; render `{active_change}` as that slice's change name. Present this context before the picker:

> There are {pending_count} proposed slices still pending, in their proposed order. The current slice is {active_change}; it will finish first. I need your choice because each automatically started later slice makes a local commit. Yes starts each remaining slice in order after its predecessor succeeds and authorizes one local commit per automatically started slice; nothing is pushed. No lets this slice finish, then presents the native route picker for the next slice. If this slice fails, is cancelled, or needs intervention, no later slice starts.

Then present the concise picker question “Should later slices start automatically after each successful slice?” (about 200 characters maximum) with localized option labels and descriptions of about 100 characters maximum. Keep stable option values `yes` and `no`:

- **Yes** (`yes`) — Start each later slice in order; authorize one local commit each, never push.
- **No** (`no`) — After this slice succeeds, present the native route picker for the next slice.

The Direct Build route choice authorizes the currently selected slice's existing single local commit. The continuation answer authorizes neither another route nor any other mutation.

**Continuation resolution (authoritative).** Once `direct_build_continuation_prompted` is `true`, an explicit chat-stated `yes` or `no` outside an active slice updates `direct_build_continuation_answer` immediately, but never selects a route or dispatches a slice. While a slice is active, keep `pending_direct_build_change` in conversation state as either `null` or the latest explicit change: its requested answer (`yes` or `no`, if any) and `route_requested` (`true` only when the user explicitly asks to choose another route). Queue it without interrupting the active slice. After the current slice returns a clean terminal result, apply any queued answer, then resolve in this order: with no pending slices, return `set_complete`; with `route_requested: true`, return `route_choice`; otherwise, answer `yes` returns `auto_continue` and answer `no` returns `route_choice`. If no change was queued, resolve from the stored answer by the same yes/no mapping. Clear the queued change after consuming the resolution. A non-clean result never starts a later slice and leaves the queued change pending until the slice completes cleanly. Thus a queued change from `no` to `yes` auto-starts the next Direct Build slice; `no` presents a fresh native route picker; and an explicit request to choose another route presents that picker regardless of the answer. `auto_continue` emits `{intent: auto-continue}`, which the machine accepts only right after a clean Direct Build finish. This state and resolver are owned here; `pipeline-direct-build.md` consumes their result but does not redefine it.

## Selection, panel, and route state

**Deterministic selection** (ordered, no name picker). On a valid **Plan - Unattended** or **Direct Build - Unattended** picker answer, use only the pending set (`set` minus `done`, preserving crystallization order; equivalently `last_crystallization_set` minus `completed_changes`):
- If no slice has been crystallized in this chat, acknowledge that no change has been crystallized and dispatch nothing.
- If no uncompleted entry remains, acknowledge that every change of the last crystallization turn is already completed and dispatch nothing.
- If one or more uncompleted entries remain, route only the first pending slice in crystallization order. Do not present a slice-name picker, even when multiple entries remain. The same first-pending rule applies to Manual handoff, Plan, and Direct Build.
- Never re-run a completed slice. A later crystallization turn replaces the pending set with that turn's emitted names; every name in the new set leaves `completed_changes` so a re-crystallized change re-enters at the first route step over its new block. Blocks from earlier turns are assumed applied or discarded and are no longer arbitrated here. A material idea change before choice invalidates the crystallized set and restarts at `Explore change` (E6).

**Route-owned panel entries (authoritative).** The choice creates the route entries; no baseline evidence entries exist. Clear the stage TODO at block emission and first render only at choice resolution (E5). The selected path creates its own entries with no baseline items:
- **Plan** (`route_mode = plan-unattended`): exactly `sai-1`, `sai-2`, `Implement`, with `sai-1` `in_progress` and the rest `pending`, then dispatch the supervised spec worker. A clean spec convergence completes `sai-1` and starts `sai-2` as `in_progress`. A clean terminal design result completes `sai-2` and starts `Implement` as `in_progress`; it does not claim implementation ran.
- **Direct Build** (`route_mode = direct-build-unattended`): exactly `Build/Implement`, `Backfill`, and `Archive`, with `Build/Implement` `in_progress`. The display label `Build/Implement` is a Build-route label only and is never the `/sai-build` command or the `meta-build` composition. The underlying eight-step Direct Build contract remains authoritative while the panel shows only these three high-level stages.
- **Manual** (`route_mode = manual`): exactly `Manual handoff`. It becomes `completed` when the path-specific handoff is emitted. Manual creates no delegated entries, dispatches no worker, changes no supervision state, and authorizes no delegated work (E1). Emit once the path-specific handoff — including the executable `/sai-1-spec` block-paste example (paste the `Ready to Propose` block, not just the name) — plus the keep-window-open recommendation, with no second choice in that turn.

**Post-Manual handoff and recommendation (owns B7).** When the picker returns exactly **Manual**, emit exactly once the closing path's handoff plus the recommendation, with no second choice in that turn. An ambiguous answer follows **Invalid answers** above and emits no handoff. **Plan - Unattended** and **Direct Build - Unattended** never emit handoff or recommendation; their terminal texts stay untouched. Choice re-presentations carry no prior handoff; every new **Manual** answer re-emits handoff plus recommendation once.
- **handoff**: the path-specific next-step instruction for opening a new chat with `/sai-1-spec`, matching the crystallization path that just closed:
  - **Single-change path**: emit the existing `**Open a new chat**` instruction and run `/sai-1-spec` with the content above.
  - **Sliced path**: Tell the user to take the **first** block to a new chat with `/sai-1-spec`, and that each later slice becomes its own change once its predecessor is specced (the "new change per follow-up" pattern).
- **recommendation**: one keep-window-open prose outside the handoff block, rendered in the user's language per the crystallization language gate (crystallization-language-gates.md step-local item 8) / `sai/policies/remember.md` (only the recommendation is localized — `Ready to Propose` scaffolding and next-step command lines stay English). It tells the user to keep this explore window open and return to it to review and refine the artifacts that `/sai-1-spec` and `/sai-2-design` create next (per the `explore-crystallization-block` capability), and closes the post-**Manual** turn. It names the literal token `review-loop` exactly once for the user-triggered review loop; the token is never presented through a picker and is never auto-started or auto-offered. The recommendation names no pipeline token.

The handoff's surrounding prose follows the selected crystallization language per the crystallization language gate (crystallization-language-gates.md step-local item 8); `/sai-1-spec`, `/sai-2-design`, and `review-loop` remain verbatim English.

**Inline-refusal path**: stays outside this close and keeps its immediate handoff with no route choice: emit the existing handoff: "Creating a proposal opens a new context. The paste-ready block follows — copy it and start a new chat with `/sai-1-spec` to keep the spec session clean." Do not dispatch a proposal in-session. Present no choice on that path.

Route state is conversation-only and scoped to the first pending slice: retain its `**Change name**`, the chosen mode, the ordered route steps, each step's `pending | in_progress | completed` state, and the active step. Reset route state when a new slice starts; preserve completed slices and every pending slice in crystallization order. Route state is emitted only by the explore coordinator, is never authored by a worker, is never persisted, and creates no milestone stamps. Each path owns its entries (E7).

A failed, cancelled, STOP-bearing, coordinator-disproved, or unrecovered result leaves the active route step `pending` and retryable, preserves earlier completed route steps, starts no later route step, and parks the slice in `explore-slice@1` per `slice.md`; only a clean terminal result completes the route (E4). A retry needs a fresh picker answer in the same mode and resumes the same first-pending slice at its parked step, with earlier route steps still `completed`. Never re-run completed slices (E2). After a clean Direct Build slice, `pipeline-direct-build.md` automatically starts the next first-pending slice only when the continuation resolves to `auto_continue`; otherwise, re-present this route choice once. Plan and Manual never auto-start later slices.
