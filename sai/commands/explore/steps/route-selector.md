# Crystallization route choice (sai-explore only)

**After printing the documents, start `## Optional pre-route actions` below (rounds 1 and 2), then present `## Native route picker` (round 3).** The inventory is already recorded; do not end the turn on the printed documents.

**Preparation first; route selection after its answer.** The shared close in `crystallization-protocol.md` owns document emission, stage-panel handling, and ordered inventory recording; its document emit records the complete ordered inventory before any document is displayed, and only after that checkpoint succeeds does its `next.follow` load this selector. When no slice is active, start the optional actions after the printed documents in that same assistant turn. Present the native three-option picker (round 3) only after rounds 1 and 2 have finished or been skipped; the user's route answer arrives in a later turn. If a slice is still active, its own pointer remains authoritative and no new question is opened. It succeeds only when a complete inventory is in the machine's `waiting` state. A panel-unavailable notice does not block the close when inventory recording succeeds; a state-store or step-load failure stops before a choice.

**Route gate (single source).** Opening the picker exposes no route and authorizes no work: no route intent, panel entry, or dispatch occurs on picker presentation alone. `explore-slice@1` keeps route intents blocked until a valid picker answer is received and `{intent: route-choice}` is emitted (`ROUTE_CHOICE_REQUIRED`), and it re-locks the gate whenever a slice finishes or is parked. For initial selection and later slices, present a fresh picker; never reuse an earlier answer. A pending Direct Build execution uses the resumption branch below instead. Automatic later-slice continuation emits `{intent: auto-continue}` under its existing consent. There is no literal pipeline token.

**The POC profile is never a route option here.** This selector recognizes exactly the three route choices below. The Direct Build `--no-specs` profile (the POC lane's pinned execution profile, `pipeline-direct-build.md`) is reachable only from inside the POC lane, which runs before `Review edge cases` and has already closed by the time this choice is presented; it is never offered as a fourth route or as a variant of any route here.

Fetch `@sai/policies/stage-machine.md` and follow it for every store interaction; the verbs, errors, quoting, pointer, and degraded-mode contract are single-sourced there and are not restated here.
Fetch `@sai/commands/explore/steps/slice.md` for inventory wiring only.
Fetch `@sai/commands/explore/steps/pipeline-selector.md` for supervision state only.
Fetch `@sai/commands/explore/steps/idea-list.md` for route-owned entries only.
Fetch `@sai/policies/question-context.md` and follow it for the route picker.
Fetch `@sai/policies/question-rounds.md` and follow it for every round below.

**Waiting state (no machine version bump).** The machine stays `explore-slice@1`.
- **Before inventory** — the initial `idle` state has no complete inventory. Plan and Direct Build intents are rejected; `next.follow` is `none`.
- **Waiting with pending slices** — `stage` is `waiting`, inventory is complete, and at least one slice is pending (`set` minus `done` is non-empty). The native picker below applies to the first pending slice; route work waits for its answer.
- **Waiting with no pending slices** — `stage` is `waiting` with no pending slice and `active` cleared. The set is exhausted: acknowledge that no route can start and dispatch nothing.
- A route that fails or is cancelled parks its active slice back in `waiting`. On its returned selector pointer, distinguish pending Direct Build execution from initial selection before presenting any options. Plan keeps its existing fresh native picker. After a completed slice, offer the picker for the next slice unless Direct Build continuation resolves to `auto_continue`.

**Inventory.** Slice names come from change documents in chat, not the wire. A `recordedList` replaces `set` without moving a running cursor and makes the newest complete document set authoritative. A slice whose stored document hash is unchanged keeps its completion and its parked cursor, and the publication answer stays when the set of change names is unchanged; every other name in the new set is pending, with no parked cursor, even if that same name completed under an older set. Do not run `openspec list --json`, enumerate changes on disk, or re-sort emitted names.

**Reply-pending state.** Keep `route_choice_reply_pending` in conversation state for the current `last_crystallization_set`. It starts `false`; the shared close sets it to `true` only after its document emit has recorded the inventory and every document has been displayed. Reset it to `false` when a new crystallization replaces the set, then set it to `true` as that new close ends. After an accepted Plan, Direct Build, or Manual picker answer, set it to `false`. If this selector is reached after a route result requiring a fresh route selection, set it to `true` before presenting a fresh native picker. A pending Direct Build execution keeps it `false` and uses the decision below. A cancelled, absent, invalid, or ambiguous route-choice response keeps it `true` and emits no route intent. It is not persisted or sent to a worker.

## Pending Direct Build execution

Before the native route picker, inspect the retained conversation state and the
first pending slice's parked mode under `slice.md`. If it is a pending Direct
Build execution, use this branch; initial selection, completed-slice selection,
and Plan behavior keep the picker below. Reach
`direct-build-coordinator.md`'s **Run state** and **Resume** only for this
pending execution.

1. Respond to a recoverable error as an obstacle under
   `@sai/policies/obstacle-escalation.md` before asking for a decision. Keep the original route identity, scope, and
   two-local-commit authorization. A recovery hand-off is not route selection.
2. When user intervention is needed, present only executable actions under
   `@sai/policies/obstacle-escalation.md` and `@sai/policies/question-context.md`, using
   the harness-native picker per the "Closed-choice prompts" rule in
   `sai/policies/remember.md` (`AskUserQuestion` on Claude Code, `question` on opencode). Name the change,
   accepted work, pending operation, blocking cause, and remaining budget.
   Offer `Resume Direct Build` only when retained state and existing recovery
   rules permit the pending operation; offer a concrete action to resolve the
   blocker when available, `Back to pending`, `Restart from the first step`,
   and a rewind to a later item the stored run state offers (the moves of
   step 4), and `Remain stopped`. Plan and Manual do not replace
   this pending execution. Budget exhaustion offers no automatic retry; an
   uncertain mutation offers verification, not replay. Invalid or cancelled
   answers preserve the stop and dispatch nothing.
3. On an explicit executable resume choice (or explicit same-chat request to
   resume), emit `{intent: resume-direct-build}` without `route-choice`, a new
   route selection, or a slice name, and consume `next.follow`. Reuse the
   retained state at its first pending step; this decision grants no additional
   attempts or commit. `Remain stopped` emits nothing and retains that state.
   `RESUMPTION_REQUIRED` redirects here without dispatch;
   `NO_PENDING_DIRECT_BUILD` requires checking state before any work, never an
   implicit new execution.
4. A pending execution that cannot or should not resume has an exit that
   keeps the set. `Back to pending` emits `--set intent=goto --set target=pending
   --set reason=<user-request|correction>`: the parked cursor is discarded, the
   completed slices, the inventory, and the publication answer stay, and the
   route picker below is presented again. `Restart from the first step` emits
   `--set intent=goto --set target=build-implement --set reason=<user-request|correction>`
   and then `{intent: resume-direct-build}`: the saved cursor becomes the first
   step and the card initializes fresh run state for it (Resume of
   `direct-build-coordinator.md`). A later item is a target only when the
   stored run state of the slice holds its checkpoint: `status` of
   `direct-build-run@1` lists the re-enterable items in `items`, and `goto`
   with `--set target=backfill` or `--set target=archive` followed by
   `{intent: resume-direct-build}` re-enters it with that state. Every move
   authorizes nothing the first selection did not, and `Back to pending` asks for
   a new selector answer. Never reset `explore-slice@1` for this: that clears
   completed slices and the publication answer.

## Optional pre-route actions

The normal post-crystallization flow is three conditional question rounds, each presented under `@sai/policies/question-rounds.md`: **round 1** asks the backlog, branch and assignment questions; **round 2** asks the publication approval; **round 3** asks the route and, conditionally, the Direct Build continuation, the branch base question, and the publication question (`## Native route picker`, `## Branch base question`, `## Publication question`), so every start-up decision of the change travels in one document. A round with no applicable question is skipped. A `Publish and stop` answer to the backlog question ends the invocation after its publication, before round 3 (`## Publish and stop close`). The three rounds describe the normal flow, not a limit: clarification, corrections, a publication `edit`, `More` for bases, an ambiguous branch name, assignee conflicts, and failures add interactions outside them. Explore presents the questions and coordinates the rounds; `to-backlog` and `new-change-branch` keep their validation and execution and never depend on Explore.

After `to-backlog` finishes with a completed set publication on any supported provider, Fetch `@sai/policies/backlog-origin-transport.md` and complete it before resolving the branch name. Transport failure leaves this action pending and blocks route disclosure; a returned correspondence kept only in conversation is not completion.

Pass the complete recorded document set, as one exported file reference per document (`node <sai-state-path> block --note "export the change document" <id> <change-name> --export --harness <claude|opencode>` returns its `document_file` and `hash`; `to-backlog` verifies the file and publishes the document as it is, with no model rewrite), whether the feature was explicitly sliced, and existing whole-objective parent content to the accepted `to-backlog` owner. When the conversation started from an existing backlog issue and the feature is sliced, also name that originating issue: `to-backlog` publishes the slices as its children and rewrites its description with the whole-objective content, instead of creating a replacement parent. Retain its structured correspondence, not titles, for later selected-slice provenance. Pass only one issue identity to `new-change-branch`: the current slice's returned identity for a single change or `per-slice`, or the originating principal issue's identity for `shared`; reuse an already-prepared initial branch. Dependency order comes from the validator-owned stored inventory, with blockers before dependents and original order among independent slices. Optional actions do not authorize assignment; only the assignment question's own answer does.

Run this sequence once for the current `last_crystallization_set`, only after every document is visible and a pending slice exists. Keep every round answer, its authorization, each completed action result and the current action in conversation state only, scoped to the current crystallized set; reset them when a new crystallization replaces the set. A picker retry, Manual re-presentation, or later slice does not repeat completed actions or re-ask answered rounds. If a skill pauses for input outside a round, keep that action pending and wait; resume there rather than opening another question. Apply `common.md`'s material-change rule before classifying a reply that revises the idea.

**Round rules.** Ask in the user's language, with short context naming the crystallized work and each question's action. A round collects every answer before it executes any action; each answer authorizes only its own action; only an explicit answer authorizes, and a missing, cancelled, or ambiguous answer leaves its action pending. Cancelling the whole round leaves all its actions pending. An edit or state change invalidates exactly the answers whose context changed; completed actions keep their results and are never repeated during recovery. Use Claude Code's `AskUserQuestion` with its automatic free-text Other entry, or opencode's `question` tool with custom/free-text input enabled. Offer **Yes** and **No** in that order, with stable values `yes` and `no`, except for the backlog question, the slice-set branch question, the assignment question, the publication question and the base question below, which have their own options.

**Before round 1.** When a linked issue exists (the originating issue, the selected `Backlog origin:` line, or an issue from an earlier publication in this conversation), resolve read-only, through the provider's existing `inspect-assignment` and `propose-assignment` capabilities (`skills/universal/to-backlog/providers/registry.json`), the concrete assignee (the authenticated user), every current assignee, and every affected issue. No registry capability returns the authenticated user without an existing issue, so when no issue exists yet the concrete assignee cannot be named: the assignment question is then asked in its intent form when the backlog answer can be `publish-continue` (an issue will be created), and left out when it is `skip-continue`.

**Round 1.** Ask only the questions that apply, in this order. The assignment question is a conditional question under `@sai/policies/question-rounds.md`: it is included when its condition can still hold, and its answer takes effect only when the condition holds.

1. **Backlog question:** “Would you like to create or update a backlog item for this crystallized proposal?” Retain the word `backlog` in the question and option descriptions in every language. Spanish example: “¿Quieres crear o actualizar el backlog con esta propuesta?” Offer three options in this order, localizing labels and descriptions and keeping the stable values: **Publish and continue with implementation** (`publish-continue`; Spanish “Publicar y continuar con la implementación”), **Publish and stop** (`publish-stop`; Spanish “Publicar y parar”), **Do not publish and continue with implementation** (`skip-continue`; Spanish “No publicar y continuar con la implementación”). Describe the two publish options as creating or updating the backlog and `skip-continue` as skipping the backlog action. One `Publish` meaning covers creation and update: the skill resolves creation versus update, and a link alone is not an origin decision by Explore. `publish-continue` and `publish-stop` record the decision: round 2 asks the publication approval and nothing is published before it. `publish-continue` behaves as the former Yes and `skip-continue` as the former No, so the continue answers leave the flow below unchanged. `publish-stop` ends the invocation once `to-backlog` finishes (`## Publish and stop close`) and makes the branch and assignment answers of this round not applicable. On `skip-continue`, skip only this action and leave out the publication question. Present it through the harness-native picker per the "Closed-choice prompts" rule in `sai/policies/remember.md` (`AskUserQuestion` on Claude Code, `question` on opencode).
2. **Branch question:** a conditional question under `@sai/policies/question-rounds.md`, whose condition is that the backlog answer is `publish-continue` or `skip-continue`; under `publish-stop` its answer is recorded as not applicable: no branch is created and the base question is not asked. Ask one branch question for the whole `last_crystallization_set`, chosen by its size (the recorded `explore-slice@1` inventory, not the pending remainder). Keep `branch_strategy` in conversation state (`single`, `shared`, `per-slice`, or `none`) and `slice_branches` (slice name to the branch prepared for it) as defined in `## Slice branch chain`; reset both when a new crystallization replaces the set. The strategy is also recorded in `explore-slice@1` once the branch answer is final (`## Branch strategy record`).
   - **One recorded change:** “Would you like to create and switch to a local change branch for this crystallized proposal?” Yes records the decision: the branch name is resolved after publication, round 3 asks the base, and the branch is created at the creation point (`## Branch creation point`). On No, skip only this action and leave out the base question. Present it through the harness-native picker per the "Closed-choice prompts" rule in `sai/policies/remember.md` (`AskUserQuestion` on Claude Code, `question` on opencode).
   - **More than one recorded change (a slice set):** ask one three-choice question instead, localized from “Would you like to create a new branch?” (Spanish example: “¿Quieres crear una nueva rama?”). Offer these options in this order, localizing labels and descriptions and keeping the stable values `shared`, `per-slice`, `none`: **Yes, create a single one for the main issue** (`shared`; Spanish “Sí, crea una única para la issue principal”), **Create one branch per slice** (`per-slice`; Spanish “Crear una rama por slice”), **Do not create anything** (`none`; Spanish “No crear nada”). The question names the crystallized work and says that no branch is published. On `shared`, the pending branch is the one shared branch: it is decided through the installed `new-change-branch` skill as for a single change but with the originating principal issue's identity when one exists, created once at the creation point (`## Branch creation point`), and every slice reuses it. On `per-slice`, the first pending slice's branch is the pending branch, named after that slice and created at the creation point the same way; follow `## Slice branch chain` for every later slice. On `none`, skip only this action, keep the current branch and every existing branch as they are, and leave out the base question. Present it through the harness-native picker per the "Closed-choice prompts" rule in `sai/policies/remember.md` (`AskUserQuestion` on Claude Code, `question` on opencode).
3. **Assignment question:** a conditional question, localized from “If an issue is linked or will be created, should it be assigned when implementation starts?” It is asked once for the whole `last_crystallization_set`, and its answer is the **set-level assignment answer**: it applies to the issue of every slice in the set, so later slices start without asking it again (`backlog-implementation-start.md` § Set-level answer). Its condition is that the backlog answer is `publish-continue` or `skip-continue`; under `publish-stop` the answer is recorded as not applicable and nothing is assigned. Ask it when a linked issue exists. With no linked issue, ask it in its intent form only when the backlog answer can be `publish-continue` (the issue will be created); when the backlog answer is `skip-continue` it is left out, and the intent form applies only when the backlog answer is `publish-continue`. With a linked issue, name the concrete assignee and every affected issue before the picker, and say that nothing is assigned now and that assignment executes only when implementation starts. In the intent form no user is named yet: say that the authenticated user of the backlog provider will be assigned once the issue exists, and offer only **Assign** (`assign`) and **Skip assignment** (`skip`). When the condition ends up unmet (the answer was collected for an issue that is no longer linked), record the answer as not applicable: it authorizes nothing. Record the answer in conversation state as the set-level assignment answer, scoped to the current set and reset with it when a new crystallization replaces the set: an approved answer bound to the concrete user, the approved previous assignees, and the existing issue; an intent answer bound to the issue that will be created, with its user resolved at the first implementation start; `skip` bound to the set. `backlog-implementation-start.md` verifies it when each slice starts. Present it through the harness-native picker per the "Closed-choice prompts" rule in `sai/policies/remember.md` (`AskUserQuestion` on Claude Code, `question` on opencode).

**Round 2.** Runs only when the backlog answer is `publish-continue` or `publish-stop` and the prepared proposal does not report `auto_approve: true`; otherwise it is not presented. ## Branch creation point

A pending branch is the local change branch whose name is resolved (`After round 2`, step 2) and whose base round 3 asks (`## Branch base question`). One creation point serves the single, `shared`, and `per-slice` branches: right after exactly one valid route answer of round 3 and before `{intent: route-choice}` is emitted (before the hand-off for Manual), as `## After a valid answer` orders it. In Direct Build automatic continuation, a later `per-slice` branch is created at its own earlier point (`## Slice branch chain`).

Hand the installed `new-change-branch` skill the base answer of round 3 as a supplied base bound to the base reference it prepared, together with the resolved name. The skill creates the branch locally and switches to it, and never pushes or publishes. Its base-SHA recheck in `create` makes a base that moved since the preparation a failed creation. After the creation, record the branch as `slice_branches[<first pending slice name>]` when `branch_strategy` is `per-slice`.

- **No valid route answer.** A cancelled, absent, or invalid route answer starts no route and creates no branch, whatever the base answer was; the branch stays pending and the re-presented round 3 asks again.
- **Missing or cancelled base answer.** Create no branch and give up the branch for the set: set `branch_strategy` to `none`, start the route on the current branch, and withhold publication by keeping `publication_withheld` in conversation state, scoped to the set, so that every route reads the publication answer as `no`, whatever was answered, stored, or set by `pr.publishAfterRun`. No push ever reaches a branch the user did not authorize. The closing report of each slice says that the branch was not created and why, and that nothing was published for that reason.
- **Failed creation.** The failure blocks the route start and is an obstacle under `@sai/policies/obstacle-escalation.md`, escalated with the options `retry`, `skip`, and `stop`. `retry` prepares the chosen base again and repeats the creation. `skip` applies the missing-base rule above. `stop` starts no route, emits no route intent, keeps `route_choice_reply_pending = true`, and leaves the branch pending.
- **Manual.** The hand-off names the created branch and its base.

## Publish and stop close

Applies when the backlog answer is `publish-stop`. The answer lives in conversation state only, scoped to the current set: it is never stored in `explore-slice@1`. The round 1 branch and assignment answers are not applicable: no branch is created, nothing is assigned, and round 2 asks only the publication approval. An `edit` answer to the approval keeps this decision: the edited proposal gets its full confirmation, and the close below applies once it is published.

The close runs after `to-backlog` finishes, whichever way it ends: published; the approval cancelled; ended without complete success after the `to-backlog` recovery (`skills/universal/to-backlog/publication-recovery.md`), which it follows unchanged; or skipped through the `skip` answer of the retry-or-skip question that missing or denied skill access raises. Then, in this order:

1. Dispose the live explorers as `@sai/policies/worker-lifecycle.md` says, and retire the main-session chain as `@sai/policies/cache-warming.md` § Retire at terminal output says.
2. Print the terminal output in the user's language, stating the actual outcome:
   - **Published:** the issue link as `to-backlog` returned it: the created or updated issue for a single change, or the parent and every child for a sliced set (`skills/universal/to-backlog/slice-set.md`).
   - **Approval cancelled, or skipped after missing skill access:** that no backlog item was published.
   - **Recovery ended without complete success:** the result `to-backlog` reported: nothing published, or the published part with its links. A sliced set may be partially published, so never claim that nothing was published without that report.

The close emits no `explore-slice@1` intent, runs no `sai-state close`, never presents round 3, and emits no route intent. A later message in the same chat presents no route picker: implementing the change needs a new `/sai-explore` invocation, for example one that imports the published issue.

## Slice branch chain

Applies only after the slice-set branch question returned `per-slice` (`shared` creates nothing more; `none` and a single change keep the existing behavior). `slice_branches` and the chain live in conversation state only: never persist them, never send them to a worker, and never add them to `explore-slice@1` (the strategy itself is recorded there, `## Branch strategy record`). Inventory order is dependency order, so the chain's previous branch is the branch of the slice that precedes the starting slice in `last_crystallization_set`.

1. **When the chain grows.** Prepare a later slice's branch only when its previous slice is completed: Direct Build archive completed, or `next-slice` at `implement` in Plan or Manual. A slice that is pending, failed, cancelled, parked, or still at sai-1 or sai-2 holds the chain at its position, and planning completion alone never completes a slice. The first slice's branch is the pending branch, created at the creation point (`## Branch creation point`) from the base answer of round 3.
2. **When to create.** Prepare the starting slice's branch immediately before that slice starts, so no worker, Step 1 snapshot, or handoff runs on the previous slice's branch: at the creation point (`## Branch creation point`), after a valid Plan, Direct Build, or Manual picker answer and before `{intent: route-choice}` is emitted (for Manual, before the handoff), and in Direct Build automatic continuation before `{intent: auto-continue}` is emitted (`pipeline-direct-build.md`). Choosing `per-slice` authorizes every local creation and switch in the chain in advance, so automatic continuation asks nothing further.
3. **How to create.** For the first slice, follow `## Branch creation point`. For a later slice, load the installed `new-change-branch` skill with the slice's change name, the first branch's type, the slice's own issue identity when one was returned, `base` set to the previous slice's branch, and `require_clean: true`; the base is a supplied base through the skill's generic supplied-base capability, with no base question. Never push or publish.
4. **Uncommitted changes.** When creation stops on uncommitted changes, create nothing and start nothing: name the slice, say that the previous slice's work must be committed first, and wait. In automatic continuation present the native route picker for that slice instead. When the user reports the commit, retry the creation before the slice starts.
