# Crystallization route choice (sai-explore only)

**After printing the blocks, start `## Optional pre-route actions` below (rounds 1 and 2), then present `## Native route picker` (round 3).** The inventory is already recorded; do not end the turn on the printed blocks.

**Preparation first; route selection after its answer.** The shared close in `crystallization-protocol.md` owns block emission, stage-panel handling, and ordered inventory recording; its block emit records the complete ordered inventory before any block is displayed, and only after that checkpoint succeeds does its `next.follow` load this selector. When no slice is active, start the optional actions after the printed blocks in that same assistant turn. Present the native three-option picker (round 3) only after rounds 1 and 2 have finished or been skipped; the user's route answer arrives in a later turn. If a slice is still active, its own pointer remains authoritative and no new question is opened. It succeeds only when a complete inventory is in the machine's `waiting` state. A panel-unavailable notice does not block the close when inventory recording succeeds; a state-store or step-load failure stops before a choice.

**Route gate (single source).** Opening the picker exposes no route and authorizes no work: no route intent, panel entry, or dispatch occurs on picker presentation alone. `explore-slice@1` keeps route intents blocked until a valid picker answer is received and `{intent: route-choice}` is emitted (`ROUTE_CHOICE_REQUIRED`), and it re-locks the gate whenever a slice finishes or is parked. For initial selection and later slices, present a fresh picker; never reuse an earlier answer. A pending Direct Build execution uses the resumption branch below instead. Automatic later-slice continuation emits `{intent: auto-continue}` under its existing consent. Fast-track never auto-selects a route. There is no literal pipeline token.

**The POC profile is never a route option here.** This selector recognizes exactly the three route choices below. The Direct Build `--no-specs` profile (the POC lane's pinned execution profile, `pipeline-direct-build.md`) is reachable only from inside the POC lane, which runs before `Review edge cases` and has already closed by the time this choice is presented; it is never offered as a fourth route or as a variant of any route here.

Fetch @sai/policies/stage-machine.md and follow it for every store interaction; the verbs, errors, quoting, pointer, and degraded-mode contract are single-sourced there and are not restated here.
Fetch @sai/commands/explore/steps/slice.md for inventory wiring only.
Fetch @sai/commands/explore/steps/pipeline-selector.md for supervision state only.

Fetch @sai/policies/question-context.md and follow it for the route picker.

**Waiting state (no machine version bump).** The machine stays `explore-slice@1`.
- **Before inventory** — the initial `idle` state has no complete inventory. Plan and Direct Build intents are rejected; `next.follow` is `none`.
- **Waiting with pending slices** — `stage` is `waiting`, inventory is complete, and at least one slice is pending (`set` minus `done` is non-empty). The native picker below applies to the first pending slice; route work waits for its answer.
- **Waiting with no pending slices** — `stage` is `waiting` with no pending slice and `active` cleared. The set is exhausted: acknowledge that no route can start and dispatch nothing.
- A route that fails or is cancelled parks its active slice back in `waiting`. On its returned selector pointer, distinguish pending Direct Build execution from initial selection before presenting any options. Plan keeps its existing fresh native picker. After a completed slice, offer the picker for the next slice unless Direct Build continuation resolves to `auto_continue`.

**Inventory.** Slice names come from `Ready to Propose` blocks in chat, not the wire. A `recordedList` replaces `set` without moving a running cursor, discards parked cursors, and makes the newest complete block set authoritative. A name in the new set is pending even if that same name completed under an older set. Do not run `openspec list --json`, enumerate changes on disk, or re-sort emitted names.

**Reply-pending state.** Keep `route_choice_reply_pending` in conversation state for the current `last_crystallization_set`. It starts `false`; the shared close sets it to `true` only after its block emit has recorded the inventory and every block has been displayed. Reset it to `false` when a new crystallization replaces the set, then set it to `true` as that new close ends. After an accepted Plan, Direct Build, or Manual picker answer, set it to `false`. If this selector is reached after a route result requiring a fresh route selection, set it to `true` before presenting a fresh native picker. A pending Direct Build execution keeps it `false` and uses the decision below. A cancelled, absent, invalid, or ambiguous route-choice response keeps it `true` and emits no route intent. It is not persisted or sent to a worker.

## Optional pre-route actions

The normal post-crystallization flow is three conditional question rounds, each presented under `@sai/policies/question-rounds.md`: **round 1** asks the backlog, branch and assignment questions; **round 2** asks publication approval and the branch base; **round 3** asks the route and, conditionally, the Direct Build continuation and the change overview question (`## Native route picker`, `## Change overview question`). A round with no applicable question is skipped. The three rounds describe the normal flow, not a limit: clarification, corrections, a publication `edit`, `More` for bases, an ambiguous branch name, assignee conflicts, and failures add interactions outside them. Explore presents the questions and coordinates the rounds; `to-backlog` and `new-change-branch` keep their validation and execution and never depend on Explore.

After `to-backlog` finishes with a completed set publication on any supported provider, Fetch @sai/policies/backlog-origin-transport.md and complete it before resolving the branch name. Transport failure leaves this action pending and blocks route disclosure; a returned correspondence kept only in conversation is not completion.

Pass the complete recorded block set, whether the feature was explicitly sliced, and existing whole-objective parent content to the accepted `to-backlog` owner. When the conversation started from an existing backlog issue and the feature is sliced, also name that originating issue: `to-backlog` publishes the slices as its children and rewrites its description with the whole-objective content, instead of creating a replacement parent. Retain its structured correspondence, not titles, for later selected-slice provenance. Pass only one issue identity to `new-change-branch`: the current slice's returned identity for a single change or `per-slice`, or the originating principal issue's identity for `shared`; reuse an already-prepared initial branch. Dependency order comes from the validator-owned stored inventory, with blockers before dependents and original order among independent slices. Optional actions do not authorize assignment; only the assignment question's own answer does.

Run this sequence once for the current `last_crystallization_set`, only after every block is visible and a pending slice exists. Keep every round answer, its authorization, each completed action result and the current action in conversation state only, scoped to the current crystallized set; reset them when a new crystallization replaces the set. A picker retry, Manual re-presentation, or later slice does not repeat completed actions or re-ask answered rounds. If a skill pauses for input outside a round, keep that action pending and wait; resume there rather than opening another question. Apply `common.md`'s material-change rule before classifying a reply that revises the idea.

**Round rules.** Ask in the user's language, with short context naming the crystallized work and each question's action. A round collects every answer before it executes any action; each answer authorizes only its own action; only an explicit answer authorizes, and a missing, cancelled, or ambiguous answer leaves its action pending. Cancelling the whole round leaves all its actions pending. An edit or state change invalidates exactly the answers whose context changed; completed actions keep their results and are never repeated during recovery. Use Claude Code's `AskUserQuestion` with its automatic free-text Other entry, or opencode's `question` tool with custom/free-text input enabled. Offer **Yes** and **No** in that order, with stable values `yes` and `no`, except for the slice-set branch question, the assignment question, the publication question and the base question below, which have their own options. All questions remain explicit under `--fast-track` in Claude Code and opencode.

**Before round 1.** When a linked issue exists (the originating issue, the selected `**Backlog origin**`, or an issue from an earlier publication in this conversation), resolve read-only, through the provider's existing `inspect-assignment` and `propose-assignment` capabilities (`skills/universal/to-backlog/providers/registry.json`), the concrete assignee (the authenticated user), every current assignee, and every affected issue. No registry capability returns the authenticated user without an existing issue, so when no issue exists yet the concrete assignee cannot be named: the assignment question is then asked in its intent form when the backlog answer can be Yes (an issue will be created), and left out when it is No.

**Round 1.** Ask only the questions that apply, in this order. The assignment question is a conditional question under `@sai/policies/question-rounds.md`: it is included when its condition can still hold, and its answer takes effect only when the condition holds.

Yes records the decision: round 2 asks the publication approval and nothing is published before it. The skill resolves creation versus update; a link alone is not an origin decision by Explore. On No, skip only this action and leave out the publication question. Present it through the harness-native picker per the "Closed-choice prompts" rule in `sai/policies/remember.md` (`AskUserQuestion` on Claude Code, `question` on opencode).
2. **Branch question:** Ask one branch question for the whole `last_crystallization_set`, chosen by its size (the recorded `explore-slice@1` inventory, not the pending remainder). Keep `branch_strategy` in conversation state (`single`, `shared`, `per-slice`, or `none`) and `slice_branches` (slice name to the branch prepared for it) as defined in `## Slice branch chain`; reset both when a new crystallization replaces the set.
   - **One recorded change:** “Would you like to create and switch to a local change branch for this crystallized proposal?” Yes records the decision: round 2 asks the base and the branch is created after publication. On No, skip only this action and leave out the base question. Present it through the harness-native picker per the "Closed-choice prompts" rule in `sai/policies/remember.md` (`AskUserQuestion` on Claude Code, `question` on opencode).
   - **More than one recorded change (a slice set):** ask one three-choice question instead, localized from “Would you like to create a new branch?” (Spanish example: “¿Quieres crear una nueva rama?”). The question names the crystallized work and says that no branch is published. On `shared`, create the branch once after publication through the installed `new-change-branch` skill, as for a single change but with the originating principal issue's identity when one exists, and let every slice reuse that branch. On `per-slice`, create the first pending slice's branch the same way, named after that slice, then follow `## Slice branch chain` for every later slice. ## Slice branch chain

Applies only after the slice-set branch question returned `per-slice` (`shared` creates nothing more; `none` and a single change keep the existing behavior). The strategy, `slice_branches`, and the chain live in conversation state only: never persist them, never send them to a worker, and never add them to `explore-slice@1`. Inventory order is dependency order, so the chain's previous branch is the branch of the slice that precedes the starting slice in `last_crystallization_set`.

1. **When the chain grows.** Prepare a later slice's branch only when its previous slice is completed: Direct Build archive completed, or `next-slice` at `implement` in Plan or Manual. A slice that is pending, failed, cancelled, parked, or still at sai-1 or sai-2 holds the chain at its position, and planning completion alone never completes a slice. The first slice's branch is the initial branch prepared before the route picker.
2. **When to create.** Prepare the starting slice's branch immediately before that slice starts, so no worker, Step 1 snapshot, or handoff runs on the previous slice's branch: after a valid Plan, Direct Build, or Manual picker answer and before `{intent: route-choice}` is emitted (for Manual, before the handoff), and in Direct Build automatic continuation before `{intent: auto-continue}` is emitted (`pipeline-direct-build.md`). Choosing `per-slice` authorizes every local creation and switch in the chain in advance, so automatic continuation asks nothing further.
3. **How to create.** Load the installed `new-change-branch` skill with the slice's change name, the first branch's type, the slice's own issue identity when one was returned, `base` set to the previous slice's branch, and `require_clean: true`; the base is a supplied base through the skill's generic supplied-base capability, with no base question. Never push or publish.
4. **Uncommitted changes.** When creation stops on uncommitted changes, create nothing and start nothing: name the slice, say that the previous slice's work must be committed first, and wait. In automatic continuation present the native route picker for that slice instead. When the user reports the commit, retry the creation before the slice starts.
5. **Existing expected branch.** The expected name is the branch that the skill's `name` operation resolves for the slice; `name` reporting that the branch already exists is the lookup in git. When `slice_branches` records that branch for this slice (this conversation prepared it), resume on it: switch to it locally when it is not active, create nothing, and keep local changes. Otherwise ask one native closed-choice question, a conditional extra interaction outside the rounds, to reuse the existing branch (switch to it and record it) or to give a corrected name (run the skill again with it). Present it through the harness-native picker per the "Closed-choice prompts" rule in `sai/policies/remember.md` (`AskUserQuestion` on Claude Code, `question` on opencode). Never rename, overwrite, or delete the existing branch.
6. **Record.** After a branch is prepared or reused, set `slice_branches[<slice name>]` to it.

## Native route picker

This is round 3, a closed choice. Present it after rounds 1 and 2 have finished or been skipped, and only after a complete ordered inventory has been recorded successfully and the machine returns this selector, and only when at least one slice is pending and the pending-execution branch above does not apply. Before opening the picker, use the user's language for a short context that names the first-pending change, states that the complete proposal set was recorded in display order, and explains that this selection chooses only the route for that change. Explain that Plan and Direct Build authorize their existing delegated-write scopes only after the user selects them; Direct Build also authorizes its existing one local commit. Manual starts no worker and uses the block in a new `/sai-1-spec` chat. This context, question, and options follow `@sai/policies/question-context.md`; fixed route titles and command literals stay unchanged.

Present it through the harness-native picker per the "Closed-choice prompts" rule in `sai/policies/remember.md` (`AskUserQuestion` on Claude Code, `question` on opencode). Present round 3 under `@sai/policies/question-rounds.md`: the route question is single-select and always present, and the Direct Build continuation question and the change overview question below join the same round only when their conditions are met. Localize the route question from “Which route should start for the first pending change?”, with these three options in this order. Localize descriptions, but keep the fixed option labels exactly as shown:

1. Label: `Plan - Unattended`. Description: Create the spec/design plan and stop for your review. Stable identity: `plan-unattended`.
2. Label: `Direct Build - Unattended`. Description: Implement, update specs, archive, and authorize one local commit. Stable identity: `direct-build-unattended`.
3. Label: `Manual`. Description: Take this block to a new chat with `/sai-1-spec`; start no worker. Stable identity: `manual`.

The only accepted route choices, in order, are:

- **Plan - Unattended** (`plan-unattended`) — Runs `sai-1` and `sai-2` to create the plan and stops for pre-implementation human review.
- **Direct Build - Unattended** (`direct-build-unattended`) — Implements the change directly and updates specs afterward: ideal for fixes and simple changes.
- **Manual** (`manual`) — Paste the `Ready to Propose` block into a new chat with `/sai-1-spec`.

Keep the stable identities out of the picker text; they are not localized and are selected only through their corresponding native picker options, never accepted as text aliases.

**Invalid answers.** An answer that does not map to exactly one fixed picker option is ambiguous: select no route, emit no route intent, and dispatch nothing. Map only the exact returned fixed label to its identity; a native picker answer is the only route-choice input, so a typed route name outside the picker, a cancelled picker, an absent response, an `Other`/free-text answer, or an answer that maps to zero or multiple options is ambiguous too; never infer a route from option position or free text. State that no route was selected, preserve the waiting inventory, emit no route intent (no `{intent: route-choice}`, `plan`, or `direct-build`) until one valid option is returned, keep `route_choice_reply_pending = true`, and re-present the native picker. If the user revises the proposed idea instead of selecting an option, apply `common.md`'s material-change rule and do not route the stale set.

**Consent.** The route explanation renders in the user's language per the crystallization language gate (crystallization-language-gates.md step-local item 8); the fixed route names remain exactly `Plan - Unattended`, `Direct Build - Unattended`, and `Manual`. The literals `review-loop`, `/sai-1-spec`, and `/sai-2-design` stay verbatim English. Selecting **Plan - Unattended** is the explicit user act that authorizes delegated writes; it is consent to choice and dispatch only and is never consent to answer a later worker question. Selecting **Direct Build - Unattended** likewise authorizes delegated writes for the implementer, backfill, and archive workers AND pre-authorizes exactly one local commit; it too is consent to choice and dispatch only. `--fast-track` auto-selects nothing: the native picker requires an explicit answer, and that answer is the one gate to delegated writes that fast-track never skips.

## After a valid answer

After exactly one valid picker answer, record its stable identity in conversation state, prepare the slice's branch when `branch_strategy` is `per-slice` and it is not yet prepared (`## Slice branch chain`; a stop emits nothing and keeps `route_choice_reply_pending = true`), then set `route_choice_reply_pending = false` and emit `{intent: route-choice}` to `explore-slice@1`. Follow the returned pointer. This event is emitted only after the user's picker answer; it unlocks route processing but does not itself choose or start a route. Then interpret only the recorded picker identity: Plan and Direct Build emit `{intent: plan}` or `{intent: direct-build}` to `explore-slice@1` per `@sai/policies/stage-machine.md`; never send a slice name or `pick`. Manual creates no delegated route. The machine starts only the first pending slice, and `slice.md` owns its parked-slice rules.

Load `pipeline-plan-unattended.md` or `pipeline-direct-build.md` only through the route emit's `next.follow`, never at picker presentation. On Direct Build, apply the continuation answer that round 3 collected (next section) before loading `pipeline-direct-build.md` or dispatching a worker; no further question is asked here.

Handle each rejection by dispatching nothing:
- `ALREADY_RUNNING` — acknowledge that a route is already running. Selection while `active` is already running queues nothing (E3).
- `PARKED_IN_OTHER_MODE` — explain that the first pending slice is parked in the other route and resumes only there; a later slice cannot bypass it.
- `NO_PENDING_SLICE` — distinguish an empty crystallization set (no change crystallized; prompt block-first) from an exhausted set (all crystallized changes already completed).

After a non-rejected initial-selection emit, consume `next.follow` per the same policy. Plan loads `pipeline-plan-unattended.md` at sai-1; a new Direct Build execution loads `pipeline-direct-build.md` at build-implement. Pending Direct Build enters through `resume-direct-build` plus its parked-stage pointer as defined above. Direct Build enters only through its applicable machine emit plus `next.follow`; never enter via an ad-hoc Temp script or any other helper path.

**Manual is not terminal** — after a Manual handoff, re-present the native route picker only when the user asks to see the choice again or to run **Plan - Unattended** or **Direct Build - Unattended**; no token form exists and none is recognized. There is no cap on re-presentations.

## Direct Build continuation

**Direct Build continuation authorization (authoritative state and consent).** Keep `direct_build_continuation_prompted` and `direct_build_continuation_answer` in conversation state for the current `last_crystallization_set`. Initialize `direct_build_continuation_prompted` to `false` and `direct_build_continuation_answer` to `unasked`; the answer becomes `yes` or `no` when resolved. Reset both values and set `pending_direct_build_change` to `null` only when a new crystallization replaces that set; Manual and Plan selections do not clear them. Round 3 carries this question as a conditional question beside the route question when more than one pending slice remains and `direct_build_continuation_prompted` is `false`: ask once through the harness-native picker, even if earlier slices used Manual or Plan. A prior chat-stated answer does not suppress this picker, because the answer exists only once the picker has asked. The answer takes effect only when the same round's route answer is Direct Build: then set `direct_build_continuation_prompted` to `true` and record the answer. When the route answer is Plan or Manual, or no valid route was answered, ignore the continuation answer: it authorizes nothing, `direct_build_continuation_prompted` stays `false`, and the answer stays `unasked`, so a later Direct Build round asks again. Only an explicit `yes` authorizes automatic continuation; `No`, a declined answer, or any answer that does not clearly map to `yes` resolves to `no`. If one or zero pending slices remain, do not ask.
