# Common explore rules

**Read-only reminder.** Exploration is read-only: `sai-explore` creates, modifies, and deletes no files and implements no code (normative rule: `sai/commands/explore/instructions.md`). Writes happen only inside a route the user explicitly selects, under that route's contract; emitting a `Ready to Propose` block selects no route.

**Chat-start clear.** At invocation start, before any panel render, start with a fresh chat-scoped idea list and perform the start clear even when no candidate idea or route exists. The start clear removes entries bearing either marker prefix (`sai-explore-stage:` or `sai-idea-list:`), leaving other surfaces' entries in place. Use the per-harness panel binding's selective clear: the marker carrier is Claude Code `description` or opencode `priority`. The read covers the markers only and never derives list content. This is a claim action, not a render; it creates no entries. If the panel tool is unavailable, apply the one-time panel-degradation rule below. Later step loads do not repeat this clear.

**Pre-crystallization closure:** Maintain a conversation-only **Closure State** for the current idea. The state is exactly one of `active-uncrystallized`, `crystallized`, or `discarded`.

- Before a candidate idea exists, no Closure State is active and this closure rule does not apply. Once a candidate idea exists under active exploration, its state starts as `active-uncrystallized`. A materially changed idea resets the progression (**Material change** below) and begins a new `active-uncrystallized` lifecycle.
- The one-time readiness signal remains at most once per stable idea, does not transition the state, and does not suppress this rule. Its Readiness Statement is folded into the first applicable stage-aware reminder after solidification and never satisfies the actionable closure on its own.
- On every successful turn while the state is `active-uncrystallized`, finish with exactly one actionable closure. When a genuine unresolved question remains and its answer could change the idea, end with that relevant question and do not append a reminder. A question whose dominant purpose is only to navigate the exploration stages — for example, asking whether to use `next-step` or whether to move to the next phase without raising substantive uncertainty about the idea — does NOT count as a genuine unresolved question; fall through to the stage-aware reminder. A question that contains substantive uncertainty capable of changing the idea remains a genuine unresolved question even when navigation wording is also present. When no genuine unresolved question remains, end with this concise reminder selected from the current stage. This fallback reminder applies even when the only apparent question is phase navigation. At stages 1 and 2 (`Explore change` and `Review edge cases`), name `next-step`. At stage 3 (`Implementation details`), name `next-step` and retain this exact sentence: *"Say `crystallize` when ready; crystallization generates the paste-ready prompt for `/sai-1-spec`."* At stage 4 no stage-aware reminder is appended: end with the pending slicing or language-gate question, re-asked after an interruption, or the completed `Ready to Propose` block(s) followed by the **Crystallization-turn close (shared)**. Evaluate this rule again on every later successful qualifying turn, so the fallback reminder repeats even after readiness has already been emitted.
- An explicit crystallization request transitions the state to `crystallized` only after slicing and both language gates complete and the `Ready to Propose` block is emitted. Do not append the pre-crystallization question-or-reminder closure to that crystallization response; preserve the block's closing behavior. An explicit discard transitions the state to `discarded`, and subsequent successful responses about that discarded idea receive no pre-crystallization closure.
- This reminder is phase navigation for the active exploration lifecycle, not an unrelated follow-up proposal, and does not authorize unrelated work. Do not apply this successful-response closure to prerequisite halts, failures, cancellations, or completed post-crystallization review-loop closes; preserve their existing remediation literals, terminal behavior, and review-loop close-acknowledgment rule.

**Emission gate (on-demand crystallization)**

Before printing any `Ready to Propose` block, judge whether the idea is solid. The Readiness Statement is the one-line maturity judgment that the idea is solid enough to crystallize on request; it is never emitted as a separate closing line and never advances a stage. If the idea crystallizes before such a reminder fires, omit the statement because the explicit crystallization request already conveys the action. This behavior applies to both the single-change and sliced protocols.

The full `Ready to Propose` block(s) are printed only when the user explicitly asks to crystallize, and only after edge-case agreement. Recognized requests include asking to crystallize, asking for the paste-ready block, asking to create a proposal or run `/sai-1-spec`, and any advancement that enters `Crystallize`. A request made before edge-case agreement remains pending with no skip path. On entry into `Crystallize`, run the slicing assessment (size and friction) first, then evaluate the crystallization language gate and only then print the block(s); the overview-language gate runs later only when a supervised **Plan (unattended)** selection confirms a dispatchable change. The applicable stage-aware reminder remains actionable before stage 4.

**Staged progression advancement (`next-step` recognition).** The stage progression advances only when the user explicitly requests it: the literal token `next-step` — recognized by the same bare-token/dominant-intent machinery as the `review-loop` token, firing when the turn is a bare token (optionally with trivial punctuation or a greeting) or when advancing the progression is the turn's dominant intent — clear natural-language intent naming the next stage or requesting crystallization, or semantic confirmation of the proposed list at the `Review edge cases` or `Implementation details` stage. Mere containment of the string `next-step` SHALL NOT fire the token and never records agreement, and a turn that negates, defers, quotes, or discusses the token SHALL NOT advance the progression and never records agreement. At either list stage, semantic confirmation records the current ordered list as agreed and advances to the next stage within the same turn. A bare `next-step` turn at either list stage with a non-empty list likewise records the current ordered list as agreed and advances within the same turn with no separate confirmation, in all modes. A same-turn revision paired with `next-step` is a revision, not navigation: it updates and renumbers, stays open, re-asks, and does not advance. An ambiguous response — never a bare `next-step`, which is always confirmation — remains discussion: clarify and re-ask. Agreement in another language is valid when its intent is clearly affirmative. Implicit agreement applies to `next-step` only: a premature `crystallize` before agreement stays pending with no skip path. `sai-explore` SHALL NOT advance a stage on its own judgment that the idea is solid or ready. The machine consumes content-based recordings of agreed or empty lists rather than readiness; these are not readiness judgments. The one-line readiness signal never advances a stage. Entering `Crystallize` counts as the explicit crystallization request and immediately starts the slicing assessment and language-gate sequence once the crystallization step named by `next.follow` is fetched.

**Material change.** Material-change detection runs before selector-response classification. When a response materially changes the explored idea, reset wins: clear the pending maturity or later selector response, staged progression, pending crystallization request, and both agreed lists; return the new active-uncrystallized lifecycle to `Explore change`; and do not emit an edge-case prompt, later selector, crystallization, or advancement automatically. The new idea waits for explicit intent under the existing staged-progression rules. An unchanged idea never starts a second review.

**Post-POC return exception to material-change detection.** The automatic advancement out of the POC lane into `Review edge cases` (`poc-lane.md`, E6) is stage progression authored by the lane, never a material change: it never triggers the reset above, never discards the agreed candidate list, and never starts a new `active-uncrystallized` lifecycle. A genuine material change authored by the user still resets the progression exactly as always, inside the lane or outside it.

**Explore change stage (stage 1 — discovery ownership).** While the stage is `Explore change`, explore owns open discovery: ask the open questions that shape the idea. Once the idea is solid, ask directly whether to move to `Review edge cases`. A declining answer stays in `Explore change`; later advancement uses the existing `next-step` path. Explore never advances the stage on its own judgment that the idea is solid.

**POC trigger (evaluated at the close of stage 1 — stop 1 of the POC lane).** Before the progression leaves `Explore change`, judge once whether the idea warrants a disposable POC. A POC is an **experiment that discriminates between competing candidates** — not a proof that one approach works — so the axis fires only when competing candidates exist. It fires on either motive:

- **Technical viability** — the idea's technical or integration approach is unproven: it depends on a third party, service, or API the project has not integrated before (no existing wrapper, adapter, or proven usage), and the available documentation, examples, or prior art do not demonstrate the specific integration pattern the idea requires. The candidates are the competing **strategies** that might work.
- **Bug diagnosis** — the idea is a fix for a bug whose cause is not established, and several **root-cause theories** compete to explain the observed behavior. The candidates are those theories.

The axis **never** fires for product or UX uncertainty — a discovery spike, a UX experiment, or "we are not sure users want this" does not qualify. It also does **not** fire when mutually exclusive candidates with a discriminating observable cannot be formulated: with nothing for the experiment to discriminate, there is no POC and the progression continues to stage 2 as usual (E3). Name the specific third party and the specific documentation gap, or the specific observed behavior and its competing theories; a vague hunch is not a trigger.

When it fires, present the go/no-go through the harness-native picker per the "Closed-choice prompts" rule in `sai/policies/remember.md`: `AskUserQuestion` on Claude Code, the `question` tool on opencode. Render the fixed context as plain text before the picker in the ambient conversation language — state the motive and the specific uncertainty in concrete terms, that the POC is a disposable experiment run on its own branch or worktree and discarded when the lane closes, that it runs through Direct Build with `--no-specs` (implementer only — no backfill, no OpenSpec specs, no artifact archive; dirty code acceptable, minimal tests or human observation as the verdict authority), and that it is not a slice of the final set and renumbers no slice. The picker carries exactly two options, in this order:

- `Yes, run a POC before continuing` — enter the POC lane. Emit `{"intent":"poc-lane"}` to `explore-idea@1` per `@sai/policies/stage-machine.md` and follow the returned `next.follow` (`poc-lane.md`), which owns the candidate agreement, the POC execution, the verdict, and the verdict menu. The intent enters the conditional `poc-lane` stage and records no list.
- `No, continue without a POC` — the progression continues to `Review edge cases` with the technical risk accepted. The axis is not raised again for this idea; do not re-litigate the choice.

`--fast-track` does not auto-approve this go/no-go, and no stage advances on explore's own judgment that a POC is warranted.

**Late explicit POC entry (stages 2 through 4).** Technical uncertainty often becomes obvious only while writing edge cases or implementation details, so the door into the lane stays open after stage 1 — but only the user opens it. Declining the stage-1 go/no-go closes the automatic prompt for that idea, never the lane itself: the axis is never re-evaluated, nothing is ever re-asked, and no stage transition raises the question again. Nothing enters the lane automatically after stage 1.

At `Review edge cases`, `Implementation details`, and `Crystallize`, an explicit user request for a POC enters the lane from wherever the progression currently sits. Recognize the request with the same bare-token/dominant-intent machinery that recognizes `next-step`: the literal token `poc-lane`, or a turn whose dominant intent is asking to run a POC before continuing. Mere containment of the string, and a turn that negates, defers, quotes, or discusses it, SHALL NOT enter the lane. When it fires, emit `{"intent":"poc-lane-late"}` to `explore-idea@1` per `@sai/policies/stage-machine.md` and follow the returned `next.follow` (`poc-lane.md`), which owns the candidate agreement, the POC execution, the verdict, and the verdict menu exactly as it does for a stage-1 entry. The intent enters the conditional `poc-lane` stage and records no list. This request is available whether or not the stage-1 trigger fired and whether or not its go/no-go was declined; explore never requests it on the user's behalf, and `--fast-track` neither triggers nor skips it. A request made at `Crystallize` leaves the crystallization sequence with no `Ready to Propose` block emitted; crystallization resumes later through ordinary advancement, never by resuming a suspended crystallization.

**Agreed lists survive the lane.** Late entry is a detour, not a reset: it never skips, weakens, or re-opens an already agreed `E1..En` or `I1..In` list. The lane closes into `Review edge cases` (`poc-lane.md`) whichever stage it was entered from. When the progression re-enters a stage whose list is already agreed, the agreement stands: the stage emits no new list, runs no second review or confirmation question, and is left by ordinary `next-step` advancement.

**List stages (`Review edge cases` and `Implementation details`).** Each list stage emits its numbered list, then one plain conversational question that follows `@sai/policies/question-context.md`: in the ambient conversation language, preserving the literal identifiers, never a native yes/no picker, and never depending on a fixed agreement phrase. The question names `next-step` as the advancement action and states that a bare `next-step` confirms the list as written and advances in the same turn. Evaluate the answer by dominant semantic intent per **Staged progression advancement**. When nothing qualifies for the list, emit exactly `- None` and record the empty list as agreed. This deterministic empty-set recording is the sole content-based agreement form; every non-empty list still requires semantic user agreement. The machine's transition function consumes this recorded state and returns the next stage and step pointer.

**Rationale ownership (crystallization fields).** Explore owns trade-offs and WHY. Record the agreed trade-offs in the block's `Decisions & Rationale` and `Trade-offs Accepted` fields, and the agreed WHY in the block's `Why` plus `Key constraints` fields.

**Optional native stage selectors (additive, harness-neutral).** Native selectors supplement the existing text questions; they never replace, shorten, or convert those questions into agreement pickers. The active harness may expose this capability only when both `available: true` and `supportsFreeText: true`. A missing capability response, `available: false`, or `supportsFreeText: false` selects the unchanged text-only fallback and cannot advance the stage.

The shared capability and response shapes are conversation contracts, not harness-specific payloads:

`NativeStageSelectorCapability = { available: boolean, supportsFreeText: boolean, present(selector, orderedOptions) -> SelectorResponse }`

`SelectorResponse = { selector: maturity|later, kind: option|free-text, value: review-edge-cases|keep-iterating|next-step|discuss-ideas-feedback|null, text: string|null }`

For `kind: option`, `value` is the stable protocol value and `text` is `null`; for `kind: free-text`, `value` is `null` and `text` carries the user's response. A response is valid only for the selector that is currently pending. The optional capability is checked before presenting either selector, and the text-only path remains authoritative whenever the complete capability is unavailable.

After the unchanged existing maturity text question has been emitted, a supported capability may present one maturity selector in this order: a localized choice equivalent to review edge cases (`review-edge-cases`), a localized choice equivalent to keep iterating (`keep-iterating`), and the free-text path. In a Spanish conversation the labels are `Revisar edge cases` and `Seguir iterando`; other labels and surrounding prose follow the conversation language while preserving the same meanings and order. The maturity selector remains conversation-only and never agrees an edge-case list.

Selecting `review-edge-cases` enters the existing edge-case writing prompt for the current idea, records `ask_mode: false` for that interaction, and waits there. It does not agree the proposed list, run implementation details, crystallize, or advance beyond that prompt. After the edge-case prompt is handled, the staged flow advances only on a later explicit `next-step` request or equivalent natural-language advancement. Selecting `keep-iterating` or submitting maturity-selector free text keeps `ask_mode: true`, preserves the current stage and agreed lists, and performs no automatic progression.

**Phase A stage TODO paint rule.** While a candidate idea is under active exploration (Closure State `active-uncrystallized`), render a four-item stage TODO on the native task panel with the labels `Explore change`, `Review edge cases`, `Implementation details`, and `Crystallize`, in that order. The current stage renders `in_progress`, completed stages render `completed`, and remaining stages render `pending`. The TODO renders from the first turn in which a candidate idea exists, re-renders exactly once per turn that changes stage state, and does not render while no candidate idea exists.

**Conditional POC entry.** The POC lane is a conditional stage and adds no entry until it fires. The list stays at four entries for every idea whose POC trigger did not fire or whose go/no-go was declined and which never asked for the lane later. When the lane is entered — at the close of stage 1 or through the late explicit request above — the list grows to five entries by inserting `POC` between `Explore change` and `Review edge cases`, and it keeps that fifth entry for the rest of the idea's progression — `POC` renders `completed` once the lane is left, exactly like any other completed stage.

On a late entry the five-entry list is painted from the position the progression now holds, by the ordinary paint rule and with no extra bookkeeping: `Explore change` stays `completed`, `POC` renders `in_progress`, and the stages that follow it render `pending` because the progression passes through them again on its way back. Their agreed lists are untouched by the repaint.

Each stage-TODO entry carries the stage-ownership marker `sai-explore-stage:<stage-id>` (stage ids `explore-change`, `poc-lane`, `review-edge-cases`, `implementation-details`, `crystallize`) in the machine-readable panel entry field pinned by the per-harness idea-list render binding (opencode `priority`, Claude Code `description`), so stage entries stay visually distinct from every other surface's entries. Rendering goes through the per-harness idea-list render binding's Phase A machinery and originates exclusively from the coordinator session, never from a worker subagent; on panel-tool degradation record exactly one visible notice — `> Panel rendering unavailable; continuing without task-panel updates.` — disable panel calls for the rest of the chat, and continue without panel rendering. The stage TODO clears at block emission as part of the emission checkpoint (`steps/crystallization-protocol.md`) and never re-renders afterward; the panel stays empty from emission until the deferred route choice resolves, with the first Phase B render only at choice resolution (`steps/idea-list.md`).

**Step fetches.** A step file already loaded in this chat is followed from context, not fetched again; the stage machine's `next.hint` text never decides a fetch.
