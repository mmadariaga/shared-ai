  9. **Post-crystallization review loop (sai-explore only)**: The review is **not** auto-offered at crystallization. The crystallization turn closes via the **Crystallization-turn close (shared)** (items 5/6/7) and the crystallization-close pipeline selector (item 10). The selector remains a two-option **Auto** / **Manual** choice over delegated pipeline execution only — it is **not** the removed global Yes/No review picker, it never offers, starts, or substitutes for this review loop, and this review loop stays picker-free at crystallization. Treat the review as a **user-triggered standing invitation** with two entry paths: the **token path** — the user fires the literal token `review-loop`, which enters the per-change loop directly (see **Token trigger** below) — and the **semantic path** — the user accepts that standing invitation in natural language, or asks to review the downstream artifacts of the changes crystallized in this chat.

    **On the semantic path only**, ask a single sí/no question in **plain conversational text** — never the harness option-picker — rendered in the conversation's ambient language: whether the user wants to review the downstream artifacts of the changes crystallized in this chat. This plain-text global question is a **deliberate, narrowly-scoped exception** to the "Closed-choice prompts" native-picker rule in `sai/policies/remember.md` (L10–15); do NOT "correct" it back into an option-picker. The exception covers ONLY this global invitation — the four-option per-change navigation menu below stays a harness option-picker. The invitation carries **no precondition** — it is available whether or not any downstream artifact exists, and whether or not this chat crystallized any change — so the section behaves identically across sessions. Answering **no** is a hard stop on the entire review section; answering **yes** enters the per-change loop over the tracked crystallized set (a no-op that ends the section when that set is empty). The token path skips this question entirely.

    **Token trigger**: `sai-explore` recognizes the literal token `review-loop` as an explicit trigger for this loop. Firing it enters the per-change loop over the tracked crystallized set **directly** — do NOT ask the plain-text global sí/no question first, because typing the token already expresses consent, exactly as the Emission gate's `crystallize` token acts without further confirmation.

    - **Firing condition (intent, not substring)**: mere containment of the string does NOT fire the token. It fires only when the turn is a **bare token** (the token alone, optionally with trivial punctuation or a greeting) or when entering the review loop is the turn's **dominant intent** — the same "explicitly asks" test the Emission gate applies to `crystallize`. A turn that negates, defers, quotes, or discusses the token — including a turn that specifies or debates this very feature — does NOT fire it.
    - **Availability**: the token is live for the whole session, independently of when — or whether — a crystallization turn occurred. Recognize it before any crystallization, on any later turn after one, and in a chat that never crystallized anything. This is the same **no precondition** property the standing invitation carries.
    - **Empty tracked set**: when the tracked crystallized set is empty, end the section immediately without entering any iteration, and print a one-line acknowledgment in the conversation's ambient language stating that no change has been crystallized in this chat and there is nothing to review. Silence is NOT an acceptable response to the token — it is indistinguishable from ignoring the user. The **Closing the loop** rule applies only after the loop actually ran; this empty-set token keeps its distinct one-line acknowledgment.
    - **English-invariant**: the token is a literal English string. Do NOT localize or translate it, and do NOT match a localized equivalent; a localized paraphrase does not fire the token path (it may still fire the semantic path on its own merits, which still asks the global question).
    - **Mixed trigger**: when a single turn satisfies both the token path and item 3's artifact-review path, serve the **item-3 review first**, then enter the loop directly with the global sí/no question skipped. The token's consent substitutes for the invitation item 3 would otherwise append; the review is never dropped.

    The token path differs from the semantic path ONLY in that the global question is skipped. Everything below — the tracked crystallized set, first-emission ordering, the per-change picker, the language gate reuse, and the read-only constraint — applies identically to both paths.

    **Tracked crystallized set**: The loop's change source is a chat-scoped tracked set: every `**Change name**` value this chat's crystallization turns (items 5/6) emitted, in first-emission order. It starts empty at the beginning of the chat, gains a name only when a crystallization turn emits one, preserves first-emission order, ignores duplicate later emissions of an already-tracked name, and is in-conversation only — never written to a file or config and never derived from repository state. It stays empty until the first crystallization turn emits a change name.

    **On Yes**: iterate the tracked crystallized set in its preserved first-emission order, without re-sorting and without any repository-wide change discovery (do NOT run `openspec list --json` or otherwise enumerate non-archived changes on disk). Unrelated non-archived changes that this chat did not crystallize are excluded. When the tracked set is empty, the per-change loop is a no-op and the section ends immediately after the global Yes. For each change in the tracked set, enter the active per-change processing window before displaying its picker and present a **four-option picker** parameterized by the current change, in this fixed order: `Review sai-1's artifacts`, `Review sai-2's artifacts`, `Review change-overview`, and `Skip`. The option labels are fixed English literals and are not localized. The picker question text follows the conversation's ambient language while naming the literal `exit` token verbatim and untranslated as the way to terminate the review loop. The `exit` token is entered through the picker's free-text field and is not a fifth native option.

   **Review Engine**: the independently invocable unit that performs the review work of every review transaction. Its invocation contract is exactly `Review Engine(changeName, artifactSetDesignator)` — `changeName` is exactly the authoritative change name, and `artifactSetDesignator` is one of `sai-1`, `sai-2`, or `change-overview`, the artifact-set designator naming the requested set. The engine is independent of the picker, the Tracked Crystallized Set, prior findings, cached contents, cached existence state, and all other navigation state. Every review selection — including a repeated selection for the same change and artifact set — starts a new review transaction, and each transaction performs this sequence in order before forming findings:
     1. Use the chat-scoped crystallized change name as authoritative and independently resolve only the exact `openspec/changes/{change-name}/` directory, without repository-wide change discovery and without substituting another change name.
      2. Check whether that exact current change directory exists. If it does not, report the missing change directory without presenting its child artifact paths as independently checked, then mark or clear nothing; the missing-directory report does not claim the child checks ran.
     3. Only when the directory exists, check every requested current path: `proposal.md` and every file matching `specs/**/*.md` for sai-1; `design.md`, `tasks.md`, and `interfaces.md` for sai-2; and `change-overview.md` plus all five source sets (`proposal.md`, `specs/**/*.md`, `design.md`, `tasks.md`, `interfaces.md`) for change-overview. Report each missing child path or missing artifact set as an absence within the existing directory, without treating it as an error; the invocation marks or clears nothing.
     4. Reread every currently available requested artifact from disk on every invocation, then form findings only from those fresh reads. Prior review output, prior findings, cached artifact contents, cached existence state, and stale absence reports are invalid evidence for the current transaction; do not conclude that contents or findings are unchanged without rereading.

   - When a `sai-1` invocation finds an existing exact change directory and an available `proposal.md` but no current `specs/**/*.md`, the engine reviews the freshly read proposal read-only, then explicitly reports that the sai-1 artifact set is **incomplete because the normative specs are missing** and that behavior review is **blocked** by the missing specs; it does not present the artifact set as fully reviewable and marks or clears nothing.
   - `Review sai-1's artifacts` produces a read-only review of the freshly read current `proposal.md` and every freshly read current file matching `specs/**/*.md` under that exact change directory.
    - `Review sai-2's artifacts` produces a read-only review of the freshly read current `design.md`, `tasks.md`, and `interfaces.md` under that exact change directory.
    - `Review change-overview` produces a read-only review of the freshly read current `change-overview.md` for human presentation, reading the overview's source artifacts (`proposal.md`, `specs/**/*.md`, `design.md`, `tasks.md`, `interfaces.md`) to validate its completeness and consistency against them, reporting divergences between the overview and its sources as findings. A `Review change-overview` transaction completes as a review only when the overview is the change's current review surface: `overview.state` reads `current` in `openspec/changes/{name}/.openspec.yaml` AND the CLI reports `change-overview.md` present/done. When the state is non-`current` — `unmaterialized`, `materializing`, `failed`, or `stale` — or when current metadata is paired with a missing/not-`done` file, the transaction produces an availability/integrity report naming the state and the mismatch, produces no findings and no `Summary:` tally, marks or clears nothing, and closes by re-presenting the same current-change four-option picker. When persisted `overview.failure_details` is present, the report names that exact persisted overview.failure_details value at `.openspec.yaml:overview.failure_details`, even if `overview.failure_kind` is absent; when persisted `overview.failure_kind` is present, it names that classification too. A failure record is diagnostic state, never a current overview. When `materializing` has neither diagnostic key after a new generation attempt began, the report says the attempt was interrupted before failure classification and that no diagnostic is available; it does not infer success, absence of failure, or reuse an older diagnostic. When `stale` has neither diagnostic key after source modification before regeneration, the report says that no generation failure diagnostic is recorded for the current stale state without asserting interruption. The availability/integrity report remains read-only, does not mark or clear review evidence, and never writes `overview.state` or any artifact.
    - The engine forms findings by reference to the shared artifact review finding contract at `sai/policies/artifact-review-contract.md`: it cites that shared contract by reference and does not restate its severity criteria, finding shape, identifier scheme, summary-line format, or tally rules. Each finding carries a severity-prefixed identifier (`H1` / `M1` / `L1`, ...) per the contract's identifier scheme, and every completed review closes with the contract's base-form tally `Summary: High=<count> Medium=<count> Low=<count>` (no `Pass` prefix, no `Contract-violations` counter — those belong to the supervised pipeline's per-pass reporting only), emitting findings in deterministic order — by severity High → Medium → Low, then by ascending numeric identifier within each severity. The engine performs no writes — it never writes `overview.state` or any other file — and the loop's read-only constraint, navigation, language-gate reuse, and close-acknowledgment rule are unchanged.

  **Review Loop Navigation**: the manual-mode-only navigation shell. The shell owns the fixed four-option per-change picker and its re-entry, `Skip` advancement, active-loop `exit` termination, the single-block print-for-paste handoff, evidence marking from completed tallies only, and the unconditional minimal close acknowledgment. It performs no review work itself: it does not resolve directories, inspect child paths, reread artifacts, or form findings. For every review selection — `Review sai-1's artifacts`, `Review sai-2's artifacts`, or `Review change-overview` — the shell invokes `Review Engine(currentChangeName, selectedArtifactSetDesignator)` with the current change name and the selected artifact-set designator. The four option labels are fixed English literals and are not localized; the `exit` token is entered through the picker's free-text field.
    **Active per-change exit window and picker precedence**: The active per-change processing window begins when the loop enters the current tracked change, before its picker is displayed. It ends when that member is skipped, the loop closes, or the active-loop `exit` token terminates the loop. The window is open only while the current tracked member is being processed: `exit` entered before the loop enters a tracked change, after the loop closes, or in an ordinary `sai-explore` turn does not fire and creates or changes no review item. An empty tracked set never opens the window.

    While the active window is open, inspect the picker interaction's free-text field for the exit token before mapping the turn as an unmatched picker response. Reuse the existing item-9 bare-token and dominant-intent matcher, narrowed so a bare spelling variant of the English token `exit`, including `Exit`, `EXIT`, surrounding whitespace, allowed trailing punctuation, or a trivial greeting, fires. A turn whose dominant intent is to exit the review loop fires only when it contains an English spelling variant of `exit`. A negated, quoted, deferred, discussed, incidental, or localized equivalent without an English spelling variant does NOT fire, including a localized turn whose dominant intent is to exit. Free text that does not fire is an unmatched picker response and re-presents the same current-change four-option picker.

    When the active-loop `exit` token fires, terminate the loop immediately, leave later tracked changes unprocessed, resolve the current change's active review item from `in_progress` to `pending` when one exists, preserve all review-evidence marks and clears, and use the existing **Closing the loop** acknowledgment and no-next-command behavior. The token is navigation, not a review transaction.

    - Treat every `Review sai-1's artifacts`, `Review sai-2's artifacts`, or `Review change-overview` selection as a new review transaction, including a repeated selection for the same change and artifact set. For each transaction, use the current chat-scoped crystallized change name as authoritative, independently resolve the exact directory under `openspec/changes/` for that current tracked name, report a missing directory without claiming its child paths were checked, check every requested current path only when the directory exists, report missing children as an absence rather than an error, reread every currently available requested artifact from disk, and form findings only from those fresh reads.     - `Review sai-1's artifacts` produces a read-only review of the freshly read current `proposal.md` and every freshly read current file matching `specs/**/*.md` under the exact change directory.     - `Review change-overview` produces a read-only review of the freshly read current `change-overview.md` for human presentation and reads its source artifacts (`proposal.md`, `specs/**/*.md`, `design.md`, `tasks.md`, and `interfaces.md`) to validate completeness and consistency. It completes as a review only when `.openspec.yaml` reads `overview.state: current` and `openspec status --change` run with the current tracked change name and `--json` reports `change-overview.md` present and done. A non-current state (`unmaterialized`, `materializing`, `failed`, or `stale`) or a current state paired with missing or not-done metadata produces an availability/integrity report naming the state and mismatch, produces no findings and no `Summary:` tally, does not mark or clear review evidence, never writes `overview.state` or any artifact, and re-presents the same four-option picker. When persisted `overview.failure_details` exists, name that exact persisted `overview.failure_details` value at `.openspec.yaml:overview.failure_details` even if `overview.failure_kind` is absent; when persisted `overview.failure_kind` exists, name it too.     Every completed review transaction uses the shared artifact-review finding contract at `sai/policies/artifact-review-contract.md`: each finding carries its severity-prefixed identifier, `Severity`, `Artifact location`, `Issue`, and `Recommended correction` in that order, and the review closes with the base-form `Summary: High=<count> Medium=<count> Low=<count>` tally. A completed transaction with no High findings marks the current change's corresponding review item — reviewed-sai-1 for sai-1 and reviewed-sai-2 for sai-2 or change-overview — while a transaction with at least one High finding clears it. The most recent completed review over the sai-2 slice decides between a sai-2 review and a change-overview review. Absence, blocked, failed, cancelled, or non-current availability transactions leave evidence unchanged. Marks and clears target only the current change's items.

     **Review-in-progress state**: When processing a change, select once at loop entry the first not-completed review item in fixed order, reviewed-sai-1 then reviewed-sai-2; if both are completed, no item is active. Keep that active reference sticky across transactions and picker re-shows. A no-High completed review over the active item advances it to the next not-completed review item; a High finding keeps it active. Selecting `Skip`, firing the active-loop `exit` token, or closing the loop resolves the active item to render `pending` without marking or clearing evidence; the exit resolution is exactly the same as the `Skip` resolution. The state is render-only: the manual review loop's setting, advancing, or resolving it never marks or clears an item; the supervised pipeline's separate item-10 state transitions are defined below and do not alter this manual-loop rule.

    When a review transaction surfaces findings, the findings block IS the handoff payload: print exactly one findings block containing every finding in the shared shape, with `Finding H1`-style identifier headings, fields in contract order (`Severity`, `Artifact location`, `Issue`, `Recommended correction`), deterministic High → Medium → Low severity order, ascending numeric identifier within each severity, and the base-form `Summary: High=<count> Medium=<count> Low=<count>` tally. Do not emit a separate `## DesignCorrectionRequest` block, a `change:` header, an acceptance step, or any other findings encoding; the findings block is emitted exactly once. Re-presenting the same current-change four-option picker after the block is loop navigation, not review output and not acceptance; picker re-entry is loop navigation, not acceptance, and is excluded from the single-encoding prohibition; it never filters, pre-selects, or confirms a finding. The user pastes the findings block at the feedback gate of a re-invoked `/sai-2-design`; design-artifact findings are applied directly by the design worker, and proposal/spec findings use the design phase's consent-gated **apply in place** versus **do not apply / leave open** path. `/sai-1-spec` is not offered for those current-change corrections. The loop never applies, forwards, or regenerates corrections itself.

    **Picker re-entry invariant**: Every review and every non-completing transaction over a change re-presents that same change's four-option picker except a turn closed by `Skip` or by firing the active-loop `exit` token. This includes completed reviews, missing directories, missing artifact sets, blocked sai-1 reviews, and availability/integrity reports. For every non-closing turn, re-presenting the picker is the only closing action: do not end silently, propose a command, or advance to another change. Only `Skip` advances to the next tracked change. The active-loop `exit` token terminates immediately and leaves later tracked changes unprocessed.

    **Language gate reuse**: Before producing any review content for a sai-1, sai-2, or change-overview transaction, evaluate item 3's artifact-review language gate, including its Persistence rule, and name the exact current artifact set as the tracked target. A different artifact set or change re-asks; the same set reuses the selected language. The global question and per-change picker are always asked in the ambient language and are never suppressed by `--fast-track`; the four option labels remain fixed English literals, and `exit` remains the untranslated English free-text token.

    **Read-only constraint**: The review loop never creates, modifies, or deletes `proposal.md`, `specs/**/*.md`, `design.md`, `tasks.md`, `interfaces.md`, `change-overview.md`, `.openspec.yaml`, or any other file. It does not alter the emitted `Ready to Propose` block. It does not auto-emit a new `Ready to Propose` block; explicit user-requested re-crystallization continues through item 8.

Do not propose `/sai-1-spec`, `/sai-2-design`, `/sai-3-implement`, or any templated next-step command, and emit no next-command prompt.
