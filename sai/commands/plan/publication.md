# Unattended completed-plan publication

The plan is already complete and its run holds the answer `yes` to the publication question of its Start (`@sai/commands/plan/coordinator.md` § Publication answer). That answer is the held confirmation for the operations below on the current change branch, which later implementation reuses: the local plan commit, the non-force push, and the creation or update of one draft request. This action starts no implementation, never marks a request ready, asks the user nothing, and never stops the run: every failure is a skipped publication with its reason in the closing report.

Load the `to-pr` skill and follow its destination, content and recovery workflow with its § Unattended publication, with the completed change name and an explicit `publish_pr_as_draft: true` request. The request passes neither `closing_change` nor `closing_line`: a plan publication carries no origin-driven closing reference, so its pull request never closes the issue linked to the change. Use the same installed `to-pr.js` and provider registry that the skill resolves. The inclusion step below runs after destination selection and before drafting the final request. It is the only exception to ordinary planning's ignored-file rule.

1. **Destination.** Run `collect`, `resolve` and `destination` as the skill's § Resolve the destination says, without asking: an unresolved provider, an ambiguous remote or target branch, or a destination that needs a question skips the publication and names the missing fact. The target branch is the one `destination` returns for the provider's default branch unless the run was given another. A detached HEAD, missing access, or an unavailable provider skips the publication the same way.
2. **Plan inclusion.** Run `plan-query` with `{change: name}` and read its result: every `proposal.files` path (ignored ones included: `proposal.md`, `design.md`, `tasks.md`, `.openspec.yaml`, and all specifications), the source branch, and any `blocked` result. A `blocked` result names owned paths whose staged content differs from both HEAD and the working tree: the commit would drop that staging, so skip the publication and name the paths so the user can commit, unstage or discard them. Otherwise run `plan-commit --unattended` with `{change: name, harness: "claude"|"opencode", provider, repository, remote, base}` taken from the destination. It uses a private Git index, takes only the paths `plan-query` lists, force-adds only the listed ignored ones, and leaves every other uncommitted file where it is, staging included. A `no_changes` result needs no new commit. Every git call runs for at most 120 s; an `uncertain` result (a commit that reached that bound) carries the HEAD read back and is never repeated: inspect HEAD and the exact-path diff, report an already-created commit separately, and skip the rest of the publication. A refusal (`refusal` in the blocked result: `default-branch`, `detached-head`, `request-merged`, `request-closed`) skips the publication; for a merged or closed request, name it from the result's `request`.
3. **Request content.** Continue the skill with fresh collection against the same destination and branch: the title, the description (all other committed changes on this branch also enter the request, so the description does not claim a documents-only request), the ratings block, `query` with `publish_pr_as_draft: true`, and `push-query`. The unattended publish keeps an open request in its draft or ready state: `publish_pr_as_draft: true` only decides the state of a request that does not exist yet. Multiple matches skip the publication; never create a duplicate.
4. **Push and publish.** Run `push --unattended`, then `prepare`, then `publish --unattended` with `publish_pr_as_draft: true` and the receipt, as the skill's § Unattended publication says. No force push, no automatic retry of a refused or rejected push, no authentication change or installation. On `uncertain` or `partial_failure`, run `recover` once, which is read-only, and report what it verified; never repeat a creation.

The design segment's code commits (the stubs and the plan tests) are ordinary commits of the branch: the whole-branch `push` carries them into the request with no step of their own, and the request shows them beside the plan documents. The plan tests fail by design, so say in the request description that its continuous integration stays red until the build runs.

Report, in one short paragraph, the local inclusion (the commit, or that nothing changed), the branch push, the request URL with its verified draft or ready state, and every warning of the `collect`, `query`, `publish` and `recover` results. When the publication was skipped or ended uncertain, report the completed steps separately from the failed one, keep the completed plan and any confirmed commit or push, and say how to continue by hand with `/to-pr` on this same branch requesting a draft.
