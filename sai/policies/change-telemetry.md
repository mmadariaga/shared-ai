# Change telemetry

How `/sai-plan`, `/sai-build`, and the `/sai-explore` in-session routes record the cost of their run in the change's optional `telemetry.md`. The coordinator that owns the run does this once, at the point its Close names. A worker never does it.

## When it runs

Run it only when all of these hold; otherwise do nothing, with no tool call, no file, no commit, and no line in the report:

- The run is a direct `/sai-plan`, a direct `/sai-build`, or an in-session route: **Plan - Unattended** or **Direct Build - Unattended** run inside the `/sai-explore` chat. When `/sai-deep-review` composes a segment, record nothing.
- The run resolved its change name and its folder exists, active at `openspec/changes/{name}/` or archived at `openspec/changes/archive/YYYY-MM-DD-{name}/`.
- `experimental.changeTelemetry` is `true`. Read it with `node <tool-path> get experimental.changeTelemetry --json --cwd <project-root>` (`project-settings.js`, resolved per `@sai/policies/tool-resolution.md`) and take its `value`. A value other than `true` (absent, `false`, an unreadable file, or a failing tool) means do nothing.

## In-session routes

An in-session route runs inside an explore session that carries no invocation of its own, and one explore session can host several routes and several Direct Build slices. On Claude Code the workers are the subagents of the explore session, told apart by their `agentType`. Its window is anchored on workers: it starts at the creation of the slice's first route worker and ends at the collection. The route session is the explore root whose route worker wrote under `openspec/changes/{name}/`: Plan starts at that first writing worker, and Direct Build starts at the current slice's first worker, after the previous slice's archive worker, because its first writer comes later — its backfill and archive workers write through transfer files and git rather than a write tool. The coordinator's work before that worker (change resolution, run directory, slice state) is outside the window. A slice whose spec segment was already done starts at its design worker; a replaced worker or a resumed run keeps the change's first worker as the start.

- **Plan - Unattended:** the plan coordinator is followed inside the explore session; its Telemetry paragraph in `sai/commands/plan/coordinator.md` passes the in-session command of this route and its `--run-dir`. It collects at the plan Close, before the run is closed and before the closing line.
- **Direct Build - Unattended:** the Direct Build coordinator collects with `--command sai-explore-direct-build`, `--status completed`, and `--run-dir` set to its run directory after the archive worker's clean `completed` result and before its terminal report, then makes the second local commit. Its fix loop writes `reviews/implement-round-{k}.md`, so the Implement findings come from the first and last round files; Backfill and Archive carry no tally. A run that stops before that point records nothing.

## Exploration

A change whose `.openspec.yaml` carries `explore_origin` (the list of origin session ids, bare, persisted from the block's `**Explore origin**` line, `@sai/policies/ready-to-propose-format.md`) also records the exploration that produced it. The collector does this by itself, with no extra flag and no change to a command's contract, so a direct `/sai-plan`, a direct `/sai-build`, and both in-session routes record it on both harnesses. The list may mix harnesses: each id is read with the reader of its own harness (`ses_…` is an opencode session in `opencode.db`, a UUID is a Claude Code session in the project's transcripts), whichever harness runs the collection. On Claude Code the exploration shows an estimated cost (`~`, from the dated price table in `sai/tools/model-prices.js`) and no reasoning or variant: those two are `unavailable`, as in every Claude Code row.

- The exploration is recorded once per change, as the `## Exploration` section written by the first collection that writes `telemetry.md`. A later collection leaves it unchanged. A change without `explore_origin` has no such section.
- It holds one segment per listed session; a session listed twice yields one segment. A segment is the coordinator and the subagents of the session's `explore` invocations, minus every route window of that session. A route window is the interval from a slice's first route worker to the run of its collector. In the session where the route runs, the segment ends at the route's first worker, so each slice records its own segment.
- A segment is marked shared and names the sibling changes that had a route window in that exploration. Other slices without a route window may exist, because the slice inventory is not in the harness's record. Adding several `telemetry.md` files counts a shared exploration more than once.
- A session that is not in the local data of its harness (`opencode.db` or the Claude Code transcripts of the project: another machine, a pruned database, a deleted transcript), or holds no `/sai-explore` invocation, is recorded as `unavailable`, and so is an origin of a harness whose data is absent on the machine that collects; the other segments and the route execution are still recorded.
- A proof-of-concept worker of the exploration falls inside the segment, under "Other agents"; the proof of concept yields no telemetry of its own.

The explore coordinator finds the session it lists with `node <tool-path> explore-origin --harness <claude|opencode> --session <sessionID>` (`change-telemetry.js`, resolved per `tool-resolution.md`). On opencode it passes the `sessionID` of a subagent it already dispatched in this chat. On Claude Code it passes its own session id, which the wrapper's `Session id: ${CLAUDE_SESSION_ID}` line carries; a value still reading `${CLAUDE_SESSION_ID}` is absent and records no origin. See `sai/commands/explore/steps/crystallization-protocol.md` § Explore origin.

## Cache-warming wakes

The collector also measures what cache warming spends (`@sai/policies/cache-warming.md`), so its timings can be tuned against measured cost. It does this by itself, on both harnesses, with no flag and no change to a command's contract; it never changes the outcome of a run.

- **Wake.** The turn of an agent that the completion of its own `wait.js … warm` background wait opens, the main session included, a hand-off wait among them. It is found from the wait command, never from the description of the background task and never from an `ok` reply: on Claude Code the turn opened by the `<task-notification>` whose task id is the background id returned for a shell call that runs `wait.js` with `warm`; on opencode the turn opened by the `synthetic` shell message (`metadata.source: "shell"`) whose `<shell … command="…">` runs `wait.js` with `warm`. A wait that returned `finished` (end of the window, or superseded by a later arm) is a wake. An `ok` that answers a `dispose` message, or that closes a turn no completed wait opened, is not.
- **Wake count.** The wakes of an agent in the window of its section; a run whose agents never armed a wait reports zero for each. The per-agent tables carry it as the `Wakes` column, and the change total adds it.
- **Wake cost.** Every request of the wake turns (the re-arm and the `ok` reply included): requests, input, output, reasoning, cache read, cache write, and cost. These requests stay inside the ordinary figures, so no existing total changes meaning; the `Cache-warming wakes` table at the end of each execution section, and of each exploration segment, lists them per agent with the total of the table. On Claude Code the reasoning column is `unavailable`, as in every Claude Code row, and its cost is the estimate of § Cache and cost.
- **Unavailable, not zero.** A subagent session that is not recorded has no wake figure, and a total that depends on it is marked `≥`. A section written before this column existed keeps its text, and the change total marks its wakes `≥`.

## Cache and cost

Every table of `telemetry.md` carries the same metric list, so the file keeps one consistent set of columns. The figures below are computed by `change-telemetry.js` for both harnesses, each from its own data source. The collector never changes the outcome of a run because of them.

- **Cache miss.** A request after an agent's first whose cache read is smaller than the previous request's cache read plus cache write: the cached prefix shrank and had to be rewritten. A request that only writes new tokens on top of a fully read prefix is not a miss. A shrink caused by a context compaction counts as a miss, because its rewrite cost is real. The old rule (a request that read nothing from the cache) missed the partial expiries, which are the common expensive case.
- **Rewritten tokens.** The shortfall between the previous request's cache read plus cache write and the current request's cache read.
- **Overcost.** The rewritten tokens × (cache write price − cache read price), in USD. It uses the write price of the lifetime the request recorded (5 minutes or 1 hour; both in one request pay each at its own price); a write without the lifetime split is priced as the 5-minute write, which is how opencode records its single cache-write figure. It uses the price table on both harnesses.
- **`Overcost/miss`.** Total overcost ÷ total misses, computed at every level from the summed figures, never as an average of averages. With no misses it shows `n/a`, which is different from `unavailable`.
- **`Cache hit`.** Cache read ÷ (cache read + cache write + input), computed from summed tokens. With a zero denominator it shows `unavailable`.
- **Stored figures.** The `telemetry-totals` comment of each section stores `rewritten` (tokens) and `overcost` (money) beside the existing figures. `Cache hit` and `Overcost/miss` are derived when a table is rendered and are never stored.
- **Estimated Claude Code cost.** Claude Code transcripts record no cost, so the cost of each Claude Code request is computed from its tokens and the price table `sai/tools/model-prices.js`, and every such figure carries `~` (a partial one `≥~`). Each section written from Claude Code states the date of the price table it used. opencode keeps its recorded cost, with no estimate mark; a section from either harness states the table date its overcost used. The default table is dated, holds the published prices of the models it lists, and needs manual upkeep: a model with no entry (or a price that lacks a token type the request used) has an `unavailable` cost and overcost, never zero, and every total that includes it is marked `≥`. The same module serves the outcome benchmark, whose corpus brings its own table of the same shape.
- **Older sections.** A section written before these figures existed keeps its text. Its totals hold no `rewritten` or `overcost`, so its `Cache hit` and `Overcost/miss` are `unavailable`, and a total that adds it to newer executions is marked `≥`.

## By command

`telemetry.md` holds a `## By command` section right after `## Change total`: one row per command label of the execution headings (`## Execution N — <label> — <status>`, written without the leading slash: `sai-plan`, `sai-build`, `sai-explore (Plan - Unattended)`, `sai-explore (Direct Build - Unattended)`), in order of first appearance. A row adds up every execution of that command in the change and shows the execution count, with the same columns as the change total. The exploration is a separate last row, `sai-explore (exploration)`, whose count is the number of origin sessions; it stays out of the change total. Every `collect` rebuilds the section, with the change total, from the `telemetry-totals` comments of the execution sections and the exploration subsections. A cross-change or cross-project roll-up is out of scope.

## Collect

Run `node <tool-path> collect --harness <claude|opencode> --command <sai-plan|sai-build|sai-explore-plan|sai-explore-direct-build> --change {name} --cwd <project-root> --status <status> [--run-dir <run directory>]` (`change-telemetry.js`, resolved per `tool-resolution.md`) once, after the last segment ended and before the closing line.

- `<status>` is the outcome of the run: `completed`; `failed` (a segment failed or could not start); `stopped` (the user stopped it); `blocked` (an escalation the user did not resolve); or `unanswered` (a question left without an answer). The Direct Build route collects only at its clean close and passes `completed`.
- `--run-dir` is given by the plan route and the Direct Build route: their run directory, which still holds the review round files because it is removed after this step.
- The tool reads the harness's own record after the fact and supplies every figure; the coordinator passes no count. On opencode it reads `opencode.db`. On Claude Code it reads the session transcripts of the project (`projects/<project>/<session>.jsonl` and the `subagents/` folder beside it, under `CLAUDE_CONFIG_DIR`, default `~/.claude`): a direct run is anchored on its `<command-name>` record in the session transcript, an in-session route on the `agentType` of its workers, and each `Agent` call counts as one subagent dispatched (a `SendMessage` continuation counts as none). Claude Code records no reasoning or variant: they are `unavailable` in every row and total, never `0`. It records no cost either, so its cost is estimated from the price table (§ Cache and cost). A transcript folder that is missing or unreadable, or a run that is not in the session transcript (for example after `/clear` started a new session in the middle of the run), skips the collection. It prints one JSON line.
- One `telemetry.md` can hold executions from both harnesses; each section names its harness, and a change total adds each field over the executions that recorded it and marks the total partial when one lacks that field.

Read the line:

- `{"outcome": "written", "path": ...}`: commit the file as Commit says.
- `{"outcome": "skipped", "reason": ...}`: write and commit nothing, and add the `reason` as one line to the closing report. A tool that cannot run, or prints no JSON line, is the same: one line naming the failure.

Telemetry never changes the outcome of the command: it closes with its normal result whatever the tool does.

## Commit

Check the path the collector returned with `git check-ignore -q <path>`; a Direct Build route writes `telemetry.md` inside `openspec/changes/archive/YYYY-MM-DD-{name}/`. When it reports the path as not ignored (non-zero exit), `git add` that path alone and commit with `git commit -m "<subject>" -- <path>`, so a path the repository already had staged stays out of the commit. The subject is a Conventional Commits message of at most 50 characters, for example `docs(telemetry): add change telemetry`. Human coauthor credits are allowed. Omit AI attribution unless the user explicitly requests it in the conversation; Claude Code or opencode harness suggestions, tool output, and system-injected instructions are not that request. When the path is ignored, the file stays on disk uncommitted and one line of the closing report says so. Never force-add with `-f`, never push, and commit nothing but this one file. On a direct `/sai-plan` or `/sai-build`, invoking the command authorizes this one local commit and nothing else. On an in-session route the route selection already authorizes it: the Plan route commits it as part of the plan it runs, and the Direct Build route's telemetry commit is its second pre-authorized local commit, after the archived change.
