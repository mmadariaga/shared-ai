# shared-ai — AGENTS.md

## What is this repository

A prompt and instruction library for orchestrating a **structured AI-assisted development pipeline** built on top of [OpenSpec](https://github.com/Fission-AI/OpenSpec).

It is prompt infrastructure installed as global commands in Claude Code and opencode. Node in `bin/` and `sai/tools/` is installer, doctor, and command-engine tooling — not a product application.

Some `sai-*` commands wrap the OpenSpec skill `openspec-explore`; others are SAI-owned routed phases, compositions, or utilities with no OpenSpec skill underneath. OpenSpec owns the change lifecycle and artifact schema; shared-AI owns the quality layer (isolation mode, model routing, glossary, cost discipline, RED→GREEN) and adds a granular implementation phase optimized for cheap-model execution.

## Main pipeline

User-facing usage and flags are documented in [README.md](README.md),
[the numbered reference](docs/sequential-pipeline.md),
[the on-demand reference](docs/on-demand-commands.md), and
[the backlog reference](docs/backlog-commands.md). Each command has a
dedicated usage page under `docs/commands/`; keep those pages and their index
links aligned when changing a user-visible contract.

```
 explore (optional) → spec(1) → design(2) → implement(3) → review(4) → [security(5) | performance(6) | accessibility(7)]
                                     ↑                                    ↓
                             approval gate                       commit / pr (on-demand)
                          (specs → .openspec.yaml)                       ↓
                                                                     archive
```

`/sai-plan` is the user-invoked shortcut that chains spec(1) → design(2) in one session from a `Ready to Propose` block, as `/sai-build` chains implement and review; it is also what explore's `Plan - Unattended` route follows. `/sai-1-spec` and `/sai-2-design` are always unattended, goal-driven commands outside the shared orchestration.

`/sai-build` is the user-invoked shortcut that chains implement(3) → review(4) in one session, then fixes the findings it selects.

`/sai-deep-review` is the user-invoked shortcut that runs review(4), runs the recommended audits (security(5), performance(6), accessibility(7)) in parallel, judges the findings in an Assessment pass, and fixes the findings it leaves through an implement(3) segment, unattended, in one session.

Each phase reads from and writes to **`openspec/changes/{change-name}/`** — single source of truth per change. Runs in **Isolation Mode**: every command starts with no inherited context, reading only the artifacts it needs.

OpenSpec skills are **internal**. Users invoke the `sai-*` wrappers exclusively. The only live OpenSpec skill fetch is `openspec-explore` (explore body); spec `steps/proposal.md` and `steps/specs.md` and archive run the `openspec` CLI directly and load no skill. Spec, design, implement, the audits, and the compositions are SAI-owned phases — they are not `opsx:apply` / `opsx:continue` overlays.


## Prerequisites

The pipeline depends on the OpenSpec CLI:
1. Install the `openspec` binary globally (see https://github.com/Fission-AI/OpenSpec).
2. Run `openspec init` in each project that will use shared-AI.

`/sai-explore` checks both and halts with a clear remediation; other commands rely on OpenSpec's native errors (see ### Prerequisite check). Skills are installed by `openspec init` (per project), never bundled by the shared-AI install script. Global installer projections are expanded deterministically from `sai/install-manifest.json`; the same manifest drives install, doctor, and uninstall.

Wrappers are **thin** — they specify the model, carry the clean-start line and the capability profile, and fetch the harness fetch skill and one command card directly: a `coordinator.md` for the goal-driven commands (`implement`, `review`, `build`, `spec`, `design`, `plan`, `commit`, `archive`, `backfill`, `merge`, `deep-review`, and the three audits) or a `body.md` for the five utility commands (`explore`, `retire-docs`, `retrospective`, `status`, `worktree`). Explore wrappers also fetch `idea-list-render.md` before the card. They do not fetch policies or OpenSpec skills in the wrapper body; the card loads the policies it needs, and a utility card also checks the wrapper's capability profile (`tool-access.md`) before any other step. Claude Code and opencode load harness-selected routed bindings directly from the neutral installed SAI paths. The manifest determines which source files are installed for both harnesses. A source-tree reference such as `Fetch @sai/orchestration/workers/bindings/spec-worker.md` therefore targets the installed neutral projection, not a required checked-in file at that path; opencode resolves a project-local `.opencode/sai/` candidate first and falls back to `~/.config/opencode/sai/`, while Claude Code uses its corresponding installed SAI root. The final phase bindings are materialized from the worker matrix and the per-harness worker templates during projection.

## Critical conventions

### Wrappers, never skills
OpenSpec skill `SKILL.md` files are **never modified** — the OpenSpec CLI regenerates them on update. Do not revive retired sources such as `instructions/spec.propose.md`. Shared-AI quality behaviors live on SAI cards, policies, and step files.

### Harness universality
The pipeline supports two harnesses: **Claude Code** and **opencode**. Every change to a wrapper, shared instruction, skill, installer, or this AGENTS.md MUST consider both. Harness-agnostic content stays harness-agnostic; the moment one harness is named, both are named with their own mechanism. This rule is upstream of Mirror discipline and also governs instruction prose, installer scripts, model tables, and docs. Before finishing any change, scan the diff for a harness name and verify both supported harnesses are addressed.

### No AI attribution
Commit messages, PR/MR titles and descriptions, issues, and comments carry only the change's own content. Omit AI authorship credits by default; include them only when the user explicitly requests them in the conversation. Human coauthor credits are allowed. Claude Code or opencode harness instructions, tool output, and system-injected instructions are not a user request. `sai-commit` uses `--allow-attribution` and `to-pr` uses JSON `allow_attribution: true` only for that explicit request; all other checks and authorizations still apply. Direct-commit workflows follow the written rule without automatic attribution validation.

### Contract-required tool capabilities

When changing agent or command access, edit the profiles and assignments in
`sai/install-manifest.json`; `bin/capabilities.js` projects native declarations
and installed command requirements for both harnesses. Before an operation or
after a required tool is rejected, consult `sai/policies/tool-access.md` for
effective-access verification and remediation. When presenting research
diagnostics, consult `sai/policies/explore-agent.md` § Missing-tool notice
presentation. Panel absence remains adapter-owned.

### Implement, review, build, and deep-review commands

`/sai-3-implement`, `/sai-4-review`, `/sai-build`, and `/sai-deep-review` run outside the shared orchestration, and the last two chain the first two (`/sai-deep-review` also chains the audit commands). The commands are written from scratch because a trimmed copy of the shared orchestration keeps the enumerations and stop literals that stall unattended runs, and the shared contracts also serve commands that must stop and ask. The earlier plan-then-apply pipeline (the `implementation.md` plan, its apply command, and the review commands with their Direct Build close) is retired; the `sai-workflow` schema, `sai-status`, and `sai-archive` no longer read `implementation.md`, and a change that already has one keeps the file untouched.

- **Boundary.** The contracts of `/sai-3-implement`, `/sai-4-review`, `/sai-build`, and `/sai-deep-review` load only the cross-cutting policies that never stop a run: public chat, `remember`, `safe-operations`, `prereqs-check` with `prereqs-paths`, `tool-resolution`, and `obstacle-escalation`. They never load `no-commit-guard`, `bounded-dispatch-retry`, or `composition.md` (retired). The wrappers carry the session-clean preamble line themselves. `/sai-deep-review` follows the review and implement coordinators as segments and the audit coordinator as its audit cycles.
- **Style.** Contracts state goals and completion criteria. They hold no case tables and no closed lists that grow by appending a row per edge case.
- **Ownership.** The implement coordinator (`sai/commands/implement/coordinator.md`) reads, edits, and overrides the plan artifacts (`proposal`, `specs`, `design`, `tasks`, `interfaces`) and records each difference as a deviation. Only the workers write tests, stubs, and production code: RED owns tests and stubs, GREEN owns production code and never touches tests. The coordinator runs each step's tests through the budget executor, arbitrates between the workers, and alone runs git.
- **Workers.** `sai-3-red-worker` and `sai-3-green-worker` (phases `red` and `green`) live for the whole run and are continued step by step (`SendMessage` on Claude Code, `task` with the `task_id` on opencode). The ADR 0188 `ready` handshake runs only when a worker is created. Their bindings render from `standalone-worker-template.md` (create and continue calls only), because their coordinator owns the lifecycle. Each role has a linear step machine (`red-steps@1`, `green-steps@1`) that delivers its step file by pointer and is reset at every step; when the store fails the coordinator sends the pointer from the static order itself. `sai-4-review-worker` (phase `review`) is created once per `/sai-4-review` run with the same standalone binding, reviews in a fresh context, fixes nothing, and is guided by `review-steps@1`; `/sai-3-implement` stays the only owner of finding fixes.
- **Commits.** Invoking the command pre-authorizes one local commit per step, holding only the run's paths and the `tasks.md` checkboxes the step completes. `/sai-4-review` commits `review.md` alone. Every path is checked with `git check-ignore` before staging and an ignored path is never force-added, so in this repository (which ignores `openspec/changes/**` except `proposal.md`) the plan artifacts stay out of the commits. Nothing is pushed.
- **Resilience.** The `implement-run@1` machine (`sai-state/machines/implement-run.js`, session key `implement-{name}`) is the coordinator's memory outside its context. It holds identifiers and paths only; free text (deviations, overrides, baselines, findings, hand-over summaries) lives in files in a run directory outside the repository, a private `mkdtemp` child of the SAI temp root created by `sai/tools/temp-root.js` (Linux: `/tmp/claude-{uid}/sai/` for Claude Code, `/tmp/opencode/sai/` for opencode; Windows and macOS: `<os.tmpdir()>/<harness>/sai/`), and workers write their report to a file there and return only its path. A run that completes removes its run directory; a stopped, blocked, or unanswered run keeps it. Each obstacle has a budget of 3 attempts, each with a different approach (corrected instruction, plan edit, override, new worker). The exhausted budget escalates at once through the native picker with coordinator-written options, one of which stops the run, and the answer resets that obstacle's counter. A hung, drifting, or unreadable worker is asked again first and then replaced; each counts as an attempt. After a compaction the coordinator resumes from the store; without the store it rebuilds from `git log` and the `tasks.md` checkboxes. A run that completes, stops, or is left unanswered persists no report file: its closing report lists the deviations with their reasons and the findings still pending after the third fix round (or says there are none), and a `build-log.md` that already exists in a change stays untouched. `/sai-build` starts no later segment after a blocked or stopped run. The `sai-state` emit response carries the machine's `run` view through the observability fields. A run interrupted under an earlier session key cannot resume; the next run starts fresh.
- **Audit reports.** After every task is checked, open fixable findings of `review.md`, `security.md`, `performance.md`, and `accessibility.md` (per `sai/policies/finding-state.md`) go through the same step cycle, with RED only when the finding needs a new test; each commit carries the fix and its ` (FIXED)` mark. Findings that carry an ` (EXCLUDED: …)` mark are skipped. Questions stay open for the user. When `/sai-build` or `/sai-deep-review` runs the coordinator as its fix segment it hands over the reports it regenerated and marked (Composition reports; `review.md` alone for `/sai-build`): only those reports are applied, and they are the run's own paths.
- **Inherent-risk ratings.** At close, a completed run that fixed at least one report finding stores the `sai/policies/inherent-risk.md` ratings block in `review.md` (computed against the `**Reviewed:**` parent branch, checked by `sai/tools/risk-signals.js validate`) and commits it alone, ignore rules applying; `sai/tools/to-pr.js collect` reports it as `inherent_risk` `fresh`, `stale`, or `absent`, and `/to-pr` publishes only a `fresh` block.
- **Review.** After GREEN, the coordinator reviews the step's staged diff for spec fidelity, test gaming, and excess scope, with at most 3 fix rounds; findings left after the third round are recorded as pending in the run directory, listed in the closing report, and the run continues.
- **`/sai-build`.** `sai/commands/build/coordinator.md` chains `/sai-3-implement`, one `/sai-4-review` pass, an assessment of its findings, and a second `/sai-3-implement` run for the findings it selects. It resolves the change once, through its first segment, and hands that name to the later segments; it marks the findings it will not fix with the excluded mark and hands the fix segment `review.md` as its only Composition report.
- **`/sai-deep-review`.** `sai/commands/deep-review/coordinator.md` is the only card; the wrapper loads the harness fetch skill and that coordinator directly, and the coordinator loads `public-chat`, `remember`, `safe-operations`, `tool-resolution`, and `finding-state`. It strips `--fast-track` silently and accepts the union of the options declared by the `options.md` files of review, security, performance, and accessibility (an unknown option, a second positional value, or an option without its value ends the run before anything is written). It follows `sai/commands/review/coordinator.md` as its first segment (its closing line is replaced), then activates the security, performance, and accessibility audits from a bounded triage parse of the freshly regenerated `review.md`; `--full` or `--path` activates all three without the parse. A triage value other than exactly `Yes` or `No` is illegible: that audit does not run and the summary warns; a missing `review.md` or no legible value closes the run with the error, with no Assessment pass and no fix segment. An empty diff (`no-changes`) stops the run before any audit. The accessibility dev-server URL is asked once, between the triage and the audit batch, when accessibility runs with `--runtime` and no `--url`, so no question pauses the parallel audits. The activated audit workers are created in one batch (several `Agent` calls in one turn on Claude Code, several `task` calls on opencode) and each runs the per-worker cycle of the audit coordinator; the driving session issues every `sai-state` call and every commit one at a time, in the fixed order security, performance, accessibility, and commits each verified report alone. An audit that fails or exhausts its budget does not close the run: the others finish, the summary shows each status, and the failed audit's findings never enter the Assessment pass. Before fixing, the coordinator checks that `/sai-3-implement` can start (otherwise it prints that command's startup literal and closes after the summary), runs the Assessment pass copied from `/sai-build` over `review.md` and this run's audit reports (it marks each excluded fixable finding with the excluded mark and its reason, commits each marked report alone, and leaves Questions open), and follows `sai/commands/implement/coordinator.md` as the fix segment, handing it those reports. There is no human findings selection. The assessment keeps no memory: a rerun regenerates `review.md` and the activated audit reports and judges again, and only the fix segment resumes through its own Resuming rule. The run commits `review.md`, each verified audit report, each report the Assessment pass marked, then one commit per fix step and the inherent-risk ratings block; it never pushes.

### Plan, spec, and design commands

`/sai-1-spec`, `/sai-2-design`, and `/sai-plan` run outside the shared orchestration, like `/sai-3-implement`, for the same reason: a trimmed copy of the shared Result Loop keeps the enumerations and stop literals that stall unattended runs (ADR 0199). They are always unattended and have no interactive mode.

- **Boundary.** The spec and design coordinators load only `public-chat`, `remember`, `safe-operations`, `tool-resolution`, the budget skill, and `sai/commands/plan/cycle.md`; `/sai-plan` loads `public-chat`, `tool-resolution`, and `cycle.md`. None of the three loads `no-commit-guard` or `composition`. They run no prerequisite check. They carry the session-clean preamble line themselves.
- **Style.** Contracts state goals and completion criteria. They hold no case tables and no closed lists that grow by appending a row per edge case.
- **Segments.** `/sai-plan` follows `sai/commands/spec/coordinator.md` and then `sai/commands/design/coordinator.md` as segments, in one session. The artifacts on disk are the only interface between them. When `proposal.md` and `specs/` already exist, the disk wins: the spec segment counts as done and a block does not rewrite the specs. When the spec segment stops or is blocked, the design segment does not start; pending review findings never stop the run.
- **Workers.** `sai-1-spec-proposal-worker` and `sai-2-design-worker` (phases `spec` and `design`) keep their names, manifest keys, and presets, and render their bindings from `standalone-worker-template.md`. A worker lives for its segment, opens with the ADR 0188 `ready` handshake, serves one message at a time, writes a report file in the run directory, and returns only its path. Their steps are delivered by pointer through `spec-steps@1` and `design-steps@1`. The worker never runs git and never asks the user: a question is a `needs_input` report that the coordinator answers.
- **Questions and assumptions.** The coordinator answers a worker question from the `Ready to Propose` block, the change's artifacts, or the repository, and records the answer as an assumption with its source. A question that none of them answers and whose answer would change the artifacts is force majeure and escalates through the native picker. Assumptions live in the run directory and the closing report only; they are never persisted in the repository.
- **Checks and review.** Each segment runs mechanical checks through the budget executor (`openspec validate <name>`, `check-delta-headers.js`, `check-cited-paths.js`, and in design `file-manifest.js verify`); a failing check is an obstacle with a budget of 3 attempts, never a finding, and a segment does not close while one fails. The coordinator then reviews the segment's artifacts in up to 3 incremental rounds (`review-delta.js` snapshots over the artifact paths, `incremental-review.md`, finding shape from `artifact-review-contract.md`) against fidelity to the input, excess scope, internal consistency, and consistency across artifacts. Findings still open after the third round are pending, listed in the closing report, and never stop the run.
- **Commits.** Each segment commits only its own paths locally, checking each with `git check-ignore` first and never force-adding; a segment whose paths are all ignored closes without a commit and says so. Nothing is pushed.
- **Resilience.** The `plan-run@1` machine (`sai-state/machines/plan-run.js`, on the shared run core `run-core.js`, session key `plan-{name}`, segments `spec` and `design`) is the coordinator's memory outside its context. It holds identifiers and paths only; free text lives in a run directory created by `temp-root.js mkdtemp --prefix plan-{name}-`. Each obstacle has a budget of 3 attempts; the exhausted budget escalates at once through the native picker with a stop option. An interrupted run resumes from the store, or from the artifacts on disk and `git log` without it, and the disk wins. A run started under an earlier session key does not resume.
- **Specs approval.** Invoking `/sai-2-design` or `/sai-plan` is the approval of the specs: the design worker writes `approval.specs.approved_at` in `.openspec.yaml` only when it is absent or empty. The overview is a separate continuation that the design coordinator sends, naming `design/steps/overview.md`, only when `--overview-lang` is set.
- **Flags.** The three commands accept and ignore `--fast-track` and `--supervised` and print no banner; `/sai-2-design` is no longer a member of the fast-track parser. `/sai-1-spec` and `/sai-plan` also accept `--block-file <path> --block-hash <sha256>`, which the spec coordinator verifies with `ready-to-propose.js verify-file`.
- **Explore.** The `Plan - Unattended` route follows the `/sai-plan` coordinator for the first pending slice (`pipeline-plan-unattended.md`), emitting the `explore-slice@1` intents; it writes the run directory through the budget executor and gains no direct write tool. The `Manual` route still hands the block to `/sai-1-spec` in a new chat.

**Step-gated instruction delivery:** `/sai-5-security`, `/sai-6-performance`, and `/sai-7-accessibility` split each worker's instruction mass into one file per plan step under `sai/commands/{security,performance,accessibility}/steps/` (`common.md` plus per-id step files; each audit's leading scope step is fileless). Each worker card loads `sai/commands/audit/worker-common.md` and its `steps/common.md` at creation; the shared audit coordinator delivers each step file by pointer through that audit's `security-steps@1`, `performance-steps@1`, or `accessibility-steps@1` machine (`sai-state/machines/linear-steps.js`). The first filed step's pointer, returned by the cycle's `sai-state reset`, opens the task message: the worker runs the fileless first step inline and reports it with the first filed step in its first `step-done`. A batch that skips stages carries every skipped id, so the next pointer lands on the step that still has work. When the store fails the coordinator sends the pointer from the static order.


Two additional step libraries are not worker-instruction delivery: `/sai-explore` loads `sai/commands/explore/steps/common.md` at start and fetches later files only when `next.follow` names them (`explore-idea@1` then `explore-slice@1` per `@sai/policies/stage-machine.md`). `/sai-3-implement`, `/sai-4-review`, `/sai-1-spec`, and `/sai-2-design` deliver their RED, GREEN, review, spec, and design step files by pointer from their own coordinators through `red-steps@1`, `green-steps@1`, `review-steps@1`, `spec-steps@1`, and `design-steps@1` (outside the shared orchestration).

### Audit coordinators and workers
`/sai-5-security`, `/sai-6-performance`, and `/sai-7-accessibility` run outside the shared orchestration, in the shape of `/sai-4-review`: one goal-driven, unattended coordinator, `sai/commands/audit/coordinator.md`, serves the three audits. The wrappers load the harness fetch skill and that coordinator, with the audit in `command_name`. The coordinator loads only `public-chat`, `remember`, `safe-operations`, `tool-resolution`, `obstacle-escalation`, and `finding-state` (never `no-commit-guard`, `bounded-dispatch-retry`, or `composition.md`), reads `sai/commands/{audit}/options.md`, and runs under the `audit-command` capability profile (coordinator plus write, shell, and `safe-operations`, so it can verify and commit). These boundaries apply equally to Claude Code and opencode.

- **Cycle.** The coordinator is written as a cycle per worker: create the worker (ADR 0188 `ready` handshake), disclose the task, process `step-done` events through `{audit}-steps@1`, verify, commit. It is not an exclusive session: each cycle has its own `sai-state` session key (`{audit}-{name}`), so `/sai-deep-review` can run several at once while the driving session issues every `sai-state` call and every commit one at a time.
- **Change resolution.** The coordinator resolves the change with the `/sai-4-review` rule (the argument, or the only change that has `proposal.md`; with none or several it prints the candidates and ends) and enforces the proposal gate; the workers have no 0/1/N picker. An unknown option, a second positional value, or an option without its value ends the run before anything is written. `--fast-track` is dropped silently.
- **Workers.** `sai-5-security-worker`, `sai-6-performance-worker`, and `sai-7-accessibility-worker` keep their identities and matrix entries; their bindings render from `standalone-worker-template.md` (create and continue calls only). Shared rules (ready handshake, report to a file, no git, scope, questions as assumptions) live in `sai/commands/audit/worker-common.md`; each `worker.md` keeps only its plan of step ids and its batching rules. A worker question that the change, its artifacts, or the repository answer is answered by the coordinator and listed as an assumption in the closing report; when nothing answers it and the answer would change the report, it escalates through the native picker.
- **Runtime.** `--runtime` is the whole authorization for performance diagnostics and accessibility scanners: no authorization question is asked, and an uninstalled or unreachable tool is marked unavailable in the report while the static audit goes on. The accessibility dev-server URL comes from `--url`; when `--runtime` arrives without it, the coordinator asks for it as an input before the worker starts. Keyboard walks and screen-reader checks are listed in the report's `## Pending Manual Checks` section.
- **Verification and commit.** Before committing, the coordinator runs `node sai/tools/lint.js audit-report <report> --audit <audit>` (template structure, the audit's own severity subset and `Summary:` form under ADR 0107b, identifiers numbered per severity, a tally matching the findings, and for accessibility the Executive Summary table) and `node sai/tools/check-cited-paths.js audit-report <name> --audit <audit>` (every backticked `path/with/slash.ext[:line]` of a finding's `File` or `Location` field exists). A failing report is an obstacle with a budget of 3 attempts (corrected instruction, new worker, mechanical repair) that escalates through the picker. Each audit commits only its report, checked with `git check-ignore`; an ignored report stays on disk and is reported as such, and nothing is pushed. An interrupted audit does not resume: the next run regenerates the report.
- **Done literals.** Each audit ends with `Security audit done.`, `Performance audit done.`, or `Accessibility audit done.`, stated once in the coordinator as `{Audit} audit done.`.
- **Inside `/sai-deep-review`.** `/sai-deep-review` runs one cycle of this coordinator per activated audit, in parallel, as its audit segment. It has already parsed the arguments, resolved the change, and settled the accessibility URL, so each cycle starts at its step machine; a worker question is answered from the repository and kept as an assumption, a question that nothing answers and whose answer would change the report escalates to the user through the native picker and pauses only its own audit while the other cycles continue, and a question whose answer would not change the report is answered with the best reading and kept as an assumption; and an audit that fails or exhausts its budget of 3 attempts is recorded as failed instead of escalating, so the others finish. The audits leave the shared orchestration for good: `composition.md`, the former per-audit `coordinator.md` and `command-bootstrap.md` cards, and the `security-standalone@1`, `performance-standalone@1`, and `accessibility-standalone@1` machines are retired (ADR 0200).

### Commit coordinator and worker
`/sai-commit` runs outside the shared orchestration, in the goal-driven shape of `/sai-merge`: the wrappers load the harness fetch skill and `sai/commands/commit/coordinator.md` directly. The coordinator is a goal-driven card (Goal, Start, run, Obstacles, Close) that loads `verified-precondition-handback`, `public-chat`, `remember`, `safe-operations`, `tool-resolution`, `obstacle-escalation`, `command-execution`, `no-commit-guard`, and `commit-rules`. `sai-commit-worker` (`sai/commands/commit/worker.md`) renders its binding from `standalone-worker-template.md`: the coordinator creates it with the ready prompt alone and continues it with `SendMessage` (Claude Code) or `task` with the `task_id` (opencode). The worker reads the staged state (`commit.js collect`), authors the message from `instructions.md` Steps 1-6 (faithfulness rule, repo-style rubric via `commit-rules.md`), and returns `needs_input` (with `summary`, `question`, `options`) or a terminal `completed`, `failed`, or `cancelled` result with a `summary`, as its final message. The authorization gate is unchanged: on `yes` (or an active `Allow on this session` grant) the COORDINATOR alone executes the git mutation through `sai/tools/commit.js apply` (message on stdin through the literal-message procedure of `command-execution.md`, `--amend` when requested, `--acknowledge-secrets` with the list the user already confirmed); the worker never runs `git add`, `git commit`, or `apply`. An amend of an already-pushed commit and sensitive-looking staged files each require the worker's confirmation question first. The no-commit guard windows around the worker stay in force. Obstacles (a worker without ready or a readable result, a failing `commit.js` call) follow `sai/policies/obstacle-escalation.md`, the shared policy for stopping on an obstacle with recovery options and escalating to the user; declined answers, the authorization question, and validation violations are planned stops, not obstacles. After an executed commit the coordinator prints the worker-authored summary verbatim and closes with exactly `Commit done.`. Both harnesses preserve the same stop texts and git surface.

### Archive coordinator and worker
`/sai-archive` runs outside the shared orchestration, in the goal-driven shape of `/sai-commit`: the wrappers load the harness fetch skill and `sai/commands/archive/coordinator.md` directly (the coordinator fetches the `archive-worker.md` and `backfill-worker.md` bindings itself). The coordinator is a goal-driven card (Goal, Start, run, Obstacles, Close); `sai-archive-worker` renders its binding from `standalone-worker-template.md`. Obstacles (a worker without ready or a readable result) follow `sai/policies/obstacle-escalation.md`; the CORE stop, retirement refusals, the CLI archive stops, and the commit-gate questions are planned stops, not obstacles. The coordinator runs no prerequisite check (only `/sai-explore` does), parses `--fast-track` itself (banner + cleaned remainder), resolves the change via the shared change-picker before dispatch, and declares `fast_track_active` to the worker as session state alongside the envelope — never an envelope key. The worker owns the read-only pre-flight (Classification Check, informational delta-sync summary vs main specs, capability-retirement detection, target-name collision check) by following `sai/commands/archive/instructions.md` and returns findings as payload content; any worker `needs_input` is presented by the coordinator through the native picker and forwarded verbatim. Terminal navigation prints the worker-authored summary verbatim and closes with exactly `Archive done.` only when the move executed. Stop texts and gate question wordings are pinned in the cards.

### Merge coordinator and worker
`/sai-merge` runs outside the shared orchestration, in the shape of `/sai-3-implement`: one goal-driven, always-unattended coordinator, `sai/commands/merge/coordinator.md`. The wrappers load the harness fetch skill and that coordinator directly. The coordinator loads only `public-chat`, `remember`, `safe-operations`, `tool-resolution`, `obstacle-escalation`, and `incremental-review` (never `no-commit-guard`) and no budget binding, because it runs `sai/tools/merge.js` and git itself, like the audit and deep-review coordinators. The invocation is `/sai-merge [<branch>] [--rebase|--squash]`; `--squash` wins when both are given, `--fast-track` is accepted and ignored with no banner, the branch is asked only when it is missing, and the closing report uses the chat language. Invoking the command authorizes only the local operations the coordinator lists (the launch and squash, whole-side checkouts, staging, ADR/DDR repair, the merge and squash commits, each `git rebase --continue`, the final-tree correction commit, and the repair commit); nothing is pushed.

- **Run.** The coordinator fixes the test command once, runs the suite once at `HEAD` as the baseline (`merge.js verify --baseline`), captures provenance, launches, and works one conflict stop at a time: capture the snapshot, have the worker report a strategy, have it write the resolution, check it with `merge.js resolution`, review it with `review-delta.js` and `incremental-review.md` for up to 3 rounds (fidelity to the intent of both sides, changes outside the conflict regions, leftover markers), stage it, and continue. The suite then runs once on the final tree against the baseline (after the resolution for a merge, after the last stop for a rebase). A clean launch dispatches no worker. Commit intent is the criterion for every resolution; when it cannot decide, the coordinator escalates through the picker with options it writes (one leaves the operation in progress, one aborts it), and aborts only when the user chose that.
- **Worker.** `sai-merge-worker` keeps its manifest and worker-matrix key; its binding renders from `standalone-worker-template.md` on both harnesses. One worker lives for the whole run and is continued with a pointer line (`Active step: <id> — follow sai/commands/merge/steps/<id>.md`) per judgment: `strategy`, `apply`, `test-correction`, and `renumbering-plan`. The cycle repeats per stop and has conditional steps, so there is no step machine. The worker writes only through `merge.js write`, runs no git command that changes the repository, writes its report to the run directory, and returns only the path. A replacement receives a hand-over file written by the coordinator.
- **Resilience.** The `merge-run@1` machine (`sai-state/machines/merge-run.js`, on the shared run core `run-core.js`, session key `merge-{branch}`) holds identifiers only: method, branch, stop index, baseline path, pre-launch `HEAD`, and the paths of the obstacle, finding, and assumption files. The run directory is a private `temp-root.js mkdtemp --prefix merge-` child of the SAI temp root; it is removed when the run completes and kept when the run stops or goes unanswered. Each obstacle has a budget of 3 attempts and then escalates. An interrupted run resumes only when the invocation names the same branch, and the git state wins over the store. A merge or rebase this command did not start is never touched.
- **Closing report.** It names the pre-launch `HEAD` and the command that restores the branch to it for every run that changed it, and says that the next push needs a force push when a rebase or squash rewrote commits the upstream already holds (`merge.js provenance` records that fact). A run that finalized ends with `Merge done.`.
- **Retired.** `lifecycle.md`, `presentation.md`, `coordinator-stages.md`, `instructions.md`, and `command-bootstrap.md`, the `merge.js enter --stage` and `instructions --stage` entry points, the method, language, dirty-tree, and strategy questions, and the adaptive merge TODO of `todo-structure.md` retire with ADR 0201, which supersedes ADR 0175a. `no-commit-guard` and `transfer.js` stay for the commands that still use them.

### Merge efficiency

Merge efficiency removes relay sessions and instruction volume: a result the tool computes runs in the coordinator, never through the worker, and the worker receives its instructions as one step file per judgment instead of a stage library. `sai/commands/merge/mechanics.md` is the evidence contract of `merge.js`: receipts with their dependencies and validity, records outside the repository identified by path and sha256, and the list of calls. The worker receives each conflict prepared: one `merge.js bundle` call returns the conflict bundle, built from the captured snapshot record: every conflict region with its three decoded versions and bounded context, the conflict category, and each side's commit messages. Conflicts with no text to compare (binary, deleted on one side, renamed) and files whose encoding the tool cannot determine carry no regions and admit only a whole-side choice, which stays a coordinator checkout. Resolution writes are tool-owned: the worker sends a region identifier and resolved text to `merge.js write`, which splices it into conflict regions or coordinator-named correction ranges and takes encoding, BOM, and line endings from the pre-write snapshot; text with conflict markers or an unknown region is rejected and writes nothing. The `resolution` check validates every write, protects unrelated content, and compares against the captured pre-write working file, including Git-combined content, rather than a stage's whole file. `merge.js verify --baseline` records the suite before the integration, per test when the output allows it; `verify --baseline-record` compares a later run with it, reruns a new failure once, and returns `new`, `flaky`, `preexisting`, `not-comparable`, or `unavailable`, so unattended finalization neither leaves a new failing test nor stops for one that already failed. Models are user-configured per role, so success is measured in model turns, tool calls, and tokens per run, not minutes.

### Managed agent files (tunable-seed lifecycle)

Both harnesses install their routed workers and Generic Agents as **managed agent files** — Claude Code under `~/.claude/agents/`, opencode under `~/.config/opencode/agents/`. Both use `budget-explorer.md`, `budget-executor.md`, and `budget-subagent.md` for Generic Agents. Routed workers are materialized from `agents/{harness}/worker-template.md` plus the manifest's `worker-matrix`.

All of them follow the same **tunable-seed lifecycle**:

- **Absent** — created with the repository default definition and its shipped tunables. No ownership sidecar is written or read.
- **Exact-compatible** — reused untouched.
- **Divergent body or non-tunable frontmatter** — overwritten with a console notice, while the destination's tunable lines are preserved: `model` + `effort` on Claude Code, `model` + optional `variant` on opencode.

`model` and `effort` (Claude Code), opencode `model` and optional `variant`, and the exact suffix after the standalone `<!-- User customizations below this line -->` comment are **user-owned**. All commands and agent sources/templates carry that comment. Everything else is managed: command projections use `customizable-copy`, agents use `tunable-seed`. Legacy files without the comment retain only their tunables; other edits are overwritten without a backup. OpenCode commands keep `model#variant`, agents keep separate fields. Coordinator model defaults live in each wrapper's frontmatter and worker seeds in the manifest's `worker-matrix`; no other document pins them. Doctor ignores tunables and the customization suffix when checking managed content, including existing project-local commands and agents. Uninstall ignores tunables but retains files with custom suffixes or other body changes. The opencode configuration merge is permission-only — no agent key is ever inserted into `opencode.json`/`opencode.jsonc`, and that configuration is excluded from uninstall.

The installation CLI refreshes existing manifest-owned command and agent overrides in the current project's `.claude/` and `.opencode/` roots for the selected harnesses; `setup <project-path>` refreshes both harnesses in the named project. The refresh creates no local files, scans no other project, and leaves unrelated filenames and symbolic links alone. `bin/managed-customizations.js` owns the comment boundary and byte-preserving suffix merge; install and doctor share that boundary.

Installation and project refresh delete exact manifest-declared retired file paths regardless of contents. Renamed command/agent definitions are removed without migrating their tunables or custom text; current-name definitions retain their own settings, and absent global definitions receive shipped defaults. This includes the opencode `explore.md`, `executor.md`, and `budget.md` agent filenames, globally and in the named project; Claude Code's generic names are unchanged. Retirement unlinks a file symlink itself, leaves its target alone, and skips directories and paths through linked directories. Historical hashes remain available to read-only diagnostics and guarded uninstall; they no longer gate installer retirement.

The configured agent file governs runtime dispatch — its declared mode, agent `model` and optional `variant` on opencode, and permissions decide behavior, not any config block. A project-local `.claude/agents/<name>.md` wins over the user-global seed by filename. **Restart opencode (or Claude Code) after installing or updating agent definitions**, and reinstall after upgrades to resynchronize command, skill, binding, and agent files.

### Prerequisite check
The four-check contract lives in `@sai/policies/prereqs-check.md` and is executed by `sai/tools/prereqs.js`. **`/sai-explore`, `/sai-3-implement`, and `/sai-4-review` run it** (and so `/sai-build` and `/sai-deep-review`, through their segments): each fetches `prereqs-check.md` + `prereqs-paths.md`, and they are the only `sai/commands/` callers of `prereqs.js`. ### No-commit guard
Worker "never run a mutating git command" rules are prose the worker reads at start; the no-commit guard turns the one invariant true in every project — HEAD immobility across worker stretches — into a filesystem check. `sai/tools/no-commit-guard.js` (`snapshot`/`verify`, JSON verdicts `clean | violation | allowed | n/a`) is single-sourced in `sai/policies/no-commit-guard.md`: every coordinator card that dispatches a routed worker binding (commit, archive, backfill) plus explore's three Direct Build windows pairs one snapshot and one verify per guard window. A per-invocation opt-in on `sai-archive` and `sai-backfill` that trades a fixed, audited set of gates for a single end-of-run checkpoint. The canonical model is single-sourced in `sai/policies/fast-track-flag.md`: the coordinator owns BOTH the parse and the banner except for the documented phase-owned-parse exception (`sai-backfill`); the activation signal travels everywhere as invocation-scoped session state named exactly `fast_track_active` (never an envelope key, never persisted); and every fast-track invocation produces exactly one visible `> FAST-TRACK MODE ACTIVE` confirmation. Concretely: `sai-archive` parses in its coordinator card; `sai-backfill` parses `--fast-track` and the diff-source tokens (`--staged | --unstaged | --diff <sha>`) in its worker card (phase-owned parse, no banner). `/sai-1-spec`, `/sai-2-design`, `/sai-plan`, `/sai-3-implement`, `/sai-4-review`, `/sai-build`, `/sai-deep-review`, and `/sai-merge` are outside this parser membership: they accept and ignore an explicit `--fast-track` token, because invoking them already authorizes their local commits and they ask for no approval, so the token activates nothing and emits no banner. `/sai-explore` also strips the token silently: it keeps no `fast_track_active` state and the token has no behavioral effect there. Each command's opt-out set is fixed:
- `sai-backfill` — skips generated reconciliation questions (remaining `stated-but-unevidenced` items stay non-normative), auto-proceeds the spec-conflict gate after carrying the conflict report verbatim, and auto-accepts a crystallized-block `**Change name**` without the yes/no confirmation.

Safe-operations confirmations and all unnamed gates remain in force — including backfill's hard halts and its MANDATORY STOP literal, and fast-track never suppresses an input question (a missing diff-source token still fires the normal ask).

## Installation

Commands are **user globals**, not per-project. The manifest-driven installer expands `sai/install-manifest.json` into deterministic harness projections, and the same projections are used by `doctor` for missing/drift checks and by `uninstall` for safe removal. Claude Code and opencode receive mirrored routed worker bindings, all rendered from the per-harness `standalone-worker-template.md` (the shared Orchestration Core is retired). The canonical project-agnostic ADR and DDR index templates are `sai/commands/implement/adr-index.template.md` and `sai/commands/implement/ddr-index.template.md`; the recursive `sai-commands` projection installs command-local instructions and co-located `.template.md` files for both supported harnesses, and it also covers the shared overview-generation instruction at `sai/commands/design/change-overview.md` and both index templates, which are owned by the single command that consumes each.

The `sai-agents-index` root-class projection additionally writes `SAI_AGENTS.md` — the orientation index over the four SAI documentation surfaces — to each harness root, inheriting doctor missing-file detection, drift detection, and uninstall cleanup.

- **Claude Code**: `~/.claude/commands/`
- **opencode**: `~/.config/opencode/commands/`

Supported harnesses: Claude Code and opencode.

Existing GitHub Copilot users must run the current uninstall command before upgrading. Skipping uninstall may leave orphaned Copilot files; the supported installer and uninstaller intentionally do not clean them up.

Project-local commands override user-global ones by filename in Claude Code (`.claude/commands/`) and opencode (`.opencode/commands/`). OpenSpec skills are always **project-local** (installed by `openspec init`) — never copied to user globals.

## How to modify this repo

### Add / modify an instruction
1. Edit the canonical file in `sai/commands/{name}/`, `sai/policies/`, or `sai/orchestration/` as appropriate. The ADR index template belongs at `sai/commands/implement/adr-index.template.md`, and the DDR index template at `sai/commands/implement/ddr-index.template.md`.
2. If it changes a per-phase artifact path, update the AGENTS.md artifact table above and any card that names that path. Wrappers stay thin (clean-start line + capability profile + card fetch + envelope) and do not carry REPLACEMENT blocks.
3. If it changes an installable surface, update `sai/install-manifest.json` and keep Claude Code and opencode projections explicit. Their routed bindings must remain mirrored.
4. If the recommended model changes, update the wrappers in `commands/claude/` and `commands/opencode/`.
5. Installable files (`sai/`, `skills/`, `agents/`, `commands/`, `openspec/schemas/sai-workflow/`) state their rules in their own text and never cite a shared-ai capability spec, by `openspec/specs/<name>/` path or by capability name: those folders are copied into projects where that directory does not exist. `test/installable-spec-citations.test.js` guards this.

### Prompt-writing principles
Load the `writing-for-agents` skill before modifying any prompt (cards, steps, policies, skills, agent files, AGENTS.md) and apply its principles: context pointers, context and cognitive load, information hierarchy, progressive disclosure, co-location, sprawl, completion criteria (clarity and demand), premature completion, splitting by sequence, leading words, negation, single source of truth, the environment as cache, relevance and sediment, no-ops.

**Hard gates are the exception.** A gate that halts the whole run must state why nothing less will do: an irreversible or destructive effect, a missing authorization, or a state the run cannot recover from. Everywhere else, stop only the blocked work and close it with stop options (`sai/policies/obstacle-escalation.md`) so the user can unblock the run and continue.

### Change picker
`sai/policies/change-picker.md` is the shared 0/1/N resolution instruction. A trimmed, non-empty `arguments_value` is authoritative; when it is empty, `sai/tools/change-picker.js` drives the confirm/select outcomes. `sai-status` is deliberately **not** a consumer — it resolves names via `sai/policies/status-picker.md`. `sai-backfill` is detached from the picker.

Live `Fetch @sai/policies/change-picker.md` sites:
- `sai-archive` — coordinator, after fast-track parse, **before** worker dispatch

The spec, design, plan, implement, review, build, security, performance, accessibility, and deep-review coordinators resolve the change themselves from their own startup rules (the three audits share `sai/commands/audit/coordinator.md`). `sai-1-spec` is not a consumer either: creation requires the crystallized Ready to Propose block; refinement of an existing change with artifacts needs no block, and `sai-plan` takes a block or the name of a change that already has its specs. `/sai-deep-review` resolves the change once, through its review segment, after stripping `--fast-track`, and keeps that name across segments; no later segment re-enters a wrapper or re-runs resolution.

When adding a new change-consuming command, prefer fetching `change-picker.md` on the surface that actually resolves the name (coordinator, invocation, or body). Do not add a fetch on a name-blind coordinator whose worker already owns 0/1/N, and never on `sai-status` or `sai-backfill`.

### Add a new command
1. Create `sai/commands/{name}/` with either `coordinator.md` + `worker.md` (routed) or `body.md` (utility). Isolation comes from the wrapper's clean-start line — do not add an isolation block to the card. A card loads for itself every policy it needs (`public-chat`, `remember`, the obstacle policy).
2. Create thin wrappers `commands/claude/sai-{name}.md` and `commands/opencode/sai-{name}.md`: model frontmatter, the clean-start line, the capability profile, and the card fetch.
3. Add any managed worker to the `worker-matrix` in `sai/install-manifest.json` and confirm the `sai-commands` projection covers the new files.
4. Update README.md with the command in the corresponding table.

### Specs approval gate
`sai-1-spec` stops after generating `proposal.md` and `specs/`, telling the user to review them and run `/sai-2-design` when ready. Invoking `/sai-2-design` (or `/sai-plan`) IS the approval: it asks nothing and the design worker automatically stamps `approval.specs.approved_at` (only when absent or empty) + `approval.specs.notes` (always empty string) into `.openspec.yaml` before generating anything. Bypassing `sai-2-design` (e.g. calling `opsx:continue` directly) skips this check — `opsx:*` commands are internal, document this accordingly.

### Mirror discipline
Any change to `commands/claude/` MUST be mirrored to `commands/opencode/` in the same commit (and vice versa — both stay in sync). Enforce via PR checklist. This is one consequence of the "Harness universality" convention above, which also covers shared instructions, installers, and docs.

### Format conventions
- Never use `any` in TypeScript (even though there is no TS here, it applies to code examples in instructions).
- Generated artifacts are in English unless the user explicitly requests otherwise.
